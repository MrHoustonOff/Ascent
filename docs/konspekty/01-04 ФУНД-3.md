**Должен знать**

Важно различать две вещи: адрес — «где лежит», значение — «что лежит». Почти вся работа Go с памятью построена на этом различии.

**Термины**
- **адрес** *(новое)* — номер байта в памяти процесса
- **адресное пространство** — все адреса, которые может использовать процесс

### ФУНД-3.2 Карта памяти процесса

#### ФУНД-3.2.1 Виртуальная память
**Вопросы**
- [ ] Почему два разных процесса могут использовать один и тот же адрес, и при этом не мешать друг другу? · `same address different processes virtual memory`
- [ ] Что такое виртуальная память и кто переводит виртуальный адрес в настоящий? · `virtual memory explained simply`
- [ ] Что значит, что процесс «видит» всю память своей? · `virtual address space per process`
- [ ] Как виртуальная память связана с изоляцией памяти процессов? · `virtual memory process isolation`
- [ ] Что такое страница памяти — одной фразой? · `memory page 4kb`
- [ ] Почему процесс может «занять» больше памяти, чем реально использует? · `virtual vs resident memory`

**Гуглить:** `virtual memory explained` · `виртуальная память простыми словами` · `virtual vs physical address`

**Должен знать**
Адреса, с которыми работает процесс, — не настоящие места в микросхемах памяти, а виртуальные. ОС вместе с процессором переводит каждый виртуальный адрес в физический. У каждого процесса своя таблица перевода, поэтому одинаковые адреса в разных процессах ведут в разные места — так и получается изоляция памяти.
Перевод делается кусками фиксированного размера — страницами (обычно 4 КБ). Процесс может заявить себе огромную область, а настоящая память выделяется только под те страницы, которые он реально трогает.

**Термины**
- **виртуальная память** *(новое)* — механизм, который даёт каждому процессу своё адресное пространство
- **виртуальный адрес** — адрес, который видит процесс
- **физический адрес** — настоящее место в микросхеме памяти
- **страница** — кусок памяти, которым ОС управляет целиком (обычно 4 КБ)

**Граница:** страницы памяти — одной фразой; таблицы страниц и подкачку на диск — не разбираем.
**Позже:** сколько памяти реально потребляет процесс в Linux — ОС-1.

#### ФУНД-3.2.2 Карта памяти процесса: код, данные, стек, куча
**Вопросы**
- [ ] Из каких областей состоит память процесса и что лежит в каждой? · `process memory layout text data heap stack`
- [ ] Где лежат машинные инструкции программы и почему эта область только для чтения? · `text segment read only`
- [ ] Где лежат глобальные переменные, которые существуют всё время работы программы? · `data segment global variables`
- [ ] Что такое стек и что такое куча — в одном предложении каждый? · `stack vs heap simple explanation`
- [ ] Почему стек и куча растут навстречу друг другу на классической схеме? · `stack grows down heap grows up`
- [ ] Чем стек и куча отличаются по скорости выделения и по сроку жизни данных? · `stack vs heap speed lifetime`

**Гуглить:** `memory layout of a process` · `stack vs heap memory` · `карта памяти процесса`

**Должен знать**
Память процесса поделена на области: код (машинные инструкции, только чтение), данные (глобальные значения, живут всю программу), стек и куча. Стек — память под вызовы функций: она выделяется и освобождается сама, строго по порядку вызовов, и это очень быстро. Куча — память для данных, которые должны пережить вызов, создавший их; ею нужно отдельно управлять.

**Термины**
- **стек** *(новое)* — область памяти под вызовы функций; освобождается автоматически при возврате
- **куча** *(новое)* — область памяти для данных, которые живут дольше одного вызова
- **сегмент кода** — область с машинными инструкциями программы

### ФУНД-3.3 Стек

#### ФУНД-3.3.1 Вызов функции и адрес возврата
**Вопросы**
- [ ] Откуда процессор знает, куда вернуться, когда функция закончилась? · `return address function call`
- [ ] Что такое адрес возврата и где он хранится? · `return address stored on stack`
- [ ] Что происходит по шагам, когда `main` вызывает `f`, а `f` вызывает `g`? · `call stack nested calls step by step`
- [ ] Почему возврат идёт в обратном порядке: последний вызванный заканчивает первым? · `call stack LIFO`
- [ ] Что показывает «стек вызовов» (traceback) при ошибке в Python? · `python traceback call stack`

**Гуглить:** `call stack explained` · `стек вызовов простыми словами` · `return address`

**Должен знать**
Вызов функции — это переход к её первой инструкции. Чтобы потом вернуться, процессор запоминает адрес возврата — адрес инструкции, которая идёт сразу после вызова, — и кладёт его на стек. Когда функция заканчивается, адрес возврата снимается со стека, и выполнение продолжается с него.
Вызовы вкладываются, поэтому стек работает как стопка тарелок: последний вызов заканчивается первым. Traceback в Python — это распечатка такой стопки в момент ошибки.

**Термины**
- **адрес возврата** — адрес инструкции, к которой вернуться после вызова
- **стек вызовов** — цепочка вызовов, которые сейчас не закончились
- **«последним пришёл — первым ушёл»** — порядок работы стека

**Граница:** регистры и инструкции `call`/`ret` по отдельности — не нужны.

**Должен знать**
Кадр стека — участок стека, который получает один вызов функции: в нём адрес возврата, аргументы и локальные значения этого вызова. При вызове кадр кладётся на верх стека, при возврате снимается — вместе со всеми локальными значениями.

#### ФУНД-3.3.3 Как стек растёт при вызовах и освобождается при возврате
**Вопросы**
- [ ] Что значит «вершина стека» и как она перемещается при вызове и возврате? · `stack pointer explained`
- [ ] Почему выделение памяти на стеке почти бесплатное? · `why stack allocation is fast`
- [ ] Почему на стеке нельзя «освободить» значение из середины? · `stack memory LIFO free`
- [ ] Почему стек не нужно чистить — старые данные просто перезаписываются следующим кадром? · `stack memory not cleared after return`
- [ ] Какой размер стека у обычной программы в Linux (порядок величины)? · `default stack size linux 8mb`

**Гуглить:** `stack pointer and stack allocation` · `stack allocation vs heap allocation cost`

**Должен знать**
У стека есть вершина — граница, до которой он сейчас занят. Новый кадр — это просто перенос вершины на размер кадра, возврат — перенос обратно. Никакого поиска свободного места, никакого учёта: поэтому выделение на стеке почти бесплатное.
Цена этой простоты — строгий порядок: освобождается только верхний кадр и только целиком. Данные, которые должны жить дольше вызова, на стеке держать нельзя. Размер стека ограничен — обычно несколько мегабайт на программу.

**Термины**
- **вершина стека** — граница занятой части стека, перемещается при вызове и возврате

#### ФУНД-3.3.4 Рекурсия и переполнение стека
**Вопросы**
- [ ] Что такое рекурсия? Напиши факториал рекурсивно. · `recursion factorial example`
- [ ] Почему у рекурсии обязательно должен быть случай, когда она останавливается? · `recursion base case`
- [ ] Почему слишком глубокая рекурсия падает: что заканчивается? · `stack overflow recursion why`

**Гуглить:** `recursion explained` · `stack overflow error cause` · `python RecursionError maximum recursion depth`

**Должен знать**
Рекурсия — когда функция вызывает саму себя. Каждый вызов получает свой кадр, и пока рекурсия не дошла до конца, все кадры лежат на стеке одновременно. Если рекурсия слишком глубокая или не останавливается, место на стеке заканчивается — это переполнение стека, программа падает.
Python заранее ставит предел глубины (около 1000) и бросает `RecursionError`. Глубокую рекурсию можно переписать циклом.

**Термины**
- **рекурсия** *(новое)* — функция, которая вызывает саму себя
- **базовый случай** — условие, при котором рекурсия останавливается
- **переполнение стека** — место на стеке закончилось, программа падает

### ФУНД-3.4 Куча

#### ФУНД-3.4.1 Куча
**Вопросы**
- [ ] Зачем нужна куча, если есть стек? Приведи пример данных, которые должны пережить функцию. · `why heap memory needed`
- [ ] Почему выделение в куче дороже, чем на стеке? · `heap allocation cost why`
- [ ] Что значит «выделить» и «освободить» память в куче? · `allocate free heap memory`
- [ ] Что будет, если память в куче выделять и никогда не освобождать? · `memory leak what is`
- [ ] Почему в Python почти все объекты живут в куче? · `python objects stored on heap`

**Гуглить:** `heap memory explained` · `stack vs heap when to use` · `memory leak simple`

**Должен знать**
Куча — область для данных, срок жизни которых не совпадает с вызовом функции: их можно создать в одной функции и пользоваться ими в другой. Выделение в куче — поиск свободного куска подходящего размера и учёт, что он занят; это заметно дороже переноса вершины стека.
Главная трудность кучи — освобождение: кто-то должен понять, что кусок больше не нужен, и вернуть его. Если не освобождать, память растёт без конца — это утечка памяти. В CPython в куче лежат почти все объекты.

**Термины**
- **выделение памяти** — получение свободного куска памяти под значение
- **утечка памяти** — память занята данными, которые больше не нужны, и не освобождается

**Граница:** как именно ищется свободное место в куче — не нужно.

#### ФУНД-3.4.2 Кто освобождает кучу: вручную, подсчёт ссылок, сборщик мусора
**Вопросы**
- [ ] Какие три способа освобождать кучу существуют? · `memory management manual reference counting garbage collection`
- [ ] Что бывает при ручном освобождении (C): забыл освободить, освободил дважды, пользуешься после освобождения? · `use after free double free`
- [ ] Как работает подсчёт ссылок и когда объект освобождается? · `reference counting explained`
- [ ] Почему подсчёт ссылок не справляется с объектами, которые ссылаются друг на друга по кругу? · `reference cycle problem`
- [ ] Как CPython сочетает подсчёт ссылок и отдельный сборщик мусора для таких кругов? · `python gc module cyclic garbage collector`
- [ ] Какой способ использует Go и что это значит для тебя как программиста? · `go garbage collected language`
- [ ] Чем плох сборщик мусора: за что приходится платить? · `garbage collection pause cost`

**Гуглить:** `reference counting vs garbage collection` · `сборщик мусора простыми словами` · `python reference counting sys.getrefcount`

**Должен знать**
Есть три подхода. Вручную (C): программист сам освобождает память — быстро, но легко ошибиться. Подсчёт ссылок (CPython): у объекта есть счётчик, сколько мест на него ссылается; когда счётчик падает до нуля, объект освобождается сразу. Минус — объекты, которые ссылаются друг на друга по кругу, никогда не доходят до нуля, поэтому в CPython есть ещё и сборщик мусора для них.
Сборщик мусора (Go): программа время от времени ищет данные, до которых больше нельзя добраться, и освобождает их сама. Ты не пишешь освобождение, но платишь работой процессора и паузами.

**Термины**
- **ручное освобождение** — программист сам вызывает освобождение памяти
- **подсчёт ссылок** *(новое)* — объект освобождается, когда на него не осталось ни одной ссылки
- **сборщик мусора** *(новое)* — часть программы, которая сама находит и освобождает ненужную память

**Граница:** алгоритмы сборки мусора — не здесь.
**Позже:** как устроен сборщик мусора в Go — GO-21.3.1–GO-21.3.7; утечки памяти в Go — GO-21.3.10.
