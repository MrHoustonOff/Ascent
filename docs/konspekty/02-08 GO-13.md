## GO-13. Ошибки

### GO-13.1 Ошибка как значение

#### GO-13.1.1 Тип error
**Вопросы**
- [ ] Что такое `error` в Go? · `golang error interface`
- [ ] Какой единственный метод у интерфейса `error`? · `go error interface Error() string`
- [ ] Почему ошибка — это значение, а не особый механизм языка? · `go errors are values`
- [ ] Какое нулевое значение у `error` и что значит `err == nil`? · `go error nil means success`
- [ ] Может ли любой твой тип стать ошибкой? · `custom type implements error`

**Гуглить:** `go blog error handling` · `rob pike errors are values` · `golang error type`

**Должен знать**
`error` — встроенный интерфейс с одним методом `Error() string`. Любой тип с таким методом — ошибка. Функция, которая может не справиться, возвращает `error` последним результатом: `nil` — всё хорошо, не `nil` — что-то пошло не так, и `Error()` объясняет что.
Ошибка — обычное значение: её можно положить в переменную, вернуть, сравнить, дополнить. Никакой особой «магии», как у исключений, нет.

**Термины**
- **error** *(новое)* — встроенный интерфейс ошибки с методом `Error() string`

#### GO-13.1.2 errors.New и fmt.Errorf
**Вопросы**
- [ ] Как создать ошибку с текстом (`errors.New`) и с подставленными значениями (`fmt.Errorf`)? · `golang errors.New fmt.Errorf`
- [ ] Как принято писать текст ошибки (строчными, без точки в конце)? · `go error strings lowercase no punctuation`
- [ ] Почему два `errors.New("x")` с одним текстом не равны? · `errors.New not equal same text`
- [ ] Что должно быть в тексте ошибки, чтобы по нему можно было найти причину? · `good error messages context`

**Гуглить:** `go errors.New` · `go code review comments error strings`

**Должен знать**
`errors.New("файл пуст")` создаёт ошибку с текстом, `fmt.Errorf("пользователь %d не найден", id)` — с подставленными значениями. Текст пишут строчными и без точки в конце: его часто будут дополнять спереди.
Каждый вызов `errors.New` создаёт новое значение, поэтому две ошибки с одинаковым текстом через `==` не равны. Хорошая ошибка говорит, что делали и с чем: «чтение config.yaml: файл не найден».

**Термины**
- **`errors.New`** — ошибка с фиксированным текстом
- **`fmt.Errorf`** — ошибка с форматированным текстом

#### GO-13.1.3 Место ошибки среди возвращаемых значений
**Вопросы**
- [ ] Где принято возвращать ошибку среди результатов функции? · `go error last return value convention`
- [ ] Что возвращать в остальных результатах, если ошибка не `nil`? · `return zero value with error`
- [ ] Можно ли пользоваться результатом, если вернулась ошибка? · `use value when err != nil`
- [ ] Почему функция, которая не может ошибиться, не должна возвращать `error`? · `don't return error if cannot fail`

**Гуглить:** `go error handling conventions` · `golang return error last`

**Должен знать**
Ошибка — последний результат: `func Load(path string) (*Config, error)`. Если ошибка не `nil`, остальные результаты — нулевые значения, и пользоваться ими нельзя (исключения из правила явно описаны в документации — одно такое встретится в GO-13.2.2).
Функция, которая не может ошибиться, ошибку не возвращает — иначе вызывающим придётся писать бессмысленные проверки.

**Термины**
- **ошибка последним результатом** — соглашение Go о месте `error`

#### GO-13.1.4 if err != nil
**Вопросы**
- [ ] Почему в Go нет исключений и чем `if err != nil` лучше и хуже `try/except`? · `go errors vs exceptions`
- [ ] Как выглядит типичная проверка с ранним возвратом? · `go if err != nil return err`
- [ ] Почему каждую ошибку проверяют сразу после вызова? · `check errors immediately go`
- [ ] Чем опасно молча проигнорировать ошибку? · `ignored error bug go`
- [ ] Какой линтер находит непроверенные ошибки (`errcheck`)? · `go errcheck linter`

**Гуглить:** `golang if err != nil` · `go why no exceptions faq` · `errcheck`

**Должен знать**
Стандартный шаг: вызвал функцию — сразу `if err != nil { return …, err }`. Путь ошибки виден прямо в коде, ничего не «вылетает» из глубины незаметно — это главный плюс. Минус — многословие: проверка после каждого вызова.
Мост из Python: исключение летит само до ближайшего `except`, и легко не заметить, откуда оно может прилететь. В Go ошибку обрабатываешь или передаёшь явно. Проигнорированная ошибка — частый источник багов; линтер `errcheck` их находит.

**Термины**
- **`if err != nil`** — проверка ошибки сразу после вызова

### GO-13.2 Виды ошибок и их проверка

#### GO-13.2.1 Sentinel-ошибки
**Вопросы**
- [ ] Что такое sentinel-ошибка? Приведи пример из стандартной библиотеки. · `go sentinel errors`
- [ ] Как объявить свою: `var ErrNotFound = errors.New("not found")`? · `declare sentinel error var`
- [ ] Почему её объявляют переменной уровня пакета и экспортируют? · `exported sentinel error`
- [ ] Почему сравнение по тексту `err.Error() == "not found"` — плохо? · `don't compare error strings`
- [ ] Чем плохи sentinel-ошибки (часть API, связывают пакеты)? · `sentinel errors drawbacks`

**Гуглить:** `golang sentinel errors` · `dave cheney dont just check errors handle them gracefully`

**Должен знать**
Sentinel-ошибка — заранее созданное значение ошибки, с которым сравнивают: `var ErrNotFound = errors.New("not found")`. Вызывающий проверяет «это та самая ошибка?»: `sql.ErrNoRows`, `io.EOF`, `os.ErrNotExist` — примеры из стандартной библиотеки.
Сравнивать ошибки по тексту нельзя: текст могут поменять. Минус sentinel-ошибок — они становятся частью API пакета, и от них зависят другие пакеты.

**Термины**
- **sentinel-ошибка** *(новое)* — заранее объявленное значение ошибки для сравнения

#### GO-13.2.2 io.Reader, io.Writer и io.EOF
**Вопросы**
- [ ] Какие методы у `io.Reader` и `io.Writer`? · `go io.Reader io.Writer interface`
- [ ] Как читать из `io.Reader` до конца и что означает `io.EOF`? · `go read until io.EOF loop`
- [ ] Почему `Read` может вернуть данные и `io.EOF` одновременно и что тогда делать? · `io.Reader returns n > 0 and EOF`
- [ ] Почему `io.EOF` — не ошибка, а сигнал? · `io.EOF is not an error`
- [ ] Какие типы реализуют `io.Reader` (файл, строка, тело ответа)? · `types implementing io.Reader`
- [ ] Что делает `io.ReadAll` и когда им нельзя пользоваться? · `io.ReadAll large input`

**Гуглить:** `go io.Reader explained` · `golang io.EOF` · `go io package`

**Должен знать**
`io.Reader` — интерфейс с одним методом `Read(p []byte) (n int, err error)`: прочитать до `len(p)` байтов в `p`. `io.Writer` — `Write(p []byte) (n int, err error)`. Это главные маленькие интерфейсы Go: их реализуют файлы, строки, сетевые соединения, сжатие — и любой код, умеющий работать с ними, работает со всем этим сразу.
`io.EOF` — sentinel-ошибка «данные кончились», это нормальный конец, а не сбой. Правило чтения: сначала обработай `n` полученных байтов, потом смотри на ошибку. `io.ReadAll` читает всё в память — не для огромных данных.

**Термины**
- **io.Reader, io.Writer** *(новое)* — интерфейсы «читать байты» и «писать байты»
- **`io.EOF`** — сигнал «данные закончились»

#### GO-13.2.3 Свой тип ошибки
**Вопросы**
- [ ] Как сделать свой тип ошибки с дополнительными полями? · `go custom error type struct`

#### GO-13.2.4 Оборачивание ошибки: %w
**Вопросы**
- [ ] Как обернуть ошибку, сохранив исходную? · `go wrap error %w`
- [ ] Чем `%w` отличается от `%v` в `fmt.Errorf`? · `fmt.Errorf %w vs %v`
- [ ] Что добавлять в обёртку (что делали и с чем)? · `error wrapping context message`
- [ ] Как выглядит итоговый текст ошибки после нескольких обёрток? · `wrapped error message chain`
- [ ] Когда сознательно не оборачивать (не раскрывать детали реализации)? · `when not to wrap errors`

**Гуглить:** `go 1.13 error wrapping` · `go blog working with errors`

**Должен знать**
`fmt.Errorf("загрузка профиля %d: %w", id, err)` создаёт новую ошибку, которая дополняет текст и хранит исходную внутри — это оборачивание. С `%v` получился бы только текст, а исходная ошибка потерялась бы для проверок.
Каждый уровень добавляет свой контекст, и в итоге текст читается как путь: «обработка заказа: загрузка профиля 42: запрос к базе: no rows». Не оборачивают, когда не хотят, чтобы вызывающий зависел от внутренних ошибок (тогда `%v`).

**Термины**
- **оборачивание ошибки** *(новое)* — новая ошибка с контекстом, хранящая исходную

#### GO-13.2.5 Цепочка обёрток и Unwrap
**Вопросы**
- [ ] Что такое цепочка обёрток? · `go error chain`
- [ ] Что делает `errors.Unwrap` и метод `Unwrap() error` у своего типа? · `go Unwrap method custom error`
- [ ] Как своему типу ошибки стать частью цепочки? · `custom error type wrap cause`
- [ ] Почему вручную ходить по цепочке через `Unwrap` почти не нужно? · `use errors.Is instead of Unwrap`

**Гуглить:** `golang errors.Unwrap` · `go custom error Unwrap`

**Должен знать**
Обёрнутые ошибки образуют цепочку: внешняя → внутренняя → исходная. `errors.Unwrap(err)` даёт следующую ошибку в цепочке (или `nil`). Свой тип становится звеном цепочки, если у него есть метод `Unwrap() error`, возвращающий вложенную ошибку.
Ходить по цепочке руками почти никогда не нужно: для проверок есть `errors.Is` и `errors.As`, которые делают это сами.

**Термины**
- **цепочка обёрток** — последовательность ошибок, обёрнутых друг в друга
- **`Unwrap`** — получить следующую ошибку из цепочки

#### GO-13.2.6 errors.Is
**Вопросы**
- [ ] Чем `errors.Is(err, ErrNotFound)` лучше `err == ErrNotFound`? · `go errors.Is vs ==`
- [ ] Как `errors.Is` проходит по цепочке обёрток? · `errors.Is unwrap chain`
- [ ] Найдёт ли `errors.Is` sentinel, обёрнутый через `%v`? · `errors.Is with %v not found`
- [ ] Как проверить, что файла нет (`errors.Is(err, fs.ErrNotExist)`)? · `go check file not exist errors.Is`

**Гуглить:** `golang errors.Is` · `go errors.Is example`

**Должен знать**
`errors.Is(err, target)` проверяет, есть ли `target` где-то в цепочке обёрток `err`. Простое `==` сравнивает только внешнюю ошибку и после первой же обёртки перестаёт находить sentinel. Поэтому ошибки проверяют через `errors.Is`.
Если ошибку завернули через `%v`, связи нет — `errors.Is` её не найдёт.

**Термины**
- **`errors.Is`** — есть ли конкретное значение ошибки в цепочке

#### GO-13.2.7 errors.As
**Вопросы**
- [ ] Чем `errors.Is` отличается от `errors.As` и когда что использовать? · `errors.Is vs errors.As`
- [ ] Почему в `errors.As` передают указатель на переменную? · `errors.As pointer to target`
- [ ] Как достать `*ValidationError` из обёрнутой ошибки и прочитать поле? · `errors.As custom error type example`
- [ ] Что появилось в Go 1.26 — `errors.AsType`, и чем удобнее? · `go 1.26 errors.AsType`

**Гуглить:** `golang errors.As` · `go 1.26 errors.AsType`

**Должен знать**
`errors.Is` ищет конкретное значение, `errors.As` — ошибку определённого типа: `var ve *ValidationError; if errors.As(err, &ve) { use(ve.Field) }`. Он проходит цепочку и, найдя ошибку подходящего типа, записывает её в переменную по указателю.
С Go 1.26 есть `errors.AsType`: тип указывают в квадратных скобках, а результат и признак «нашлось» возвращаются сразу — без отдельной переменной.

**Термины**
- **`errors.As`** — найти в цепочке ошибку нужного типа и достать её

### GO-13.3 Ловушки и границы

#### GO-13.3.1 Typed nil при возврате ошибки
**Вопросы**
- [ ] Функция возвращает `error`, а внутри лежит nil-указатель на свою ошибку. Почему вызывающий видит не `nil`? · `go typed nil error`
- [ ] Покажи код, где `var e *MyErr; return e` даёт ошибку, не равную `nil`. · `return nil pointer as error`
- [ ] Как это исправить: возвращать буквальный `nil`? · `fix typed nil return nil`
- [ ] Почему переменную для ошибки лучше объявлять типом `error`, а не `*MyErr`? · `declare err as error not concrete type`

**Гуглить:** `go faq nil error not nil` · `typed nil interface golang`

**Должен знать**
`error` — интерфейс, поэтому к нему относится ловушка «не nil, хотя внутри nil». Если функция объявлена с результатом `error`, а возвращает переменную `var e *MyErr` (равную `nil`), интерфейс получит тип `*MyErr` и пустой указатель — и `err != nil` у вызывающего будет истинным.
Исправление: в случае успеха возвращать буквальный `nil`, а переменные для ошибок объявлять с типом `error`.

**Термины**
- **typed nil** *(новое)* — интерфейс с типом, но с nil-значением внутри

#### GO-13.3.2 Паника или ошибка
**Вопросы**
- [ ] Когда уместна паника, а когда — возврат ошибки? · `go panic vs error when`
- [ ] Почему библиотека почти никогда не должна паниковать? · `libraries should not panic`
- [ ] Что делать с ошибкой при запуске программы, когда продолжать бессмысленно? · `fail at startup log.Fatal vs panic`
- [ ] Когда функцию с ошибкой оборачивают в `Must…`? · `go Must pattern`

**Гуглить:** `effective go errors panic` · `golang panic or error`

**Должен знать**
Ошибка — для всего, что может случиться при нормальной работе: нет файла, неверный ввод, сеть недоступна. Вызывающий решает, что с этим делать. Паника — для ситуаций «программа сломана»: нарушено внутреннее правило, ошибка программиста.
Библиотека не паникует на плохих данных — она возвращает ошибку. Если программа не может стартовать без настроек, `main` пишет понятное сообщение и завершается с кодом 1. `Must…`-обёртки — для значений, известных при запуске.

**Термины**
- **граница паники** — паника только для невозможных состояний

#### GO-13.3.3 recover на верхнем уровне программы
**Вопросы**
- [ ] Как не дать панике в одной части программы уронить всю программу? · `go recover top level`
- [ ] Где ставят `recover` (вокруг обработки одного запроса или задачи)? · `recover per request handler`
- [ ] Как превратить пойманную панику в ошибку и записать распечатку стека (`debug.Stack`)? · `go recover log stack trace debug.Stack`
- [ ] Почему `recover` в каждой функции — плохая идея? · `don't recover everywhere`

**Гуглить:** `golang recover best practices` · `runtime/debug.Stack`

**Должен знать**
`recover` ставят на «границе»: вокруг обработки одного запроса, одной задачи из очереди. Отложенная функция ловит панику, записывает сообщение и стек (`debug.Stack()`), превращает в ошибку и даёт программе работать дальше со следующим запросом.
Ловить панику в каждой функции — значит прятать баги. Поймали — обязательно записали, иначе никто не узнает.

**Термины**
- **граница восстановления** — место, где паника превращается в ошибку и не идёт дальше

#### GO-13.3.4 Логировать или возвращать ошибку
**Вопросы**
- [ ] Почему плохо и логировать ошибку, и возвращать её? · `log and return error anti pattern`
- [ ] Кто должен записать ошибку в журнал: тот, кто её получил первым, или тот, кто её окончательно обработал? · `who should log the error`
- [ ] Что значит «обработать ошибку» (повторить, вернуть значение по умолчанию, сообщить пользователю)? · `handle error once`
- [ ] Как обёртки с контекстом заменяют запись в журнал на каждом уровне? · `wrap instead of log`

**Гуглить:** `dave cheney handle errors once` · `log or return error golang`

**Должен знать**
Правило: ошибку обрабатывают один раз. Либо возвращают выше с контекстом, либо обрабатывают на месте — и тогда, если нужно, записывают в журнал. Если делать и то и другое, одна и та же ошибка оказывается в журнале пять раз на пяти уровнях, и разобраться невозможно.
Обёртки с контекстом делают запись на каждом уровне ненужной: на верху получится одна строка со всем путём.

**Термины**
- **«обработать один раз»** — ошибку либо возвращают, либо обрабатывают, но не оба сразу
