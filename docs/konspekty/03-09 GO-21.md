## GO-21. Память и сборщик мусора

### GO-21.1 Стек или куча

#### GO-21.1.1 Стек горутины против кучи
**Вопросы**
- [ ] Кто решает, где окажется переменная: на стеке горутины или в куче? · `go stack or heap who decides`
- [ ] Можно ли этим управлять из кода, как `new` или `malloc` в C? · `go new does not mean heap`
- [ ] Почему `new(T)` или `&T{}` не обязательно выделяют память в куче? · `new allocates on stack go`
- [ ] Почему значения на стеке не нагружают сборщик мусора? · `stack allocation no gc`

**Гуглить:** `go stack vs heap allocation` · `go faq stack or heap`

**Должен знать**
В Go программист не выбирает, где лежит переменная: это решает компилятор. Правило: если значение не может пережить свою функцию, оно лежит в кадре стека горутины и исчезает при возврате бесплатно. Если может — уезжает в кучу, и его потом убирает сборщик мусора.
`new(T)` и `&T{}` не означают «в куче»: если указатель не уходит из функции, значение останется на стеке.

**Термины**
- **размещение значения** — решение компилятора: стек горутины или куча

#### GO-21.1.2 Escape analysis
**Вопросы**
- [ ] Что такое escape analysis? · `go escape analysis explained`
- [ ] Что значит, что значение «убегает» из функции? · `value escapes function`
- [ ] Почему возврат указателя на локальную переменную безопасен именно благодаря escape analysis? · `return pointer local variable escape analysis`
- [ ] Почему анализ осторожен и иногда отправляет в кучу то, что могло бы жить на стеке? · `escape analysis conservative`

**Гуглить:** `golang escape analysis` · `ardan labs escape analysis`

**Должен знать**
Escape analysis — анализ при компиляции: компилятор прослеживает, куда может попасть адрес каждого значения. Если адрес может пережить функцию (её вернули, сохранили в долгоживущей структуре, передали в горутину), значение «убегает» и размещается в куче.
Анализ осторожен: если компилятор не может доказать, что значение не убегает, он кладёт его в кучу. Отсюда возврат указателя на локальную переменную безопасен — она просто окажется в куче.

**Термины**
- **escape analysis** *(новое)* — анализ компилятора, решающий, какие значения уезжают в кучу

#### GO-21.1.3 Типичные причины переезда в кучу
**Вопросы**
- [ ] Какие типичные причины переезда в кучу ты знаешь? · `common causes heap escape go`
- [ ] Почему значение, положенное в интерфейс (например, аргумент `fmt.Println`), часто уезжает в кучу? · `interface conversion escapes heap`
- [ ] Почему `make([]int, n)` с `n`, известным только при работе, уезжает в кучу? · `make slice non constant size escapes`
- [ ] Почему переменная, захваченная замыканием или горутиной, может уехать в кучу? · `closure captured variable escapes`
- [ ] Почему очень большое значение кладут в кучу, даже если оно не убегает? · `large allocation heap go`

**Гуглить:** `go escape analysis examples` · `why does my variable escape to heap`

**Должен знать**
Частые причины: возврат указателя на локальное значение; сохранение в интерфейс (`any`, аргументы `fmt.Println`) — компилятор не знает, что с ним сделают; захват замыканием, которое переживёт функцию, или передача в горутину; размер, неизвестный при компиляции (`make([]T, n)`); слишком большое значение для стека; сохранение адреса в глобальную переменную или в другое значение в куче.

**Термины**
- **переезд в кучу** — компилятор размещает значение в куче, потому что оно может пережить функцию

#### GO-21.1.4 Флаг -gcflags=-m
**Вопросы**
- [ ] Как увидеть решения компилятора о куче (`go build -gcflags=-m`)? · `go build -gcflags -m`
- [ ] Что значат сообщения «escapes to heap» и «moved to heap: x»? · `escapes to heap moved to heap meaning`
- [ ] Что добавляет `-m -m`? · `gcflags -m -m explain`
- [ ] Почему на эти сообщения смотрят только после замера, а не «на всякий случай»? · `benchmark allocs per op`

**Гуглить:** `go gcflags -m` · `reading escape analysis output`

**Должен знать**
`go build -gcflags=-m ./...` печатает решения компилятора: «moved to heap: x» — переменная `x` размещена в куче, «escapes to heap» — значение убегает, «does not escape» — осталось на стеке. `-m -m` объясняет, почему.
Смотрят на это, только когда профиль показал, что выделения памяти — узкое место. Число выделений на операцию покажет замер, о котором будет в блоке тестов.

**Термины**
- **`-gcflags=-m`** — флаг, печатающий решения escape analysis

#### GO-21.1.5 Цена выделения в куче
**Вопросы**
- [ ] Почему выделение в куче дороже, чем на стеке? · `heap allocation cost go`
- [ ] Из чего складывается цена: найти место, обнулить память, потом найти и убрать сборщиком? · `allocation cost gc cost`
- [ ] Почему значения в куче хуже для кэша процессора? · `heap fragmentation cache locality`
- [ ] Почему «меньше выделений» почти всегда значит «быстрее» в горячем коде? · `reduce allocations performance go`

**Гуглить:** `go allocation performance` · `reduce heap allocations go`

**Должен знать**
Выделение на стеке — сдвиг вершины стека. В куче — найти свободное место, обнулить его, а потом сборщику мусора нужно найти, что значение умерло, и вернуть место. Чем больше выделений, тем чаще и дольше работает сборщик. Плюс разбросанные по куче значения хуже лежат в кэше процессора.
Поэтому в горячем коде снижают число выделений: заранее задают ёмкость, переиспользуют буферы, не кладут без нужды значения в интерфейсы.

**Термины**
- **давление на сборщик** — нагрузка на сборщик мусора от частых выделений

### GO-21.2 Аллокатор

#### GO-21.2.1 Аллокатор Go
**Вопросы**
- [ ] Как Go быстро находит место в куче для нового значения? · `go memory allocator overview`
- [ ] Почему аллокатор Go берёт память у ОС большими кусками и раздаёт сам? · `go allocator arenas from os`
- [ ] Чем маленькие значения выделяются иначе, чем большие (больше 32 КБ)? · `go large object allocation 32kb`
- [ ] На каком аллокаторе основан аллокатор Go (TCMalloc) — одной фразой? · `go allocator tcmalloc`

**Гуглить:** `go memory allocator` · `visual guide to go memory allocator`

**Должен знать**
Аллокатор Go берёт у ОС память крупными кусками и сам раздаёт её значениям. Маленькие значения (до 32 КБ) кладутся в заранее нарезанные блоки подходящего размера, большие получают свой отдельный участок. Идея взята у TCMalloc: у каждого рабочего потока свой запас, общие структуры трогаются редко.
Так большинство выделений обходится без блокировок и без обращения к ОС.

**Термины**
- **аллокатор** *(новое)* — часть рантайма, выделяющая память в куче

#### GO-21.2.2 Размерные классы
**Вопросы**
- [ ] Что такое размерные классы? · `go size classes`
- [ ] Почему значение на 33 байта займёт 48? · `go size class rounding waste`
- [ ] Как это объясняет, почему ёмкость после `append` иногда больше расчётной? · `append capacity rounded size class`
- [ ] Сколько примерно размерных классов в Go (около 70)? · `go sizeclasses.go`

**Гуглить:** `go size classes table` · `sizeclasses.go`

**Должен знать**
Маленькие значения выделяются не точно по размеру, а округлением вверх до одного из размерных классов (8, 16, 24, 32, 48, 64… байт — около 70 классов до 32 КБ). Блоки одного класса лежат вместе, поэтому найти свободный — просто взять следующий.
Плата — немного потерянного места: значение на 33 байта займёт 48. Отсюда и «лишняя» ёмкость после `append`: рантайм округляет размер нового массива до класса и отдаёт слайсу всё место.

**Термины**
- **размерный класс** *(новое)* — стандартный размер блока, до которого округляется выделение

#### GO-21.2.3 Локальный кэш памяти у каждого P
**Вопросы**
- [ ] Почему горутины почти не мешают друг другу при выделении памяти? · `go mcache per p no lock`
- [ ] Что происходит, когда в локальном запасе кончились блоки нужного класса? · `mcache refill mcentral`
- [ ] Как называются уровни аллокатора (mcache, mcentral, mheap)? · `mcache mcentral mheap`

**Гуглить:** `go mcache mcentral mheap` · `go allocator per p cache`

**Должен знать**
У каждого P есть свой локальный кэш блоков всех размерных классов (mcache). Горутина, работающая на этом P, выделяет память из него без блокировок. Когда блоки нужного класса кончились, P берёт новую порцию из общего хранилища этого класса (mcentral), а оно — из кучи целиком (mheap).
Общие уровни защищены блокировками, но к ним обращаются редко, поэтому выделение в среднем быстрое и почти не упирается в соседей.

**Термины**
- **локальный кэш памяти** — запас свободных блоков у каждого P

**Граница:** mspan, mcache, mcentral, mheap — названиями.

### GO-21.3 Сборщик мусора

#### GO-21.3.1 Достижимость и корни
**Вопросы**
- [ ] Как сборщик мусора понимает, что значение больше не нужно? · `go gc reachability`
- [ ] Что такое корни сборки (стеки горутин, глобальные переменные, регистры)? · `gc roots go`
- [ ] Почему недостижимое значение — мусор, даже если на него где-то ссылается другой мусор? · `unreachable cycle garbage`
- [ ] Чем это отличается от подсчёта ссылок в CPython (циклы не проблема)? · `tracing gc vs reference counting cycles`

**Гуглить:** `garbage collection reachability roots` · `tracing garbage collector`

**Должен знать**
Сборщик Go не считает ссылки, а ищет достижимые значения. Корни — то, что программа использует прямо сейчас: переменные в стеках всех горутин, глобальные переменные, регистры. Достижимо всё, до чего можно дойти от корней по указателям. Остальное — мусор.
Поэтому циклы не проблема: два значения, ссылающиеся друг на друга, но недостижимые от корней, будут собраны. В CPython для этого нужен отдельный сборщик циклов.

**Термины**
- **корни сборки** *(новое)* — стеки горутин, глобальные переменные и регистры, от которых ищется живое
- **достижимость** — до значения можно дойти от корней по указателям

#### GO-21.3.2 Пометка и очистка
**Вопросы**
- [ ] Из каких двух фаз состоит сборка (пометка и очистка)? · `mark and sweep explained`
- [ ] Что делает фаза пометки и что — фаза очистки? · `mark phase sweep phase`
- [ ] Перемещает ли сборщик Go значения в памяти (нет уплотнения)? · `go gc non moving non compacting`
- [ ] Делит ли сборщик Go значения на «молодые» и «старые» (нет поколений) и почему? · `go gc not generational why`

**Гуглить:** `mark and sweep gc` · `go gc design non generational`

**Должен знать**
Сборка идёт в две фазы. Пометка: обойти всё, что достижимо от корней, и пометить живым. Очистка: пройти по памяти и сделать блоки непомеченных значений свободными для новых выделений. Очистка в Go идёт постепенно, вперемешку с работой программы.
Сборщик Go не перемещает значения (адреса не меняются) и не делит их на поколения — escape analysis и так оставляет на стеке большую часть короткоживущих значений.

**Термины**
- **пометка** — фаза поиска и отметки живых значений
- **очистка** — фаза освобождения памяти непомеченных значений

#### GO-21.3.3 Трёхцветная маркировка
**Вопросы**
- [ ] Как работает трёхцветная маркировка? · `tri-color marking explained`
- [ ] Что значат белый, серый и чёрный цвета? · `white grey black gc`
- [ ] Почему пометка заканчивается, когда серых не осталось? · `tricolor termination`
- [ ] Почему трёхцветная схема позволяет помечать по частям, вперемешку с программой? · `incremental concurrent marking tricolor`

**Гуглить:** `tricolor mark and sweep` · `go gc tricolor animation`

**Должен знать**
Все значения в начале белые. Корни красятся в серые. Дальше по одному: берут серое, все его белые «соседи» по указателям становятся серыми, а оно само — чёрным (оно и его ссылки просмотрены). Когда серых не осталось, всё чёрное — живое, всё белое — мусор.
Такая схема позволяет вести пометку частями и одновременно с работой программы: в любой момент понятно, что уже проверено, а что ещё нет.

**Термины**
- **трёхцветная маркировка** *(новое)* — пометка с белыми (не найдены), серыми (найдены, не просмотрены) и чёрными (просмотрены) значениями

#### GO-21.3.4 Сборка параллельно с программой и короткие stop-the-world
**Вопросы**
- [ ] Почему сборщику Go почти не нужно останавливать программу и где всё же бывают паузы? · `go gc concurrent stop the world pauses`
- [ ] Какие две короткие остановки есть в каждом цикле сборки? · `go gc stw phases`
- [ ] Какой длины обычно паузы (доли миллисекунды)? · `go gc pause times microseconds`
- [ ] Что такое «помощь сборщику»: почему активно выделяющая горутина сама помогает помечать? · `go gc mark assist`
- [ ] Сколько процессора сборщик берёт себе во время пометки (около 25%)? · `go gc 25 percent cpu`

**Гуглить:** `go gc pauses` · `go gc guide` · `mark assist latency`

**Должен знать**
Сборщик Go работает одновременно с программой: на пометку уходит около четверти процессора, остальное — программе. Полная остановка (stop-the-world) нужна лишь дважды за цикл и коротко — включить и выключить пометку; обычно это десятки–сотни микросекунд.
Если горутина выделяет память быстрее, чем сборщик успевает помечать, её заставляют помочь — часть её времени уходит на пометку. Это и есть «тормоза от сборщика» под нагрузкой, а не долгие паузы.

**Термины**
- **stop-the-world** *(новое)* — короткая остановка всех горутин для служебной работы сборщика
- **помощь сборщику** — выделяющая горутина сама выполняет часть пометки

#### GO-21.3.5 Барьер записи
**Вопросы**
- [ ] Зачем нужен барьер записи? · `go gc write barrier why`
- [ ] Что может пойти не так, если программа во время пометки перекладывает указатель с серого значения в чёрное? · `concurrent marking lost object`
- [ ] Почему барьер включается только во время пометки? · `write barrier only during mark`
- [ ] Что такое гибридный барьер — одной фразой? · `go hybrid write barrier`

**Гуглить:** `go write barrier` · `hybrid write barrier proposal`

**Должен знать**
Пока сборщик помечает, программа продолжает менять указатели. Опасный случай: указатель на белое значение записали в уже чёрное, а из серого убрали — сборщик к нему больше не придёт и выбросит живое значение. Барьер записи — небольшой код, который при каждой записи указателя во время пометки сообщает сборщику об изменении, и живое значение не теряется.
Вне пометки барьер выключен и ничего не стоит. В Go гибридный барьер, благодаря которому стеки не нужно пересматривать в конце.

**Термины**
- **барьер записи** *(новое)* — проверка при записи указателя, защищающая пометку от потерь

**Граница:** гибридный барьер — одной фразой.

#### GO-21.3.6 Когда запускается сборка: GOGC
**Вопросы**
- [ ] Когда запускается сборка? · `when does go gc run`
- [ ] Что значит `GOGC=100`: следующая сборка, когда куча вырастет вдвое от живого объёма? · `gogc 100 meaning`
- [ ] Что будет при `GOGC=50` и `GOGC=200`: чаще/реже, меньше/больше памяти? · `gogc tradeoff memory cpu`
- [ ] Что делает `GOGC=off`? · `gogc off`
- [ ] Можно ли предсказать, что сборка отработает за заданное время? · `predict gc duration`

**Гуглить:** `go gc guide gogc` · `tuning go gc`

**Должен знать**
`GOGC` задаёт, насколько может вырасти куча после сборки до следующей. При `GOGC=100` (по умолчанию) следующая сборка начнётся, когда куча вырастет на 100% от живого объёма после прошлой сборки: было живых 50 МБ — следующая сборка около 100 МБ. Меньше `GOGC` — сборки чаще, памяти меньше, процессора больше; больше — наоборот. `GOGC=off` выключает сборку по росту.
Время сборки зависит от объёма живых данных и числа указателей, поэтому точно предсказать его нельзя.

**Термины**
- **GOGC** *(новое)* — настройка роста кучи между сборками в процентах

#### GO-21.3.7 GOMEMLIMIT
**Вопросы**
- [ ] Что настраивает `GOMEMLIMIT`? · `go gomemlimit`
- [ ] Почему это «мягкий» лимит, а не жёсткий? · `gomemlimit soft limit`
- [ ] Как `GOMEMLIMIT` помогает не упасть по нехватке памяти, когда процессу выдан лимит снаружи? · `gomemlimit container oom`
- [ ] Зачем сочетать `GOGC=off` и `GOMEMLIMIT`? · `gogc off gomemlimit combination`
- [ ] Что будет, если живых данных больше лимита (сборщик не уйдёт в бесконечную работу)? · `gomemlimit death spiral protection`

**Гуглить:** `go 1.19 gomemlimit` · `go gc guide memory limit`

**Должен знать**
`GOMEMLIMIT` (Go 1.19) — мягкий предел памяти рантайма: когда общий объём приближается к нему, сборщик запускается чаще, чтобы уложиться. Это позволяет держать память близко к лимиту, выданному процессу, и не падать от его превышения, а при малой нагрузке не тратить лишний процессор.
Предел мягкий: если живых данных больше лимита, сборщик не будет работать бесконечно — его доля процессора ограничена, и память просто превысит лимит. Сочетание `GOGC=off` + `GOMEMLIMIT` значит «собирать только тогда, когда приблизились к лимиту».

**Термины**
- **GOMEMLIMIT** *(новое)* — мягкий предел памяти, по которому сборщик ускоряется

#### GO-21.3.8 Green Tea GC
**Вопросы**
- [ ] Что такое Green Tea GC и с какой версии он по умолчанию? · `go green tea gc`
- [ ] Чем он отличается: помечает память страницами, а не прыгает от значения к значению? · `green tea gc span based marking`
- [ ] Почему это лучше для кэша процессора и сколько экономит процессора на сборке? · `green tea gc performance`
- [ ] Изменилось ли что-нибудь для программиста? · `green tea gc user visible changes`

**Гуглить:** `go green tea garbage collector` · `go 1.26 release notes gc`

**Должен знать**
Green Tea — новая реализация пометки, по умолчанию с Go 1.26. Вместо того чтобы прыгать по памяти от значения к значению, она собирает работу по участкам памяти: значения одного участка просматриваются вместе. Это гораздо лучше ложится на кэши процессора и заметно сокращает процессорное время сборки (на типичных программах — на десятки процентов).
Для программиста ничего не меняется: те же `GOGC`, `GOMEMLIMIT` и та же модель.

**Термины**
- **Green Tea** *(новое)* — реализация пометки по участкам памяти, по умолчанию с Go 1.26

#### GO-21.3.9 Как снизить нагрузку на сборщик
**Вопросы**
- [ ] Как снизить нагрузку на сборщик мусора? · `reduce gc pressure go`
- [ ] Почему меньше указателей в данных — меньше работы при пометке? · `pointer free data faster gc`
- [ ] Как помогают предвыделение ёмкости и `sync.Pool`? · `preallocate sync.Pool reduce allocations`
- [ ] Почему `[]Item` часто лучше `[]*Item` для сборщика? · `slice of values vs slice of pointers gc`
- [ ] Почему сначала нужно измерить (профиль памяти), а потом оптимизировать? · `profile before optimizing allocations`

**Гуглить:** `go reduce allocations` · `go gc tuning guide`

**Должен знать**
Нагрузка на сборщик — это частота выделений (как часто запускать сборку) и число указателей в живых данных (сколько просматривать при пометке). Снижают её: меньше выделений (предвыделение, переиспользование буферов через `sync.Pool`, без лишних интерфейсов), меньше указателей (`[]Item` вместо `[]*Item`, значения вместо указателей в больших map).
Начинать нужно с профиля памяти: оптимизировать то, что реально выделяет больше всего.

**Термины**
- **данные без указателей** — значения, которые сборщику не нужно просматривать внутри

### GO-21.4 Рантайм целиком

#### GO-21.4.1 Что делает рантайм Go: сводная картина
**Вопросы**
- [ ] Расскажи за две минуты, что делает рантайм Go, пока работает твоя программа. · `what does go runtime do`
- [ ] Какие части рантайма ты уже знаешь (планировщик, стеки, аллокатор, сборщик, сетевой поллер, таймеры)? · `go runtime components`
- [ ] Чем управление памятью в Go отличается от CPython? · `go vs python memory management`
- [ ] Почему рантайм Go — не виртуальная машина? · `go runtime not a vm`

**Гуглить:** `go runtime overview` · `go runtime vs jvm` · `cpython memory management`

**Должен знать**
Рантайм Go — библиотека, вкомпилированная в каждую программу. Он: планирует горутины по потокам (GMP, вытеснение, кража работы); растит и уменьшает их стеки; выделяет память (размерные классы, локальные кэши P); собирает мусор одновременно с программой (трёхцветная пометка, барьер записи, `GOGC`, `GOMEMLIMIT`); ждёт сеть через поллер и обслуживает таймеры; проверяет границы и ловит паники.
Это не виртуальная машина: код уже машинный, рантайм лишь помогает ему. Мост из CPython: там интерпретатор выполняет байткод, память управляется подсчётом ссылок плюс сборщиком циклов, а GIL не даёт потокам выполнять байткод параллельно.

**Термины**
- **рантайм Go** — встроенная в программу часть, управляющая горутинами, памятью и сборкой мусора
