## GO-4. Функции

### GO-4.1 Объявление и вызов

#### GO-4.1.1 Объявление функции
**Вопросы**
- [ ] Как выглядит объявление `func имя(параметры) результат { … }`? · `golang function declaration`
- [ ] Почему у каждого параметра и результата обязательно указан тип? · `go function parameter types required`
- [ ] Чем объявление функции в Go отличается от `def` в Python (нет аргументов по умолчанию, нет именованных аргументов)? · `go no default parameters`
- [ ] Можно ли объявить функцию внутри другой функции через `func name()`? · `go nested function declaration not allowed`
- [ ] Важен ли порядок объявления функций в файле? · `go function order in file`

**Гуглить:** `go tour functions` · `golang func syntax` · `go no default arguments why`

**Должен знать**
`func add(a int, b int) int { return a + b }`: имя, параметры с типами, тип результата. Типы проверяются при компиляции: вызвать функцию с неподходящими аргументами нельзя.
Мост из Python: в Go нет значений по умолчанию, именованных аргументов и `*args`-магии на каждом шагу — функция вызывается ровно с теми аргументами, что объявлены. Функции объявляются на уровне пакета, порядок в файле не важен.

**Термины**
- **параметр** — переменная функции, которая получает значение при вызове
- **аргумент** — значение, переданное при вызове

**Граница:** функции с переменным числом аргументов (`...`) — позже, в GO-7.5.9.

#### GO-4.1.2 Параметры одного типа
**Вопросы**
- [ ] Как сократить `func f(a int, b int, c string)`? · `go function parameters same type shorthand`
- [ ] Как читать `func f(a, b int, c, d string)`: какой тип у `b`, а у `c`? · `go grouped parameters`
- [ ] Когда сокращение ухудшает читаемость? · `go parameter grouping readability`

**Гуглить:** `golang consecutive parameters same type`

**Должен знать**
Если несколько параметров подряд одного типа, тип пишут один раз в конце группы: `func f(a, b int, s string)` — `a` и `b` целые, `s` — строка. То же работает для результатов.

**Термины**
- **общий тип параметров** — один тип на несколько соседних параметров

#### GO-4.1.3 Несколько возвращаемых значений
**Вопросы**
- [ ] Как объявить функцию, которая принимает два `int` и возвращает их сумму и разность? · `go function multiple return values`
- [ ] Как принять несколько результатов одной строкой? · `go assign multiple return values`
- [ ] Почему в Go так часто последним результатом идёт признак ошибки? · `go return value and err convention`
- [ ] Чем это отличается от возврата кортежа в Python? · `python return tuple vs go multiple returns`
- [ ] Можно ли передать все результаты функции сразу как аргументы другой: `g(f())`? · `go pass multiple return values as arguments`

**Гуглить:** `golang multiple return values` · `go comma ok idiom`

**Должен знать**
`func divmod(a, b int) (int, int) { return a / b, a % b }` — несколько результатов пишут в скобках, а принимают множественным присваиванием: `q, r := divmod(7, 2)`.
В Go это основа обработки ошибок: функция возвращает результат и последним значением признак ошибки, а вызывающий сразу проверяет его. В Python функция возвращает один кортеж, который распаковывается; в Go это настоящие отдельные значения — положить их в одну переменную нельзя.

**Термины**
- **несколько результатов** — функция возвращает больше одного значения

#### GO-4.1.4 Пропуск результатов через _
**Вопросы**
- [ ] Как взять только второй результат функции? · `go ignore first return value`
- [ ] Можно ли просто не принимать результаты и вызвать `f()` отдельной строкой? · `go call function ignore all results`
- [ ] Почему выбрасывать признак ошибки через `_` — плохая привычка? · `go ignoring errors bad practice`

**Гуглить:** `golang blank identifier return values`

**Должен знать**
`_, r := divmod(7, 2)` — ненужный результат отбрасывают через `_`. Если не нужны вообще все результаты, функцию можно просто вызвать отдельной строкой.
Но принять часть результатов нельзя: либо все, либо ничего. Выбрасывать ошибку через `_` можно только тогда, когда точно знаешь, что её не бывает.

**Термины**
- **`_`** — место для ненужного результата

#### GO-4.1.5 Именованные результаты и голый return
**Вопросы**
- [ ] Что такое именованные результаты: `func f() (sum int, err error)`? · `go named return values`
- [ ] Какие значения у них в начале функции? · `named results zero values`
- [ ] Что такое голый `return` и что он возвращает? · `go naked return`
- [ ] Почему голый `return` в длинной функции — плохо? · `naked return readability`
- [ ] Когда именованные результаты полезны (документация, работа вместе с `defer`)? · `when to use named results go`

**Гуглить:** `golang named results` · `go naked return considered harmful`

**Должен знать**
Результатам можно дать имена: `func split(n int) (x, y int)`. Это обычные переменные функции, в начале у них нулевые значения. Голый `return` без значений возвращает их текущие значения.
В короткой функции именованные результаты служат подсказкой «что означает каждое значение». В длинной голый `return` вредит: читателю приходится выяснять, что лежит в переменных к этому моменту. Важное применение — изменение результата через `defer`.

**Термины**
- **именованные результаты** — результаты функции с именами; ведут себя как переменные
- **голый `return`** — `return` без значений, возвращает именованные результаты

#### GO-4.1.6 Числа из строк и обратно: strconv.Itoa и strconv.Atoi
**Вопросы**
- [ ] Как превратить строку `"42"` в число и обратно? · `golang strconv atoi itoa`
- [ ] Почему `strconv.Atoi` возвращает два значения, а `strconv.Itoa` — одно? · `atoi returns error why`
- [ ] Что вернёт `strconv.Atoi("12a")` и как это проверить? · `strconv.Atoi invalid syntax`
- [ ] Как перевести строку в `int64` или `float64` (`ParseInt`, `ParseFloat`)? · `golang strconv ParseInt ParseFloat`
- [ ] Чем `strconv.Itoa(n)` отличается от `fmt.Sprint(n)`? · `strconv.Itoa vs fmt.Sprint performance`

**Гуглить:** `golang strconv package` · `go convert string to int` · `strconv.ParseFloat example`

**Должен знать**
`strconv.Itoa(42)` даёт `"42"` и не может ошибиться. `strconv.Atoi("42")` возвращает число и признак ошибки: строка может не быть числом, поэтому результат всегда проверяют, прежде чем использовать. Для других размеров и дробных чисел есть `ParseInt`, `ParseFloat` и обратные `FormatInt`, `FormatFloat`.
`fmt.Sprint(n)` тоже превращает число в строку, но медленнее; в горячем коде предпочитают `strconv`.

**Термины**
- **`strconv`** — пакет преобразований между строками и числами
- **разбор строки** — получение значения из текста

#### GO-4.1.7 Ловушка string(65)
**Вопросы**
- [ ] Что выведет `string(65)` и как получить строку `"65"`? · `go string(int) conversion`
- [ ] Почему `string(n)` превращает число в символ с этим номером? · `go string from rune conversion`
- [ ] Что скажет `go vet` про такую запись? · `go vet stringintconv`
- [ ] Можно ли сделать `int("42")`? · `go cannot convert string to int`
- [ ] Когда `string(r)` для руны — это ровно то, что нужно? · `go convert rune to string`

**Гуглить:** `go string(int) pitfall` · `vet stringintconv`

**Должен знать**
`string(65)` — это `"A"`: преобразование целого в строку берёт число как code point и даёт строку из одного символа. Чтобы получить текст `"65"`, нужен `strconv.Itoa(65)`. Обратное `int("42")` вообще не скомпилируется — только `strconv.Atoi`.
`go vet` ругается на `string(int)`, потому что это почти всегда ошибка. Осознанно так делают только с рунами: `string('Ж')`.

**Термины**
- **`string(rune)`** — строка из одного символа с этим code point

### GO-4.2 Вызов в памяти

#### GO-4.2.1 Передача аргументов и кадр функции
**Вопросы**
- [ ] Как передаются аргументы в функцию в Go? · `go pass by value`
- [ ] Что лежит в кадре функции во время её работы? · `go function stack frame`
- [ ] Почему говорят, что в Go всё передаётся «по значению»? · `everything is passed by value in go`
- [ ] Как передаются аргументы в Python и почему функция там может изменить переданный список? · `python pass by object reference`
- [ ] От чего зависит цена передачи аргумента? · `cost of passing large value go`

**Гуглить:** `go function arguments copy` · `python call by sharing` · `go pass by value explained`

**Должен знать**
При вызове значения аргументов копируются в параметры — новые переменные в кадре вызванной функции. Функция работает со своими копиями. Это и есть передача по значению, и в Go она единственная. Цена передачи — размер копии.
Мост из Python: туда передаётся ярлык на тот же объект, поэтому функция может изменить переданный список «на месте». В Go так бывает только тогда, когда внутри значения лежит адрес — разберём по мере появления таких типов.

**Термины**
- **передача по значению** — параметр получает копию аргумента

#### GO-4.2.2 Изменение параметра внутри функции
**Вопросы**
- [ ] Функция присвоила новое значение своему параметру. Что увидит вызывающий и почему? · `go modify parameter does not affect caller`
- [ ] Как вернуть изменённое значение, если поменять исходное нельзя? · `go return modified value`
- [ ] Напиши `double(x int)`, которая «не работает», и исправь её через результат. · `go function cannot modify argument`
- [ ] Почему такое поведение делает код проще для понимания? · `value semantics benefits`

**Гуглить:** `golang change argument inside function` · `go value semantics`

**Должен знать**
Параметр — локальная копия, поэтому присваивание ему внутри функции не видно снаружи: у вызывающего его переменная не изменилась. Чтобы передать результат, функция его возвращает: `x = double(x)`.
Плюс такого правила: глядя на вызов, ты знаешь, что функция не может тайно поменять твою переменную.

**Термины**
- **локальная копия** — параметр, который не связан с переменной вызывающего

#### GO-4.2.3 Рекурсия в Go
**Вопросы**
- [ ] Как написать рекурсивный факториал или Фибоначчи на Go? · `golang recursion example`
- [ ] Есть ли в Go предел глубины рекурсии, как в Python? · `go recursion depth limit`
- [ ] Что произойдёт при бесконечной рекурсии в Go? · `go stack overflow fatal error goroutine stack exceeds`
- [ ] Почему наивный рекурсивный Фибоначчи такой медленный? · `naive fibonacci exponential time`
- [ ] Когда рекурсию лучше заменить циклом? · `recursion vs iteration go`

**Гуглить:** `golang recursion` · `go stack exceeds 1000000000-byte limit`

**Должен знать**
Рекурсия в Go работает как везде: каждый вызов получает свой кадр. Явного предела глубины, как в Python, нет — стек растёт сам, но до большого предела (около 1 ГБ на 64-битных системах). При бесконечной рекурсии программа падает с фатальной ошибкой о переполнении стека, и поймать её нельзя.
Если рекурсия может быть очень глубокой или считает одно и то же много раз (наивный Фибоначчи), её переписывают циклом или запоминают уже посчитанное.

**Термины**
- **фатальная ошибка** — падение программы, которое нельзя перехватить

### GO-4.3 Функция как значение

#### GO-4.3.1 Функциональные типы
**Вопросы**
- [ ] Что такое функциональный тип? Запиши тип функции, которая принимает `int` и возвращает `bool`. · `go function type`
- [ ] Какое нулевое значение у функционального типа и что будет при вызове такой функции? · `go nil function call panic`
- [ ] Можно ли сравнить две функции через `==`? · `go compare functions`
- [ ] Как дать функциональному типу имя: `type Predicate func(int) bool`? · `go named function type`

**Гуглить:** `golang function types` · `go func type declaration`

**Должен знать**
У функции тоже есть тип — её «подпись»: `func(int) bool` — функция, принимающая `int` и возвращающая `bool`. Имена параметров в тип не входят. Такому типу можно дать имя: `type Predicate func(int) bool`.
Нулевое значение функционального типа — `nil`; вызов его вызывает панику. Сравнивать функции можно только с `nil`.

**Термины**
- **функциональный тип** *(новое)* — тип функции: её параметры и результаты
- **сигнатура** — список типов параметров и результатов функции

**Граница:** `nil` подробно — по мере появления типов, где он встречается.

#### GO-4.3.2 Функция в переменной и функция как аргумент
**Вопросы**
- [ ] Как положить функцию в переменную и вызвать через неё? · `go assign function to variable`
- [ ] Как передать функцию в другую функцию как аргумент? · `go pass function as argument`
- [ ] Что значит «функции первого класса»? · `first class functions`
- [ ] Напиши `apply(x int, f func(int) int) int`. · `go higher order function example`
- [ ] Где ты уже встречал функцию-аргумент в Python (`sorted(key=...)`, `map`)? · `python key function higher order`

**Гуглить:** `golang first class functions` · `higher order functions go`

**Должен знать**
Функции в Go — значения «первого класса»: их можно класть в переменные, передавать аргументами и возвращать из других функций. `f := strings.ToUpper; f("go")`. Функция, которая принимает или возвращает функцию, — функция высшего порядка, как `sorted(key=…)` в Python.
Это основа многих будущих приёмов: сортировка по своему правилу, обработчики, промежуточные слои.

- **функция первого класса** — функцию можно использовать как обычное значение

- [ ] Как записать функцию без имени и сразу вызвать её? · `go anonymous function immediately invoked`

### GO-4.4 Замыкания

#### GO-4.4.1 Замыкания
**Вопросы**
- [ ] Что такое замыкание? · `go closure explained`
- [ ] Напиши функцию-счётчик, которая при каждом вызове возвращает следующее число. · `go closure counter example`
- [ ] Почему два счётчика, созданные отдельно, считают независимо? · `closure independent state`
- [ ] Где замыкания встречаются на практике (генераторы, обработчики, настройка поведения)? · `closures practical use go`

**Гуглить:** `golang closures` · `go tour function closures`

**Должен знать**
Замыкание — анонимная функция, которая пользуется переменными из окружающей функции. Например, `counter()` объявляет `n := 0` и возвращает `func() int { n++; return n }`: каждый вызов результата увеличивает ту же `n`.
Каждый вызов `counter()` создаёт новую `n`, поэтому два счётчика независимы. Так функция получает собственное состояние без глобальных переменных.

**Термины**
- **замыкание** *(новое)* — функция вместе с внешними переменными, которыми она пользуется

#### GO-4.4.2 Захват переменной
**Вопросы**
- [ ] Что именно захватывает замыкание: значение или саму переменную? · `go closure captures variable by reference`
- [ ] Что выведет код, где переменную меняют после создания замыкания, но до его вызова? · `closure sees later changes`
- [ ] Как захватить именно текущее значение (передать аргументом или скопировать в новую переменную)? · `capture value in closure go`
- [ ] Как CPython хранит захваченные переменные (cell-объекты, `__closure__`)? · `python closure cell objects`

**Гуглить:** `go closure capture semantics` · `python __closure__ cell`

**Должен знать**
Замыкание захватывает саму переменную, а не её значение на момент создания. Если переменную изменить снаружи, замыкание увидит новое значение; если замыкание её изменит, это увидит и окружающая функция.
Чтобы зафиксировать значение, его копируют в новую переменную или передают в функцию аргументом. Мост из Python: там захват устроен так же — через cell-объекты, общие для внешней функции и замыкания.

**Термины**
- **захват переменной** *(новое)* — замыкание получает доступ к самой переменной, не к её копии

#### GO-4.4.3 Время жизни захваченной переменной
**Вопросы**
- [ ] Почему захваченная переменная продолжает жить после выхода из функции? · `closure variable lifetime after return`
- [ ] Как это сочетается с тем, что кадр стека исчезает при возврате? · `closure variable stack or heap`
- [ ] Когда захваченная переменная наконец освобождается? · `closure garbage collected`
- [ ] Чем это может обернуться для памяти (замыкание держит большой объём данных)? · `closure memory retention`

**Гуглить:** `go closure variable escapes to heap` · `closure lifetime`

**Должен знать**
Переменная живёт, пока на неё есть ссылка, а замыкание — такая ссылка. Поэтому `n` из `counter()` продолжает жить после возврата из `counter`, хотя её кадр уже снят со стека: компилятор заранее кладёт такую переменную не в кадр, а в кучу. Освободит её сборщик мусора, когда пропадёт последнее замыкание.
Побочный эффект: замыкание, захватившее большой кусок данных, держит его в памяти, пока живёт само.

**Термины**
- **время жизни переменной** — от создания до момента, когда её можно освободить

#### GO-4.4.4 Переменная цикла в замыканиях: до и после Go 1.22

- [ ] Что выведут замыкания, созданные в цикле `for i := 0; i < 3; i++`, до Go 1.22 и после? · `go 1.22 loop variable semantics`
- [ ] Почему до Go 1.22 все замыкания видели последнее значение? · `go loop variable capture bug before 1.22`

**Должен знать**
До Go 1.22 переменная цикла была одной на весь цикл, и все замыкания захватывали её одну — после цикла они видели последнее значение. Чинили копией `i := i` в начале тела.

**Термины**
- **переменная цикла** — переменная, объявленная в заголовке `for`

### GO-4.5 defer

#### GO-4.5.1 defer
**Вопросы**
- [ ] Зачем нужен `defer`? Приведи пример из жизни. · `golang defer use cases`
- [ ] Когда выполняется отложенный вызов: в конце блока или при выходе из функции? · `go defer runs when function returns`
- [ ] Выполнится ли `defer`, если функция завершилась паникой? · `defer runs on panic`
- [ ] Почему `defer f.Close()` ставят сразу после успешного открытия файла? · `go defer close file pattern`
- [ ] Чем `defer` похож на `with` и `try/finally` в Python? · `go defer vs python with finally`

**Гуглить:** `go defer tutorial` · `go blog defer panic recover`

**Должен знать**
`defer вызов()` откладывает вызов до выхода из текущей функции — неважно, через какой `return` или из-за паники. Его ставят сразу после получения ресурса: открыл файл — `defer f.Close()`. Так освобождение не забудется ни на одном пути выхода.
Мост из Python: похоже на `try/finally` и `with`, но `defer` привязан к функции, а не к блоку.

**Термины**
- **defer** *(новое)* — отложить вызов до выхода из функции
- **отложенный вызов** — вызов, поставленный через `defer`

#### GO-4.5.2 Порядок выполнения нескольких defer
**Вопросы**
- [ ] В каком порядке выполняются несколько `defer`? · `go multiple defer order`
- [ ] Что выведет цикл `for i := range 3 { defer fmt.Println(i) }`? · `defer in loop order output`
- [ ] Почему обратный порядок логичен для ресурсов, которые зависят друг от друга? · `defer lifo resource cleanup order`

**Гуглить:** `golang defer lifo` · `defer stack order`

**Должен знать**
Отложенные вызовы выполняются в обратном порядке — LIFO: последний `defer` срабатывает первым, как стопка тарелок. `for i := range 3 { defer fmt.Println(i) }` выведет 2, 1, 0.
Это удобно: ресурсы освобождаются в порядке, обратном получению — сначала закрывается то, что открыли последним и что могло зависеть от предыдущего.

**Термины**
- **LIFO** *(новое)* — «последним пришёл — первым ушёл»

#### GO-4.5.3 Когда вычисляются аргументы defer
**Вопросы**
- [ ] Когда вычисляются аргументы отложенного вызова: при `defer` или при выполнении? · `go defer arguments evaluated immediately`
- [ ] Что выведет `x := 1; defer fmt.Println(x); x = 2`? · `defer println variable value`
- [ ] Как получить значение на момент выхода (анонимная функция-замыкание)? · `defer closure latest value`
- [ ] Что будет с `defer fmt.Println(time.Since(start))` и почему так не замерить время? · `defer time.Since evaluated immediately`

**Гуглить:** `golang defer argument evaluation` · `defer closure vs direct call`

**Должен знать**
Аргументы отложенного вызова вычисляются сразу, в строке с `defer`, а сам вызов — при выходе. Поэтому `x := 1; defer fmt.Println(x); x = 2` напечатает 1.
Нужно значение на момент выхода — пишут замыкание: `defer func() { fmt.Println(x) }()`; оно прочитает переменную в самом конце.

**Термины**
- **вычисление аргументов `defer`** — происходит сразу, а не при выполнении отложенного вызова

#### GO-4.5.4 defer и именованный результат
**Вопросы**
- [ ] Как `defer` может изменить результат функции? · `defer modify named return value`
- [ ] Что вернёт `func f() (n int) { defer func() { n++ }(); return 1 }`? · `go defer named result puzzle`
- [ ] В каком порядке: присваивание результата в `return`, потом `defer`, потом выход? · `go return statement defer order`
- [ ] Почему с неименованным результатом такой трюк не работает? · `defer cannot modify unnamed return`
- [ ] Где это используют на практике (добавить контекст к ошибке при выходе)? · `defer wrap error named return`

**Гуглить:** `go defer named result` · `defer return value modification`

**Должен знать**
`return 1` в функции с именованным результатом `n` сначала присваивает `n = 1`, потом выполняет отложенные вызовы и только затем выходит. Если замыкание под `defer` изменит `n`, вызывающий получит изменённое значение: пример выше вернёт 2.
С неименованным результатом замыканию нечего менять — у результата нет имени. На практике так в одном месте дополняют ошибку, вернувшуюся из любого `return`.

**Термины**
- **порядок выхода** — присвоить результат → выполнить `defer` → вернуться

#### GO-4.5.5 defer внутри цикла
**Вопросы**
- [ ] Чем плох `defer` внутри длинного цикла? · `defer in loop resource leak`
- [ ] Что будет, если в цикле открыть 10 000 файлов с `defer f.Close()`? · `too many open files defer loop`
- [ ] Как исправить: вынести тело цикла в отдельную функцию? · `defer in loop fix function`
- [ ] Сколько стоит сам `defer` в современных версиях Go? · `go defer performance cost 1.14`

**Гуглить:** `golang defer in loop` · `defer inside for loop problem`

**Должен знать**
`defer` срабатывает при выходе из функции, а не из итерации. В цикле все отложенные вызовы копятся до конца функции: 10 000 открытых файлов закроются только в самом конце, а до этого ОС может отказать в новых.
Решение — вынести тело цикла в отдельную функцию (или анонимную функцию), тогда `defer` сработает в конце каждой итерации. Сам `defer` сейчас почти бесплатный, проблема только в отложенном освобождении.

**Термины**
- **накопление `defer`** — отложенные вызовы в цикле ждут конца функции

### GO-4.6 panic и recover

#### GO-4.6.1 panic и раскрутка стека
**Вопросы**
- [ ] Что происходит в программе после паники? · `go panic what happens`
- [ ] Что такое раскрутка стека и в каком порядке выполняются отложенные вызовы при панике? · `go panic stack unwinding defer`
- [ ] Что печатается в терминале, когда паника доходит до самого верха? · `go panic stack trace output`
- [ ] Как читать распечатку стека при панике: где сообщение, где файл и строка? · `read go panic stack trace`
- [ ] Какие ошибки во время работы вызывают панику сами (деление на ноль, выход за границы)? · `go runtime panics list`

**Гуглить:** `golang panic` · `go stack unwinding` · `reading go stack traces`

**Должен знать**
Паника прерывает обычное выполнение функции. Дальше идёт раскрутка стека: в текущей функции выполняются её отложенные вызовы, затем функция завершается, паника переходит к вызывающему — и так вверх по цепочке. Если её никто не перехватит, программа печатает сообщение и распечатку стека (какие функции, файлы и строки были в стеке) и завершается.
Сам рантайм паникует при делении на ноль, выходе за границы и других ошибках, которые компилятор поймать не может.

**Термины**
- **раскрутка стека** *(новое)* — выход из функций по цепочке вызовов с выполнением их `defer`
- **распечатка стека** (stack trace) — цепочка вызовов в момент паники

#### GO-4.6.2 Вызов panic вручную
**Вопросы**
- [ ] Как вызвать панику самому и что можно передать в `panic`? · `go panic with message`
- [ ] Когда разумно паниковать вручную (невозможное состояние, ошибка программиста)? · `go when to call panic`
- [ ] Что такое функции `Must…` (`regexp.MustCompile`) и почему они паникуют? · `go must functions panic`
- [ ] Почему паника при запуске программы лучше, чем странное поведение потом? · `fail fast principle`

**Гуглить:** `golang panic function` · `regexp.MustCompile panic`

**Должен знать**
`panic("сообщение")` вызывает панику вручную; передать можно любое значение. Это сигнал «так быть не может, программа сломана», а не способ сообщить о нормальной ошибке.
Классика — функции `Must…`: `regexp.MustCompile` паникует при неверном шаблоне. Так делают для значений, которые готовят при запуске программы: если шаблон в коде неверный, лучше сразу упасть, чем работать дальше.

**Термины**
- **`panic`** — функция языка, вызывающая панику
- **`Must…`** — функция, которая паникует вместо возврата ошибки

#### GO-4.6.3 recover
**Вопросы**
- [ ] Где и как можно перехватить панику? · `go recover example`
- [ ] Почему `recover` работает только внутри отложенного вызова? · `why recover only works in deferred function`
- [ ] Что вернёт `recover()`, если паники не было? · `recover returns nil no panic`
- [ ] Можно ли перехватить панику, случившуюся в другой функции выше по стеку? · `recover scope caller callee`
- [ ] Как превратить панику в обычную ошибку через именованный результат? · `recover convert panic to error`
- [ ] Почему фатальные ошибки (переполнение стека) нельзя перехватить? · `go fatal error cannot be recovered`

**Гуглить:** `golang recover` · `go defer panic recover blog` · `recover named return error`

**Должен знать**
`recover()` останавливает раскрутку и возвращает значение, переданное в `panic`. Работает только при прямом вызове из функции под `defer`: только отложенные вызовы выполняются во время паники. Если паники нет, `recover()` возвращает `nil`.
Перехватить можно панику из любой функции ниже по стеку. Обычно перехват ставят на границе: обработчик запроса не должен ронять весь сервис. Фатальные ошибки рантайма через `recover` не ловятся.

**Термины**
- **recover** *(новое)* — функция языка, перехватывающая панику внутри `defer`

#### GO-4.6.4 Когда использовать панику
**Вопросы**
- [ ] Когда паника в своём коде уместна, а когда нет? · `go panic vs error guidelines`
- [ ] Почему в Go не принято использовать панику как `raise` в Python? · `go panic not exceptions`
- [ ] Почему библиотека не должна паниковать на неверных данных пользователя? · `library should not panic`
- [ ] Что значит «паника — это баг»? · `panic indicates programmer error`

**Гуглить:** `effective go panic` · `go errors vs exceptions` · `don't panic go proverb`

**Должен знать**
Паника — для ситуаций, которых не должно быть никогда: ошибка программиста, нарушенное внутреннее правило, невозможность запуститься. Всё, что может случиться при нормальной работе (неверный ввод, нет файла, сеть упала), в Go возвращают обычным значением ошибки.
Мост из Python: исключения там — обычный механизм ошибок, а в Go аналогичный приём через `panic`/`recover` считается плохим стилем.

**Термины**
- **ожидаемая ошибка** — ситуация, которая бывает при нормальной работе; не повод для паники

#### GO-4.6.5 os.Exit и отложенные вызовы
**Вопросы**
- [ ] Выполнятся ли отложенные вызовы, если программа завершилась через `os.Exit`? · `go os.Exit defer not run`
- [ ] Что делает `log.Fatal` и почему у него та же ловушка? · `log.Fatal skips defer`
- [ ] Что значит код возврата `os.Exit(1)` для ОС и скриптов? · `exit code 0 1 meaning`
- [ ] Как правильно завершить программу с кодом, не потеряв отложенные вызовы (вынести логику в `run()`)? · `go main run pattern exit code`

**Гуглить:** `golang os.Exit defer` · `go main func run pattern`

**Должен знать**
`os.Exit(code)` завершает процесс немедленно: отложенные вызовы не выполняются, данные, не записанные до конца, теряются. `log.Fatal` печатает сообщение и вызывает `os.Exit(1)` — с тем же эффектом.
Код возврата 0 — успех, всё остальное — неудача. Частый приём: вся логика в функции `run() error` со своими `defer`, а `main` только вызывает её и при ошибке делает `os.Exit(1)`.

**Термины**
- **`os.Exit`** — немедленное завершение процесса с кодом возврата
- **код возврата** — число, которым процесс сообщает ОС об успехе или неудаче
