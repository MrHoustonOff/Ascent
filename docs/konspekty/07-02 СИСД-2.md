## СИСД-2. Масштабирование

### СИСД-2.1 Масштабирование сервиса

#### СИСД-2.1.1 Вертикальное и горизонтальное масштабирование
**Вопросы**
- [ ] Чем вертикальное масштабирование отличается от горизонтального? · `vertical vs horizontal scaling`
- [ ] Почему вертикальное проще, но упирается в потолок и остаётся единой точкой отказа? · `vertical scaling limits`
- [ ] Что требуется от сервиса, чтобы его можно было запустить в нескольких копиях? · `horizontal scaling requirements`
- [ ] Почему сервис масштабировать легко, а базу — трудно? · `why databases are hard to scale`
- [ ] Почему на секции сначала стоит предложить вертикальное масштабирование базы? · `scale up before scale out database`

**Гуглить:** `scale up vs scale out` · `horizontal scaling explained`

**Должен знать**
Масштабирование — способность выдержать больше нагрузки. Вертикальное — дать машине больше процессоров и памяти: ничего не меняется в коде, но есть потолок, цена растёт быстрее мощности, а машина по-прежнему одна. Горизонтальное — запустить несколько копий и разделить работу: потолка почти нет, падение одной копии не останавливает систему, но копии должны быть одинаковыми и взаимозаменяемыми.
Сервис размножить легко. С базой труднее: данные должны быть согласованы между копиями. Поэтому для базы честный первый шаг — машина мощнее, затем копии для чтения, и только потом деление данных.

**Термины**
- **масштабирование** *(новое)* — увеличение нагрузки, которую выдерживает система
- **вертикальное / горизонтальное** — мощнее одна машина / больше одинаковых машин

**Позже:** копии базы для чтения — СИСД-2.2.1; деление данных между серверами — СИСД-2.3.2.

#### СИСД-2.1.2 Сервис без состояния
**Вопросы**
- [ ] Что значит «сервис без состояния»? · `stateless service`
- [ ] Почему сессии в памяти процесса мешают запустить несколько копий? · `in memory session horizontal scaling problem`
- [ ] Куда выносят состояние (база, Redis, объектное хранилище)? · `externalize state stateless`
- [ ] Почему локальный кэш в памяти допустим, а локальные данные пользователя — нет? · `local cache stateless service`
- [ ] Как это связано с тем, что pod одноразовый? · `stateless pods kubernetes`

**Гуглить:** `stateless vs stateful services` · `twelve factor app processes`

**Должен знать**
Сервис без состояния не хранит у себя ничего, что нужно для следующего запроса: сессии, корзины, загруженные файлы лежат в базе, Redis или внешнем хранилище. Тогда любой запрос может обработать любая копия, копии можно добавлять, убирать и перезапускать без потерь.
Локальный кэш допустим — это лишь ускорение, его потеря ничего не ломает. Сервис с состоянием (базы, брокеры) масштабируют совсем иначе и намного труднее.

**Термины**
- **сервис без состояния** *(новое)* — сервис, любая копия которого может обработать любой запрос

#### СИСД-2.1.3 Балансировщик нагрузки
**Вопросы**
- [ ] Что делает балансировщик нагрузки? · `load balancer explained`
- [ ] Как балансировщик узнаёт, что копия сервиса нездорова (проверки здоровья)? · `load balancer health checks`
- [ ] Не становится ли сам балансировщик единой точкой отказа и как с этим борются? · `load balancer single point of failure`
- [ ] Чем балансировщик отличается от Service в Kubernetes по сути? · `kubernetes service load balancing`

**Гуглить:** `what is a load balancer`

**Должен знать**
Балансировщик стоит перед копиями сервиса и раздаёт им запросы. Он регулярно проверяет здоровье копий и перестаёт слать запросы тем, что не отвечают, — так падение одной копии незаметно для клиента. Сам балансировщик делают отказоустойчивым: две копии с общим адресом или облачный управляемый. Service в Kubernetes — та же идея внутри кластера.

**Термины**
- **балансировщик** *(новое)* — узел, распределяющий запросы между копиями сервиса
- **проверка здоровья** — периодический запрос балансировщика к копии, чтобы понять, жива ли она

#### СИСД-2.1.4 Алгоритмы балансировки
**Вопросы**
- [ ] Как работает round robin? · `round robin load balancing`
- [ ] Чем least connections лучше при запросах разной длительности? · `least connections load balancing`
- [ ] Когда нужна привязка клиента к одной копии и почему её стараются избегать? · `sticky sessions drawbacks`
- [ ] Какие ещё алгоритмы есть (взвешенный, по хешу адреса)? · `load balancing algorithms`

**Гуглить:** `load balancing algorithms explained`

**Должен знать**
Round robin — по очереди: первый запрос первой копии, второй — второй и так по кругу. Просто и хорошо, если запросы примерно одинаковые. Least connections — туда, где сейчас меньше всего активных запросов: лучше, если одни запросы короткие, а другие долгие.
Остальное — названиями: взвешенный вариант (мощной машине больше), по хешу адреса клиента (один клиент — одна копия). Привязка к копии — признак того, что сервис хранит состояние; лучше вынести состояние наружу.

**Термины**
- **round robin** — раздача запросов по кругу
- **least connections** — запрос туда, где меньше активных соединений

**Граница:** round robin и least connections — учим; остальное названиями.

#### СИСД-2.1.5 Балансировка на уровне L4 и на уровне L7
**Вопросы**
- [ ] Чем балансировка на L4 отличается от балансировки на L7? · `l4 vs l7 load balancing`
- [ ] Что видит балансировщик L4 (адреса и порты), а что — L7 (путь, заголовки, cookie)? · `layer 4 vs layer 7 load balancer what it sees`
- [ ] Почему L7 может направлять `/api` и `/static` на разные сервисы, а L4 — нет? · `path based routing l7`
- [ ] Где происходит расшифровка TLS при L7-балансировке? · `tls termination load balancer`
- [ ] Почему L4 быстрее и проще? · `l4 load balancer performance`

**Гуглить:** `layer 4 vs layer 7 load balancing`

**Должен знать**
L4 работает на уровне TCP/UDP: видит только адреса и порты и пересылает соединение целиком, не заглядывая внутрь. Быстро, подходит для любого протокола.
L7 понимает HTTP: видит путь, заголовки, cookie — и может отправить `/api/orders` в один сервис, `/static` в другой, повторить запрос на другой копии, добавить заголовки. Для этого он расшифровывает TLS у себя. Дороже по ресурсам, но гибче; для HTTP-сервисов обычно L7.

**Термины**
- **L4 / L7** — балансировка по адресам и портам / по содержимому HTTP-запроса
- **терминирование TLS** — расшифровка TLS на балансировщике, дальше — обычный трафик

#### СИСД-2.1.6 Обратный прокси, nginx и API-шлюз
**Вопросы**
- [ ] Что такое обратный прокси и чем он отличается от обычного прокси? · `reverse proxy vs forward proxy`
- [ ] Зачем nginx перед Go-сервисом, если `net/http` и сам справляется? · `nginx in front of go server`
- [ ] Что делает API-шлюз (проверка токена, ограничение частоты, маршрутизация)? · `api gateway pattern`
- [ ] Почему проверку токена удобно делать в шлюзе, а не в каждом сервисе? · `api gateway authentication`

**Гуглить:** `what is a reverse proxy` · `api gateway pattern microservices`

**Должен знать**
Обратный прокси принимает запросы от клиентов вместо сервиса и пересылает их дальше; клиент о сервисах за ним не знает. Обычный прокси, наоборот, действует от имени клиента. nginx — самый частый обратный прокси: TLS, отдача статики, сжатие, ограничение размера тела и частоты, балансировка между копиями.
API-шлюз — обратный прокси для набора сервисов: одна точка входа, маршрутизация по путям, проверка токена, ограничение частоты, логи. Сервисы за ним получают уже проверенные запросы.

**Термины**
- **обратный прокси** *(новое)* — сервер, принимающий запросы клиентов за сервисы
- **nginx** — популярный веб-сервер и обратный прокси
- **API-шлюз** — единая точка входа для набора сервисов

#### СИСД-2.1.7 CDN
**Вопросы**
- [ ] Что такое CDN и какую задачу решает? · `what is a cdn`
- [ ] Какие данные отдают через CDN (картинки, скрипты, видео), а какие — нет? · `what to serve from cdn`
- [ ] Как CDN связана с заголовками кэширования HTTP? · `cdn cache control headers`

**Должен знать**
CDN — сеть серверов по всему миру, хранящих копии статических файлов ближе к пользователю. Картинка грузится из соседнего города, а не с другого континента, и запрос не доходит до твоего сервиса. Сколько хранить копию, CDN узнаёт из заголовков `Cache-Control`. Чтобы обновить файл, проще всего менять его имя (`app.3f2a.js`), а не ждать истечения кэша.

**Термины**
- **CDN** *(новое)* — сеть серверов, раздающих статику ближе к пользователю

#### СИСД-2.1.8 Объектное хранилище: S3
**Вопросы**
- [ ] Где хранить картинки товаров и почему не в базе? · `store images in database or s3`
- [ ] Что такое объектное хранилище (бакет, ключ, объект)? · `object storage explained`
- [ ] Что такое подписанная ссылка и как клиент загружает файл прямо в S3? · `s3 presigned url upload`
- [ ] Что хранится в базе, если сам файл в S3? · `store file metadata in database`

**Гуглить:** `amazon s3 basics` · `presigned url upload`

**Должен знать**
Картинки и файлы не хранят в базе: они раздувают её, замедляют резервные копии и отнимают ресурсы у запросов. Их кладут в объектное хранилище — S3 или совместимое (MinIO): плоское пространство «бакет + ключ → объект», почти безграничное и дешёвое. В базе хранят только ключ и сведения о файле.
Загружать удобно подписанной ссылкой: сервис выдаёт клиенту временную ссылку, и файл идёт прямо в S3, минуя сервис. Отдают файлы через CDN.

**Термины**
- **объектное хранилище** — хранилище файлов по ключу, например S3
- **подписанная ссылка** — временная ссылка с правом загрузить или скачать объект

**Граница:** почему файлы не в базе — одной фразой.

### СИСД-2.2 Репликация базы

#### СИСД-2.2.1 Ведущая база и реплики для чтения
**Вопросы**
- [ ] Зачем базе реплики и какие запросы на них отправляют? · `read replicas explained`
- [ ] Почему все записи идут только в ведущую базу? · `primary replica writes`
- [ ] Чем репликация отличается от деления данных на части? · `replication vs partitioning data`
- [ ] Как приложение решает, куда отправить запрос (два пула соединений)? · `read write splitting application`
- [ ] Помогают ли реплики, если не справляется запись? · `read replicas do not scale writes`

**Гуглить:** `postgresql streaming replication` · `read replicas scaling`

**Должен знать**
Ведущая база принимает все записи и пересылает изменения репликам (в PostgreSQL — через журнал WAL). Реплики — полные копии только для чтения. Тяжёлые чтения (списки, отчёты) отправляют на реплики, записи и чтения, которым нужна свежесть, — на ведущую. В приложении это обычно два пула: для записи и для чтения.
Реплики масштабируют чтение и дают запасную копию, но запись по-прежнему упирается в одну машину. Репликация — копии всех данных; деление данных — каждый сервер хранит свою часть.

**Термины**
- **ведущая база** — копия базы, принимающая записи
- **реплика** — копия базы только для чтения, получающая изменения от ведущей

**Позже:** деление данных между серверами — СИСД-2.3.2.

#### СИСД-2.2.2 Синхронная и асинхронная репликация
**Вопросы**
- [ ] Чем синхронная репликация отличается от асинхронной? · `synchronous vs asynchronous replication`
- [ ] Почему асинхронная быстрее, но может потерять последние записи при падении ведущей? · `async replication data loss`
- [ ] Почему синхронная замедляет запись и что будет, если реплика недоступна? · `synchronous replication latency availability`
- [ ] Какая используется по умолчанию в PostgreSQL? · `postgresql synchronous_commit replication default`

**Гуглить:** `postgresql synchronous replication`

**Должен знать**
Асинхронная репликация: ведущая подтверждает запись сразу, а реплики догоняют позже. Быстро, но реплики отстают, и если ведущая упадёт, последние записи могут не успеть дойти. Это вариант по умолчанию в PostgreSQL.
Синхронная: ведущая ждёт, пока хотя бы одна реплика подтвердит запись. Не теряем данные, но каждая запись медленнее, а при недоступной реплике запись встаёт. Часто берут компромисс: одна синхронная реплика, остальные асинхронные.

**Термины**
- **синхронная / асинхронная репликация** — подтверждение записи после реплики / не дожидаясь её

#### СИСД-2.2.3 Задержка репликации и чтение своих записей
**Вопросы**
- [ ] Пользователь сохранил данные и не увидел их на следующей странице. Почему? · `replication lag read after write`
- [ ] Что такое «чтение своих записей» и как его обеспечить? · `read your own writes consistency`
- [ ] Почему чтение сразу после записи отправляют на ведущую базу? · `route reads to primary after write`
- [ ] Как измерить задержку реплики? · `postgresql replication lag monitoring`

**Гуглить:** `read-your-writes` · `replication lag`

**Должен знать**
При асинхронной репликации реплика отстаёт на миллисекунды, а под нагрузкой — на секунды. Пользователь сохранил профиль (запись в ведущую), открыл страницу (чтение с реплики) — и видит старые данные.
Решения: читать с ведущей то, что пользователь только что изменил (например, несколько секунд после его записи или всегда для его собственных данных); или вернуть клиенту результат записи прямо в ответе. Задержку реплик измеряют и выводят в метрики.

**Термины**
- **задержка репликации** — насколько реплика отстаёт от ведущей
- **чтение своих записей** — гарантия, что пользователь видит собственные изменения

#### СИСД-2.2.4 Переключение на реплику при падении ведущей
**Вопросы**
- [ ] Что делать, если ведущая база упала? · `database failover`
- [ ] Почему при переключении могут потеряться последние записи? · `failover data loss async replication`
- [ ] Что такое «раздвоение», когда две базы считают себя ведущими? · `split brain database`

**Гуглить:** `postgresql failover`

**Должен знать**
Одну из реплик назначают новой ведущей и переключают на неё приложение — вручную или автоматически специальным инструментом. При асинхронной репликации записи, не дошедшие до реплики, теряются. Главная опасность — две базы одновременно считают себя ведущими и принимают записи; поэтому старую ведущую надёжно отключают.

**Термины**
- **переключение** — назначение реплики новой ведущей базой при отказе

**Граница:** одной фразой, без инструментов.

#### СИСД-2.2.5 Пул соединений перед базой
**Вопросы**
- [ ] Почему при 50 копиях сервиса база может упереться в число соединений? · `too many connections postgres microservices`
- [ ] Что делает внешний пул соединений вроде pgbouncer? · `pgbouncer explained`
- [ ] Как размер пула в каждой копии связан с лимитом базы? · `connection pool size per instance`

**Гуглить:** `pgbouncer transaction pooling`

**Должен знать**
У каждой копии сервиса свой пул соединений. 50 копий × 20 соединений = 1 000, а PostgreSQL тяжело держит столько: каждое соединение — отдельный процесс. Поэтому либо уменьшают пул в копии, либо ставят перед базой внешний пул (pgbouncer): копии держат много лёгких соединений к нему, а он — немного настоящих к базе.

**Термины**
- **внешний пул соединений** — посредник, делящий немного соединений с базой между многими клиентами

**Граница:** pgbouncer — названием.

### СИСД-2.3 Разделение данных

#### СИСД-2.3.1 Партиционирование таблицы
**Вопросы**
- [ ] Что такое партиционирование таблицы? · `postgresql table partitioning`
- [ ] Чем партиционирование по диапазону отличается от партиционирования по хешу? · `range vs hash partitioning`
- [ ] Почему старые данные удобно удалять целыми частями? · `drop partition retention`
- [ ] Почему партиционирование не помогает, если сервер не выдерживает записи? · `partitioning same server limits`

**Гуглить:** `postgresql declarative partitioning`

**Должен знать**
Партиционирование — одна большая таблица делится на части внутри одной базы, например по месяцам: `events_2026_10`, `events_2026_11`. Запрос с условием по дате читает только нужную часть, индексы меньше, а старый месяц удаляется целиком за мгновение вместо долгого `DELETE`. Делить можно по диапазону, по списку значений или по хешу.
Но всё по-прежнему на одном сервере: если он не выдерживает записи, партиционирование не поможет.

**Термины**
- **партиционирование** — деление таблицы на части внутри одной базы

#### СИСД-2.3.2 Шардирование
**Вопросы**
- [ ] Что такое шардирование и чем оно отличается от партиционирования? · `sharding vs partitioning`
- [ ] Чем шардирование отличается от репликации? · `sharding vs replication`
- [ ] Когда без шардирования уже не обойтись? · `when to shard database`
- [ ] Почему шардирование — крайняя мера? · `sharding complexity drawbacks`
- [ ] Как запрос находит нужный шард? · `shard routing`

**Гуглить:** `database sharding explained`

**Должен знать**
Шардирование — данные делятся между разными серверами баз: пользователи 1–1 000 000 на одном, следующие — на другом. Каждый шард хранит свою часть и принимает свою долю записей — так масштабируют запись и объём. Приложение (или прослойка) по ключу определяет, в какой шард идти.
Репликация копирует все данные, шардирование делит их; на практике каждый шард ещё и реплицируют. Это крайняя мера: усложняется всё — запросы, транзакции, миграции. Сначала — машина мощнее, реплики, кэш, партиционирование.

**Термины**
- **шардирование** *(новое)* — деление данных между разными серверами баз
- **шард** — один сервер с частью данных

#### СИСД-2.3.3 Ключ шардирования
**Вопросы**
- [ ] Как выбрать ключ шардирования? · `choosing a shard key`
- [ ] Что будет при неудачном ключе (горячий шард)? · `hot shard problem`
- [ ] Почему ключ должен совпадать с тем, по чему чаще всего ищут? · `shard key query pattern`
- [ ] Почему шардировать по дате создания — обычно плохая идея? · `shard by timestamp hotspot`
- [ ] Чем деление по хешу ключа отличается от деления по диапазонам? · `hash vs range sharding`

**Гуглить:** `shard key selection`

**Должен знать**
Ключ шардирования определяет, в какой шард попадёт запись. Хороший ключ равномерно распределяет данные и нагрузку и совпадает с главным запросом: в магазине — `user_id`, тогда все заказы пользователя лежат в одном шарде и читаются одним запросом.
Плохой ключ создаёт горячий шард: по дате — все новые записи идут в один шард; по стране — один шард с огромной страной. Хеш ключа даёт равномерность, диапазоны — удобные выборки по диапазону, но риск перекоса.

**Термины**
- **ключ шардирования** — поле, по которому выбирается шард
- **горячий шард** — шард, получающий непропорционально большую нагрузку

#### СИСД-2.3.4 Что ломается при шардировании
**Вопросы**
- [ ] Что ломается при шардировании? · `sharding problems cross shard`
- [ ] Почему JOIN и транзакции между шардами становятся трудными? · `cross shard join transaction`
- [ ] Как выполнить запрос, которому нужны данные всех шардов? · `scatter gather query`
- [ ] Почему уникальность и автоинкремент перестают работать сами? · `unique constraint across shards`
- [ ] Почему добавить шард — это перенос данных? · `resharding data migration`

**Гуглить:** `sharding pitfalls`

**Должен знать**
JOIN и транзакции между шардами база больше не делает — это работа приложения. Запрос «по всем шардам» (отчёт, поиск не по ключу) рассылают каждому шарду и собирают ответы — медленно. Уникальность поля гарантируется только внутри шарда, автоинкремент в каждом свой. Добавить шард — значит перенести часть данных, а при делении «хеш по модулю числа шардов» переезжает почти всё.
Поэтому ключ выбирают так, чтобы главные операции укладывались в один шард.

**Термины**
- **межшардовый запрос** — запрос, которому нужны данные нескольких шардов

#### СИСД-2.3.5 Консистентное хеширование
**Вопросы**
- [ ] Какую задачу решает консистентное хеширование? · `consistent hashing explained`
- [ ] Почему при `hash(key) % N` добавление сервера перемещает почти все ключи? · `modulo hashing rebalancing problem`
- [ ] Как выглядит идея кольца и сколько ключей переезжает при добавлении узла? · `consistent hashing ring`

**Гуглить:** `consistent hashing`

**Должен знать**
При делении `hash(key) % N` смена N с 4 на 5 меняет шард почти у всех ключей. Консистентное хеширование размещает и серверы, и ключи на одном «кольце» значений хеша; ключ принадлежит ближайшему серверу по часовой стрелке. Добавили сервер — переезжает только часть ключей соседнего участка (~1/N). Используется в распределённых кэшах и хранилищах.

**Термины**
- **консистентное хеширование** *(новое)* — способ раздачи ключей, при котором смена числа узлов двигает мало ключей

**Граница:** идея одной картинкой, без алгоритма.

#### СИСД-2.3.6 Уникальные идентификаторы в распределённой системе
**Вопросы**
- [ ] Как генерировать уникальные id, если база не одна? · `distributed unique id generation`
- [ ] Чем UUID хорош и чем плох как первичный ключ? · `uuid primary key pros cons`
- [ ] Почему UUIDv7 удобнее UUIDv4 для индекса? · `uuidv7 vs uuidv4 index`
- [ ] Как устроен идентификатор вида Snowflake (время + номер узла + счётчик)? · `twitter snowflake id`

**Гуглить:** `uuidv7` · `snowflake id`

**Должен знать**
Автоинкремент работает только внутри одной базы. Варианты: UUID — 128 бит, генерируется где угодно без согласования; UUIDv4 случайный и разбрасывает вставки по индексу, UUIDv7 начинается со времени и растёт почти по порядку — индексу так легче. Snowflake-подобные id — 64 бита: время, номер узла, счётчик; компактны и упорядочены по времени.

**Термины**
- **UUIDv7** — UUID, начинающийся с метки времени

**Граница:** Snowflake — названием.
