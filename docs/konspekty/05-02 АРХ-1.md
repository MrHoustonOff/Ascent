## АРХ-1. Архитектура сервиса

### АРХ-1.1 Слои

#### АРХ-1.1.1 Зачем делить код на слои
**Вопросы**
- [ ] Зачем делить код сервиса на слои? · `why layered architecture backend`
- [ ] Что плохого в обработчике HTTP, который сам пишет SQL и сам считает бизнес-правила? · `fat handler anti pattern`
- [ ] Как слои помогают тестировать логику без базы и без HTTP? · `layers testability`
- [ ] Что значит «одна причина для изменения» у каждого слоя? · `separation of concerns`

**Гуглить:** `layered architecture explained` · `separation of concerns`

**Должен знать**
Если обработчик сам разбирает запрос, считает правила и пишет SQL, то любое изменение затрагивает всё сразу, логику нельзя проверить без настоящей базы и HTTP, а повторно использовать её (например, из фоновой задачи) нельзя. Слои разделяют ответственность: один отвечает за протокол, другой — за правила, третий — за хранение.
Каждый слой меняется по своей причине: сменили формат API — меняется только верхний слой, сменили базу — только нижний.

**Термины**
- **слой** — часть кода с одной зоной ответственности
- **разделение ответственности** — каждая часть кода отвечает за своё

#### АРХ-1.1.2 Обработчик, сервис, репозиторий
**Вопросы**
- [ ] Чем занимается обработчик, сервис и репозиторий? · `handler service repository pattern go`
- [ ] Где проверяют формат запроса, а где — бизнес-правила («нельзя отменить оплаченный заказ»)? · `validation handler vs service layer`
- [ ] Почему в репозитории не должно быть бизнес-логики? · `repository no business logic`
- [ ] Как выглядит путь запроса «создать заказ» через три слоя? · `create order layers example`

**Гуглить:** `go handler service repository` · `repository pattern go`

**Должен знать**
Обработчик (transport) — разбирает HTTP или gRPC, проверяет формат, вызывает сервис, превращает результат и ошибки в ответ. Сервис (бизнес-логика) — правила предметной области: можно ли отменить заказ, сколько списать. Репозиторий — хранение: SQL-запросы, превращение строк в структуры и обратно.
Путь «создать заказ»: обработчик разобрал JSON → сервис проверил правила, посчитал сумму → репозиторий записал → сервис вернул заказ → обработчик ответил `201`.

**Термины**
- **обработчик** — слой протокола: разбор запроса и ответ
- **сервис** — слой бизнес-логики
- **репозиторий (слой)** *(новое)* — слой доступа к хранилищу

#### АРХ-1.1.3 Направление зависимостей
**Вопросы**
- [ ] В какую сторону направлены зависимости между слоями и почему? · `dependency direction layers`
- [ ] Почему сервис не должен импортировать пакет `net/http` или знать о JSON? · `service layer independent of transport`
- [ ] Почему репозиторий не должен вызывать обработчик? · `no upward dependencies`
- [ ] Как это защищает от циклического импорта? · `layering avoids import cycles go`

**Гуглить:** `dependency rule clean architecture` · `go import cycle layers`

**Должен знать**
Зависимости идут в одну сторону: обработчик знает о сервисе, сервис — о том, что ему нужно от хранилища, но не наоборот. Сервис не импортирует `net/http` и не знает про JSON — его можно вызвать из HTTP, gRPC, фоновой задачи или теста.
В Go это ещё и защита от циклического импорта, который компилятор запрещает.

**Термины**
- **направление зависимостей** — верхние слои зависят от нижних, а не наоборот

#### АРХ-1.1.4 Чистая архитектура
**Вопросы**
- [ ] Что такое чистая архитектура в общих словах? · `clean architecture explained`
- [ ] Почему в центре — бизнес-логика, а база и HTTP — «детали снаружи»? · `clean architecture dependency rule`
- [ ] Как интерфейсы позволяют логике не зависеть от базы? · `dependency inversion clean architecture`
- [ ] Почему в Go её применяют облегчённо, без десятка слоёв? · `clean architecture go pragmatic`
- [ ] Что такое гексагональная архитектура — одной фразой? · `hexagonal architecture ports adapters`

**Гуглить:** `clean architecture uncle bob` · `go clean architecture example`

**Должен знать**
Чистая архитектура ставит в центр бизнес-логику, а всё внешнее — базу, HTTP, очереди сообщений — считает сменными деталями. Правило одно: зависимости направлены внутрь, к логике; логика описывает, что ей нужно, интерфейсами, а внешние слои их реализуют.
В Go это обычно три-четыре пакета, а не десяток слоёв из книги. Гексагональная архитектура («порты и адаптеры») — та же идея под другим названием.

**Термины**
- **чистая архитектура** *(новое)* — логика в центре, внешние детали зависят от неё

**Граница:** гексагональная архитектура — названием.

#### АРХ-1.1.5 Отдельные модели для API, логики и базы
**Вопросы**
- [ ] Зачем разные модели для JSON, логики и строк базы? · `separate dto domain db models`
- [ ] Что пойдёт не так, если одна структура с тегами `json` и `db` используется везде? · `single struct json db tags problems`
- [ ] Как не отдать наружу лишнее поле (хеш пароля)? · `leak internal fields api`
- [ ] Чем платят за отдельные модели (код преобразований) и когда можно обойтись одной? · `dto mapping overhead`

**Гуглить:** `dto vs domain model` · `go separate models layers`

**Должен знать**
У каждого слоя своя форма данных: запрос и ответ API (что видит клиент), модель логики (что важно правилам), строка базы (как хранится). Если одна структура с тегами `json` и `db` идёт везде, переименование столбца ломает API, а хеш пароля легко случайно отдать клиенту.
Цена отдельных моделей — функции-преобразования между ними. В маленьком сервисе часть моделей можно объединить, но модель ответа API лучше держать отдельно.

**Термины**
- **DTO** — структура для передачи данных через границу слоя (запрос, ответ)
- **модель предметной области** — структура, которой оперирует бизнес-логика

#### АРХ-1.1.6 Раскладка Go-проекта: cmd и internal
**Вопросы**
- [ ] Как разложить Go-проект по папкам и зачем нужна `internal`? · `go project layout cmd internal`
- [ ] Что лежит в `cmd/имя/main.go`? · `go cmd directory`
- [ ] Почему `golang-standards/project-layout` — не официальный стандарт? · `project-layout not official`
- [ ] Как называть пакеты: по смыслу (`order`, `user`) или по слою (`handlers`, `models`)? · `go package by feature vs layer`

**Гуглить:** `go organizing a go module` · `go project layout`

**Должен знать**
Обычная раскладка: `cmd/app/main.go` — точка входа и сборка зависимостей; `internal/…` — весь код сервиса, который никто снаружи не импортирует; `migrations/` — миграции. `internal` компилятор защищает от импорта из других модулей.
Официального шаблона нет; популярный «project-layout» — соглашение сообщества, и для небольшого сервиса он избыточен. Пакеты лучше называть по смыслу (`order`, `payment`), а не по виду кода (`utils`, `models`).

**Термины**
- **`cmd/`** — папка с точками входа программ
- **`internal/`** — код, который нельзя импортировать снаружи модуля

### АРХ-1.2 Зависимости

#### АРХ-1.2.1 Внедрение зависимостей через конструктор
**Вопросы**
- [ ] Что такое внедрение зависимостей через конструктор? · `dependency injection constructor go`
- [ ] Почему сервис получает репозиторий параметром `NewService(repo, clock)`, а не создаёт его сам? · `why inject dependencies`
- [ ] Как это помогает в тестах подменить базу? · `di testing fake repository`
- [ ] Почему глобальные переменные-зависимости (`var db *sql.DB`) — плохо? · `global db variable anti pattern`

**Гуглить:** `dependency injection go` · `constructor injection`

**Должен знать**
Внедрение зависимостей — объект получает всё, что ему нужно, снаружи, обычно параметрами конструктора: `NewOrderService(repo OrderRepo, pay Payments) *OrderService`. Сам он ничего не создаёт и не берёт из глобальных переменных.
Так зависимости видны в сигнатуре, а в тесте вместо настоящей базы передают простую реализацию интерфейса в памяти.

**Термины**
- **внедрение зависимостей** *(новое)* — передача зависимостей объекту снаружи, а не создание внутри

#### АРХ-1.2.2 Кто объявляет интерфейс зависимости
**Вопросы**
- [ ] Где объявлять интерфейс репозитория: рядом с базой или в сервисе? Почему? · `go interface consumer side repository`
- [ ] Почему интерфейс должен содержать только методы, которые сервис реально вызывает? · `small interface repository`
- [ ] Что возвращает конструктор репозитория — интерфейс или конкретный тип? · `return concrete type repository constructor`
- [ ] Как это связано с GO-12.4.4 и GO-12.4.5? · `accept interfaces return structs repository`

**Гуглить:** `go interfaces belong to consumer` · `go repository interface where`

**Должен знать**
Интерфейс объявляет тот, кто им пользуется: пакет сервиса описывает `type OrderRepo interface { Create(ctx, o) error; ByID(ctx, id) (Order, error) }` — ровно то, что ему нужно. Пакет базы возвращает конкретный `*PostgresRepo`, который этому интерфейсу подходит неявно.
Так сервис не зависит от пакета базы, интерфейс маленький, а подменить его в тесте — дело нескольких строк.

**Термины**
- **интерфейс зависимости** — интерфейс, объявленный потребителем под свои нужды

#### АРХ-1.2.3 Сборка зависимостей в main
**Вопросы**
- [ ] Где собираются все зависимости сервиса? · `go wire dependencies in main`
- [ ] В каком порядке: настройки → база → репозитории → сервисы → обработчики → сервер? · `composition root order`
- [ ] Почему `main` — единственное место, которое знает обо всех конкретных типах? · `composition root`
- [ ] Как вынести сборку в функцию `run(ctx) error`? · `go main run pattern`

**Гуглить:** `composition root go` · `mat ryer how i write http services`

**Должен знать**
Все конкретные зависимости создаются в одном месте — в `main` (или в `run`, которую он вызывает): прочитать настройки → открыть пул базы → создать репозитории → сервисы с этими репозиториями → обработчики с сервисами → сервер. Это «корень композиции»: только здесь известно, что за интерфейсом прячется Postgres.
Остальной код получает зависимости готовыми и ничего не знает о том, как их собрали.

**Термины**
- **корень композиции** — место, где создаются и связываются все зависимости

#### АРХ-1.2.4 Транзакция на несколько репозиториев
**Вопросы**
- [ ] Где открывать транзакцию, если она затрагивает два репозитория? · `transaction across repositories go`
- [ ] Почему транзакцию открывает сервис, а не репозиторий? · `transaction boundary service layer`
- [ ] Как передать транзакцию репозиториям (интерфейс «выполнитель запросов» для `db` и `tx`)? · `go repository accept db or tx interface`
- [ ] Что такое менеджер транзакций `WithinTx(ctx, func(ctx) error)`? · `go transaction manager pattern`

**Гуглить:** `go transactions repository pattern` · `unit of work go`

**Должен знать**
Граница транзакции — бизнес-операция («создать заказ и списать остаток»), поэтому её открывает сервис. Репозитории принимают не `*sql.DB`, а маленький интерфейс с `ExecContext`/`QueryContext`, которому подходят и `*sql.DB`, и `*sql.Tx`.
Удобный вариант — менеджер транзакций: `txm.WithinTx(ctx, func(ctx context.Context) error { … })` кладёт транзакцию в контекст, а репозитории берут её оттуда, если она есть. Сервис при этом не знает про SQL.

**Термины**
- **граница транзакции** — какая операция выполняется в одной транзакции
- **менеджер транзакций** — помощник, выполняющий функцию внутри транзакции

#### АРХ-1.2.5 Конфигурация из переменных окружения
**Вопросы**
- [ ] Откуда сервис берёт настройки и почему не из констант в коде? · `twelve factor config env`
- [ ] Как прочитать настройки в структуру при запуске (`os.Getenv` или библиотека вроде `envconfig`)? · `go envconfig struct`
- [ ] Почему настройки проверяют при запуске и падают сразу, если чего-то не хватает? · `fail fast config validation`
- [ ] Где хранить секреты (пароль базы) — точно не в git? · `secrets not in git`
- [ ] Почему настройки передают в компоненты явно, а не читают окружение в глубине кода? · `don't read env deep in code`

**Гуглить:** `12 factor app config` · `kelseyhightower envconfig`

**Должен знать**
Настройки (адрес базы, порт, таймауты, ключи) приходят из переменных окружения: один и тот же исполняемый файл запускается на ноутбуке, в тестах и на сервере с разными значениями, а секреты не попадают в код. При запуске их читают в одну структуру `Config`, проверяют и при ошибке сразу падают с понятным сообщением.
Дальше компоненты получают нужные значения через конструкторы — `os.Getenv` в глубине кода превращает настройки в скрытые зависимости.

**Термины**
- **конфигурация** — настройки сервиса, которые меняются между окружениями
- **секрет** — настройка, которую нельзя показывать: пароли, ключи

#### АРХ-1.2.6 DI-фреймворки
**Вопросы**
- [ ] Что такое DI-фреймворки (wire, fx)? · `go wire vs fx`
- [ ] Почему в Go чаще собирают зависимости руками в `main`? · `go manual dependency injection`

**Гуглить:** `google wire` · `uber fx`

**Должен знать**
wire генерирует код сборки зависимостей заранее, fx собирает их во время работы. В большинстве Go-сервисов хватает ручной сборки в `main`: она явная и понятная, а фреймворк добавляет магию.

**Термины**
- **DI-фреймворк** — библиотека, автоматически собирающая зависимости

**Граница:** wire и fx — одной фразой.

### АРХ-1.3 SOLID и простые принципы

#### АРХ-1.3.1 Принцип единственной ответственности
**Вопросы**
- [ ] Расшифруй SOLID. · `solid principles explained`
- [ ] Что значит «у модуля одна причина для изменения»? · `single responsibility principle`
- [ ] Приведи пример нарушения: сервис, который и считает скидки, и шлёт письма, и пишет отчёты. · `srp violation example`
- [ ] Как в Go проявляется этот принцип на уровне пакетов? · `srp go packages`

**Гуглить:** `solid principles go` · `dave cheney solid go design`

**Должен знать**
SOLID — пять принципов: единственной ответственности, открытости-закрытости, подстановки Лисков, разделения интерфейсов, инверсии зависимостей. Первый: у модуля (пакета, типа) должна быть одна причина для изменения — одна зона ответственности. Сервис заказов, который ещё шлёт письма и строит отчёты, меняется при любой правке писем.
В Go это пакеты, названные по одной задаче, и типы, которые делают одно.

**Термины**
- **SOLID** *(новое)* — пять принципов проектирования
- **единственная ответственность** — одна причина для изменения модуля

#### АРХ-1.3.2 Принцип открытости-закрытости
**Вопросы**
- [ ] Что значит «открыт для расширения, закрыт для изменения»? · `open closed principle`
- [ ] Как добавить новый способ оплаты, не переписывая `switch` в сервисе? · `ocp interface new payment method`
- [ ] Как интерфейсы в Go дают это свойство? · `ocp go interfaces`

**Гуглить:** `open closed principle example go`

**Должен знать**
Код должен позволять добавлять поведение, не переписывая уже работающее. Вместо `switch method { case "card": …; case "sbp": … }` в сервисе — интерфейс `Payment` с реализацией на каждый способ; новый способ — новый тип, старый код не трогают.

**Термины**
- **открытость-закрытость** — расширение без изменения существующего кода

#### АРХ-1.3.3 Принцип подстановки Лисков
**Вопросы**
- [ ] Что значит принцип подстановки Лисков? · `liskov substitution principle simple`
- [ ] Почему реализация интерфейса не должна удивлять (паниковать там, где другие возвращают ошибку)? · `lsp violation example`
- [ ] Как это относится к Go, где наследования нет (реализации одного интерфейса взаимозаменяемы)? · `lsp go interfaces`

**Гуглить:** `liskov substitution principle explained`

**Должен знать**
Любую реализацию интерфейса можно подставить вместо другой, и код, который им пользуется, не должен сломаться. В Go это значит: все реализации `Storage` ведут себя одинаково по смыслу — возвращают одинаковые ошибки на «не найдено», не паникуют там, где другие возвращают ошибку, не требуют особого порядка вызовов.

**Термины**
- **подстановка Лисков** — реализации интерфейса взаимозаменяемы без сюрпризов

#### АРХ-1.3.4 Принцип разделения интерфейсов
**Вопросы**
- [ ] Что значит принцип разделения интерфейсов? · `interface segregation principle`
- [ ] Почему большой интерфейс `Repository` с двадцатью методами плох для потребителя, которому нужен один? · `fat interface problem`
- [ ] Как маленькие интерфейсы Go (`io.Reader`) воплощают этот принцип? · `isp go io.Reader`

**Гуглить:** `interface segregation go`

**Должен знать**
Клиента не заставляют зависеть от методов, которые ему не нужны. Вместо одного огромного интерфейса — несколько маленьких под конкретные задачи. В Go это получается само: интерфейсы объявляет потребитель, и они маленькие, как `io.Reader` с одним методом.

**Термины**
- **разделение интерфейсов** — маленькие интерфейсы под конкретные нужды

#### АРХ-1.3.5 Принцип инверсии зависимостей
**Вопросы**
- [ ] Что такое инверсия зависимостей и как она связана с интерфейсами? · `dependency inversion principle`
- [ ] Почему сервис должен зависеть от интерфейса хранилища, а не от пакета Postgres? · `depend on abstractions not concretions`
- [ ] Чем инверсия зависимостей отличается от внедрения зависимостей? · `dependency inversion vs dependency injection`

**Гуглить:** `dependency inversion vs injection`

**Должен знать**
Модули верхнего уровня (логика) не зависят от модулей нижнего (база) — оба зависят от абстракции, интерфейса, который объявлен рядом с логикой. Так «стрелка» зависимости разворачивается: пакет Postgres зависит от интерфейса сервиса, а не сервис от Postgres.
Инверсия — принцип (от чего зависеть), внедрение — способ (как передать реализацию: через конструктор).

**Термины**
- **инверсия зависимостей** — логика и детали зависят от абстракции, объявленной у логики

#### АРХ-1.3.6 DRY, KISS, YAGNI
**Вопросы**
- [ ] Что значат DRY, KISS и YAGNI? · `dry kiss yagni`
- [ ] Когда DRY вредит (общая функция для двух вещей, которые лишь похожи сегодня)? · `when dry hurts wrong abstraction`
- [ ] Почему «на будущее» абстракции чаще мешают? · `yagni premature abstraction`
- [ ] Что значит «немного копирования лучше, чем немного зависимости» из пословиц Go? · `a little copying is better than a little dependency`

**Гуглить:** `go proverbs` · `the wrong abstraction sandi metz`

**Должен знать**
DRY — не повторяй одно и то же знание в нескольких местах. KISS — делай просто. YAGNI — не делай того, что пока не нужно. DRY вредит, когда объединяют вещи, которые лишь похожи сегодня, а меняться будут по-разному: неверная общая абстракция хуже двух копий.
Пословица Go: «немного копирования лучше, чем немного зависимости». На собесе ждут, что ты знаешь и правила, и когда им не следовать.

**Термины**
- **DRY / KISS / YAGNI** — не повторяйся / делай проще / не делай лишнего заранее

### АРХ-1.4 Паттерны проектирования

#### АРХ-1.4.1 Паттерн проектирования
**Вопросы**
- [ ] Что такое паттерн проектирования? · `design pattern definition`
- [ ] Почему паттерн — словарь для разговора с командой, а не код для копирования? · `design patterns vocabulary`
- [ ] Почему многие классические паттерны в Go не нужны или выглядят иначе (функции первого класса, интерфейсы)? · `design patterns in go`

**Гуглить:** `refactoring guru design patterns` · `go design patterns`

**Должен знать**
Паттерн — типовое решение типовой задачи с общепринятым названием: сказал «фабрика» или «адаптер», и все поняли, о чём речь. Это словарь, а не готовый код. Многие классические паттерны придуманы для языков с классами; в Go их заменяют функции, замыкания и маленькие интерфейсы.

**Термины**
- **паттерн проектирования** — названное типовое решение типовой задачи

#### АРХ-1.4.2 Фабрика
**Вопросы**
- [ ] Что такое фабрика и как она выглядит в Go (функция, возвращающая реализацию интерфейса по настройке)? · `factory pattern go`
- [ ] Чем фабрика отличается от конструктора `NewX`? · `factory vs constructor`
- [ ] Что такое строитель (Builder) и почему в Go он встречается редко? · `builder pattern go`

**Гуглить:** `factory pattern golang`

**Должен знать**
Фабрика — функция, которая решает, какой конкретный тип создать: `NewStorage(cfg) (Storage, error)` вернёт Postgres или память в зависимости от настройки. Конструктор `NewX` создаёт один известный тип, фабрика выбирает из нескольких. Строитель — пошаговая сборка сложного объекта; в Go его обычно заменяет приём из АРХ-1.4.8.

**Термины**
- **фабрика** — функция, выбирающая и создающая конкретную реализацию
- **строитель** — пошаговая сборка объекта

#### АРХ-1.4.3 Одиночка
**Вопросы**
- [ ] Почему одиночку избегают и что делают вместо него в Go? · `singleton anti pattern go`
- [ ] Как в Go делают одиночку через `sync.Once`? · `go singleton sync.Once`
- [ ] Почему глобальный единственный экземпляр мешает тестам? · `singleton testing problems`

**Гуглить:** `singleton go sync.Once` · `singleton considered harmful`

**Должен знать**
Одиночка — тип, у которого в программе ровно один экземпляр, доступный отовсюду. В Go его делают через `sync.Once` и переменную пакета. Избегают потому, что это глобальное состояние: скрытая зависимость, тесты мешают друг другу, нельзя подменить.
Вместо одиночки создают один экземпляр в `main` и передают его через конструкторы.

**Термины**
- **одиночка** *(новое)* — единственный глобальный экземпляр типа

#### АРХ-1.4.4 Адаптер
**Вопросы**
- [ ] Что такое адаптер? · `adapter pattern explained`
- [ ] Как обернуть клиент чужого сервиса так, чтобы он подходил под твой интерфейс? · `adapter third party client interface go`
- [ ] Почему `http.HandlerFunc` — тоже адаптер? · `HandlerFunc adapter pattern`

**Гуглить:** `adapter pattern go`

**Должен знать**
Адаптер приводит один интерфейс к другому: тонкая обёртка вокруг клиента платёжной системы реализует твой интерфейс `Payments`, переводя вызовы и ошибки. Так чужая библиотека не расползается по коду. `http.HandlerFunc` — адаптер из функции в `http.Handler`.

**Термины**
- **адаптер** — обёртка, приводящая чужой интерфейс к нужному

#### АРХ-1.4.5 Декоратор
**Вопросы**
- [ ] Как в Go выглядит декоратор? Где ты его уже встречал? · `decorator pattern go middleware`
- [ ] Как добавить логирование или кэш к репозиторию, не меняя его кода (тип с тем же интерфейсом, оборачивающий оригинал)? · `decorator repository caching logging`
- [ ] Почему middleware — частный случай декоратора? · `middleware is decorator`

**Гуглить:** `decorator pattern golang`

**Должен знать**
Декоратор — обёртка с тем же интерфейсом, что и оборачиваемый объект, которая добавляет поведение до или после вызова. Например, `CachedRepo` реализует `OrderRepo`, сначала смотрит в кэш, а при промахе вызывает настоящий репозиторий. Middleware в `net/http` — тот же декоратор для обработчиков.

**Термины**
- **декоратор** *(новое)* — обёртка с тем же интерфейсом, добавляющая поведение

#### АРХ-1.4.6 Стратегия
**Вопросы**
- [ ] Что такое стратегия? · `strategy pattern explained`

- [ ] Когда стратегию оформляют интерфейсом, а когда функцией? · `strategy interface vs func go`

**Термины**

#### АРХ-1.4.7 Наблюдатель
**Вопросы**
- [ ] Что такое наблюдатель (подписчики на событие)? · `observer pattern explained`

#### АРХ-1.4.8 Функциональные опции
**Вопросы**
- [ ] Что такое функциональные опции и когда они удобнее конструктора с десятью параметрами? · `functional options pattern go`
- [ ] Как выглядит `NewServer(addr, WithTimeout(5*time.Second), WithLogger(l))`? · `functional options example`
- [ ] Как вариадический параметр `opts ...Option` делает опции необязательными? · `variadic options go`
- [ ] Чем это лучше структуры с настройками и чем хуже? · `functional options vs config struct`

**Гуглить:** `dave cheney functional options` · `functional options golang`

**Должен знать**
Функциональная опция — функция, которая настраивает объект: `type Option func(*Server)`, `func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }`. Конструктор `NewServer(addr string, opts ...Option)` задаёт значения по умолчанию и применяет переданные опции. Обязательное — обычными параметрами, необязательное — опциями.
Удобно для библиотек: новые настройки добавляются без изменения сигнатуры. Для внутреннего кода часто проще структура `Config`.

**Термины**
- **функциональные опции** *(новое)* — настройка объекта через функции-опции в конструкторе

### АРХ-1.5 Монолит и микросервисы

#### АРХ-1.5.1 Монолит
**Вопросы**
- [ ] Что такое монолит? · `monolith architecture`
- [ ] Какие плюсы у монолита (просто разрабатывать, выкладывать, отлаживать, транзакции в одной базе)? · `monolith advantages`
- [ ] Когда монолит начинает мешать (большая команда, долгая сборка, всё падает вместе)? · `monolith problems scale`

**Гуглить:** `monolith vs microservices` · `monolith first martin fowler`

**Должен знать**
Монолит — всё приложение собирается и выкладывается одним исполняемым файлом с одной базой. Его просто разрабатывать, тестировать, выкладывать и отлаживать, а транзакции охватывают любые данные. Мешать он начинает, когда команд много и они мешают друг другу, сборка и выкладка долгие, а ошибка в одной части роняет всё.

**Термины**
- **монолит** *(новое)* — приложение, собираемое и выкладываемое целиком

#### АРХ-1.5.2 Микросервисы
**Вопросы**
- [ ] Чем монолит отличается от микросервисов? · `microservices explained`
- [ ] По какому принципу делят систему на сервисы (по предметной области, у каждого своя база)? · `microservices boundaries own database`
- [ ] Как микросервисы общаются (HTTP, gRPC, сообщения)? · `microservices communication`
- [ ] Почему «общая база для всех сервисов» убивает смысл микросервисов? · `shared database anti pattern microservices`

**Гуглить:** `microservices martin fowler` · `database per service`

**Должен знать**
Микросервисы — система из небольших сервисов, каждый отвечает за свою часть предметной области, выкладывается отдельно и владеет своими данными. Общаются по сети: HTTP, gRPC, асинхронные сообщения. Если сервисы делят одну базу, их нельзя менять независимо — смысл теряется.

**Термины**
- **микросервис** *(новое)* — небольшой независимо выкладываемый сервис со своими данными

#### АРХ-1.5.3 Плюсы и минусы микросервисов
**Вопросы**
- [ ] Какие плюсы у микросервисов (независимые команды и выкладки, рост отдельных частей под нагрузку)? · `microservices pros`
- [ ] Какие минусы (сеть вместо вызова функции, распределённые транзакции, сложная отладка, инфраструктура)? · `microservices cons`
- [ ] Почему при маленькой команде микросервисы чаще вредят? · `microservices small team`
- [ ] Что значит «распределённый монолит»? · `distributed monolith`

**Гуглить:** `microservices tradeoffs` · `distributed monolith`

**Должен знать**
Плюсы: команды работают и выкладываются независимо, части можно отдельно усиливать под нагрузку, сбой одной части не обязательно роняет всё, можно выбирать технологии. Минусы: вызов функции превращается в сетевой вызов, который может упасть или задержаться; транзакции между сервисами невозможны напрямую; отладка и наблюдение сложнее; нужна инфраструктура.
Если сервисы всё равно приходится выкладывать вместе, получается распределённый монолит — худшее из двух миров.

**Термины**
- **распределённый монолит** — микросервисы, которые нельзя менять и выкладывать независимо

#### АРХ-1.5.4 Модульный монолит
**Вопросы**
- [ ] Что такое модульный монолит и почему с него часто начинают? · `modular monolith`
- [ ] Как модули внутри монолита отделяют друг от друга (свои пакеты, интерфейсы, свои таблицы)? · `modular monolith boundaries go`
- [ ] Как такой монолит потом разрезать на сервисы? · `extract microservice from modular monolith`

**Гуглить:** `modular monolith explained`

**Должен знать**
Модульный монолит — один исполняемый файл, но внутри чёткие модули с границами: свои пакеты в `internal`, общение через интерфейсы, свои таблицы. Он прост в выкладке, как монолит, но готов к разделению: модуль с чёткими границами легко вынести в отдельный сервис, когда это понадобится. С него разумно начинать.

**Термины**
- **модульный монолит** — монолит с чёткими внутренними границами модулей
