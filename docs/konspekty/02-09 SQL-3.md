## SQL-3. Агрегация и сложные запросы

### SQL-3.1 Агрегация

#### SQL-3.1.1 Агрегатные функции: COUNT, SUM, AVG, MIN, MAX
**Вопросы**
- [ ] Что делает агрегатная функция и сколько строк вернёт `SELECT count(*) FROM orders`? · `sql aggregate functions`
- [ ] Как посчитать общую сумму, среднюю и максимальную цену заказа? · `sql sum avg max example`
- [ ] Как агрегатные функции обращаются с `NULL` (пропускают)? · `sql aggregate functions ignore null`
- [ ] Что вернёт `sum` по таблице без строк — 0 или `NULL`? · `sum of empty set returns null`
- [ ] Почему `avg` по целым в PostgreSQL возвращает дробное число, а деление целых — нет? · `postgresql avg integer returns numeric`

**Гуглить:** `postgresql aggregate functions` · `sum empty table null coalesce`

**Должен знать**
Агрегатная функция сворачивает много строк в одно значение: `count` — количество, `sum` — сумма, `avg` — среднее, `min`/`max`. Если строки не разбивать на части, весь результат — одна строка. Значения `NULL` агрегатные функции пропускают.
Ловушка: по пустому набору строк `sum`, `avg`, `max` возвращают `NULL`, а не 0; если нужен 0 — `COALESCE(sum(x), 0)`.

**Термины**
- **агрегатная функция** *(новое)* — функция, сворачивающая много строк в одно значение

#### SQL-3.1.2 COUNT(*), COUNT(столбец), COUNT(DISTINCT столбец)
**Вопросы**
- [ ] Чем `COUNT(*)` отличается от `COUNT(столбец)` и `COUNT(DISTINCT столбец)`? · `count(*) vs count(column) vs count distinct`
- [ ] Что вернёт `COUNT(phone)`, если у половины пользователей телефон `NULL`? · `count column with nulls`
- [ ] Как посчитать, сколько разных покупателей сделали заказ? · `count distinct customers`
- [ ] Быстрее ли `COUNT(1)`, чем `COUNT(*)`? · `count(1) vs count(*) postgresql`

**Гуглить:** `sql count star vs count column` · `count distinct`

**Должен знать**
`COUNT(*)` считает строки. `COUNT(столбец)` — строки, где в этом столбце не `NULL`. `COUNT(DISTINCT столбец)` — сколько разных значений (без `NULL`). Поэтому `COUNT(phone)` при половине пустых телефонов вернёт половину строк.
`COUNT(1)` и `COUNT(*)` в PostgreSQL одинаковы по скорости и смыслу — это частый миф собесов.

**Термины**
- **`COUNT(*)`** — число строк
- **`COUNT(столбец)`** — число непустых значений

#### SQL-3.1.3 GROUP BY
**Вопросы**
- [ ] Как посчитать сумму заказов по каждому покупателю? · `sql group by sum per customer`
- [ ] Какие столбцы можно писать в `SELECT` вместе с `GROUP BY`? · `column must appear in the group by clause`
- [ ] Как сгруппировать по двум столбцам (город и месяц)? · `group by multiple columns`
- [ ] Как сгруппировать по дню, если в столбце момент времени (`date_trunc`)? · `postgresql group by day date_trunc`
- [ ] Как посчитать в одном запросе «сколько всего» и «сколько оплачено» через `count(*) FILTER` или `CASE`? · `postgresql filter clause conditional count`

**Гуглить:** `sql group by` · `postgresql filter where aggregate`

**Должен знать**
`GROUP BY customer_id` разбивает строки на группы с одинаковым значением, и агрегатные функции считаются для каждой группы: `SELECT customer_id, sum(total) FROM orders GROUP BY customer_id`. В `SELECT` можно писать только столбцы из `GROUP BY` и агрегатные функции — иначе непонятно, какое из значений группы показать.
Группировать можно по нескольким столбцам и по выражениям (`date_trunc('day', created_at)`). Условные подсчёты в одной группе — `count(*) FILTER (WHERE status = 'paid')` или `sum(CASE WHEN … THEN 1 ELSE 0 END)`.

**Термины**
- **GROUP BY** *(новое)* — группировка строк по значениям для агрегации
- **группа** — строки с одинаковыми значениями столбцов группировки

#### SQL-3.1.4 HAVING
**Вопросы**
- [ ] Что делает `HAVING`? · `sql having clause`
- [ ] Найди пользователей, у которых больше трёх заказов за месяц. · `sql having count > 3`
- [ ] Можно ли в `HAVING` использовать агрегатную функцию, которой нет в `SELECT`? · `having aggregate not in select`
- [ ] Можно ли `HAVING` без `GROUP BY`? · `having without group by`

**Гуглить:** `sql having` · `having vs where`

**Должен знать**
`HAVING` отбирает группы по условию с агрегатными функциями: `GROUP BY user_id HAVING count(*) > 3`. Агрегатная функция в `HAVING` не обязана быть в `SELECT`.
`HAVING` без `GROUP BY` возможен: тогда вся таблица — одна группа, и результат — одна строка или ни одной.

**Термины**
- **HAVING** *(новое)* — условие отбора групп после агрегации

#### SQL-3.1.5 WHERE против HAVING
**Вопросы**
- [ ] Чем `WHERE` отличается от `HAVING`? · `where vs having difference`
- [ ] Почему `WHERE count(*) > 3` — ошибка? · `aggregate functions are not allowed in where`
- [ ] Куда поставить условие «только заказы за март» и почему лучше в `WHERE`? · `filter before group by performance`
- [ ] Как одновременно использовать оба в одном запросе? · `where and having together example`

**Гуглить:** `sql where vs having` · `aggregate not allowed in where`

**Должен знать**
`WHERE` отбирает строки до группировки, `HAVING` — группы после неё. Поэтому агрегатные функции в `WHERE` писать нельзя: групп ещё нет.
Условия на сами строки («заказы за март») всегда ставят в `WHERE`: меньше строк попадёт в группировку, и запрос быстрее. В `HAVING` — только условия на итоги групп.

**Термины**
- **`WHERE` против `HAVING`** — отбор строк до группировки против отбора групп после

#### SQL-3.1.6 В каком порядке выполняются части SELECT
**Вопросы**
- [ ] В каком порядке логически выполняются части `SELECT`? · `sql logical query processing order`
- [ ] Почему псевдоним из `SELECT` нельзя использовать в `WHERE`, но можно в `ORDER BY`? · `sql alias in where vs order by`
- [ ] Где в этом порядке `DISTINCT` и `LIMIT`? · `sql order of execution distinct limit`
- [ ] Совпадает ли логический порядок с тем, как база на самом деле выполняет запрос? · `logical vs physical query execution`

**Гуглить:** `sql order of execution` · `logical query processing`

**Должен знать**
Логический порядок: `FROM` и соединения → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`/`OFFSET`. Из него всё следует: в `WHERE` нет псевдонимов, потому что `SELECT` ещё «не выполнен»; в `ORDER BY` они уже есть.
Это порядок смысла, а не реальной работы: база может выполнять шаги как угодно, лишь бы результат был таким же.

**Термины**
- **логический порядок выполнения** — в каком порядке «применяются» части запроса по смыслу

**Позже:** как база выполняет запрос на самом деле — PG-2.2.1.

### SQL-3.2 Подзапросы

#### SQL-3.2.1 Подзапрос в WHERE: IN
**Вопросы**
- [ ] Как найти покупателей, у которых есть заказы дороже 10 000, через подзапрос? · `sql subquery in where in`
- [ ] Сколько столбцов должен вернуть подзапрос в `IN`? · `subquery must return only one column`
- [ ] Как сравнить со скалярным подзапросом (`price > (SELECT avg(price) …)`)? · `scalar subquery`
- [ ] Возможно ли соединение с подзапросом? · `join with subquery`
- [ ] Когда тот же результат лучше получить соединением? · `subquery vs join`

**Гуглить:** `sql subquery` · `postgresql scalar subquery`

**Должен знать**
Подзапрос — запрос внутри запроса. `WHERE id IN (SELECT customer_id FROM orders WHERE total > 10000)` — подзапрос возвращает один столбец, и внешний запрос проверяет вхождение. Подзапрос, возвращающий одно значение, можно сравнивать как число: `price > (SELECT avg(price) FROM products)`.
Часто то же можно записать соединением; выбирают то, что понятнее, — современные базы обычно выполняют оба одинаково.

**Термины**
- **подзапрос** *(новое)* — запрос, вложенный в другой запрос
- **скалярный подзапрос** — подзапрос, возвращающий одно значение

#### SQL-3.2.2 EXISTS
**Вопросы**
- [ ] Чем `IN` с подзапросом отличается от `EXISTS`? · `in vs exists sql`
- [ ] Что возвращает `EXISTS` и важно ли, что выбрать в его подзапросе (`SELECT 1`)? · `exists select 1`
- [ ] Почему `EXISTS` может остановиться на первой найденной строке? · `exists short circuit`
- [ ] Найди товары, которые ни разу не заказывали, через `NOT EXISTS`. · `not exists example`

**Гуглить:** `sql exists` · `not exists vs not in`

**Должен знать**
`EXISTS (подзапрос)` истинно, если подзапрос вернул хотя бы одну строку; что именно он выбирает, неважно, поэтому пишут `SELECT 1`. База может остановиться на первой найденной строке.
`IN` проверяет вхождение значения в список, `EXISTS` — само наличие строк. `NOT EXISTS` — надёжный способ искать «то, у чего нет пары», без ловушки с `NULL` из следующего урока.

**Термины**
- **`EXISTS`** — проверка, что подзапрос вернул хотя бы одну строку

#### SQL-3.2.3 NOT IN и NULL
**Вопросы**
- [ ] Почему `NOT IN` возвращает пустой результат, если в подзапросе есть `NULL`? · `not in subquery null empty result`
- [ ] Распиши `x NOT IN (1, NULL)` через `AND` и трёхзначную логику. · `not in null three valued logic`
- [ ] Почему `IN` с `NULL` в списке такой проблемы не создаёт? · `in with null works`
- [ ] Как переписать запрос безопасно (`NOT EXISTS` или фильтр `IS NOT NULL`)? · `replace not in with not exists`

**Гуглить:** `sql not in null trap` · `not in vs not exists null`

**Должен знать**
`x NOT IN (1, NULL)` — это `x <> 1 AND x <> NULL`. Второе сравнение всегда «неизвестно», поэтому всё условие никогда не станет истинным, и запрос вернёт ноль строк. Если в подзапросе для `NOT IN` есть хоть один `NULL`, результат пуст.
`IN` так не ломается: там `OR`, и одного истинного сравнения достаточно. Безопасная замена — `NOT EXISTS` или явный `WHERE col IS NOT NULL` внутри подзапроса.

**Термины**
- **ловушка `NOT IN`** — `NULL` в подзапросе делает результат пустым

#### SQL-3.2.4 Подзапрос в FROM
**Вопросы**
- [ ] Как использовать результат запроса как таблицу в `FROM`? · `subquery in from derived table`
- [ ] Почему подзапросу в `FROM` нужно имя? · `subquery in from must have an alias`
- [ ] Как посчитать среднее число заказов на покупателя (сначала посчитать по покупателям, потом среднее)? · `average of counts subquery`
- [ ] Как это помогает против размножения строк при соединении? · `pre aggregate subquery before join`

**Гуглить:** `sql derived table` · `subquery in from clause`

**Должен знать**
Подзапрос в `FROM` — временная таблица из результата: `SELECT avg(cnt) FROM (SELECT customer_id, count(*) AS cnt FROM orders GROUP BY customer_id) AS per_customer`. Ему обязательно дают имя.
Так делают двухшаговые расчёты: сначала итоги по одному признаку, потом по ним. Это же лекарство от размножения строк: сначала посчитать заказы и отзывы по отдельности, потом соединить готовые итоги.

**Термины**
- **производная таблица** — подзапрос в `FROM`, используемый как таблица

#### SQL-3.2.5 Коррелированный подзапрос
**Вопросы**
- [ ] Что такое коррелированный подзапрос и почему он может быть медленным? · `correlated subquery`
- [ ] Как вывести для каждого покупателя дату его последнего заказа через подзапрос в `SELECT`? · `correlated subquery in select`
- [ ] Почему такой подзапрос выполняется «для каждой строки» внешнего запроса? · `correlated subquery per row`
- [ ] Как заменить его соединением с заранее посчитанными итогами? · `replace correlated subquery`

**Гуглить:** `sql correlated subquery` · `correlated subquery performance`

**Должен знать**
Коррелированный подзапрос ссылается на столбцы внешнего запроса: `SELECT c.name, (SELECT max(o.created_at) FROM orders o WHERE o.customer_id = c.id) FROM customers c`. По смыслу он выполняется заново для каждой строки внешнего запроса — на больших таблицах это может быть медленно.
Часто его заменяют соединением с заранее посчитанными итогами или приёмом из темы SQL-3.3.

**Термины**
- **коррелированный подзапрос** *(новое)* — подзапрос, зависящий от текущей строки внешнего запроса

#### SQL-3.2.6 CTE: WITH
**Вопросы**
- [ ] Зачем нужен CTE? · `sql cte with clause`
- [ ] Как переписать запрос с подзапросом в `FROM` через `WITH`? · `cte vs subquery`
- [ ] Можно ли объявить несколько CTE подряд и ссылаться на предыдущие? · `multiple ctes`
- [ ] Что такое рекурсивный CTE и где он нужен (дерево категорий) — одной фразой? · `recursive cte tree`

**Гуглить:** `postgresql with queries` · `cte explained`

**Должен знать**
`WITH per_customer AS (SELECT …) SELECT … FROM per_customer` — CTE: подзапрос с именем, объявленный до основного запроса. Длинный запрос превращается в цепочку понятных шагов, каждый со своим именем, и следующий шаг может ссылаться на предыдущие.
`WITH RECURSIVE` позволяет обходить деревья (категории, комментарии) — достаточно знать, что такое есть.

**Термины**
- **CTE** *(новое)* — именованный подзапрос в `WITH`

**Граница:** рекурсивные CTE — одной фразой.

### SQL-3.3 Оконные функции

#### SQL-3.3.1 Оконная функция и OVER
**Вопросы**
- [ ] Чем оконная функция отличается от агрегации с `GROUP BY`? · `window function vs group by`
- [ ] Как вывести каждый заказ и рядом общую сумму всех заказов (`sum(total) OVER ()`)? · `sum over empty window`
- [ ] Что задаёт `OVER (…)`? · `sql over clause`
- [ ] Где можно писать оконные функции, а где нельзя (в `WHERE` нельзя)? · `window functions not allowed in where`
- [ ] Как отфильтровать по результату оконной функции (подзапрос или CTE)? · `filter by window function result`

**Гуглить:** `postgresql window functions tutorial` · `sql window functions explained`

**Должен знать**
Оконная функция считает то же, что агрегатная, но не сворачивает строки: каждая строка остаётся, а рядом появляется результат по её «окну». `SELECT id, total, sum(total) OVER () FROM orders` — каждый заказ и общая сумма. `OVER (…)` задаёт окно: какие строки учитывать и в каком порядке.
Оконные функции считаются после `WHERE` и `GROUP BY`, поэтому фильтровать по их результату можно только снаружи — через подзапрос или CTE.

**Термины**
- **оконная функция** *(новое)* — функция по «окну» строк, не сворачивающая результат
- **окно** — набор строк, по которому считается функция для текущей строки

#### SQL-3.3.2 PARTITION BY
**Вопросы**
- [ ] Что делает `PARTITION BY` в `OVER`? · `sql partition by`
- [ ] Как вывести каждый товар и среднюю цену в его категории? · `avg over partition by category`
- [ ] Чем `PARTITION BY` отличается от `GROUP BY` по результату? · `partition by vs group by`
- [ ] Как посчитать долю заказа в сумме заказов покупателя? · `percentage of group total window`

**Гуглить:** `postgresql partition by` · `window partition example`

**Должен знать**
`PARTITION BY category` делит строки на части, и окно каждой строки — только её часть: `avg(price) OVER (PARTITION BY category)` даёт среднюю цену категории рядом с каждым товаром. Это как `GROUP BY`, только строки не сворачиваются.
Так удобно сравнивать строку с её группой: доля в сумме, отклонение от среднего.

**Термины**
- **`PARTITION BY`** — разбиение строк на независимые окна

#### SQL-3.3.3 ROW_NUMBER, RANK, DENSE_RANK
**Вопросы**
- [ ] Чем `ROW_NUMBER` отличается от `RANK` и `DENSE_RANK`? · `row_number vs rank vs dense_rank`
- [ ] Что получат три товара с одинаковыми продажами в каждой из функций? · `rank ties example`
- [ ] Зачем в `OVER` нужен `ORDER BY` для нумерации? · `row_number order by required`
- [ ] Почему `ROW_NUMBER` при равных значениях может давать разный порядок от запуска к запуску? · `row_number non deterministic ties`

**Гуглить:** `postgresql row_number rank dense_rank` · `rank vs dense_rank`

**Должен знать**
Все три нумеруют строки окна в порядке `ORDER BY` внутри `OVER`. `ROW_NUMBER` — всегда 1, 2, 3, 4, даже при равенстве. `RANK` — равным одинаковый номер с пропуском следующих: 1, 2, 2, 4. `DENSE_RANK` — без пропусков: 1, 2, 2, 3.
При равных значениях `ROW_NUMBER` расставит их произвольно; чтобы результат был стабильным, в `ORDER BY` добавляют второй столбец (например, `id`).

**Термины**
- **`ROW_NUMBER`** — сквозная нумерация строк окна
- **`RANK` / `DENSE_RANK`** — нумерация с одинаковыми номерами для равных (с пропуском и без)

#### SQL-3.3.4 Топ-N в каждой группе
**Вопросы**
- [ ] Как найти топ-3 товара по продажам в каждой категории? · `sql top n per group window function`
- [ ] Для каждого пользователя вывести его последний заказ. · `latest row per group postgresql`
- [ ] Почему нужен подзапрос или CTE вокруг `ROW_NUMBER`? · `filter row_number in where`
- [ ] Какую функцию нумерации выбрать, если у двух товаров одинаковые продажи на третьем месте? · `top n ties rank vs row_number`
- [ ] Что такое `DISTINCT ON` в PostgreSQL и как он решает задачу «последний заказ»? · `postgresql distinct on latest`

**Гуглить:** `top n per group sql` · `greatest n per group` · `postgresql distinct on`

**Должен знать**
Классика собесов: пронумеровать строки внутри каждой группы и оставить первые N. `WITH r AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY category ORDER BY sales DESC) AS rn FROM products) SELECT * FROM r WHERE rn <= 3`. Фильтр по `rn` — снаружи, потому что в `WHERE` того же запроса оконных функций нет.
Нужны все товары с равными продажами на границе — бери `RANK` или `DENSE_RANK`. «Последний заказ пользователя» — та же задача с N = 1; в PostgreSQL её ещё короче решает `DISTINCT ON`.

**Термины**
- **топ-N в группе** — первые N строк каждой группы по заданному порядку

#### SQL-3.3.5 LAG и LEAD
**Вопросы**
- [ ] Как найти разницу с предыдущей строкой (выручка дня минус выручка вчера)? · `sql lag difference previous row`
- [ ] Что вернёт `LAG` для первой строки окна? · `lag first row null default`
- [ ] Чем `LEAD` отличается от `LAG`? · `lag vs lead`
- [ ] Как посчитать время между соседними заказами одного пользователя? · `lag partition by user time between`

**Гуглить:** `postgresql lag lead` · `difference from previous row sql`

**Должен знать**
`LAG(x) OVER (ORDER BY day)` — значение `x` из предыдущей строки окна, `LEAD` — из следующей. Для первой строки `LAG` вернёт `NULL` (или значение по умолчанию третьим аргументом). Так считают изменения «день к дню» и промежутки между событиями — с `PARTITION BY user_id` отдельно для каждого пользователя.

**Термины**
- **`LAG` / `LEAD`** — значение из предыдущей / следующей строки окна

#### SQL-3.3.6 Накопительная сумма
**Вопросы**
- [ ] Как посчитать накопительную сумму выручки по дням? · `running total sql window`
- [ ] Почему `sum(x) OVER (ORDER BY day)` даёт накопительную сумму, а `sum(x) OVER ()` — общую? · `window frame default order by`
- [ ] Что такое рамка окна (`ROWS BETWEEN …`) и как посчитать скользящее среднее за 7 дней? · `moving average rows between 6 preceding`
- [ ] Почему при одинаковых значениях в `ORDER BY` накопительная сумма «прыгает» (RANGE против ROWS)? · `running total duplicates range vs rows`

**Гуглить:** `postgresql running total` · `window frame rows between` · `moving average sql`

**Должен знать**
С `ORDER BY` внутри `OVER` окно по умолчанию — от первой строки до текущей, поэтому `sum(revenue) OVER (ORDER BY day)` — накопительная сумма. Рамку можно задать явно: `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` — скользящее окно из 7 строк.
Тонкость: рамка по умолчанию включает все строки с тем же значением `ORDER BY`, поэтому при повторах сумма «прыгает»; `ROWS` вместо рамки по умолчанию это убирает.

**Термины**
- **накопительная сумма** — сумма от начала до текущей строки
- **рамка окна** — какие строки вокруг текущей входят в окно

**Граница:** все виды рамок — не нужны, достаточно `ROWS BETWEEN`.

### SQL-3.4 Наборы и запись

#### SQL-3.4.1 UNION против UNION ALL
**Вопросы**
- [ ] Чем `UNION` отличается от `UNION ALL` и что быстрее? · `union vs union all`
- [ ] Какие требования к запросам, которые объединяют (число и типы столбцов)? · `union column count types must match`
- [ ] Зачем `UNION` убирает дубликаты и чего это стоит? · `union remove duplicates cost`
- [ ] Что делают `INTERSECT` и `EXCEPT`? · `sql intersect except`

**Гуглить:** `sql union all` · `postgresql except intersect`

**Должен знать**
`UNION` склеивает результаты двух запросов в один и убирает повторяющиеся строки; `UNION ALL` склеивает как есть. Убрать повторы — значит отсортировать или сравнить все строки, поэтому `UNION ALL` быстрее; если повторов быть не может или они нужны — бери его.
У запросов должно быть одинаковое число столбцов совместимых типов. `INTERSECT` — строки, которые есть в обоих, `EXCEPT` — есть в первом, но нет во втором.

**Термины**
- **`UNION` / `UNION ALL`** — объединение результатов с удалением повторов / без

#### SQL-3.4.2 INSERT … ON CONFLICT
**Вопросы**
- [ ] Как вставить строку или обновить её, если такая уже есть, одним запросом? · `postgresql upsert on conflict`
- [ ] Что значит `ON CONFLICT (email) DO NOTHING`? · `on conflict do nothing`
- [ ] Как в `DO UPDATE` обратиться к значениям, которые пытались вставить (`EXCLUDED`)? · `on conflict do update excluded`
- [ ] Почему для `ON CONFLICT` нужно ограничение уникальности на этих столбцах? · `on conflict requires unique constraint`
- [ ] Почему «проверить `SELECT`-ом, потом вставить» — ненадёжно при одновременных запросах? · `check then insert race condition`

**Гуглить:** `postgresql insert on conflict` · `upsert postgresql`

**Должен знать**
`INSERT … ON CONFLICT (email) DO NOTHING` — вставить, а если строка с таким email уже есть, ничего не делать. `ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name` — обновить существующую; `EXCLUDED` — значения, которые пытались вставить. Это UPSERT одним запросом.
Конфликт определяется по ограничению уникальности или первичному ключу на указанных столбцах. Вариант «сначала проверить, потом вставить» ломается, когда два запроса делают это одновременно, — `ON CONFLICT` решает это внутри базы.

**Термины**
- **UPSERT** *(новое)* — «вставь или обнови» одной операцией
- **ON CONFLICT** *(новое)* — что делать при нарушении уникальности при вставке

#### SQL-3.4.3 RETURNING
**Вопросы**
- [ ] Как сразу получить `id` вставленной строки? · `postgresql insert returning id`
- [ ] Работает ли `RETURNING` с `UPDATE` и `DELETE`? · `update delete returning`
- [ ] Как вернуть несколько столбцов, включая значения по умолчанию (`created_at`)? · `returning multiple columns default`
- [ ] Почему это лучше, чем отдельный `SELECT` после вставки? · `returning vs select after insert`

**Гуглить:** `postgresql returning` · `insert returning`

**Должен знать**
`INSERT … RETURNING id, created_at` возвращает значения вставленной строки — включая те, что база сгенерировала сама: `id`, значения по умолчанию. Работает и с `UPDATE` (новые значения), и с `DELETE` (удалённые строки).
Это один запрос вместо двух, и он не может «промахнуться» мимо своей строки, как отдельный `SELECT` после вставки.

**Термины**
- **RETURNING** *(новое)* — вернуть столбцы строк, затронутых изменением
