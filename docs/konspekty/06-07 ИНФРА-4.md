## ИНФРА-4. Git и CI/CD

### ИНФРА-4.1 Git в команде

#### ИНФРА-4.1.1 Коммит, ветка, удалённый репозиторий
**Вопросы**
- [ ] Что такое коммит и почему он — снимок всего проекта, а не «разница»? · `git commit snapshot`
- [ ] Что такое ветка (просто указатель на коммит)? · `git branch pointer`
- [ ] Чем `fetch` отличается от `pull`, и что делает `push`? · `git fetch vs pull`
- [ ] Как писать хорошее сообщение коммита? · `good commit message`
- [ ] Почему коммиты лучше делать маленькими и о чём-то одном? · `atomic commits`

**Гуглить:** `git basics` · `pro git book` · `how to write a git commit message`

**Должен знать**
Коммит — сохранённое состояние проекта с автором, сообщением и ссылкой на предыдущий коммит. Ветка — просто подвижный указатель на коммит. Удалённый репозиторий (`origin`) — копия на сервере: `fetch` скачивает новое, `pull` — скачивает и вливает в текущую ветку, `push` — отправляет свои коммиты.
Хороший коммит — одно логическое изменение и сообщение «что и зачем» в повелительной форме: «Добавить повтор запроса к платёжному сервису».

**Термины**
- **коммит** — сохранённое состояние проекта в git
- **ветка** — указатель на коммит, двигающийся при новых коммитах
- **удалённый репозиторий** — копия репозитория на сервере

#### ИНФРА-4.1.2 Merge против rebase
**Вопросы**
- [ ] Чем merge отличается от rebase? · `git merge vs rebase`
- [ ] Почему rebase переписывает историю (создаёт новые коммиты)? · `rebase rewrites history`
- [ ] Когда rebase опасен (ветка, которую уже взяли другие)? · `golden rule of rebasing`
- [ ] Что такое squash (склеить все коммиты ветки в один при слиянии)? · `squash merge`
- [ ] Как обновить свою ветку от `main` перед ревью? · `rebase feature branch on main`

**Гуглить:** `merging vs rebasing atlassian` · `git rebase explained`

**Должен знать**
Merge соединяет две ветки коммитом слияния: история сохраняется как была, с развилками. Rebase переносит твои коммиты поверх другой ветки, создавая новые копии: история становится прямой, но старые коммиты заменены. Поэтому rebase делают только для своей ветки, которую ещё никто не взял, — иначе у коллег история разойдётся.
Squash при слиянии склеивает все коммиты ветки в один.

**Термины**
- **merge** — слияние веток коммитом слияния
- **rebase** *(новое)* — перенос коммитов поверх другой ветки с переписыванием истории

#### ИНФРА-4.1.3 Конфликты и их разрешение
**Вопросы**
- [ ] Почему возникает конфликт (одни строки изменены по-разному в двух ветках)? · `git merge conflict why`
- [ ] Как разрешить конфликт: что значат маркеры `<<<<<<<`, `=======`, `>>>>>>>`? · `resolve git conflict markers`
- [ ] Как проверить, что после разрешения всё работает (собрать и прогнать тесты)? · `test after resolving conflicts`
- [ ] Как уменьшить число конфликтов (маленькие ветки, частое обновление от `main`)? · `avoid merge conflicts`

**Гуглить:** `resolving merge conflicts`

**Должен знать**
Конфликт — git не может сам соединить изменения: одни и те же строки поменяли в двух ветках по-разному. В файле появляются маркеры с обоими вариантами; нужно оставить правильный код, убрать маркеры, добавить файл и завершить слияние. После этого обязательно собрать и прогнать тесты.
Чем короче живут ветки и чем чаще их обновляют от `main`, тем конфликтов меньше.

**Термины**
- **конфликт** — несовместимые изменения одних строк в двух ветках

#### ИНФРА-4.1.4 Pull request и код-ревью
**Вопросы**
- [ ] Как проходит pull request и код-ревью? · `pull request code review process`
- [ ] Каким должен быть хороший pull request (маленький, с описанием, с тестами)? · `good pull request size description`
- [ ] На что смотрят на ревью (правильность, читаемость, тесты, безопасность)? · `code review checklist`
- [ ] Как принимать замечания и как оставлять их самому? · `code review etiquette`

**Гуглить:** `google code review guide` · `how to do code review`

**Должен знать**
Pull request — предложение влить ветку в `main`: описание, что и зачем изменено, обсуждение и проверки. Коллеги смотрят код на ревью — правильность, понятность, тесты, безопасность — и оставляют замечания; автор исправляет, после одобрения ветку вливают.
Хороший pull request маленький (его реально прочитать), с понятным описанием и тестами. Замечания — к коду, не к человеку.

**Термины**
- **pull request** *(новое)* — запрос на слияние ветки с обсуждением и проверками
- **код-ревью** — проверка изменений коллегами перед слиянием

#### ИНФРА-4.1.5 Модели веток
**Вопросы**
- [ ] Что такое Git flow и trunk-based development — одной фразой каждое? · `git flow vs trunk based`
- [ ] Почему большинство команд с частыми выкладками выбирают короткие ветки от `main`? · `trunk based short lived branches`

**Гуглить:** `trunk-based development`

**Должен знать**
Git flow — много долгоживущих веток (develop, release, hotfix) под редкие выпуски. Trunk-based — все работают от `main` короткими ветками на день-два и вливают часто; недоделанное прячут за флагами. Команды с частыми выкладками сервисов обычно выбирают второе.

**Термины**
- **trunk-based** — работа короткими ветками от `main`

**Граница:** Git flow и trunk-based — названиями и одной фразой.

### ИНФРА-4.2 Конвейер выкладки

#### ИНФРА-4.2.1 CI
**Вопросы**
- [ ] Что такое CI и что в нём должно запускаться? · `continuous integration explained`
- [ ] Какие шаги типичны для Go (сборка, `go vet`, линтер, тесты с `-race`, сборка образа)? · `go ci pipeline steps`
- [ ] Почему pull request нельзя влить, пока CI красный? · `required status checks`
- [ ] Как ускорить CI (кэш модулей и сборки)? · `github actions go cache`
- [ ] Как выглядит простой файл GitHub Actions для Go? · `github actions go workflow`

**Гуглить:** `github actions go` · `continuous integration`

**Должен знать**
CI (непрерывная интеграция) — на каждый push и pull request автоматически собрать проект и проверить его: `go build ./...`, `go vet ./...`, линтер, `go test -race ./...`, при необходимости — сборка образа. Красный результат блокирует слияние: в `main` попадает только то, что собирается и проходит тесты.
Чтобы CI был быстрым, кэшируют скачанные модули и результаты сборки.

**Термины**
- **CI/CD** *(новое)* — автоматическая проверка (CI) и выкладка (CD) каждого изменения
- **конвейер** — последовательность автоматических шагов проверки и выкладки

#### ИНФРА-4.2.2 CD
**Вопросы**
- [ ] Чем CD отличается от CI? · `ci vs cd`
- [ ] Чем непрерывная поставка отличается от непрерывного развёртывания? · `continuous delivery vs deployment`
- [ ] Почему выкладка должна быть автоматической и повторяемой, а не «руками по SSH»? · `why automate deployment`
- [ ] Что происходит после слияния: образ с версией → реестр → выкладка → проверка? · `cd pipeline steps`

**Гуглить:** `continuous delivery vs continuous deployment`

**Должен знать**
CD продолжает CI: после слияния собирается образ с версией, публикуется в реестр и выкладывается — сначала на тестовое окружение, потом на прод. Непрерывная поставка — всё готово к выкладке, нажимает человек; непрерывное развёртывание — выкладка на прод тоже автоматическая.
Автоматическая выкладка одинакова каждый раз и легко откатывается; ручная — источник ошибок.

**Термины**
- **непрерывная поставка** — каждое изменение готово к выкладке
- **непрерывное развёртывание** — каждое изменение выкладывается автоматически

#### ИНФРА-4.2.3 Линтеры в CI: golangci-lint
**Вопросы**
- [ ] Какой линтер для Go ты запустишь в CI? · `golangci-lint`
- [ ] Что находят линтеры сверх `go vet` (непроверенные ошибки, затенение, мёртвый код)? · `golangci-lint linters list errcheck staticcheck`
- [ ] Как настроить набор линтеров файлом `.golangci.yml`? · `golangci yml config`

**Гуглить:** `golangci-lint quick start`

**Должен знать**
golangci-lint запускает сразу десятки линтеров: `errcheck` (непроверенные ошибки), `staticcheck` (баги и устаревшее), `govet`, `ineffassign`, проверки затенения и стиля. Набор задают файлом `.golangci.yml` и запускают в CI на каждый pull request.

**Термины**
- **golangci-lint** — инструмент, запускающий набор линтеров Go
