## PG-2. Индексы и план запроса

### PG-2.1 Индексы

#### PG-2.1.1 Полный просмотр таблицы
**Вопросы**
- [ ] Как база ищет строку, если ускоряющих структур нет? · `full table scan explained`
- [ ] Как PostgreSQL хранит таблицу на диске (страницы по 8 КБ)? · `postgresql heap pages 8kb`
- [ ] Почему время поиска растёт вместе с размером таблицы? · `full scan linear time`
- [ ] Почему для маленькой таблицы полный просмотр — нормально и даже быстрее всего? · `seq scan small table fastest`

**Гуглить:** `postgresql table storage pages` · `full table scan`

**Должен знать**
Таблица хранится в файле, разбитом на страницы по 8 КБ, а строки лежат в них без определённого порядка. Без вспомогательной структуры, чтобы найти `WHERE email = 'a@b.ru'`, база читает все страницы подряд и проверяет каждую строку. Время растёт пропорционально размеру таблицы.
Для маленьких таблиц это самый быстрый способ: прочитать пару страниц проще, чем что-то искать.

**Термины**
- **полный просмотр** — чтение всех строк таблицы подряд
- **страница** — блок данных таблицы на диске, обычно 8 КБ

#### PG-2.1.2 Индекс
**Вопросы**
- [ ] Что такое индекс и чем он похож на алфавитный указатель в конце книги? · `database index analogy`
- [ ] Как создать индекс (`CREATE INDEX ON users (email)`)? · `postgresql create index`
- [ ] Что хранит индекс: значения столбца и ссылки на строки? · `index stores value and row pointer`
- [ ] Почему индекс — это отдельная структура, которую база поддерживает сама? · `index maintained automatically`
- [ ] Какие индексы создаются автоматически (первичный ключ, `UNIQUE`)? · `postgresql automatic indexes primary key unique`

**Гуглить:** `database indexes explained` · `use the index luke`

**Должен знать**
Индекс — отдельная упорядоченная структура: значения столбца и для каждого — ссылка на строку в таблице. Как указатель в конце книги: найти слово в упорядоченном списке быстро, а по номеру страницы перейти к нужному месту. `CREATE INDEX ON users (email)` создаёт его, дальше база сама обновляет индекс при каждом изменении таблицы.
Для первичного ключа и `UNIQUE` индекс создаётся автоматически — так база быстро проверяет уникальность.

**Термины**
- **индекс в базе** *(новое)* — упорядоченная структура для быстрого поиска строк по значению

#### PG-2.1.3 B-дерево
**Вопросы**
- [ ] Как устроено B-дерево в общих чертах? · `b-tree index explained`
- [ ] Почему поиск в B-дереве занимает несколько шагов даже для миллиарда строк? · `b-tree height logarithmic`
- [ ] Почему B-дерево подходит и для `=`, и для `<`, `BETWEEN`, `ORDER BY`? · `b-tree range queries order by`
- [ ] Почему листья дерева связаны друг с другом? · `b-tree leaf linked list range scan`
- [ ] Почему узлы дерева размером со страницу диска? · `b-tree node page size`

**Гуглить:** `b-tree index postgresql` · `use the index luke anatomy`

**Должен знать**
B-дерево — дерево с широкими узлами: каждый узел — страница с сотнями упорядоченных ключей и ссылок на нижний уровень. Поиск идёт от корня вниз, выбирая нужный промежуток на каждом уровне; уровней обычно 3–4 даже для огромных таблиц, поэтому поиск — несколько чтений страниц.
Листья упорядочены и связаны между собой, поэтому B-дерево умеет не только `=`, но и диапазоны (`<`, `BETWEEN`) и выдачу в порядке `ORDER BY` без сортировки. Это вид индекса по умолчанию.

**Термины**
- **B-дерево** *(новое)* — сбалансированное дерево с широкими упорядоченными узлами
- **лист** — нижний уровень дерева со ссылками на строки

**Граница:** алгоритмическая сторона — отдельно, вне этого плана.

#### PG-2.1.4 Цена индекса
**Вопросы**
- [ ] Чем платят за индекс? · `cost of database indexes`
- [ ] Почему индексы замедляют вставку и изменение? · `indexes slow down inserts`
- [ ] Сколько места занимает индекс по сравнению с таблицей? · `index size disk`
- [ ] Почему лишний неиспользуемый индекс — вред, а не «на всякий случай»? · `unused indexes harm`
- [ ] Как найти неиспользуемые индексы (`pg_stat_user_indexes`)? · `find unused indexes postgresql`

**Гуглить:** `index overhead write performance` · `postgresql unused indexes query`

**Должен знать**
Каждый индекс нужно обновлять при каждой вставке, изменении проиндексированного столбца и удалении — запись становится медленнее с каждым индексом. Индекс занимает место на диске и в памяти, вытесняя из кэша полезные данные.
Поэтому индексы создают под конкретные запросы, а неиспользуемые удаляют; статистика использования есть в `pg_stat_user_indexes`.

**Термины**
- **цена индекса** — медленнее запись, больше места, больше нагрузка на кэш

#### PG-2.1.5 Составной индекс и порядок столбцов
**Вопросы**
- [ ] Индекс на `(a, b)`, а запрос фильтрует только по `b`. Будет ли он использован? А только по `a`? · `composite index column order`
- [ ] Почему составной индекс похож на телефонный справочник (фамилия, потом имя)? · `composite index phone book analogy`
- [ ] Как выбрать порядок столбцов: сначала по равенству, потом по диапазону? · `composite index equality then range`
- [ ] Может ли индекс `(a, b)` помочь с `WHERE a = 1 ORDER BY b`? · `composite index where order by`
- [ ] Что изменилось в PostgreSQL 18 (пропуск по первому столбцу)? · `postgresql 18 skip scan`

**Гуглить:** `composite index order of columns` · `multicolumn index postgresql`

**Должен знать**
Составной индекс `(a, b)` упорядочен сначала по `a`, внутри — по `b`, как справочник по фамилии, потом по имени. Он отлично работает для `a = …` и для `a = … AND b = …`, а также для `a = … ORDER BY b`. Для условия только по `b` он почти бесполезен — найти всех «Иванов» по имени без фамилии в справочнике нельзя (в PostgreSQL 18 появился пропуск по первому столбцу, но рассчитывать на него не стоит).
Порядок столбцов: сначала те, что сравниваются на равенство, затем диапазон или сортировка.

**Термины**
- **составной индекс** — индекс по нескольким столбцам в заданном порядке
- **ведущий столбец** — первый столбец составного индекса

#### PG-2.1.6 Покрывающий индекс и Index Only Scan
**Вопросы**
- [ ] Что такое покрывающий индекс? · `covering index explained`
- [ ] Почему запрос, которому хватает данных из индекса, не читает таблицу? · `index only scan`
- [ ] Как добавить в индекс столбцы «для выдачи», не участвующие в поиске (`INCLUDE`)? · `postgresql include columns index`
- [ ] Почему для Index Only Scan важна уборка `VACUUM` (карта видимости)? · `index only scan visibility map vacuum`

**Гуглить:** `postgresql index only scan` · `covering index include`

**Должен знать**
Если все столбцы, которые нужны запросу, есть в индексе, база может ответить, вообще не заходя в таблицу, — это Index Only Scan, он очень быстрый. Индекс, содержащий все нужные столбцы, называют покрывающим; столбцы «только для выдачи» добавляют через `INCLUDE`.
Но из-за многоверсионности базе нужно знать, видна ли строка; для страниц, которые недавно менялись, она всё равно сходит в таблицу. Помогает регулярный `VACUUM`, который отмечает «чистые» страницы.

**Термины**
- **покрывающий индекс** *(новое)* — индекс, содержащий все столбцы, нужные запросу
- **Index Only Scan** — ответ только по индексу, без чтения таблицы

#### PG-2.1.7 Уникальный индекс
**Вопросы**
- [ ] Чем уникальный индекс отличается от ограничения `UNIQUE`? · `unique index vs unique constraint`
- [ ] Почему ограничение `UNIQUE` под капотом создаёт уникальный индекс? · `unique constraint creates index`
- [ ] Когда нужен именно индекс (уникальность по выражению или с условием)? · `unique index on expression partial`
- [ ] Как сделать email уникальным без учёта регистра? · `unique lower email index`

**Гуглить:** `postgresql unique index vs constraint`

**Должен знать**
Ограничение `UNIQUE` — правило схемы; PostgreSQL реализует его уникальным индексом. Разница в возможностях: на ограничение могут ссылаться внешние ключи, а уникальный индекс можно построить по выражению или с условием — например, уникальность email без учёта регистра: `CREATE UNIQUE INDEX ON users (lower(email))`.

**Термины**
- **уникальный индекс** — индекс, запрещающий повтор значений

#### PG-2.1.8 Частичный индекс и индекс по выражению
**Вопросы**
- [ ] Что такое частичный индекс (`WHERE deleted_at IS NULL`) и когда он экономит место? · `postgresql partial index`
- [ ] Почему частичный индекс используется, только если условие запроса совпадает с условием индекса? · `partial index condition match`
- [ ] Что такое индекс по выражению (`lower(email)`) и почему без него `WHERE lower(email) = …` не ускоряется? · `postgresql expression index`
- [ ] Как сделать «уникальный активный email» через частичный уникальный индекс? · `partial unique index soft delete`

**Гуглить:** `partial indexes postgresql` · `expression index`

**Должен знать**
Частичный индекс охватывает только строки по условию: `CREATE INDEX ON orders (created_at) WHERE status = 'new'` — меньше места и быстрее, если запросы ищут именно новые заказы. Используется, только если условие запроса подразумевает условие индекса.
Индекс по выражению хранит не значение столбца, а результат выражения: `CREATE INDEX ON users (lower(email))`. Нужен, когда запрос фильтрует по выражению — обычный индекс по `email` для `lower(email) = …` не подойдёт.

**Термины**
- **частичный индекс** — индекс только по строкам, подходящим под условие
- **индекс по выражению** — индекс по результату выражения от столбцов

#### PG-2.1.9 Другие виды индексов: Hash, GIN, GiST, BRIN
**Вопросы**
- [ ] Какие виды индексов, кроме B-дерева, есть в Postgres и для чего каждый? · `postgresql index types`
- [ ] Чем B-дерево отличается от Hash-индекса? · `b-tree vs hash index`
- [ ] Для чего GIN (массивы, `jsonb`, полнотекстовый поиск)? · `gin index jsonb`
- [ ] Для чего GiST (геоданные, диапазоны)? · `gist index use cases`
- [ ] Для чего BRIN (огромные таблицы, где данные лежат по порядку, — логи по времени)? · `brin index time series`

**Гуглить:** `postgresql index types` · `gin vs gist`

**Должен знать**
Hash — только равенство, без диапазонов и сортировки; редко лучше B-дерева. GIN — «обратный» индекс для значений, внутри которых много элементов: массивы, `jsonb`, полнотекстовый поиск. GiST — для геоданных, диапазонов и поиска «ближайших». BRIN — крошечный индекс по диапазонам страниц для огромных таблиц, где данные естественно упорядочены (события по времени).

**Термины**
- **Hash / GIN / GiST / BRIN** — виды индексов под равенство, составные значения, геометрию и диапазоны, огромные упорядоченные таблицы

**Граница:** названием и одной задачей для каждого.

#### PG-2.1.10 Селективность
**Вопросы**
- [ ] Что такое селективность условия? · `selectivity database`
- [ ] Почему индекс по полю «пол» или «активен ли» обычно бесполезен? · `low cardinality index useless`
- [ ] Почему, если условию отвечает половина таблицы, полный просмотр быстрее индекса? · `index vs full scan threshold random io`
- [ ] Чем селективность отличается для `status = 'new'` при 1% новых и при 90% новых? · `selectivity skewed data`

**Гуглить:** `index selectivity` · `cardinality vs selectivity`

**Должен знать**
Селективность — какая доля строк подходит под условие. Чем она меньше, тем полезнее индекс: найти 10 строк из миллиона по индексу — мгновенно. Если подходит половина таблицы, переход по индексу к каждой строке — это множество разрозненных чтений, и прочитать таблицу подряд быстрее.
Поэтому индекс по столбцу с парой значений почти всегда бесполезен — кроме случая, когда искомое значение редкое (тогда хорош частичный индекс).

**Термины**
- **селективность** *(новое)* — доля строк, подходящих под условие

#### PG-2.1.11 Когда индекс не используется
**Вопросы**
- [ ] Почему индекс может не использоваться, хотя он есть? · `why postgresql not using index`
- [ ] Почему `WHERE lower(email) = …` или `WHERE created_at::date = …` не используют индекс по столбцу? · `function on indexed column`
- [ ] Почему `LIKE '%чай'` не использует индекс, а `LIKE 'чай%'` может? · `like leading wildcard index`
- [ ] Почему несовпадение типов (сравнение текста с числом) мешает индексу? · `implicit cast prevents index`
- [ ] Почему база может решить, что полный просмотр дешевле (мало строк, плохая селективность, устаревшая статистика)? · `planner chooses seq scan`

**Гуглить:** `postgresql index not used reasons` · `use the index luke where clause`

**Должен знать**
Частые причины: функция или приведение типа над столбцом (`lower(email)`, `created_at::date`) — нужен индекс по выражению или переписанное условие; шаблон, начинающийся с `%`; несовпадение типов; условие не по ведущему столбцу составного индекса; `OR` по разным столбцам; низкая селективность; маленькая таблица; устаревшая статистика.
Во всех случаях не гадают, а смотрят план запроса — следующая тема.

**Термины**
- **неиспользуемый индекс** — индекс есть, но планировщик выбрал другой путь

### PG-2.2 План запроса

#### PG-2.2.1 EXPLAIN
**Вопросы**
- [ ] Что показывает `EXPLAIN`? · `postgresql explain`
- [ ] Как читать план: дерево узлов, вложенность снизу вверх? · `how to read explain plan`
- [ ] Что значат `cost=0.00..123.45` и `rows=10`? · `explain cost rows meaning`
- [ ] Почему стоимость — условные единицы, а не миллисекунды? · `explain cost units`
- [ ] Чем помогают сервисы визуализации планов (explain.depesz.com, explain.dalibo.com)? · `explain visualizer`

**Гуглить:** `postgresql explain tutorial` · `explain.depesz.com`

**Должен знать**
`EXPLAIN запрос` показывает план — как база собирается выполнить запрос, не выполняя его. План — дерево узлов: листья читают таблицы, верхние соединяют, фильтруют, сортируют. У каждого узла оценка: `cost=начало..всего` в условных единицах и `rows` — сколько строк ожидается.
Так видно, какие таблицы читаются целиком, используются ли индексы и где ожидается больше всего строк.

**Термины**
- **EXPLAIN** *(новое)* — команда, показывающая план выполнения запроса
- **план запроса** — дерево шагов, которыми база выполнит запрос
- **планировщик** — часть базы, выбирающая план

#### PG-2.2.2 Seq Scan, Index Scan, Bitmap Scan
**Вопросы**
- [ ] Чем Seq Scan отличается от Index Scan и Bitmap Scan? · `seq scan vs index scan vs bitmap scan`
- [ ] Когда база выбирает Bitmap Scan (строк много, но не половина таблицы)? · `bitmap heap scan when`
- [ ] Что значит Index Only Scan в плане? · `index only scan explain`
- [ ] Что значит строка `Filter: …` и `Rows Removed by Filter` в плане? · `explain filter rows removed`

**Гуглить:** `postgresql scan types` · `bitmap heap scan explained`

**Должен знать**
Seq Scan — полный просмотр таблицы. Index Scan — найти в индексе и сходить за каждой строкой в таблицу; хорош для немногих строк. Bitmap Scan — сначала по индексу собрать «карту» нужных страниц, потом прочитать их по порядку; середина между двумя, когда строк много. Index Only Scan — ответ прямо из индекса.
`Filter` в плане — условие, проверяемое после чтения строк; много отброшенных строк — повод подумать об индексе.

**Термины**
- **Seq Scan** *(новое)* — полный просмотр таблицы в плане
- **Index Scan** *(новое)* — поиск по индексу с чтением строк из таблицы
- **Bitmap Scan** — сбор нужных страниц по индексу и их чтение по порядку

#### PG-2.2.3 EXPLAIN ANALYZE
**Вопросы**
- [ ] Чем `EXPLAIN` отличается от `EXPLAIN ANALYZE`? · `explain vs explain analyze`
- [ ] Почему `EXPLAIN ANALYZE` нельзя бездумно запускать для `DELETE` на рабочей базе? · `explain analyze executes query`
- [ ] Как сравнить ожидаемые `rows` и фактические `actual rows` и что значит большое расхождение? · `explain analyze estimate vs actual`
- [ ] Что добавляет `BUFFERS` (сколько страниц прочитано из памяти и с диска)? · `explain analyze buffers`
- [ ] Дан медленный запрос и его план — как найти причину? · `slow query explain analyze diagnosis`

**Гуглить:** `postgresql explain analyze` · `explain analyze buffers`

**Должен знать**
`EXPLAIN ANALYZE` действительно выполняет запрос и показывает рядом с оценками фактическое время и число строк каждого узла. Поэтому изменяющие запросы анализируют внутри транзакции с последующим `ROLLBACK`. `BUFFERS` добавляет, сколько страниц прочитано из кэша и с диска.
Главное — сравнить ожидаемые и фактические строки: расхождение в разы значит, что планировщик ошибся (часто — устаревшая статистика) и мог выбрать плохой план. Затем ищут самый дорогой узел и Seq Scan по большой таблице с сильным `Filter`.

**Термины**
- **`EXPLAIN ANALYZE`** — выполнение запроса с фактическими временами по узлам плана

#### PG-2.2.4 Способы соединения: Nested Loop, Hash Join, Merge Join
**Вопросы**
- [ ] Какие способы соединения таблиц выбирает Postgres? · `postgresql join algorithms`
- [ ] Когда хорош Nested Loop (мало строк снаружи и индекс внутри)? · `nested loop join when`
- [ ] Как работает Hash Join (построить хеш-таблицу по меньшей стороне)? · `hash join explained`
- [ ] Когда выбирают Merge Join (обе стороны уже упорядочены)? · `merge join explained`

**Гуглить:** `nested loop vs hash join vs merge join`

**Должен знать**
Nested Loop — для каждой строки внешней стороны искать пары во внутренней; хорош, когда снаружи мало строк, а внутри есть индекс. Hash Join — по меньшей стороне строится хеш-таблица, большая сторона проходит по ней; для соединений по равенству больших наборов. Merge Join — обе стороны упорядочены по ключу и сливаются за один проход.
Планировщик выбирает способ по оценкам строк — поэтому ошибка оценки часто превращается в плохое соединение.

**Термины**
- **Nested Loop / Hash Join / Merge Join** — вложенный цикл, хеш-таблица, слияние упорядоченных

#### PG-2.2.5 Статистика и ANALYZE
**Вопросы**
- [ ] Откуда планировщик знает, сколько строк вернёт условие? · `postgresql statistics planner`
- [ ] Что делает команда `ANALYZE` и кто запускает её автоматически? · `postgresql analyze autovacuum`
- [ ] Почему после массовой загрузки данных стоит запустить `ANALYZE`? · `analyze after bulk load`

**Гуглить:** `postgresql analyze statistics` · `pg_stats`

**Должен знать**
Планировщик оценивает число строк по статистике: сколько всего строк, частые значения столбцов, распределение. Её собирает `ANALYZE` (автоматически — тот же фоновый процесс уборки). После массовой загрузки или удаления статистика устаревает, оценки врут, и план может стать плохим — тогда `ANALYZE таблица` вручную.

**Термины**
- **статистика** — сведения о распределении данных для оценок планировщика
- **`ANALYZE`** — сбор статистики по таблице

### PG-2.3 Медленные запросы

#### PG-2.3.1 OFFSET на дальних страницах
**Вопросы**
- [ ] Почему `OFFSET` медленный на дальних страницах и как это исправить? · `offset pagination slow`
- [ ] Что база делает при `OFFSET 100000 LIMIT 20` (читает и выбрасывает 100 000 строк)? · `offset reads and discards rows`
- [ ] Как курсорная выдача `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20` использует индекс? · `keyset pagination index`
- [ ] Зачем в курсоре второй столбец (`id`) для одинаковых значений времени? · `keyset pagination tie breaker`

**Гуглить:** `keyset pagination postgresql` · `use the index luke no offset`

**Должен знать**
`OFFSET 100000 LIMIT 20` заставляет базу найти и выбросить 100 000 строк, чтобы отдать 20; чем дальше страница, тем медленнее. Курсор вместо этого начинает с места, где закончилась прошлая страница: `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20` — с индексом по `(created_at, id)` это мгновенно на любой глубине.
Второй столбец в курсоре разрешает ничьи: без него строки с одинаковым временем могут пропасть или повториться.

**Термины**
- **курсорная выдача** — продолжение с последней строки прошлой страницы

#### PG-2.3.2 Проблема N+1 запросов
**Вопросы**
- [ ] Что такое проблема N+1 и как её решить? · `n+1 query problem`
- [ ] Покажи пример: список из 100 заказов и для каждого отдельный запрос за покупателем. · `n+1 example orders customers`
- [ ] Почему 101 быстрый запрос медленнее одного «тяжёлого»? · `round trips latency database`
- [ ] Как исправить через соединение или через `WHERE id = ANY($1)` одним запросом? · `fix n+1 join any array`
- [ ] Как заметить N+1 в логах (много одинаковых запросов на один вызов)? · `detect n+1 queries`

**Гуглить:** `n+1 problem` · `postgresql any array parameter`

**Должен знать**
N+1 — один запрос достаёт список из N элементов, а потом для каждого делается ещё один запрос: 1 + 100 обращений к базе вместо одного-двух. Каждый поход в базу — сетевой круг и разбор запроса, поэтому сумма получается огромной, хотя каждый запрос быстрый.
Исправление — достать связанные данные сразу: соединением или вторым запросом `WHERE customer_id = ANY($1)` по всем идентификаторам и сопоставлением в коде.

**Термины**
- **N+1** *(новое)* — один запрос за списком плюс по запросу на каждый элемент

#### PG-2.3.3 Индекс для внешнего ключа
**Вопросы**
- [ ] Почему внешнему ключу обычно нужен индекс? · `index on foreign key postgresql`
- [ ] Создаёт ли PostgreSQL индекс на ссылающийся столбец сам? · `postgresql does not index foreign keys automatically`
- [ ] Почему без него удаление покупателя проверяет все заказы полным просмотром? · `on delete foreign key check seq scan`
- [ ] Как такой индекс ускоряет соединение «покупатель → заказы»? · `foreign key index join performance`

**Гуглить:** `postgresql foreign key index` · `missing index on foreign key`

**Должен знать**
PostgreSQL создаёт индекс для первичного ключа, но не для внешнего ключа в ссылающейся таблице. Без индекса по `orders.customer_id` запросы «заказы покупателя» и соединения идут полным просмотром, а при удалении покупателя база проверяет все заказы на ссылки — тоже полным просмотром, под блокировкой.
Поэтому столбцу внешнего ключа почти всегда добавляют индекс.

**Термины**
- **индекс внешнего ключа** — индекс на ссылающийся столбец, создаётся вручную

### PG-2.4 Не только Postgres

#### PG-2.4.1 OLTP и OLAP
**Вопросы**
- [ ] Чем OLTP отличается от OLAP? · `oltp vs olap`
- [ ] Какие запросы типичны для каждого (один заказ по `id` против «выручка по месяцам за 3 года»)? · `oltp olap query examples`
- [ ] Почему аналитические запросы на рабочей базе мешают пользователям? · `analytics on production database`
- [ ] Как данные попадают из рабочей базы в аналитическую — в общих словах? · `etl cdc to analytics`

**Гуглить:** `oltp vs olap` · `data warehouse basics`

**Должен знать**
OLTP — много коротких запросов к отдельным строкам: создать заказ, прочитать профиль; важны быстрые изменения и транзакции. Так работает Postgres сервиса. OLAP — редкие тяжёлые запросы, которые просматривают миллионы строк ради итогов: выручка по месяцам, воронки.
Аналитика на рабочей базе съедает её ресурсы и тормозит пользователей, поэтому данные копируют в отдельное аналитическое хранилище.

**Термины**
- **OLTP** — транзакционная нагрузка: много коротких запросов
- **OLAP** — аналитическая нагрузка: тяжёлые запросы по большим объёмам

#### PG-2.4.2 Колоночное хранение и ClickHouse
**Вопросы**
- [ ] Зачем рядом с Postgres ставят ClickHouse? · `clickhouse vs postgresql`
- [ ] Почему колоночное хранение ускоряет аналитику (читаются только нужные столбцы)? · `columnar storage explained`
- [ ] Почему столбцы хорошо сжимаются? · `columnar compression`
- [ ] Почему ClickHouse плох для частых изменений отдельных строк? · `clickhouse updates deletes`

**Гуглить:** `columnar database explained` · `what is clickhouse`

**Должен знать**
Postgres хранит строки целиком, поэтому «сумма по одному столбцу» читает все столбцы всех строк. Колоночная база хранит каждый столбец отдельно: запрос читает только нужные, а однотипные данные подряд сжимаются в разы. Аналитика по миллиардам строк становится быстрой.
ClickHouse — такая база, она стоит рядом с Postgres во многих компаниях. Но изменять и удалять отдельные строки в ней дорого — это хранилище для «дописать и считать».

**Термины**
- **колоночное хранение** — данные хранятся по столбцам, а не по строкам
- **ClickHouse** — колоночная аналитическая база

**Граница:** устройство движков ClickHouse — за кадром.

#### PG-2.4.3 Документные базы
**Вопросы**
- [ ] Когда выбирают документную базу вместо реляционной? · `document database vs relational when`
- [ ] Что такое документ (JSON-подобная запись произвольной формы)? · `document database explained`
- [ ] Чем `jsonb` в Postgres закрывает часть этих задач? · `postgresql jsonb vs mongodb`

**Гуглить:** `mongodb vs postgresql` · `postgresql jsonb`

**Должен знать**
Документная база (MongoDB) хранит записи-документы произвольной формы, похожие на JSON, и хорошо подходит, когда структура данных сильно различается от записи к записи и редко нужны связи и транзакции между ними. Для большинства бэкендов Postgres удобнее, а гибкие поля в нём закрывает `jsonb` с GIN-индексом.

**Термины**
- **документная база** — база, хранящая записи произвольной формы

**Граница:** MongoDB — названием и одной фразой, когда её выбирают.
