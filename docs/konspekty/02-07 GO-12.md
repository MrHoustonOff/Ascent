## GO-12. Интерфейсы

### GO-12.1 Интерфейс как контракт

#### GO-12.1.1 Интерфейс
**Вопросы**
- [ ] Что такое интерфейс в Go? · `go interfaces tour`
- [ ] Как объявить интерфейс `type Shape interface { Area() float64 }`? · `golang interface declaration`
- [ ] Что можно положить в переменную типа `Shape`? · `go interface variable holds any implementing type`
- [ ] Как функция, принимающая `Shape`, работает с кругом и квадратом одинаково? · `go interface function parameter example`
- [ ] Почему интерфейс описывает «что умеет», а не «что такое»? · `interface behavior not data`

**Гуглить:** `golang interfaces explained` · `go by example interfaces` · `effective go interfaces`

**Должен знать**
Интерфейс — тип, который перечисляет методы: `type Shape interface { Area() float64 }`. В переменную типа `Shape` можно положить значение любого типа, у которого есть метод `Area() float64`, — круг, квадрат, что угодно. Функция, принимающая `Shape`, вызывает `Area()` и не знает, какой именно тип пришёл.
Интерфейс описывает поведение, а не данные: «умеет считать площадь», а не «является фигурой».

**Термины**
- **интерфейс** *(новое)* — тип, заданный списком методов
- **конкретный тип** — обычный тип с данными, который может лежать в интерфейсе

#### GO-12.1.2 Неявная реализация
**Вопросы**
- [ ] Как тип реализует интерфейс и чем это отличается от `implements` в других языках? · `go implicit interface implementation`
- [ ] Почему тип из чужого пакета может подходить под твой интерфейс, хотя его автор о нём не знал? · `go interfaces decoupling packages`
- [ ] Что такое утиная типизация и как она устроена в Python? · `duck typing python`
- [ ] Чем интерфейс Go похож на `typing.Protocol` в Python и чем отличается (проверка при компиляции)? · `typing.Protocol vs go interface`
- [ ] Какой минус у неявной реализации (тип «случайно» подошёл)? · `implicit interfaces downside`

**Гуглить:** `golang interfaces implemented implicitly` · `python typing.Protocol structural typing`

**Должен знать**
В Go тип не объявляет, что реализует интерфейс: достаточно иметь все его методы с нужными сигнатурами. Это неявная реализация. Поэтому интерфейс можно объявить позже и в другом пакете, и уже существующие типы — даже чужие — ему подойдут.
Мост из Python: это утиная типизация («крякает — значит утка»), но проверенная компилятором — ближе всего к `typing.Protocol`, только проверка обязательна и происходит при сборке.

**Термины**
- **неявная реализация** *(новое)* — тип подходит под интерфейс, просто имея его методы
- **утиная типизация** — подходит всё, что умеет нужное

#### GO-12.1.3 Набор методов типа
**Вопросы**
- [ ] Что такое набор методов типа? · `go method set`
- [ ] Какие методы входят в набор методов `T`, а какие — `*T`? · `method set T vs *T`
- [ ] Почему у `*T` есть и методы с получателем-значением? · `pointer method set includes value methods`
- [ ] Как набор методов связан с тем, подходит ли тип под интерфейс? · `method set interface satisfaction`

**Гуглить:** `golang method sets` · `go spec method sets`

**Должен знать**
Набор методов — все методы, которые есть у типа с точки зрения интерфейсов. У `T` — только методы с получателем по значению. У `*T` — и с получателем по указателю, и по значению (по указателю всегда можно достать значение).
Тип подходит под интерфейс, если в его наборе методов есть все методы интерфейса.

**Термины**
- **набор методов** *(новое)* — методы, которые считаются принадлежащими типу

#### GO-12.1.4 Почему T не реализует интерфейс, если метод объявлен на *T
**Вопросы**
- [ ] Почему значение `T` не подходит под интерфейс, если метод объявлен на `*T`? · `go does not implement method has pointer receiver`
- [ ] Почему при прямом вызове `c.Inc()` это работает, а через интерфейс — нет? · `addressable vs interface value`
- [ ] Как исправить: положить в интерфейс `&c`? · `assign pointer to interface`
- [ ] Почему значение, лежащее в интерфейсе, нельзя адресовать? · `interface value not addressable`

**Гуглить:** `golang method has pointer receiver` · `go interface pointer receiver`

**Должен знать**
Метод на `*T` не входит в набор методов `T`, поэтому `var s Shape = c` не скомпилируется: «method has pointer receiver». Прямой вызов `c.Inc()` работает только потому, что компилятор берёт адрес переменной. Значение внутри интерфейса — копия, у неё нет адреса, и брать адрес за тебя Go не будет: изменения ушли бы в копию.
Исправление — класть в интерфейс указатель: `var s Shape = &c`.

**Термины**
- **ошибка «pointer receiver»** — значение `T` не реализует интерфейс с методами на `*T`

#### GO-12.1.5 Проверка реализации при компиляции
**Вопросы**
- [ ] Как на этапе компиляции проверить, что тип реализует интерфейс? · `go compile time interface check`
- [ ] Что значит строка `var _ Shape = (*Circle)(nil)`? · `var _ Interface = (*T)(nil)`
- [ ] Почему такая проверка полезна при неявной реализации? · `why assert interface implementation go`
- [ ] Что произойдёт, если кто-то переименует метод? · `interface check catches rename`

**Гуглить:** `golang verify interface compliance` · `uber go style guide interface compliance`

**Должен знать**
`var _ Shape = (*Circle)(nil)` — присваивание nil-указателя нужного типа в переменную интерфейса, которое тут же выбрасывается. Если `*Circle` перестанет подходить под `Shape` (переименовали метод, сменили сигнатуру), сборка упадёт прямо на этой строке. Во время работы программы строка ничего не стоит.
Такую проверку ставят рядом с типом, который обязан реализовывать интерфейс.

**Термины**
- **проверка реализации** — строка, которая падает при компиляции, если тип перестал подходить

### GO-12.2 Интерфейс изнутри

#### GO-12.2.1 Что хранит значение интерфейса
**Вопросы**
- [ ] Из каких двух частей состоит значение интерфейса? · `go interface value type and data`
- [ ] Сколько весит переменная интерфейса? · `go interface size 16 bytes`
- [ ] Что хранится во второй части — само значение или указатель на него? · `interface data pointer copy`
- [ ] Почему значение, положенное в интерфейс, — это копия? · `go interface stores copy of value`

**Гуглить:** `go interface internals` · `russ cox go interfaces`

**Должен знать**
Значение интерфейса — пара: какой конкретный тип в нём лежит и указатель на данные. 16 байт на 64-битной системе. Когда значение кладут в интерфейс, Go копирует его (часто в кучу), и интерфейс указывает на эту копию; если положить указатель, копируется сам указатель.
Из этой пары «тип + данные» следуют все остальные свойства интерфейсов.

**Термины**
- **динамический тип** — конкретный тип, который сейчас лежит в интерфейсе
- **динамическое значение** — данные, на которые указывает интерфейс

#### GO-12.2.2 iface и таблица методов
**Вопросы**
- [ ] Чем iface отличается от eface? · `go iface vs eface`
- [ ] Что лежит в таблице методов (itab): тип интерфейса, конкретный тип, адреса методов? · `go itab structure`
- [ ] Как вызов `s.Area()` через интерфейс находит нужную функцию? · `interface method dispatch itab`
- [ ] Почему таблица строится один раз для пары «интерфейс + тип» и кэшируется? · `itab cache`

**Гуглить:** `go itab explained` · `go interface method dispatch`

**Должен знать**
Интерфейс с методами устроен как iface: первая часть — указатель на таблицу методов (itab), вторая — на данные. В таблице — описание интерфейса, конкретного типа и адреса функций-методов этого типа в порядке методов интерфейса. Вызов `s.Area()` — взять адрес из таблицы и вызвать его с данными.
Таблица для пары «интерфейс + конкретный тип» строится один раз и переиспользуется. Пустой интерфейс устроен проще — это eface.

**Термины**
- **iface** *(новое)* — устройство интерфейса с методами: таблица методов + данные
- **eface** *(новое)* — устройство пустого интерфейса: тип + данные
- **itab** — таблица методов конкретного типа для конкретного интерфейса

**Граница:** поля внутренних структур по именам — не нужны.

#### GO-12.2.3 Пустой интерфейс и any
**Вопросы**
- [ ] Что такое пустой интерфейс `interface{}` и почему под него подходит любой тип? · `go empty interface`
- [ ] Что такое `any` и чем отличается от `interface{}`? · `go any alias interface{}`
- [ ] Где `any` используется в стандартной библиотеке (`fmt.Println`, разбор JSON)? · `fmt.Println any parameters`
- [ ] Почему `any` в своём коде — признак того, что типы стоит продумать лучше? · `avoid interface{} any overuse`
- [ ] Можно ли сложить два значения типа `any`? · `cannot add any values`

**Гуглить:** `golang empty interface any` · `go 1.18 any`

**Должен знать**
Пустой интерфейс `interface{}` не требует ни одного метода, поэтому под него подходит любое значение. С Go 1.18 у него есть короткое имя `any` — псевдоним, то же самое. Через него `fmt.Println` принимает что угодно, а JSON разбирается в `map[string]any`.
Но с `any` нельзя ничего сделать, не выяснив конкретный тип: даже сложить два `any` нельзя. В своём коде `any` — повод подумать о типах лучше.

**Термины**
- **any** *(новое)* — псевдоним пустого интерфейса, принимает любое значение

#### GO-12.2.4 eface: устройство пустого интерфейса
**Вопросы**
- [ ] Чем eface проще iface? · `go eface structure`
- [ ] Что лежит в первой части eface (описание типа) и зачем оно? · `eface _type field`
- [ ] Почему значение в `any` почти всегда уходит в кучу? · `any boxing allocation`
- [ ] Какие маленькие значения Go кладёт в интерфейс без выделения памяти? · `go interface no allocation small values`

**Гуглить:** `go eface internals` · `go interface allocation`

**Должен знать**
eface — две части: указатель на описание конкретного типа и указатель на данные. Таблицы методов нет — у пустого интерфейса нет методов. Описание типа нужно, чтобы потом узнать, что лежит внутри, и сравнивать значения.
Данные должны лежать где-то по адресу, поэтому значение, положенное в `any`, обычно копируется в кучу. Для некоторых маленьких значений Go обходится без выделения памяти.

**Термины**
- **описание типа** — информация рантайма о типе: размер, имя, как сравнивать

#### GO-12.2.5 Нулевое значение интерфейса
**Вопросы**
- [ ] Какое нулевое значение у интерфейса? · `go nil interface`
- [ ] Когда интерфейс равен nil (обе части пустые)? · `interface nil when type and value nil`
- [ ] Что будет при вызове метода у nil-интерфейса? · `call method on nil interface panic`
- [ ] Чем nil-интерфейс отличается от интерфейса, внутри которого nil-указатель? · `nil interface vs interface holding nil pointer`

**Гуглить:** `golang nil interface value` · `go faq nil error`

**Должен знать**
Нулевое значение интерфейса — nil: обе части пустые, ни типа, ни данных. `s == nil` истинно только в этом случае. Вызов метода у nil-интерфейса — паника: неизвестно, чей метод вызывать.
Если же в интерфейс положили nil-указатель, первая часть уже не пуста (тип известен) — и такой интерфейс nil не равен. Об этом следующий урок.

**Термины**
- **nil-интерфейс** — интерфейс без типа и без данных

#### GO-12.2.6 Интерфейс с nil-указателем внутри
**Вопросы**
- [ ] Почему интерфейс, в который положили nil-указатель, не равен nil? · `go interface holding nil pointer not nil`
- [ ] Что выведет `var p *Circle; var s Shape = p; fmt.Println(s == nil)`? · `nil pointer in interface == nil false`
- [ ] Почему функция, возвращающая `*MyErr(nil)` через интерфейс, вернёт «не nil»? · `return nil pointer as interface bug`
- [ ] Как писать функции, чтобы не попасть в эту ловушку (возвращать явный nil)? · `return nil explicitly interface`
- [ ] Можно ли вызвать метод у такого интерфейса? · `call method interface nil pointer receiver`

**Гуглить:** `go faq why is my nil error value not equal to nil` · `nil pointer interface gotcha`

**Должен знать**
`var p *Circle; var s Shape = p` — в `s` лежит тип `*Circle` и пустой указатель. Тип известен, поэтому `s != nil`, хотя внутри nil. Классический баг: функция объявлена с результатом-интерфейсом, внутри возвращает переменную-указатель, равную nil, — снаружи проверка `!= nil` срабатывает.
Правило: если «ничего нет», возвращай буквальный `nil`, а не nil-указатель конкретного типа. Метод у такого интерфейса вызвать можно — он получит nil-получатель.

**Термины**
- **«не nil, хотя внутри nil»** — интерфейс с типом, но с пустым указателем

#### GO-12.2.7 Цена вызова через интерфейс
**Вопросы**
- [ ] Сколько стоит вызов метода через интерфейс по сравнению с прямым вызовом? · `go interface method call cost`
- [ ] Почему компилятор не может встроить тело метода в место вызова через интерфейс? · `go inlining interface calls`
- [ ] Когда цена интерфейса реально важна, а когда нет? · `interface overhead matters when`
- [ ] Что такое девиртуализация — одной фразой? · `go devirtualization pgo`

**Гуглить:** `go interface call overhead` · `go pgo devirtualization`

**Должен знать**
Вызов через интерфейс — косвенный: сначала прочитать адрес из таблицы методов, потом перейти по нему. Это несколько наносекунд, плюс компилятор не может подставить тело метода прямо в место вызова и сделать другие оптимизации. Ещё одна цена — значение, положенное в интерфейс, часто уезжает в кучу.
В обычном коде это незаметно; считать стоит только в самых горячих циклах. Иногда компилятор сам заменяет такой вызов прямым, если знает конкретный тип.

**Термины**
- **косвенный вызов** — вызов функции по адресу из таблицы

### GO-12.3 Достать тип обратно

#### GO-12.3.1 Утверждение типа
**Вопросы**
- [ ] Как достать конкретный тип из интерфейса: `c := s.(*Circle)`? · `go type assertion`
- [ ] Что будет, если угадал неверно? · `type assertion panic wrong type`
- [ ] Можно ли через утверждение типа проверить, умеет ли значение ещё один интерфейс? · `type assertion to another interface`
- [ ] Чем утверждение типа отличается от преобразования типа `T(x)`? · `type assertion vs type conversion`

**Гуглить:** `golang type assertion` · `go tour type assertions`

**Должен знать**
`c := s.(*Circle)` — утверждение типа: «в `s` лежит `*Circle`, дай его». Если там другой тип, будет паника. Вместо конкретного типа можно указать другой интерфейс: `s.(fmt.Stringer)` проверяет, есть ли у значения нужные методы.
Это не преобразование: `T(x)` меняет тип значения при компиляции, а утверждение проверяет во время работы, что уже лежит в интерфейсе.

**Термины**
- **утверждение типа** *(новое)* — `x.(T)`: достать из интерфейса значение типа `T`

#### GO-12.3.2 Утверждение типа с проверкой «comma ok»
**Вопросы**
- [ ] Как безопасно проверить тип без паники? · `go type assertion comma ok`
- [ ] Что лежит в `c`, если `ok == false`? · `type assertion ok false zero value`
- [ ] Как проверить, что значение умеет дополнительный метод, и использовать его, если умеет? · `optional interface check go`

**Гуглить:** `golang comma ok type assertion` · `go optional interfaces pattern`

**Должен знать**
`c, ok := s.(*Circle)` не паникует: если тип не тот, `ok` будет `false`, а `c` — нулевым значением. Это та же форма «comma ok», что у map.
Частый приём — проверка необязательной способности: `if st, ok := v.(fmt.Stringer); ok { … }` — использовать метод, если он есть.

**Термины**
- **утверждение с проверкой** — `v, ok := x.(T)`, без паники

#### GO-12.3.3 type switch
**Вопросы**
- [ ] Когда удобнее type switch? · `go type switch`
- [ ] Как записать `switch v := x.(type) { case int: …; case string: … }`? · `golang type switch syntax`
- [ ] Какой тип у `v` в каждой ветке и в `default`? · `type switch variable type per case`
- [ ] Можно ли в одном `case` перечислить два типа и какой тогда тип у `v`? · `type switch multiple types case`
- [ ] Как проверить `nil` в type switch? · `type switch case nil`

**Гуглить:** `golang type switch` · `go tour type switches`

**Должен знать**
`switch v := x.(type) { … }` проверяет тип значения в интерфейсе сразу против нескольких вариантов. В каждой ветке `v` имеет тип этой ветки, а в `default` и в ветках с несколькими типами — тип исходного интерфейса. `case nil` ловит nil-интерфейс.
Удобно, когда нужно по-разному обработать несколько возможных типов — например, значения из разобранного JSON.

**Термины**
- **type switch** *(новое)* — `switch` по типу значения в интерфейсе

#### GO-12.3.4 Сравнение интерфейсов
**Вопросы**
- [ ] Когда два интерфейса равны через `==`? · `go compare interface values`
- [ ] Равны ли интерфейсы с одинаковым значением, но разными типами (`int(1)` и `int64(1)`)? · `interface equality different dynamic types`
- [ ] Можно ли сравнить интерфейс с конкретным значением? · `compare interface with concrete value`
- [ ] Можно ли использовать интерфейс ключом map? · `interface as map key`

**Гуглить:** `golang interface comparison` · `go spec interface equality`

**Должен знать**
Интерфейсы равны, если у них одинаковый динамический тип и равные значения (или оба nil). `any(1) == any(int64(1))` — `false`: типы разные. Интерфейс можно сравнить и с конкретным значением — оно будет «завёрнуто» в интерфейс.
Поэтому интерфейс может быть ключом map — с одной оговоркой из следующего урока.

**Термины**
- **равенство интерфейсов** — одинаковый динамический тип и равные значения

#### GO-12.3.5 Паника при сравнении несравнимых типов в интерфейсе
**Вопросы**
- [ ] Когда сравнение двух интерфейсов вызывает панику? · `runtime error comparing uncomparable type`
- [ ] Почему `any([]int{1}) == any([]int{1})` компилируется, но паникует? · `compare slices in interface panic`
- [ ] Что будет, если положить в `map[any]int` ключ-слайс? · `map interface key slice panic`
- [ ] Почему компилятор не может поймать это заранее? · `interface comparison runtime check`

**Гуглить:** `go comparing uncomparable type panic` · `hash of unhashable type go`

**Должен знать**
Компилятор разрешает сравнивать любые интерфейсы, потому что не знает, что в них будет. Если во время работы оба содержат один и тот же несравнимый тип (слайс, map, функцию), сравнение паникует: `comparing uncomparable type []int`. То же при использовании такого значения ключом в `map[any]…`.
Разные типы внутри сравниваются без паники — просто не равны.

**Термины**
- **паника сравнения** — сравнение интерфейсов с несравнимым содержимым во время работы

### GO-12.4 Интерфейсы в дизайне

#### GO-12.4.1 fmt.Stringer
**Вопросы**
- [ ] Что такое `fmt.Stringer` и какой у него метод? · `golang fmt.Stringer`
- [ ] Почему `fmt.Println` печатает `time.Duration` как `1.5s`? · `fmt uses String method`
- [ ] Напиши `String()` для своего перечисления на `iota`. · `go enum String method iota`
- [ ] Почему `String()` с получателем-указателем не сработает при печати значения? · `String method pointer receiver not called`
- [ ] Что будет, если внутри `String()` вызвать `fmt.Sprintf("%v", x)` для того же значения? · `String method infinite recursion`

**Гуглить:** `go fmt.Stringer` · `go stringer tool`

**Должен знать**
`fmt.Stringer` — интерфейс с одним методом `String() string`. `fmt` проверяет, есть ли он у значения, и если есть, печатает его результат. Поэтому `time.Duration` выводится как `1.5s`: у неё есть `String()`.
Удобно для своих перечислений и типов. Две ловушки: метод на `*T` не вызовется при печати значения `T`; вызов `fmt.Sprintf("%v", x)` для того же `x` внутри `String()` — бесконечная рекурсия.

**Термины**
- **`fmt.Stringer`** — интерфейс «умею превращаться в строку»

#### GO-12.4.2 Встраивание интерфейсов
**Вопросы**
- [ ] Как собрать интерфейс из двух других? · `go embed interfaces`
- [ ] Что будет, если в двух встроенных интерфейсах один и тот же метод? · `go overlapping interface methods`
- [ ] Можно ли встроить интерфейс в структуру и что это даст? · `embed interface in struct`
- [ ] Как такой приём используют, чтобы реализовать только часть методов (например, в тестах)? · `embed interface partial implementation test`

**Гуглить:** `golang interface embedding` · `go embedding interface in struct`

**Должен знать**
Интерфейс можно собрать из других встраиванием: `type ReadCloser interface { Reader; Closer }` — набор методов объединяется. Одинаковые методы из разных частей допустимы, если сигнатуры совпадают.
Интерфейс можно встроить и в структуру: она «получит» все его методы, а вызов нереализованного запаникует. Так в тестах делают подменный тип, реализуя только нужный метод.

**Термины**
- **встраивание интерфейсов** — интерфейс, собранный из других интерфейсов

#### GO-12.4.5 «Принимай интерфейсы, возвращай структуры»
**Вопросы**
- [ ] Что значит «принимай интерфейсы, возвращай структуры»? · `accept interfaces return structs`
- [ ] Почему конструктор лучше возвращать конкретный тип, а не интерфейс? · `go constructor return concrete type`
- [ ] Когда возвращать интерфейс всё же нормально? · `when to return interface go`
- [ ] Как это связано с ловушкой «nil-указатель внутри интерфейса»? · `return concrete type avoid nil interface trap`

**Гуглить:** `golang accept interfaces return structs` · `jack lindamood accept interfaces`

**Должен знать**
Функция принимает интерфейс — так ей подойдёт любое значение с нужными методами, и её легко тестировать. А возвращает конкретный тип — так вызывающий получает все методы и поля, а сам решит, через какой интерфейс с ним работать.
Возвращать интерфейс уместно, когда реализаций несколько и выбор скрыт внутри (и для ошибок). Бонус правила: возвращая конкретный тип, не попадёшь в ловушку «не nil, хотя внутри nil».

**Термины**
- **«принимай интерфейсы, возвращай структуры»** — правило дизайна функций в Go

#### GO-12.4.6 ООП в Go целиком: инкапсуляция, композиция, полиморфизм
**Вопросы**
- [ ] Как в Go устроены инкапсуляция, композиция и полиморфизм без классов? · `oop in go`
- [ ] Что такое полиморфизм и как интерфейс его даёт? · `polymorphism go interfaces`
- [ ] Чем отвечать на вопрос «есть ли в Go ООП»? · `is go object oriented faq`
- [ ] Чего из ООП в Go нет и почему это сделано нарочно (наследование, перегрузка)? · `go no inheritance overloading why`
- [ ] Как бы ты переписал на Go иерархию классов из Python? · `python class hierarchy to go`

**Гуглить:** `go faq is go object oriented` · `golang oop explained` · `polymorphism explained`

**Должен знать**
ООП в Go собирается из трёх частей. Инкапсуляция — экспорт по заглавной букве на уровне пакета. Композиция — встраивание одних типов в другие вместо наследования. Полиморфизм — интерфейсы: один код работает с разными типами, у которых есть нужные методы. Плюс методы у любого своего типа.
Классов, наследования и перегрузки функций в Go нет — нарочно: так код проще читать и связи между частями слабее. Мост из Python: иерархия классов в Go превращается в маленькие интерфейсы и структуры со встраиванием.

**Термины**
- **ООП** *(новое)* — объектно-ориентированное программирование
- **полиморфизм** *(новое)* — один код работает с разными типами через общий интерфейс
