### SQL-1.1 Зачем база данных

#### SQL-1.1.1 Зачем база данных, если есть файлы
**Вопросы**
- [ ] Что пойдёт не так, если тысяча пользователей одновременно дописывает заказы в один файл? · `problems storing data in files concurrency`
- [ ] Как быстро найти один заказ среди миллиона строк в файле? · `file vs database search performance`
- [ ] Что будет с данными, если программа упадёт посреди записи в файл? · `partial write file corruption crash`
- [ ] Как в файле гарантировать, что у заказа есть существующий покупатель? · `data integrity database vs file`
- [ ] Кто и как будет читать файл, если программ, которым нужны данные, несколько? · `shared data multiple applications database`

**Гуглить:** `why use a database instead of files` · `зачем нужна база данных`

**Должен знать**
Файл хорош, пока с ним работает одна программа и данных мало. Когда данных много и их одновременно читают и меняют многие пользователи, появляются задачи: не потерять запись при одновременном изменении, не оставить полузаписанные данные при сбое, быстро находить нужное, проверять правила (например, что у заказа есть покупатель).
База данных решает эти задачи один раз и для всех — поэтому почти любой бэкенд хранит данные в ней.

**Термины**
- **база данных** — организованное хранилище данных с правилами доступа и проверки
- **целостность данных** — данные не противоречат правилам и друг другу

#### SQL-1.1.2 СУБД
**Вопросы**
- [ ] Чем СУБД отличается от самой базы данных? · `dbms vs database difference`
- [ ] Почему СУБД — это отдельная программа, а твой код общается с ней по сети? · `database server separate process`

**Гуглить:** `what is dbms` · `что такое субд` · `sql language overview`

**Должен знать**

Запросы пишут на SQL — языке, где ты описываешь, *что* хочешь получить, а *как* это достать, решает СУБД.

**Термины**
- **СУБД** *(новое)* — программа, которая управляет базами данных
- **SQL** — язык запросов к базам, где данные лежат в таблицах

#### SQL-1.1.3 Виды баз данных
**Вопросы**
- [ ] Что такое реляционная база и почему данные в ней лежат в таблицах? · `relational database explained`
- [ ] Какие виды баз данных ты знаешь, кроме реляционных (ключ-значение, документные, колоночные, графовые)? · `types of databases nosql`
- [ ] Для чего подходит хранилище «ключ-значение»? · `key value store use cases`
- [ ] Чем документная база вроде MongoDB отличается от таблиц? · `document database vs relational`
- [ ] Почему для большинства бэкендов по умолчанию берут реляционную базу? · `why relational database default choice`

**Гуглить:** `types of databases` · `sql vs nosql` · `виды баз данных`

**Должен знать**
Реляционная база хранит данные в таблицах со строгими столбцами, а связи между таблицами задаются значениями. Это самый распространённый вид, например MySQL. Есть и другие: «ключ-значение» — быстро достать значение по ключу; документные (MongoDB) — хранить записи свободной формы; колоночные — для аналитики по огромным объёмам.
По умолчанию на бэкенде выбирают реляционную базу: она надёжна, строга и умеет почти всё; другие виды берут под конкретную задачу.

**Термины**
- **реляционная база** *(новое)* — база, где данные лежат в таблицах, а связи задаются значениями
- **ключ-значение** — хранилище, где по ключу лежит значение
- **NoSQL** — общее имя нереляционных баз

**Граница:** устройство нереляционных баз — не нужно.

#### SQL-1.2.2 Типы столбцов
**Вопросы**
- [ ] Зачем столбцу тип? · `why column types matter database`
- [ ] Какие типы ты использовал бы для имени, цены и даты заказа? · `postgresql data types text numeric timestamptz`
- [ ] Чем `integer` отличается от `bigint` и как это связано с `int32`/`int64`? · `postgresql integer bigint range`
- [ ] Почему для денег берут `numeric` или целые копейки, а не `real`/`double precision`? · `postgresql money numeric vs float`
- [ ] Чем `text` отличается от `varchar(n)` в PostgreSQL? · `postgresql text vs varchar`
- [ ] Чем `timestamp` отличается от `timestamptz` и что выбирать? · `postgresql timestamp vs timestamptz`
- [ ] Какие ещё типы часто встречаются (`boolean`, `uuid`, `jsonb`)? · `postgresql common data types`

**Гуглить:** `postgresql data types` · `postgresql numeric money` · `don't do this postgresql wiki`

**Должен знать**
Тип столбца задаёт, какие значения в нём допустимы, и база проверяет это при каждой записи. Основное: `integer` (4 байта) и `bigint` (8 байт) для целых, `numeric` для точных дробных (деньги), `text` для строк, `boolean`, `timestamptz` для момента времени и `uuid` для идентификаторов.
Правила те же, что в ФУНД-2: у целых есть диапазон, `real`/`double precision` — числа с плавающей точкой, для денег не годятся. Для времени почти всегда бери `timestamptz` — он хранит момент, а не «часы на стене».

**Термины**
- **тип столбца** — допустимые значения столбца
- **`numeric`** — точное десятичное число
- **`timestamptz`** — момент времени с учётом часового пояса

**Граница:** все типы PostgreSQL — не нужны; `jsonb` — знать, что есть.

#### SQL-1.2.3 CREATE TABLE
**Вопросы**
- [ ] Как создать таблицу `products` с названием, ценой и датой создания? · `postgresql create table example`
- [ ] Что делает `NOT NULL` у столбца? · `not null constraint`
- [ ] Как задать значение по умолчанию (`DEFAULT now()`)? · `postgresql default value column`

- **`CREATE TABLE`** — команда создания таблицы

#### SQL-1.2.4 Первичный ключ
**Вопросы**
- [ ] Что такое первичный ключ и почему он должен быть у каждой таблицы? · `primary key explained`
- [ ] Какие два правила база проверяет для первичного ключа (уникальный, не пустой)? · `primary key unique not null`
- [ ] Почему имя или email — плохой первичный ключ? · `natural key vs surrogate key`
- [ ] Может ли первичный ключ состоять из нескольких столбцов? · `composite primary key`
- [ ] Как объявить первичный ключ в `CREATE TABLE`? · `postgresql primary key syntax`

**Гуглить:** `primary key database` · `surrogate vs natural key` · `первичный ключ что это`

**Должен знать**
Первичный ключ — столбец (или набор столбцов), который однозначно определяет строку: значения уникальны и не бывают пустыми, база проверяет это сама. По нему строку находят, обновляют и на неё ссылаются из других таблиц.
Обычно ключ — искусственный `id`, не несущий смысла: имя может повториться, email — смениться, а `id` остаётся навсегда.

**Термины**
- **первичный ключ** *(новое)* — уникальный непустой идентификатор строки
- **суррогатный ключ** — искусственный `id` без смысла в предметной области

#### SQL-1.2.5 Автоматически генерируемый ключ: IDENTITY
**Вопросы**
- [ ] Как сделать, чтобы `id` новой строки база выдавала сама? · `postgresql identity column`
- [ ] Чем `GENERATED ALWAYS AS IDENTITY` отличается от `GENERATED BY DEFAULT`? · `generated always vs by default identity`
- [ ] Что такое `serial` и почему сейчас советуют `IDENTITY`? · `serial vs identity postgresql`
- [ ] Почему в `id` бывают «дырки» (1, 2, 5) и почему это нормально? · `postgresql identity gaps why`
- [ ] Как получить `id` только что вставленной строки (`RETURNING id`)? · `postgresql insert returning id`

**Гуглить:** `postgresql identity column` · `serial vs identity` · `insert returning`

**Должен знать**
`id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY` — база сама выдаёт следующий номер при каждой вставке. `ALWAYS` запрещает задавать `id` вручную, `BY DEFAULT` разрешает. Старый способ — `serial`, новый и рекомендуемый — `IDENTITY`.
Номера не обязаны идти без пропусков: неудачная вставка всё равно «тратит» номер. Узнать выданный `id` помогает `RETURNING id` в конце вставки.

**Термины**
- **`IDENTITY`** — столбец, значения которого база генерирует сама
- **`RETURNING`** — вернуть значения из вставленной или изменённой строки

**Граница:** `uuid` вместо числового ключа — знать, что так тоже делают.

#### SQL-1.3.3 WHERE и логические условия
**Вопросы**
- [ ] Как выбрать товары дороже 1000? · `sql where greater than`
- [ ] Какие операции сравнения есть в SQL (`=`, `<>`, `<`, `>=`)? Почему равенство — одинарное `=`? · `sql comparison operators`
- [ ] Как работают `AND`, `OR`, `NOT`? · `sql and or not`
- [ ] Что вернёт `WHERE a = 1 OR b = 2 AND c = 3` без скобок? · `sql and or precedence`
- [ ] Почему лучше всегда ставить скобки, когда смешиваешь `AND` и `OR`? · `sql parentheses and or`

**Гуглить:** `sql where clause` · `sql operator precedence and or`

**Должен знать**
`WHERE` оставляет только строки, для которых условие истинно: `WHERE price > 1000 AND in_stock`. Равенство — `=`, неравенство — `<>` или `!=`. Условия объединяют `AND`, `OR`, `NOT`.
`AND` связывает сильнее `OR`, поэтому `a OR b AND c` значит `a OR (b AND c)`. Смешиваешь — ставь скобки, иначе легко получить совсем не те строки.

**Термины**
- **`WHERE`** — условие отбора строк

#### SQL-1.3.4 IN, BETWEEN и LIKE
**Вопросы**
- [ ] Что делают `IN`, `BETWEEN` и `LIKE`? · `sql in between like`
- [ ] Включает ли `BETWEEN 10 AND 20` сами границы? · `sql between inclusive`
- [ ] Чем `%` отличается от `_` в `LIKE`? · `sql like wildcard % _`
- [ ] Как найти без учёта регистра (`ILIKE` в PostgreSQL)? · `postgresql ilike`
- [ ] Почему `LIKE '%чай%'` на большой таблице медленный? · `like leading wildcard slow`

**Гуглить:** `sql in operator` · `sql between` · `postgresql like ilike`

**Должен знать**
`status IN ('new', 'paid')` — значение из списка, короче цепочки `OR`. `price BETWEEN 10 AND 20` — диапазон, границы включены. `name LIKE 'Ч%'` — поиск по шаблону: `%` — любое количество символов, `_` — ровно один. В PostgreSQL `ILIKE` ищет без учёта регистра.
Шаблон, начинающийся с `%`, заставляет базу просмотреть все строки подряд — на больших таблицах это медленно.

**Термины**

#### SQL-1.3.5 ORDER BY, LIMIT и OFFSET
**Вопросы**
- [ ] Напиши запрос: все товары дороже 1000, отсортированные по цене по убыванию. · `sql order by desc`
- [ ] Как выбрать вторую страницу по 20 строк? · `sql limit offset pagination`
- [ ] Как отсортировать по двум столбцам? · `sql order by multiple columns`

- **`LIMIT` / `OFFSET`** — сколько строк взять и сколько пропустить
- **постраничный вывод** — выдача результата частями (страницами)

#### SQL-1.4.2 Трёхзначная логика
**Вопросы**
- [ ] Что вернёт `NULL = NULL` и почему? · `null = null returns null`
- [ ] Какие три значения бывают у условия в SQL? · `sql three valued logic`
- [ ] Что вернут `NULL AND false`, `NULL OR true`, `NOT NULL`? · `three valued logic truth table`
- [ ] Почему `WHERE price <> 100` не возвращает строки, где `price` — `NULL`? · `where not equal excludes null`
- [ ] Почему `NOT IN` со списком, где есть `NULL`, может вернуть ноль строк? · `not in null trap`

**Гуглить:** `sql three-valued logic` · `null comparison sql` · `not in with null`

**Должен знать**
В SQL у условия три значения: истина, ложь и «неизвестно» (`NULL`). Сравнение с `NULL` даёт «неизвестно» — даже `NULL = NULL`, ведь два неизвестных значения нельзя признать равными. `WHERE` оставляет только строки с истиной, поэтому строки с `NULL` в сравниваемом столбце молча пропадают.
`NULL AND false` — ложь, `NULL OR true` — истина: если ответ уже ясен, неизвестность не мешает. Ловушка собесов — `NOT IN` со списком, где есть `NULL`: условие никогда не становится истинным.

**Термины**
- **трёхзначная логика** *(новое)* — логика с тремя значениями: истина, ложь, неизвестно

#### SQL-1.4.3 IS NULL и COALESCE
**Вопросы**
- [ ] Как правильно найти строки, где столбец пустой? · `sql is null`
- [ ] Почему `WHERE x = NULL` ничего не находит? · `where = null vs is null`
- [ ] Как подставить значение вместо `NULL` (`COALESCE`)? · `postgresql coalesce`
- [ ] Как сравнить два значения, считая два `NULL` равными (`IS NOT DISTINCT FROM`)? · `is not distinct from`
- [ ] Что делает `NULLIF` и как с его помощью избежать деления на ноль? · `nullif division by zero`

**Гуглить:** `sql is null` · `coalesce function` · `nullif postgresql`

**Должен знать**
Проверять на `NULL` нужно только через `IS NULL` / `IS NOT NULL`; `= NULL` всегда даёт «неизвестно» и ничего не находит. `COALESCE(a, b, 0)` возвращает первое значение, которое не `NULL`, — так подставляют значение по умолчанию.
`IS NOT DISTINCT FROM` сравнивает, считая два `NULL` равными. `NULLIF(x, 0)` превращает 0 в `NULL` — деление на него даст `NULL`, а не ошибку.

**Термины**
- **`IS NULL`** — проверка, что значение отсутствует
- **`COALESCE`** — первое значение из списка, которое не `NULL`
