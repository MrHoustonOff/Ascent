## GO-23. HTTP-клиент

### GO-23.1 Клиент и его ловушки

#### GO-23.1.1 http.Client
**Вопросы**
- [ ] Что не так с `http.Get` и клиентом по умолчанию? · `go http.Get default client problems`
- [ ] Как создать свой `http.Client` и отправить запрос через `client.Do(req)`? · `go http.Client Do example`
- [ ] Почему клиент создают один раз и переиспользуют, а не на каждый запрос? · `reuse http.Client`
- [ ] Безопасно ли пользоваться одним `http.Client` из многих горутин? · `http.Client concurrent safe`
- [ ] Считается ли ответ `500` ошибкой для `client.Do`? · `go http client error on 500`

**Гуглить:** `go http client tutorial` · `don't use default http client`

**Должен знать**
`http.Get(url)` пользуется общим `http.DefaultClient` без таймаута — для сервиса это плохо. Свой клиент создают один раз (`client := &http.Client{Timeout: 5 * time.Second}`) и пользуются им из всех горутин: он потокобезопасен и держит внутри набор открытых соединений.
`client.Do(req)` возвращает ошибку только при сбое сети или протокола. Ответ `500` — это не ошибка `Do`: код нужно проверять самому в `resp.StatusCode`.

**Термины**
- **`http.Client`** — HTTP-клиент со своими соединениями и настройками

#### GO-23.1.2 Таймаут http.Client по умолчанию
**Вопросы**
- [ ] Какой таймаут у клиента по умолчанию? · `go default http client no timeout`
- [ ] Что случится с сервисом, если другой сервис перестал отвечать, а таймаута нет? · `no timeout goroutine pile up`
- [ ] Что охватывает `Client.Timeout`: соединение, запрос, чтение тела? · `http.Client Timeout covers body`
- [ ] Как выбрать значение таймаута? · `choose http client timeout value`

**Гуглить:** `go http client timeout` · `don't use go default http client`

**Должен знать**
У `http.DefaultClient` таймаута нет вообще: если другой сервис завис, запрос будет ждать вечно, а вместе с ним — горутина обработчика и всё, что она держит. Под нагрузкой такие горутины копятся, и сервис падает следом.
`Client.Timeout` ограничивает весь запрос целиком — от соединения до чтения тела. Значение выбирают по ожидаемому времени ответа с запасом, а не «минуту на всякий случай».

**Термины**
- **`Client.Timeout`** — предел времени на весь запрос, включая чтение тела

#### GO-23.1.3 Закрыть тело ответа
**Вопросы**
- [ ] Почему тело ответа нужно закрывать, даже если оно не нужно? · `go close response body why`
- [ ] Где ставить `defer resp.Body.Close()` — после проверки ошибки? · `defer resp.Body.Close after err check`
- [ ] Почему для повторного использования соединения тело нужно дочитать до конца? · `drain response body reuse connection`
- [ ] К какой ошибке приводят незакрытые тела (`too many open files`, утечка горутин)? · `unclosed response body leak`

**Гуглить:** `go resp.Body.Close` · `go http client leak`

**Должен знать**
Тело ответа — поток из открытого соединения. Пока его не закрыли, соединение и связанные с ним горутины не освобождаются; незакрытые тела копятся до «too many open files». Поэтому сразу после проверки ошибки: `if err != nil { return err }; defer resp.Body.Close()`.
Чтобы соединение вернулось в пул для следующего запроса, тело дочитывают до конца: если оно не нужно — `io.Copy(io.Discard, resp.Body)`.

**Термины**
- **закрытие тела ответа** — обязательное освобождение соединения после ответа

#### GO-23.1.4 Переиспользование соединений
**Вопросы**
- [ ] Как клиент переиспользует соединения? · `go http transport connection pool`
- [ ] Что такое `http.Transport` и что он хранит? · `http.Transport explained`
- [ ] Что значат `MaxIdleConnsPerHost` (по умолчанию 2!) и `IdleConnTimeout`? · `MaxIdleConnsPerHost default 2`
- [ ] Почему при множестве запросов к одному сервису стоит поднять `MaxIdleConnsPerHost`? · `increase MaxIdleConnsPerHost`
- [ ] Почему новый клиент на каждый запрос убивает переиспользование? · `new http client per request bad`

**Гуглить:** `go http transport tuning` · `MaxIdleConnsPerHost`

**Должен знать**
Внутри клиента — `http.Transport`: пул открытых соединений по хостам. После ответа (если тело дочитано и закрыто) соединение возвращается в пул, и следующий запрос к тому же хосту идёт без нового TCP- и TLS-рукопожатия.
По умолчанию в пуле держится всего 2 простаивающих соединения на хост: при сотнях запросов в секунду к одному сервису лишние закрываются и открываются заново. Тогда поднимают `MaxIdleConnsPerHost`. Новый клиент на каждый запрос — новый пул и никакого переиспользования.

**Термины**
- **`http.Transport`** — часть клиента, управляющая соединениями
- **простаивающее соединение** — открытое соединение, ждущее следующего запроса

#### GO-23.1.5 Запрос с context
**Вопросы**
- [ ] Как ограничить время всего запроса к другому сервису? · `go http request with context timeout`
- [ ] Как создать запрос с контекстом (`http.NewRequestWithContext`)? · `http.NewRequestWithContext`
- [ ] Почему в обработчике передают `r.Context()` в исходящий запрос? · `propagate request context to outgoing http`
- [ ] Чем таймаут через context отличается от `Client.Timeout`? · `context timeout vs client timeout`

**Гуглить:** `go http request context` · `NewRequestWithContext`

**Должен знать**
`req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)` привязывает запрос к контексту: при отмене или истечении срока запрос прерывается. В обработчике передают контекст входящего запроса — тогда если клиент ушёл, исходящие запросы тоже отменятся.
`Client.Timeout` — общий предел клиента на любой запрос, контекст — предел конкретной операции, в том числе общий срок на несколько вызовов подряд. Используют оба.

**Термины**
- **запрос с контекстом** — исходящий запрос, отменяемый вместе с контекстом

### GO-23.2 Повторы

#### GO-23.2.1 Какие запросы можно повторять
**Вопросы**
- [ ] Какие запросы можно безопасно повторять, а какие нет? · `which http requests safe to retry`
- [ ] Какие ответы стоит повторять (`502`, `503`, `504`, `429`, сетевые ошибки), а какие нет (`400`, `404`)? · `retryable status codes`
- [ ] Почему `POST` без ключа идемпотентности повторять опасно? · `retry post duplicate`
- [ ] Что значит заголовок `Retry-After`? · `retry-after header`

**Гуглить:** `http retry best practices` · `retryable errors`

**Должен знать**
Повторяют только то, что может пройти со второй попытки и не навредит: идемпотентные методы (`GET`, `PUT`, `DELETE`) и `POST` с ключом идемпотентности. Повторяют при сетевых сбоях и ответах `502`, `503`, `504`, `429` (уважая `Retry-After`). Ответы 4xx вроде `400` и `404` повторять бессмысленно — ошибка в запросе, второй раз будет то же.

**Термины**
- **повторяемая ошибка** — ошибка, после которой повтор может помочь

#### GO-23.2.2 Экспоненциальная задержка
**Вопросы**
- [ ] Что такое экспоненциальная задержка? · `exponential backoff explained`
- [ ] Почему повторять сразу и подряд — плохо для упавшего сервиса? · `retry storm`
- [ ] Как вычислить задержку: `база × 2^попытка`, с верхним пределом? · `backoff formula cap`
- [ ] Напиши функцию повтора с экспоненциальной задержкой и проверкой `ctx.Done()`. · `go retry with backoff context`

**Гуглить:** `exponential backoff` · `go retry backoff example`

**Должен знать**
Если сервис перегружен, мгновенные повторы от всех клиентов добивают его — шторм повторов. Экспоненциальная задержка увеличивает паузу после каждой неудачи: 100 мс, 200, 400, 800… до верхнего предела. Сервис получает время прийти в себя.
Пауза между попытками — это `select` с таймером и `ctx.Done()`, чтобы повторы останавливались при отмене.

**Термины**
- **экспоненциальная задержка** *(новое)* — пауза между повторами, растущая в геометрической прогрессии

#### GO-23.2.3 Джиттер
**Вопросы**
- [ ] Зачем к экспоненциальной задержке добавляют джиттер? · `backoff jitter why`
- [ ] Что случится, если тысяча клиентов упали одновременно и повторяют по одному и тому же расписанию? · `thundering herd retries`
- [ ] Чем «полный джиттер» (случайно от 0 до задержки) отличается от небольшой добавки? · `full jitter vs equal jitter`

**Гуглить:** `aws exponential backoff and jitter` · `thundering herd`

**Должен знать**
Если много клиентов получили ошибку в один момент, с одинаковой задержкой они и повторят в один момент — волнами. Джиттер — случайная составляющая: задержку выбирают случайно в пределах рассчитанного значения (например, от 0 до `база × 2^попытка`). Повторы размазываются по времени, и пиков нет.

**Термины**
- **джиттер** *(новое)* — случайный разброс задержки повторов

#### GO-23.2.4 Ограничение числа повторов и общий дедлайн
**Вопросы**
- [ ] Почему повторы нужно ограничивать и числом, и общим временем? · `limit retries max attempts deadline`
- [ ] Почему повторы на нескольких уровнях вызовов умножаются (3 × 3 × 3 = 27)? · `retry amplification layers`
- [ ] Как общий срок через context не даёт повторам пережить запрос пользователя? · `retry within context deadline`
- [ ] Что делать, когда попытки кончились (вернуть последнюю ошибку с контекстом)? · `retry exhausted error`

**Гуглить:** `retry budget` · `retry amplification`

**Должен знать**
Повторы ограничивают числом (2–3 попытки) и общим сроком (контекст запроса): иначе пользователь ушёл, а сервис всё ещё повторяет. Если повторяет каждый уровень цепочки сервисов, попытки перемножаются: три уровня по три повтора — 27 запросов к самому нижнему, который и так тонет. Поэтому повторяют обычно на одном уровне.
Когда попытки кончились, возвращают последнюю ошибку, обёрнутую с числом попыток.

**Термины**
- **общий срок повторов** — все попытки укладываются в срок контекста
- **умножение повторов** — повторы на каждом уровне цепочки перемножаются
