# ТЗ Б: Доставка вебхуков с гарантиями

**Одной фразой:** сервис, который принимает события и доставляет их на чужие URL так, что ни одно не теряется, даже когда получатели тормозят, падают, а сам сервис перезапускают.
**Срок:** 3–4 дня, максимум 7.
**Когда:** после СИСД-3 в этапе 7. Нужны АРХ-2 и БРОК-2 (гарантии доставки, outbox) и СИСД-3.2 (circuit breaker). В плане проект стоит в уроке СБОР-1.2.1.
**Главное правило:** код пишешь сам. ИИ можно спрашивать как справочник и просить проверить уже написанное. Генерировать им файлы нельзя (урок СБОР-1.3.1).

Парный вариант — [[98 ТЗ А — Распродажа без перепродажи]]. Сравнение — в конце того файла.

## Зачем именно этот проект

- **Это самый «гошный» проект из возможных:** worker pool, семафоры, context, таймауты, корректная остановка. Ровно то, что Авито даёт на лайвкодинге («worker pool с graceful shutdown»).
- **Он про надёжность:** at-least-once, ретраи с экспоненциальной задержкой и джиттером, circuit breaker, идемпотентность. Это язык, на котором говорят команды платформы.
- **Задача настоящая.** Так работают уведомления о платежах в платёжных системах и события в любом маркетплейсе.

## Что делает сервис

1. Администратор регистрирует **получателя**: URL, типы событий, на которые он подписан, и лимит одновременных доставок. В ответ сервис выдаёт секрет для подписи.
2. **Производитель** (другой сервис) отправляет событие: тип и JSON. Повтор с тем же `Idempotency-Key` не создаёт второе событие.
3. Для каждого подписанного получателя создаётся **доставка**. Диспетчер отправляет её POST-запросом с подписью.
4. Получатель ответил 2xx — доставка успешна. Не ответил или ответил ошибкой — повтор по расписанию. Попытки кончились — доставка «мёртвая», её можно перезапустить вручную.
5. Получатель, который падает раз за разом, временно отключается (circuit breaker), чтобы не тратить на него воркеры.

**Гарантия: at-least-once.** Каждая доставка в итоге становится успешной или мёртвой, ни одна не теряется. Дубли возможны, поэтому получатель отсекает их по `X-Webhook-Id`. В README объясни, почему exactly-once между двумя сервисами по HTTP без помощи получателя невозможен.

Идентификация упрощена: администратор — `X-Admin-Token`, производитель — `X-Producer-ID`. В README напиши, как это закрывается в настоящем сервисе (СЕТЬ-3.2.1).

## Модель данных

```sql
-- endpoints: получатели
id                 BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
url                TEXT    NOT NULL
secret             TEXT    NOT NULL
event_types        TEXT[]  NOT NULL
active             BOOLEAN NOT NULL DEFAULT true
max_in_flight      INT     NOT NULL DEFAULT 4 CHECK (max_in_flight BETWEEN 1 AND 32)
failure_streak     INT     NOT NULL DEFAULT 0
circuit_open_until TIMESTAMPTZ
created_at         TIMESTAMPTZ NOT NULL DEFAULT now()

-- events
id              UUID PRIMARY KEY
producer_id     TEXT  NOT NULL
idempotency_key TEXT  NOT NULL
request_hash    TEXT  NOT NULL
type            TEXT  NOT NULL
payload         JSONB NOT NULL
created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
UNIQUE (producer_id, idempotency_key)

-- deliveries: одна строка на пару «событие × получатель»
id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
event_id         UUID   NOT NULL REFERENCES events(id)
endpoint_id      BIGINT NOT NULL REFERENCES endpoints(id)
status           TEXT   NOT NULL CHECK (status IN ('pending','in_flight','succeeded','dead'))
attempt          INT    NOT NULL DEFAULT 0
next_attempt_at  TIMESTAMPTZ NOT NULL DEFAULT now()
lease_until      TIMESTAMPTZ          -- аренда: до какого момента доставка «наша»
last_status_code INT
last_error       TEXT
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
UNIQUE (event_id, endpoint_id)
```

**Индексы** (обоснуй в README, приложи `EXPLAIN ANALYZE` запроса захвата):
- частичный `(next_attempt_at) WHERE status = 'pending'`;
- частичный `(lease_until) WHERE status = 'in_flight'`.

## Ключевые требования

### Приём события: outbox в одной транзакции

1. Проверяем повтор по `(producer_id, idempotency_key)`. Повтор с тем же `request_hash` — 200 и существующий `event_id`; с другим хешем — 422. При параллельных одинаковых запросах один из них упирается в UNIQUE, откатывается и тоже отвечает 200.
2. Вставляем событие.
3. Вставляем доставки для всех активных получателей, подписанных на этот тип (`type = ANY(event_types)`).
4. Коммитим и отвечаем 202.

Событие и «что отправить» появляются в базе атомарно. Это и есть transactional outbox (БРОК-2.6.2). В README объясни, что сломалось бы, если бы мы сохраняли событие и сразу слали HTTP из хендлера.

### Диспетчер

- `DISPATCH_WORKERS` воркеров (по умолчанию 8). Каждый в цикле **захватывает** пачку доставок короткой транзакцией:
  ```sql
  SELECT … FROM deliveries d JOIN endpoints e ON e.id = d.endpoint_id
  WHERE e.active AND (e.circuit_open_until IS NULL OR e.circuit_open_until < now())
    AND ( (d.status = 'pending'   AND d.next_attempt_at <= now())
       OR (d.status = 'in_flight' AND d.lease_until < now()) )   -- аренда протухла: прошлый владелец умер
  ORDER BY d.next_attempt_at LIMIT 10
  FOR UPDATE OF d SKIP LOCKED
  ```
  Затем ставит захваченным `status = 'in_flight'`, `lease_until = now() + 30s`, `attempt = attempt + 1` и коммитит.
- **HTTP-запрос делается вне транзакции.** В README объясни, почему держать транзакцию открытой на время сетевого вызова — ошибка: соединения пула и блокировки висят столько, сколько тормозит чужой сервер (GO-25.2.4).
- Результат записывается новой короткой транзакцией. Обновлять нужно только если `status = 'in_flight'` и аренда ещё наша (сверяем `attempt`): опоздавший воркер не должен затереть чужой результат.
- Если сработала аренда, а первый воркер тоже доставил, получатель получит дубль. Это допустимо: at-least-once.

### Как трактовать ответ получателя

| Ответ | Что делаем |
|---|---|
| 2xx | succeeded |
| 410 Gone | получатель выключается (`active = false`), доставка становится dead |
| 429 | повтор не раньше `Retry-After` |
| 408, 5xx, таймаут, сетевая ошибка | повтор с экспоненциальной задержкой |
| 3xx | редиректы **не следуем**, считаем ошибкой и повторяем |
| прочие 4xx | сразу dead: повтор не поможет |

**Задержка повтора:** `min(base · 2^(attempt-1), max)` с полным джиттером, то есть случайное время от нуля до этого значения. По умолчанию base = 1 с, max = 10 мин, не больше 8 попыток, потом dead. В README объясни, зачем джиттер: без него тысяча упавших доставок вернётся к получателю одновременно (GO-23.2.3, СИСД-3.2.3).

### Circuit breaker на получателя

- Каждый неуспех увеличивает `failure_streak`, успех обнуляет.
- 5 неуспехов подряд размыкают цепь: `circuit_open_until = now() + 1 мин`. Каждое следующее размыкание удваивает паузу, не больше 30 минут.
- Пока цепь разомкнута, запрос захвата этого получателя пропускает, и его доставки ждут.
- Состояние хранится **в базе, а не в памяти,** чтобы его видели все реплики сервиса. Компромисс — лишняя запись на каждый результат; опиши его в README.

### Лимит одновременных доставок на получателя

- Внутри процесса держим `map[endpointID]chan struct{}` под мьютексом. Канал — семафор ёмкостью `max_in_flight`.
- Перед HTTP-вызовом воркер занимает слот, после вызова освобождает, причём в `defer`.
- Ограничение действует на одну реплику. В README напиши, что при N репликах реальный лимит в N раз больше, и как это решается (общий счётчик, например в Redis, — одной фразой).

### HTTP-клиент

- Один `http.Client` на весь процесс, `Timeout` 5 с, настроенный `Transport` (`MaxIdleConnsPerHost`).
- Своя функция `CheckRedirect`, возвращающая `http.ErrUseLastResponse`.
- Тело ответа читаем через `io.LimitReader` (не больше 1 КБ, для `last_error`), потом закрываем. Почему это важно — урок GO-23.1.3.
- Подпись: заголовки `X-Webhook-Id` (id события, одинаковый на всех повторах), `X-Webhook-Timestamp` и `X-Webhook-Signature` = HMAC-SHA256(secret, timestamp + "." + body).
- В README одной строкой: URL получателя может указывать во внутреннюю сеть (SSRF); как это закрывают — запрет приватных адресов.

### Корректная остановка

По SIGTERM:
1. HTTP-сервер перестаёт принимать запросы (`Shutdown`);
2. воркеры перестают захватывать новые доставки;
3. начатые HTTP-вызовы доделываются, пока не выйдет `SHUTDOWN_TIMEOUT`, затем их контексты отменяются;
4. недоделанные доставки ничего не записывают, их аренда протухает, и после рестарта их подхватят. Ничего не теряется — в этом и смысл аренды.

## Тестовый получатель `cmd/sink`

Отдельная маленькая программа: учебный «чужой сервис».
- Флаги: доля ошибок (500), задержка, режим «всегда 410», режим «429 с Retry-After».
- Проверяет подпись; запросы с неверной подписью отклоняет с кодом 401.
- Отсекает дубли по `X-Webhook-Id` и считает уникальные и повторные.
- `GET /stats` отдаёт счётчики и максимальное число одновременных запросов, которое он видел.

В `docker-compose.yml` — сервис, Postgres и три экземпляра sink с разной надёжностью.

## Тесты (обязательный минимум, все с `-race`)

1. Табличные тесты: расчёт задержки (случайность подставляется снаружи), подпись, трактовка ответов по таблице выше.
2. Тесты сервиса с фейковым репозиторием (ТЕСТ-1.2.2).
3. Хендлеры через `httptest` (ТЕСТ-1.3.3).
4. Диспетчер против `httptest.Server`: 2xx, 500 с повтором, 410 с выключением, 429 с Retry-After, таймаут, редирект.
5. Circuit breaker: размыкается после 5 ошибок и замыкается после паузы (свои «часы» или `testing/synctest`).
6. **Лимит на получателя:** sink фиксирует максимум одновременных запросов, и он не превышает `max_in_flight`.
7. **SKIP LOCKED:** 4 воркера, 500 доставок, получатель всегда отвечает 200; каждая доставка ровно одна, дублей ноль.
8. **Аренда:** захватить доставки и «упасть», не записав результат; после истечения аренды доставки переотправляются и завершаются успешно.
9. **Идемпотентный приём:** 20 параллельных запросов с одним ключом создают одно событие.
10. **Сквозной тест:** 1000 событий, три получателя с 30% ошибок и рестартом relay посередине. В итоге все доставки succeeded, каждый получатель увидел каждое событие хотя бы один раз, число дублей выведено в лог.
