# ТЗ А: Распродажа без перепродажи

**Одной фразой:** сервис резервирования товара на распродаже. 100 единиц, тысячи покупателей одновременно — и ни одной лишней проданной.
**Срок:** 2–3 дня, максимум 7.
**Когда:** после ПРОГОН-5: к этому моменту пройдено всё нужное для основной части. Пункты «Если останется время» — после ПРОГОН-6. В плане проект стоит в уроке СБОР-1.2.1.
**Главное правило:** код пишешь сам. ИИ можно спрашивать как справочник («как называется функция в pgx») и просить проверить уже написанное. Генерировать им файлы нельзя. Смысл проекта в том, чтобы про каждую строку ты мог честно сказать «это писал я» (урок СБОР-1.3.1).

Парный вариант — [[99 ТЗ Б — Доставка вебхуков]]. Выбор между ними сделаешь, когда дойдёшь до проекта. Сравнение — в конце этого файла.

## Зачем именно этот проект

- **Домен целевых компаний.** У Озона есть стажировки ровно в такие команды: «Корзина», «Склады, остатки и методы доставки», «Страница оформления заказа».
- **Настоящая гонка за данные.** Конкуренция за остаток — главная задача, без которой сервис не работает, а не украшение.
- **Результат доказывается тестом.** На собесе звучит так: «5000 параллельных покупок, остаток 100 — продано ровно 100, и это проверяет тест».

| Аномалия сериализации (write skew) | лимит товара на одного покупателя | PG-1.2.5 |

## Что делает сервис

1. Администратор создаёт товар с остатком (например, 100 штук).
2. Покупатель резервирует 1–2 единицы. Резерв живёт 10 минут, и всё это время товар недоступен другим.
3. Покупатель подтверждает резерв, то есть покупает (оплату считаем мгновенной и не моделируем) — или отменяет его. Товар при отмене возвращается в остаток.
4. Неподтверждённые резервы истекают. Фоновые воркеры возвращают их товар в остаток.
5. Один покупатель держит не больше **2 единиц** одного товара (активные и подтверждённые резервы вместе).
6. Повтор запроса с тем же `Idempotency-Key` не создаёт второй резерв, а возвращает первый.

Покупателя опознаём по заголовку `X-Client-ID` (UUID), администратора — по `X-Admin-Token` из переменной окружения. Это **сознательное упрощение**. В README напиши, что заголовки подделываются, и как это закрывается в настоящем сервисе (урок СЕТЬ-3.2.1).

## Главный инвариант

Для каждого товара в любой момент должно выполняться:

```
stock_available + sum(qty активных и подтверждённых резервов) == stock_total
stock_available >= 0
```

Ни одна операция, ни одна гонка и ни один SIGTERM не нарушают это равенство. Его проверяют интеграционные тесты, а SQL проверки лежит в README.

## Модель данных

```sql
-- products
id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
title           TEXT   NOT NULL
price_kopecks   BIGINT NOT NULL CHECK (price_kopecks > 0)   -- деньги в целых копейках (ФУНД-2.3.4)
stock_total     INT    NOT NULL CHECK (stock_total >= 0)
stock_available INT    NOT NULL CHECK (stock_available >= 0)
created_at      TIMESTAMPTZ NOT NULL DEFAULT now()

-- reservations
id              UUID PRIMARY KEY
product_id      BIGINT NOT NULL REFERENCES products(id)
client_id       UUID   NOT NULL
qty             INT    NOT NULL CHECK (qty BETWEEN 1 AND 2)
status          TEXT   NOT NULL CHECK (status IN ('active','confirmed','cancelled','expired'))
expires_at      TIMESTAMPTZ NOT NULL
idempotency_key TEXT   NOT NULL
request_hash    TEXT   NOT NULL        -- чтобы отличить честный повтор от другого запроса с тем же ключом
created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
UNIQUE (client_id, idempotency_key)
```

**Индексы** (каждый обоснуй в README, приложи `EXPLAIN ANALYZE`):
- для истечения: частичный `(expires_at) WHERE status = 'active'`;
- для лимита на покупателя: `(product_id, client_id) WHERE status IN ('active','confirmed')`.

## API

Ошибки отдаются в формате `{"error": "...", "request_id": "..."}`.

| Метод и путь | Что делает | Коды |
|---|---|---|
| `POST /v1/products` | Создать товар (нужен `X-Admin-Token`) | 201, 400, 401 |
| `GET /v1/products/{id}` | Товар и текущий остаток | 200, 404 |
| `POST /v1/products/{id}/reservations` | Тело `{"qty": 1}`; нужны заголовки `X-Client-ID` и `Idempotency-Key` | 201, 200 (повтор), 400, 404, 409 (нет остатка), 422 (лимит на покупателя или ключ уже занят другим запросом), 429 |
| `GET /v1/reservations/{id}` | Статус резерва (только своего) | 200, 404 |
| `POST /v1/reservations/{id}/confirm` | Подтвердить, то есть купить | 200, 404, 409 (уже отменён), 410 (истёк) |
| `DELETE /v1/reservations/{id}` | Отменить, товар возвращается в остаток | 204, 404, 409 (уже подтверждён) |
| `GET /healthz`, `GET /readyz` | Процесс жив / база отвечает | 200, 503 |

## Ключевые требования

### Резерв: одна транзакция

1. Блокируем строку товара: `SELECT … FROM products WHERE id = $1 FOR UPDATE`. С этого момента все запросы к этому товару идут по очереди.
2. Ищем повтор по `(client_id, idempotency_key)`. Нашли и `request_hash` совпадает — возвращаем существующий резерв с кодом 200. Хеш другой — 422. Проверка безопасна именно потому, что её делают после блокировки.
3. Проверяем лимит покупателя: сумма qty его активных и подтверждённых резервов плюс новый qty ≤ 2.
4. Списываем остаток, если хватает; если нет — 409.
5. Вставляем резерв. Если сработал UNIQUE (тот же ключ уже использован для другого товара), откатываем транзакцию и отдаём 422. Иначе коммитим.

**Ловушка, которую нужно объяснить в README.** Почему шаги 2 и 3 безопасны только благодаря шагу 1. Без блокировки товара два параллельных запроса одного покупателя оба увидят «у него 1 штука», оба добавят ещё по одной — получится 3. Это аномалия сериализации (write skew, урок PG-1.2.5). Блокировка строки товара выстраивает все резервы этого товара в очередь. Альтернатива — уровень SERIALIZABLE с повтором транзакции. Сравни два подхода в README.

### Подтверждение против истечения

Подтверждение и воркер истечения могут прийти к одному резерву одновременно, и выиграть должен ровно один. Подтверждение делается одним условным UPDATE:

```sql
UPDATE reservations SET status = 'confirmed'
WHERE id = $1 AND status = 'active' AND expires_at > now()
```

Если ни одна строка не обновилась, отдельным запросом выясняем причину и возвращаем 410 или 409.

### Воркеры истечения

- В сервисе `EXPIRE_WORKERS` воркеров (по умолчанию 2), каждый просыпается по `time.Ticker`.
- Каждый в транзакции берёт пачку: `SELECT … WHERE status = 'active' AND expires_at < now() ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED`.
- Для каждого резерва в той же транзакции ставит статус expired и возвращает qty в `stock_available`.
- Два воркера никогда не обрабатывают один резерв. Это проверяется тестом.

### Middleware и сервер

- Порядок обёрток: recover → request id → логирование → rate limit → таймаут.
- Rate limit — свой token bucket на каждый `X-Client-ID`: не больше 10 запросов резерва в минуту, иначе 429 и `Retry-After`. Хранилище — map под мьютексом; горутина-чистильщик по тикеру.
- У `http.Server` выставлены все таймауты; все запросы к базе идут через `…Context`.

### Корректная остановка

По SIGTERM (`signal.NotifyContext`):
1. `server.Shutdown` с таймаутом;
2. отмена контекста воркеров: воркер доделывает текущую транзакцию и выходит;
3. `wg.Wait()`;
4. закрытие пула соединений.

Инвариант после остановки не нарушен, и это проверяет тест.

## Нагрузочный генератор `cmd/loadgen`

Отдельная программа на Go: тот же язык, но теперь клиентская сторона.
- Параметры: число покупателей, число запросов, параллелизм.
- Worker pool с ограничением параллелизма через семафор или errgroup (GO-20.1.4, GO-20.1.5).
- Один `http.Client` с таймаутом на всех; тело каждого ответа закрывается (GO-23.1.2, GO-23.1.3).
- Итог: сколько 201, 409, 422 и 429, p50 и p99 задержки, и проверка «продано ровно stock_total».

Вывод генератора на 5000 запросов приложи в README.

## Тесты (обязательный минимум, все с `-race`)

1. Табличные тесты валидации запросов (ТЕСТ-1.1.3).
2. Тесты сервиса с фейковым репозиторием (ТЕСТ-1.2.2).
3. Тесты хендлеров через `httptest`: все коды из таблицы API (ТЕСТ-1.3.3).
4. Тест rate limit со своими «часами» или через `testing/synctest` (ТЕСТ-1.3.5).
5. **Нет перепродажи:** остаток 100, 2000 горутин, 700 покупателей; в итоге продано ровно 100, инвариант цел.
6. **Лимит на покупателя под гонкой:** 50 параллельных запросов одного покупателя по 1 штуке; в итоге у него ровно 2.
7. **Идемпотентность под гонкой:** 20 параллельных запросов с одним ключом создают ровно один резерв.
8. **Подтверждение против истечения:** резервы с почти истёкшим сроком, параллельные подтверждения и воркеры; каждый резерв в итоге либо confirmed, либо expired, инвариант цел.
9. **SKIP LOCKED:** два воркера и 500 просроченных резервов; каждый обработан ровно один раз.

Базу для интеграционных тестов поднимает testcontainers или отдельный сервис в compose (ТЕСТ-1.3.2).
