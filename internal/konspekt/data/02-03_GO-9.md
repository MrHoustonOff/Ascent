### GO-9.1 Map в коде

#### GO-9.1.1 Map
**Вопросы**
- [ ] Что такое map и как записывается её тип `map[string]int`? · `go maps tour`
- [ ] Как прочитать значение, записать новое и узнать количество пар (`len`)? · `golang map basic operations`
- [ ] Есть ли у map `cap`? · `go map cap not allowed`
- [ ] Чем map похожа на `dict` в Python и чем отличается (один тип ключей и значений, нет порядка)? · `python dict vs go map`
- [ ] Почему поиск по ключу в map быстрый, а в слайсе — нет? · `map lookup O(1) vs slice O(n)`

**Гуглить:** `golang map tutorial` · `go blog maps in action` · `python dict vs go map`

**Должен знать**
Map — словарь: по ключу быстро находится значение. Тип `map[K]V` задаёт тип ключей и тип значений; `m["a"] = 1` записывает, `v := m["a"]` читает, `len(m)` — число пар. `cap` у map нет.
Мост из Python: это `dict`, но все ключи одного типа и все значения одного типа, а порядок пар не сохраняется. Поиск по ключу в среднем не зависит от размера map — в отличие от перебора слайса.

**Термины**
- **map** *(новое)* — словарь «ключ → значение»: `map[K]V`
- **пара** — ключ вместе с его значением

#### GO-9.1.2 Создание: make и литерал
**Вопросы**
- [ ] Как создать map через `make` и через литерал `map[string]int{"a": 1}`? · `go create map make literal`
- [ ] Зачем `make(map[string]int, 100)` с числом и что это число значит? · `go make map size hint`
- [ ] Почему пустой литерал `map[string]int{}` — тоже рабочая map? · `go empty map literal`
- [ ] Почему в многострочном литерале нужна запятая после последней пары? · `go trailing comma composite literal`

**Гуглить:** `golang make map` · `go map literal`

**Должен знать**
`m := make(map[string]int)` создаёт пустую рабочую map, `m := map[string]int{"a": 1, "b": 2}` — сразу с парами. Второй аргумент `make` — подсказка, сколько пар ожидается: map заранее выделит место и не будет перестраиваться при наполнении. Это не ёмкость и не ограничение.
В многострочном литерале запятая после последней пары обязательна.

**Термины**
- **литерал map** — `map[K]V{k: v, …}`
- **подсказка размера** — второй аргумент `make` для map

#### GO-9.1.3 Чтение отсутствующего ключа и проверка «comma ok»
**Вопросы**
- [ ] Что вернёт чтение отсутствующего ключа и как отличить его от нулевого значения? · `go map missing key zero value`
- [ ] Как работает `v, ok := m[k]`? · `go comma ok idiom map`
- [ ] Почему в Go нет `KeyError`, как в Python? · `go map no exception missing key`
- [ ] Как удобно посчитать частоту слов `m[w]++`, пользуясь нулевым значением? · `go word count map increment`
- [ ] Как проверить наличие ключа, не беря значение (`_, ok := m[k]`)? · `go check key exists map`

**Гуглить:** `golang comma ok` · `go map check if key exists`

**Должен знать**
Чтение отсутствующего ключа не ошибка: вернётся нулевое значение типа значений. Чтобы отличить «ключа нет» от «значение равно нулю», используют форму `v, ok := m[k]` — «comma ok»: `ok` равно `true`, только если ключ есть.
Нулевое значение удобно: `m[w]++` для нового слова начинает с 0. В Python в таких случаях бросается `KeyError`; в Go ничего не бросается — проверяй `ok`, когда разница важна.

**Термины**
- **comma ok** *(новое)* — форма `v, ok := …`, где `ok` сообщает, нашлось ли значение

#### GO-9.1.4 Удаление: delete
**Вопросы**
- [ ] Как удалить ключ (`delete(m, k)`)? · `golang delete map key`
- [ ] Что будет, если удалить ключ, которого нет? · `delete non existent key go`
- [ ] Как очистить map целиком (`clear(m)` с Go 1.21)? · `go clear map`
- [ ] Освобождает ли удаление память, которую занимала map? · `go map delete does not shrink`

**Гуглить:** `go delete from map` · `go map memory not freed after delete`

**Должен знать**
`delete(m, k)` удаляет пару; удаление отсутствующего ключа ничего не делает и не паникует. `clear(m)` удаляет все пары разом.
Важная деталь: map в Go не уменьшается. После удаления миллиона пар место под них остаётся занятым; чтобы вернуть память, создают новую map и переносят в неё нужное.

**Термины**
- **`delete`** — функция языка: удалить пару из map

#### GO-9.1.5 nil-map
**Вопросы**
- [ ] Что будет при записи в nil-map, а что — при чтении? · `go assignment to entry in nil map`
- [ ] Почему `var m map[string]int` даёт nil-map? · `go map zero value nil`
- [ ] Какие операции с nil-map безопасны (`len`, чтение, `range`, `delete`)? · `nil map operations safe`
- [ ] Как не забыть создать map, если она — поле чего-то другого? · `initialize map before use go`

**Гуглить:** `golang nil map panic` · `assignment to entry in nil map`

**Должен знать**
Нулевое значение map — nil: объявленная через `var` map ещё не создана. Читать из неё можно (всегда нулевое значение), `len` даёт 0, `range` ничего не делает, `delete` ничего не делает. Но запись паникует: `assignment to entry in nil map`.
Поэтому map всегда создают через `make` или литерал перед записью. Слайс из nil можно растить через `append`, map — нет.

**Термины**
- **nil-map** — map с нулевым значением: читать можно, писать нельзя

#### GO-9.1.6 Сравнимые типы
**Вопросы**
- [ ] Что такое сравнимый тип? · `go comparable types`
- [ ] Какие типы сравнимы, а какие нет (слайс, map, функция)? · `go which types are comparable`
- [ ] Почему слайсы нельзя сравнить через `==`? · `why slices not comparable go`
- [ ] Можно ли сравнить map с nil? А две map между собой? · `compare map to nil`

**Гуглить:** `go spec comparison operators` · `golang comparable`

**Должен знать**
Сравнимый тип — тот, значения которого можно сравнить через `==`. Сравнимы `bool`, числа, строки, указатели, массивы из сравнимых элементов. Несравнимы слайсы, map и функции — их можно сравнить только с nil.
У слайса нет одного очевидного смысла «равенства»: сравнивать заголовки или элементы? Go не стал выбирать, и для сравнения элементов есть `slices.Equal` и `maps.Equal`.

**Термины**
- **сравнимый тип** *(новое)* — тип, значения которого сравниваются через `==`

#### GO-9.1.7 Какие типы могут быть ключом
**Вопросы**
- [ ] Какие типы могут быть ключом map и почему слайс не может? · `go map key types`
- [ ] Как использовать составной ключ, например пару координат `[2]int`? · `go map composite key array`
- [ ] Почему дробное число — плохой ключ (NaN, ошибки округления)? · `float as map key problem NaN`
- [ ] Как сделать ключом слайс, если очень нужно (превратить в строку)? · `go use slice as map key`

**Гуглить:** `golang map key type comparable` · `go map key NaN`

**Должен знать**
Ключом может быть только сравнимый тип: map должна уметь проверить, что найденный ключ равен искомому. Поэтому слайсы, map и функции ключами быть не могут, а строки, числа и массивы — могут. Составной ключ делают массивом: `map[[2]int]bool`.
Дробные числа ключом использовать можно, но опасно: из-за округления «тот же» ключ может не найтись, а NaN не равен себе и не находится никогда.

**Термины**
- **ключ map** — значение сравнимого типа, по которому ищется пара

- [ ] Как обойти map в порядке ключей? · `go iterate map sorted keys`

- **порядок обхода** — у map не определён и случаен

#### GO-9.1.9 Map, переданная в функцию

#### GO-9.1.10 Запись в map во время обхода
**Вопросы**
- [ ] Можно ли удалять ключи из map во время обхода `range`? · `go delete map during iteration safe`
- [ ] Что будет с парой, добавленной во время обхода: попадёт ли она в обход? · `go add to map during range`
- [ ] Как безопасно удалить из map все пары, подходящие под условие? · `go filter map delete in loop`
- [ ] Почему в Python изменение `dict` во время обхода — ошибка, а в Go — нет? · `python dictionary changed size during iteration`

**Гуглить:** `golang modify map while iterating` · `go spec for range map`

**Должен знать**
Удалять пары во время обхода можно: удалённая, ещё не пройденная пара в обход уже не попадёт. Добавлять тоже можно, но новая пара может попасть в обход, а может нет — это не определено. Поэтому удаление «по условию» прямо в `range` — нормальный приём, а добавление во время обхода — плохой.
В Python изменение размера `dict` во время обхода — ошибка `RuntimeError`.

**Термины**
- **изменение при обходе** — удаление безопасно, добавление — с неопределённым результатом

#### GO-9.1.12 make против new
**Вопросы**
- [ ] Чем `make` отличается от `new`? · `go make vs new`
- [ ] Что вернёт `new(map[string]int)` и почему в такую map нельзя писать? · `new map nil pointer to map`
- [ ] Для каких типов работает `make` (слайс, map и ещё один)? · `go make types slice map chan`
- [ ] Что возвращает каждая из функций: значение или указатель? · `make returns value new returns pointer`

**Гуглить:** `golang make vs new` · `effective go allocation new make`

**Должен знать**
`new(T)` для любого типа выделяет нулевое значение и возвращает указатель `*T`. `make` работает только для слайсов, map (и ещё одного типа, который будет в этапе 3) и возвращает не указатель, а готовое к работе значение: слайс с массивом, map с таблицей.
`new(map[string]int)` даёт указатель на nil-map — писать в неё нельзя. Для map и слайсов нужен `make` или литерал.

**Термины**
- **`make` против `new`** — `make` создаёт рабочий слайс или map; `new` — указатель на нулевое значение

### GO-9.2 Хеш-таблица

#### GO-9.2.1 Хеш-функция
**Вопросы**
- [ ] Что такое хеш-функция и какие свойства от неё нужны? · `hash function properties`
- [ ] Почему одинаковые ключи обязаны давать одинаковый хеш, а разные могут совпасть? · `hash function deterministic collisions`
- [ ] Почему хороший хеш «разбрасывает» похожие ключи по разным местам? · `hash function uniform distribution`
- [ ] Почему хеш-функция для map должна быть быстрой, а не криптографически стойкой? · `hash table hash vs cryptographic hash`
- [ ] Почему Go добавляет к хешу случайное начальное значение при каждом запуске? · `hash seed randomization dos`

**Гуглить:** `hash function explained` · `хеш-функция простыми словами` · `hash flooding attack`

**Должен знать**
Хеш-функция превращает ключ любого размера в число фиксированного размера — хеш. Требования для map: одинаковые ключи всегда дают одинаковый хеш, вычисление быстрое, и хеши похожих ключей разбросаны равномерно. Разные ключи иногда дают одинаковый хеш — это нормально.
Go при каждом запуске добавляет к хешу случайное начальное значение — так злоумышленник не может заранее подобрать ключи, которые «сломают» map.

**Термины**
- **хеш-функция** *(новое)* — функция, превращающая ключ в число фиксированного размера
- **хеш** *(новое)* — результат хеш-функции
- **начальное значение хеша** — случайное число, которое Go подмешивает при каждом запуске

**Граница:** устройство конкретных хеш-функций — не нужно.

#### GO-9.2.2 Хеш-таблица и коллизии
**Вопросы**
- [ ] Как хеш-таблица превращает хеш в номер ячейки массива? · `hash table index modulo`
- [ ] Что такое коллизия и как хеш-таблица с ней справляется? · `hash collision resolution`
- [ ] Чем цепочки отличаются от открытой адресации — в двух словах? · `chaining vs open addressing`
- [ ] Почему при большом числе коллизий поиск замедляется вплоть до перебора? · `hash table worst case O(n)`
- [ ] Как устроен `dict` в CPython (открытая адресация, компактный массив записей)? · `cpython dict implementation`

**Гуглить:** `hash table explained` · `hash collision` · `how python dict works internally`

**Должен знать**
Хеш-таблица — массив ячеек; номер ячейки для ключа получают из хеша (например, остаток от деления на размер массива). Поиск: посчитать хеш → перейти в ячейку → сравнить ключ. Так поиск занимает в среднем постоянное время.
Коллизия — два ключа попали в одну ячейку. Решают её двумя основными способами: цепочки (в ячейке список пар) и открытая адресация (ищем следующую свободную ячейку). Мост из Python: `dict` в CPython использует открытую адресацию.

**Термины**
- **хеш-таблица** — массив ячеек, куда пары раскладываются по хешу ключа
- **коллизия** *(новое)* — разные ключи попали в одну ячейку
- **цепочки / открытая адресация** — два способа разрешать коллизии

**Граница:** способы разрешения коллизий — двумя названиями.

#### GO-9.2.3 Коэффициент заполнения и перестройка таблицы
**Вопросы**
- [ ] Что такое коэффициент заполнения? · `hash table load factor`
- [ ] Зачем хеш-таблицу перестраивают, когда она заполняется? · `hash table rehashing resize`
- [ ] Почему при перестройке все пары раскладываются заново? · `rehash all keys new size`
- [ ] Почему перестройка дорогая, но в среднем вставка всё равно быстрая? · `amortized hash table insert`

**Гуглить:** `hash table load factor resize` · `rehashing explained`

**Должен знать**
Коэффициент заполнения — сколько пар приходится на ячейку (или на всё место в таблице). Чем он выше, тем больше коллизий и тем медленнее поиск. Поэтому, когда коэффициент превышает порог, таблицу перестраивают: выделяют массив побольше и раскладывают все пары заново, ведь номер ячейки зависит от размера.
Перестройка дорогая, но редкая — как переезд слайса при `append`, поэтому в среднем вставка остаётся быстрой.

**Термины**
- **коэффициент заполнения** *(новое)* — среднее число пар на ячейку таблицы
- **перестройка** — увеличение таблицы и раскладка всех пар заново

### GO-9.3 Устройство map

#### GO-9.3.1 Классическая map: бакеты по 8 пар
**Вопросы**
- [ ] Как устроена классическая map: что такое бакет и сколько в нём пар? · `go map buckets 8 pairs`
- [ ] Как по хешу выбирается бакет (младшие биты хеша)? · `go map bucket selection low bits`
- [ ] Почему число бакетов всегда степень двойки? · `go map 2^B buckets`
- [ ] Как пары лежат в бакете: сначала 8 ключей, потом 8 значений — и зачем так? · `go map bucket layout keys then values`
- [ ] Как map находит значение по ключу шаг за шагом? · `go map lookup algorithm`

**Гуглить:** `go map internals buckets` · `how go maps work dave cheney` · `go map implementation hmap bmap`

**Должен знать**
До Go 1.24 map — хеш-таблица из массива бакетов; их число — 2ᴮ, поэтому бакет выбирают просто младшими B битами хеша. Бакет — блок на 8 пар: восемь ключей подряд, затем восемь значений (так между ними меньше пустых промежутков в памяти).
Поиск: посчитать хеш → выбрать бакет по младшим битам → просмотреть до 8 пар, сравнивая ключи → если не нашли, перейти к следующему бакету из цепочки.

**Термины**
- **бакет** *(новое)* — блок классической map на 8 пар
- **число бакетов** — 2ᴮ, бакет выбирается младшими битами хеша

**Граница:** внутренние поля по именам — не нужны.

#### GO-9.3.2 tophash
**Вопросы**
- [ ] Зачем нужен tophash? · `go map tophash`
- [ ] Из каких битов хеша он берётся и сколько места занимает? · `tophash top 8 bits`
- [ ] Почему сравнить байт быстрее, чем сравнить длинные строки-ключи? · `tophash fast comparison`
- [ ] Какие ещё значения хранятся в tophash помимо битов хеша (пустая ячейка)? · `tophash empty markers`

**Гуглить:** `go map tophash explained` · `go runtime map.go tophash`

**Должен знать**
У каждого бакета есть массив из 8 байтов tophash — по старшему байту хеша для каждой пары. Чтобы найти ключ, map сначала сравнивает эти байты и полностью сравнивает ключ только там, где байт совпал. Сравнить байт дешевле, чем длинную строку, поэтому большинство «чужих» пар отсеивается мгновенно.

**Термины**
- **tophash** *(новое)* — старший байт хеша для каждой пары бакета; быстрый отсев

#### GO-9.3.3 Переполненные бакеты
**Вопросы**
- [ ] Что происходит, когда в бакет нужно положить девятую пару? · `go map overflow bucket`
- [ ] Как переполненные бакеты связаны в цепочку? · `overflow bucket linked list`
- [ ] Почему длинные цепочки замедляют map? · `go map overflow performance`
- [ ] Когда много переполненных бакетов вызывает перестройку без увеличения? · `go map same size grow`

**Гуглить:** `go map overflow buckets` · `go map same size grow`

**Должен знать**
Если все 8 ячеек бакета заняты, map добавляет переполненный бакет и связывает его с основным указателем — получается цепочка. Поиск идёт по всей цепочке, поэтому длинные цепочки замедляют map.
Если переполненных бакетов становится слишком много (например, после большого числа удалений и вставок), map перестраивается в таблицу того же размера, чтобы уплотнить данные.

**Термины**
- **переполненный бакет** — дополнительный бакет в цепочке, когда основной заполнен

#### GO-9.3.4 Рост map и коэффициент загрузки
**Вопросы**
- [ ] Когда map растёт? Какой порог у классической map (6,5 пары на бакет)? · `go map load factor 6.5`
- [ ] Во сколько раз растёт число бакетов? · `go map grow double buckets`
- [ ] Почему map в Go никогда не уменьшается? · `go map never shrinks`
- [ ] Как подсказка размера в `make` помогает избежать роста? · `make map hint avoid growth`

**Гуглить:** `go map growth load factor` · `go map does not shrink`

**Должен знать**
Классическая map растёт, когда в среднем на бакет приходится больше 6,5 пары: число бакетов удваивается (B увеличивается на 1). Порог выбран как компромисс между памятью и длиной цепочек.
Уменьшения нет совсем: после удаления пар бакеты остаются. Если заранее известно число пар, подсказка размера в `make` сразу создаёт нужное число бакетов, и роста не будет.

**Термины**
- **порог роста** — средняя заполненность, после которой map увеличивается

#### GO-9.3.5 Эвакуация
**Вопросы**
- [ ] Что такое эвакуация и когда она происходит? · `go map evacuation`
- [ ] Почему map переносит пары в новые бакеты постепенно, а не все сразу? · `go map incremental growth`
- [ ] При каких операциях происходит очередной шаг переноса? · `evacuation during write delete`
- [ ] Как при удвоении один старый бакет делится на два новых (по следующему биту хеша)? · `go map evacuate x y bucket split`
- [ ] Как поиск работает, пока перенос не закончен? · `lookup during map growth oldbuckets`

**Гуглить:** `go map evacuation explained` · `go map growing incremental`

**Должен знать**
При росте map создаёт новый массив бакетов, но не переносит в него все пары сразу — иначе одна вставка могла бы занять очень долго. Вместо этого перенос (эвакуация) идёт постепенно: каждая запись или удаление заодно переносит один-два старых бакета. Пары старого бакета расходятся в два новых в зависимости от следующего бита хеша.
Пока перенос не закончен, поиск смотрит и в старые бакеты.

**Термины**
- **эвакуация** *(новое)* — постепенный перенос пар из старых бакетов в новые при росте map

#### GO-9.3.6 Почему нельзя взять адрес элемента map
**Вопросы**
- [ ] Почему нельзя взять адрес элемента map (`&m[k]` не компилируется)? · `go cannot take address of map element`
- [ ] Как это связано с ростом и эвакуацией? · `map element moves during growth`
- [ ] Почему по той же причине нельзя изменить часть составного значения прямо в map? · `go cannot assign to field in map`
- [ ] Как изменить значение в map: прочитать, изменить, записать обратно? · `go modify value in map`
- [ ] Когда хранить в map указатели на значения вместо самих значений? · `go map of pointers`

**Гуглить:** `golang cannot take address of map value` · `go map value not addressable`

**Должен знать**
Пары в map могут переезжать при росте и эвакуации, поэтому адрес элемента сегодня может указывать в пустоту завтра. Go запрещает `&m[k]`, чтобы такого указателя не появилось. По той же причине нельзя изменить часть составного значения прямо в map — только прочитать копию, изменить и записать целиком.

- **неадресуемый элемент** — элемент, у которого нельзя взять адрес

#### GO-9.3.7 Почему порядок обхода случайный
**Вопросы**
- [ ] Почему порядок обхода map случайный? · `go map random iteration order why`
- [ ] Как именно Go делает порядок случайным (случайный стартовый бакет и сдвиг внутри бакета)? · `go map iteration random start bucket`
- [ ] Какие баги предотвращает такое решение? · `relying on map order bug`
- [ ] Почему `fmt.Println(m)` всё же печатает ключи по порядку? · `fmt print map sorted keys`

**Гуглить:** `go map iteration order randomization` · `go 1.12 fmt sorted map`

**Должен знать**
Порядок обхода естественно зависит от раскладки по бакетам, а она меняется при росте. Чтобы никто не начал полагаться на «вроде стабильный» порядок, Go специально делает его случайным: каждый обход начинается со случайного бакета и случайной позиции.
Исключение для удобства: `fmt` при печати сортирует ключи, поэтому вывод `fmt.Println(m)` стабилен.

**Термины**
- **случайный порядок обхода** — намеренная особенность map в Go

#### GO-9.3.8 Swiss Tables в Go 1.24
**Вопросы**
- [ ] Что изменилось в устройстве map в Go 1.24? · `go 1.24 swiss tables map`
- [ ] Что такое группа из 8 ячеек и контрольное слово с байтом на ячейку? · `swiss table control word groups`
- [ ] Как одна операция сравнивает сразу 8 байтов контрольного слова? · `swiss table parallel match`
- [ ] Почему в Swiss Tables открытая адресация вместо цепочек переполненных бакетов? · `swiss table open addressing`
- [ ] Как map разбивается на несколько небольших таблиц, чтобы рост был постепенным? · `go swiss map directory tables growth`
- [ ] Какие правила для программиста остались прежними (порядок, адрес, nil-map)? · `go 1.24 map behavior unchanged`

**Гуглить:** `go 1.24 swiss tables` · `go blog swiss tables` · `abseil swiss tables`

**Должен знать**
С Go 1.24 map устроена как Swiss Tables: ячейки собраны в группы по 8, у каждой группы есть контрольное слово — по байту на ячейку с 7 битами хеша и признаком «пусто/удалено/занято». Одной операцией процессора map сравнивает все 8 байтов сразу и находит кандидатов. Коллизии решаются открытой адресацией — проверяется следующая группа. Большая map делится на несколько таблиц до 1024 ячеек, и при росте перестраивается только одна из них.
Для программиста ничего не поменялось: порядок случайный, адрес элемента брать нельзя, nil-map нельзя писать. Map стала быстрее и экономнее.

**Термины**
- **Swiss Tables** *(новое)* — устройство map с Go 1.24: группы по 8 ячеек и контрольные байты
- **контрольное слово** — 8 байтов-меток для 8 ячеек группы

**Граница:** детали распределения по таблицам — одной фразой.

#### GO-9.3.9 Что на самом деле лежит в переменной map
**Вопросы**
- [ ] Что на самом деле лежит в переменной map и почему map в функции ведёт себя не как массив? · `go map is a pointer to runtime hmap`
- [ ] Сколько весят переменные со слайсом, map, пустой строкой и числом? · `size of slice map string int go`
- [ ] Есть ли в Go передача по ссылке? · `does go have pass by reference`
- [ ] Почему `make` для map возвращает значение, хотя внутри — указатель? · `go map value is pointer`
- [ ] Почему поэтому map, переданная в функцию, «общая», а слайс — лишь частично? · `map vs slice passed to function`

**Гуглить:** `go map is pointer` · `dave cheney there is no pass by reference in go`

**Должен знать**
Переменная map — это просто указатель на внутреннюю таблицу рантайма: 8 байт. Копия переменной — копия указателя, поэтому функция работает с теми же данными, и все изменения видны вызывающему. Nil-map — пустой указатель.
Сравни: слайс — 24 байта (указатель, длина, ёмкость), строка — 16, `int` — 8, map — 8. Передачи по ссылке в Go нет: всегда копируется значение, просто у map это значение — указатель.

**Термины**
- **map как указатель** — переменная map хранит адрес внутренней таблицы
