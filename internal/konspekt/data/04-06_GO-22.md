## GO-22. HTTP-сервер на net/http

### GO-22.1 Обработчики и маршруты

#### GO-22.1.1 Интерфейс http.Handler
**Вопросы**
- [ ] Что такое `http.Handler` и какой у него единственный метод? · `go http.Handler interface`
- [ ] Что получает `ServeHTTP(w http.ResponseWriter, r *http.Request)` и что с этим делает? · `ResponseWriter Request explained`
- [ ] Почему сервер в Go — это просто «значение, у которого есть `ServeHTTP`»? · `go http server handler concept`
- [ ] Почему в Go веб-серверы часто пишут без фреймворков? · `go standard library http no framework`

**Гуглить:** `go net/http tutorial` · `go http.Handler explained`

**Должен знать**
Пакет `net/http` — HTTP-сервер и клиент стандартной библиотеки. Обработчик — любое значение с методом `ServeHTTP(w http.ResponseWriter, r *http.Request)`: из `r` читают запрос, в `w` пишут ответ. Сервер для каждого запроса вызывает `ServeHTTP` нужного обработчика — вот и вся модель.
Стандартной библиотеки хватает для настоящих сервисов, поэтому в Go фреймворки не обязательны.

**Термины**
- **net/http** *(новое)* — стандартный пакет HTTP-сервера и клиента
- **Handler** *(новое)* — интерфейс обработчика с методом `ServeHTTP`

#### GO-22.1.2 http.HandlerFunc
**Вопросы**
- [ ] Чем `HandlerFunc` помогает? · `go http.HandlerFunc explained`
- [ ] Как обычная функция становится `http.Handler` через свой тип с методом? · `HandlerFunc type adapter`

**Гуглить:** `go HandlerFunc adapter`

**Должен знать**
`http.HandlerFunc` — свой тип на основе функции `func(http.ResponseWriter, *http.Request)` с методом `ServeHTTP`, который просто вызывает саму функцию. Поэтому `http.HandlerFunc(myFunc)` превращает обычную функцию в `Handler`. `mux.HandleFunc(pattern, f)` делает это за тебя.
Это частый пример метода у функционального типа.

**Термины**
- **HandlerFunc** — функциональный тип, реализующий `http.Handler`

#### GO-22.1.3 ServeMux и маршруты
**Вопросы**
- [ ] Как сделать маршрут `GET /users/{id}` на стандартной библиотеке? · `go 1.22 servemux pattern method path value`
- [ ] Как достать параметр пути (`r.PathValue("id")`)? · `r.PathValue`
- [ ] Что ответит `ServeMux`, если путь есть, а метод не тот (`405`)? · `servemux 405 method not allowed`
- [ ] Как выбирается маршрут, если подходят несколько (более конкретный побеждает)? · `servemux precedence most specific`
- [ ] Чем `/static/` отличается от `/static` и что значит `{path...}`? · `servemux trailing slash wildcard`

**Гуглить:** `go 1.22 routing enhancements` · `go servemux patterns`

**Должен знать**
`http.ServeMux` — маршрутизатор: по методу и пути запроса выбирает обработчик. С Go 1.22 маршрут может включать метод и параметры: `mux.HandleFunc("GET /users/{id}", h)`, а внутри — `r.PathValue("id")`. Если путь совпал, а метод нет, отвечает `405`. Из подходящих маршрутов выбирается самый конкретный.
Путь с `/` в конце (`/static/`) означает «всё, что начинается с этого», а `{path...}` захватывает остаток пути.

**Термины**
- **ServeMux** *(новое)* — маршрутизатор запросов стандартной библиотеки
- **параметр пути** — часть пути вида `{id}`, доступная через `r.PathValue`

#### GO-22.1.4 ListenAndServe
**Вопросы**
- [ ] Что делает `http.ListenAndServe(":8080", mux)`? · `go ListenAndServe`
- [ ] Что значит адрес `":8080"` (все адреса, порт 8080)? · `listen address colon port`
- [ ] Почему `ListenAndServe` не возвращается, пока сервер работает, и что возвращает при ошибке? · `ListenAndServe blocks returns error`

**Должен знать**

#### GO-22.1.5 Сколько горутин обслуживают запросы
**Вопросы**
- [ ] Сколько горутин обслуживают запросы и что это значит для общих данных сервера? · `go http server goroutine per connection`
- [ ] Почему обработчики одного сервера выполняются одновременно? · `concurrent handlers net/http`
- [ ] Что нужно сделать с map-кэшем, которым пользуются обработчики? · `shared map in http handlers mutex`
- [ ] Почему один медленный обработчик не блокирует остальных? · `slow handler does not block others`
- [ ] Ограничивает ли `net/http` число одновременных запросов сам? · `limit concurrent requests go server`

**Гуглить:** `go http server concurrency` · `data race in http handler`

**Должен знать**
Сервер запускает отдельную горутину на каждое соединение, поэтому обработчики работают одновременно. Медленный обработчик не мешает другим, но любые общие данные (map, счётчики, кэш в полях сервера) нужно защищать мьютексом или атомиками — иначе гонка данных.
Сам `net/http` число одновременных запросов не ограничивает: при всплеске горутин станет столько же, сколько запросов. Если нужно — ограничивают семафором в общей обёртке над обработчиками (о них — тема GO-22.2).

**Термины**
- **горутина на соединение** — модель конкурентности `net/http`

#### GO-22.1.7 Ответ: WriteHeader и Write, порядок вызовов
**Вопросы**
- [ ] Почему заголовки ответа нельзя менять после первого `Write`? · `go set header after write`
- [ ] Что будет, если не вызвать `WriteHeader` (код 200)? · `default status 200 go`
- [ ] Что значит предупреждение «superfluous response.WriteHeader call»? · `superfluous WriteHeader call`
- [ ] В каком порядке: `w.Header().Set(…)` → `w.WriteHeader(code)` → `w.Write(body)`? · `http response order header status body`
- [ ] Почему после ответа с ошибкой нужен `return`? · `return after http.Error`

**Гуглить:** `go ResponseWriter WriteHeader order`

**Должен знать**
Ответ уходит по порядку: заголовки, код, тело. Поэтому сначала `w.Header().Set("Content-Type", …)`, затем `w.WriteHeader(201)`, затем `w.Write(body)`. Первый `Write` без `WriteHeader` отправляет код 200 и заголовки — после этого менять их поздно. Повторный `WriteHeader` игнорируется с предупреждением.
Частый баг — отправить ошибку `http.Error(w, …)` и забыть `return`: обработчик продолжит писать в уже начатый ответ.

**Термины**
- **`http.ResponseWriter`** — интерфейс для записи заголовков, кода и тела ответа

#### GO-22.1.8 JSON на входе и на выходе
**Вопросы**

- [ ] Как запретить незнакомые поля (`DisallowUnknownFields`)? · `json DisallowUnknownFields`
- [ ] Как отправить JSON в ответ и не забыть `Content-Type`? · `go write json response`
- [ ] Чем `json.NewEncoder(w).Encode(v)` отличается от `json.Marshal` + `w.Write`? · `encoder vs marshal http`
- [ ] Как вынести запись JSON-ответа во вспомогательную функцию `writeJSON(w, code, v)`? · `go writeJSON helper`

**Гуглить:** `go json http handler` · `how to parse json request body go`

**Должен знать**
Вход: `dec := json.NewDecoder(r.Body); dec.DisallowUnknownFields(); if err := dec.Decode(&req); err != nil { … 400 … }`. Выход: `w.Header().Set("Content-Type", "application/json")`, `w.WriteHeader(code)`, `json.NewEncoder(w).Encode(resp)`. Encoder пишет прямо в ответ, без промежуточного слайса.

#### GO-22.1.9 Проверка входных данных и ответ с ошибкой
**Вопросы**
- [ ] Как ответить клиенту на некорректный запрос? · `go http validation error response`
- [ ] Чем отличаются ответы `400` (не разобрали JSON), `422` (данные не прошли проверку) и `404` (нет ресурса)? · `400 vs 422 vs 404 api`
- [ ] Почему внутреннюю ошибку нельзя отдавать клиенту как есть? · `don't leak internal errors to client`
- [ ] Как превратить ошибки слоя логики (`ErrNotFound`, `ErrConflict`) в коды ответа одним `switch` с `errors.Is`? · `map domain errors to http status`

**Гуглить:** `go http error handling patterns` · `map errors to status codes`

**Должен знать**
Обработчик проверяет вход сразу: JSON не разобрался — `400`; поля пустые или неверные — `422` (или `400`) со списком полей. Ошибки бизнес-логики переводятся в коды в одном месте: `errors.Is(err, ErrNotFound)` → `404`, `ErrConflict` → `409`, всё остальное → `500` с общим сообщением.
Текст внутренней ошибки клиенту не показывают: там может быть SQL, пути, адреса. Его пишут в лог, а клиенту — короткое «internal error».

**Термины**
- **перевод ошибок в коды** — сопоставление ошибок логики кодам HTTP

### GO-22.2 Middleware

#### GO-22.2.1 Middleware
**Вопросы**
- [ ] Что такое middleware и как его написать? · `go http middleware`
- [ ] Как выглядит сигнатура `func(next http.Handler) http.Handler`? · `middleware signature go`
- [ ] Напиши middleware, который логирует метод, путь и время обработки. · `go logging middleware`
- [ ] Как узнать код ответа в middleware (обёртка над `ResponseWriter`)? · `capture status code middleware go`
- [ ] Как это связано с замыканиями из GO-4.4? · `middleware closure`

**Гуглить:** `making and using http middleware go` · `go middleware status code`

**Должен знать**
Middleware — функция, которая принимает обработчик и возвращает новый, добавляющий поведение до и после: `func Logging(next http.Handler) http.Handler { return http.HandlerFunc(func(w, r) { start := time.Now(); next.ServeHTTP(w, r); log(r.Method, r.URL.Path, time.Since(start)) }) }`. Это замыкание вокруг `next`.
Чтобы записать код ответа, `ResponseWriter` оборачивают своим типом, который запоминает переданный в `WriteHeader` код.

**Термины**
- **middleware** *(новое)* — обёртка над обработчиком, добавляющая общее поведение

#### GO-22.2.2 Цепочка middleware
**Вопросы**
- [ ] В каком порядке выполняются middleware в цепочке? · `middleware order execution`
- [ ] Что выполнится первым при `Logging(Auth(Recover(handler)))`: «до» какого и «после» какого? · `nested middleware onion`
- [ ] Почему перехват паники ставят внешним, а логирование — ещё внешнее или рядом? · `recover middleware outermost`
- [ ] Как middleware может прервать цепочку (например, вернуть `401` и не звать `next`)? · `middleware short circuit`

**Гуглить:** `go middleware chain order` · `middleware onion model`

**Должен знать**
Middleware вкладываются как луковица: в `Logging(Auth(h))` запрос проходит Logging-«до», Auth-«до», `h`, Auth-«после», Logging-«после». Middleware может прервать цепочку — ответить сам и не вызывать `next` (так делает проверка доступа).
Перехват паники ставят снаружи бизнес-обработчиков, чтобы он ловил панику любого из них, а логирование — снаружи, чтобы записать и ответы 500.

**Термины**
- **цепочка middleware** — вложенные обёртки, выполняющиеся по принципу луковицы

#### GO-22.2.3 recover в middleware
**Вопросы**
- [ ] Как поймать панику в обработчике, чтобы сервер не упал? · `go recover middleware`
- [ ] Что `net/http` делает с паникой сам (обрывает соединение и пишет в лог)? · `net/http recovers panics`
- [ ] Почему всё равно пишут свой middleware (ответ `500`, свой формат логов, стек)? · `custom recovery middleware why`
- [ ] Поймает ли такой middleware панику в горутине, запущенной из обработчика? · `panic in goroutine from handler not recovered`

**Гуглить:** `go panic recovery middleware` · `net/http panic handling`

**Должен знать**
`net/http` сам перехватывает панику в обработчике: пишет её в лог и обрывает соединение, клиент получает обрыв вместо ответа. Свой middleware делает это правильно: `defer func() { if v := recover(); v != nil { log(v, debug.Stack()); http.Error(w, "internal error", 500) } }()` — клиент получает `500`, а лог — в формате сервиса.
Горутины, которые обработчик запустил сам, этот `recover` не защищает: паника в них уронит весь сервер.

**Термины**
- **middleware восстановления** — перехват паники с ответом `500` и записью стека

#### GO-22.2.4 context запроса
**Вопросы**
- [ ] Что произойдёт с context запроса, если клиент оборвал соединение? · `r.Context cancelled client disconnect`
- [ ] Почему `r.Context()` нужно передавать во все запросы к базе и другим сервисам? · `pass request context to db`
- [ ] Как middleware добавляет в контекст значения (номер запроса, пользователя) через `r.WithContext`? · `middleware add value to request context`
- [ ] Когда контекст запроса отменяется, даже если клиент не уходил? · `request context cancelled after handler returns`

**Гуглить:** `go http request context` · `context cancellation http handler`

**Должен знать**
У каждого запроса свой контекст `r.Context()`. Он отменяется, когда клиент оборвал соединение или когда обработчик вернулся. Передавая его в запросы к базе и в вызовы других сервисов, ты автоматически прекращаешь ненужную работу для ушедшего клиента.

### GO-22.3 Сервер, готовый к нагрузке

#### GO-22.3.1 Таймауты сервера
**Вопросы**
- [ ] Какие таймауты нужны серверу и что будет без них? · `go http server timeouts`
- [ ] Что значат `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`? · `ReadHeaderTimeout ReadTimeout WriteTimeout IdleTimeout`
- [ ] Что такое атака медленного клиента (Slowloris) и какой таймаут от неё защищает? · `slowloris go ReadHeaderTimeout`
- [ ] Какие значения таймаутов у сервера по умолчанию (никаких)? · `go http server default no timeout`
- [ ] Как ограничить время работы самого обработчика (`http.TimeoutHandler` или context)? · `http.TimeoutHandler`

**Гуглить:** `complete guide to go net/http timeouts` · `slowloris`

**Должен знать**
По умолчанию у `http.Server` таймаутов нет: клиент, который присылает заголовки по байту в минуту, держит соединение и горутину вечно, а тысяча таких клиентов кладёт сервер. `ReadHeaderTimeout` — время на заголовки (главная защита), `ReadTimeout` — на весь запрос с телом, `WriteTimeout` — на запись ответа, `IdleTimeout` — сколько держать неактивное соединение.

**Термины**
- **таймауты сервера** — пределы времени на чтение, запись и простой соединения

#### GO-22.3.2 Плавная остановка: Shutdown и сигналы
**Вопросы**
- [ ] Как остановить сервер по SIGTERM, не оборвав запросы в работе? · `go http server graceful shutdown`
- [ ] Что делает `srv.Shutdown(ctx)`: перестаёт принимать новые, ждёт текущие? · `server.Shutdown behavior`
- [ ] Почему после `Shutdown` `ListenAndServe` возвращает `http.ErrServerClosed`, и это не ошибка? · `ErrServerClosed`
- [ ] Как ограничить время ожидания через context с таймаутом? · `shutdown with timeout context`
- [ ] Что ещё нужно закрыть после сервера (воркеры, база)? · `shutdown order server workers db`

**Гуглить:** `go graceful shutdown http server` · `signal.NotifyContext shutdown`

**Должен знать**
Схема: `ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)`; сервер запускается в горутине; `main` ждёт `<-ctx.Done()`, затем `shCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)` и `srv.Shutdown(shCtx)`. `Shutdown` закрывает приём новых соединений, закрывает простаивающие и ждёт, пока текущие запросы закончатся (или истечёт контекст).
`ListenAndServe` после этого возвращает `http.ErrServerClosed` — это нормальный выход. После сервера останавливают фоновые воркеры и закрывают базу.

**Термины**
- **`Shutdown`** — плавная остановка `http.Server`
- **`http.ErrServerClosed`** — нормальное завершение после `Shutdown`

#### GO-22.3.3 Ограничение размера тела запроса
**Вопросы**
- [ ] Как не дать клиенту прислать тело в гигабайт? · `go limit request body size`
- [ ] Что делает `http.MaxBytesReader` и какую ошибку вернёт чтение при превышении? · `http.MaxBytesReader`
- [ ] Почему опасно `io.ReadAll(r.Body)` без ограничения? · `io.ReadAll request body dos`
- [ ] Какой код ответа вернуть при превышении (`413`)? · `413 payload too large`

**Гуглить:** `go MaxBytesReader` · `limit request body go`

**Должен знать**
Без ограничения клиент может прислать тело любого размера, а `io.ReadAll` или разбор JSON попытаются прочитать его целиком в память. `r.Body = http.MaxBytesReader(w, r.Body, 1<<20)` ограничивает тело мегабайтом: чтение сверх предела вернёт ошибку, и можно ответить `413`.
Ограничение ставят в общем middleware на все обработчики.

**Термины**
- **`http.MaxBytesReader`** — ограничитель размера тела запроса
