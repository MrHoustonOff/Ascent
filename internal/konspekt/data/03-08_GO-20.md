## GO-20. Паттерны конкурентности

### GO-20.1 Готовые схемы

#### GO-20.1.1 Пул воркеров
**Вопросы**
- [ ] Напиши по памяти пул воркеров: как раздать задачи и как собрать результаты? · `go worker pool example`
- [ ] Зачем ограничивать число горутин, если они дешёвые (база, внешний сервис, память)? · `why limit goroutines worker pool`
- [ ] Кто закрывает канал задач и кто — канал результатов? · `worker pool close channels who`
- [ ] Как пул должен завершаться по context? · `worker pool context cancellation`
- [ ] Как выбрать число воркеров? · `how many workers go`

**Гуглить:** `go by example worker pools` · `golang worker pool context`

**Должен знать**
Пул воркеров — N горутин читают задачи из одного канала `jobs` и пишут результаты в канал `results`. Отправитель задач закрывает `jobs`, когда задачи кончились; воркеры выходят из `for range jobs`. Отдельная горутина ждёт всех воркеров через `WaitGroup` и закрывает `results`, а `main` читает `results` через `range`.
Каждый воркер также слушает `ctx.Done()` и выходит при отмене. Число воркеров выбирают по узкому месту: для запросов к базе — по числу соединений, для вычислений — по числу ядер.

**Термины**
- **пул воркеров** *(новое)* — фиксированное число горутин, разбирающих общую очередь задач
- **воркер** — горутина-обработчик задач

#### GO-20.1.2 Конвейер
**Вопросы**
- [ ] Что такое конвейер? Сделай конвейер чисел: генератор → возведение в квадрат → печать. · `go pipeline pattern`
- [ ] Как каждая стадия закрывает свой выходной канал? · `pipeline stage close output channel`
- [ ] Как остановить весь конвейер досрочно, если потребитель ушёл? · `pipeline cancellation done channel`
- [ ] Почему конвейер — это ещё и способ обрабатывать данные потоком, не держа всё в памяти? · `streaming pipeline memory`

**Гуглить:** `go blog pipelines` · `go concurrency patterns pipeline`

**Должен знать**
Конвейер — цепочка стадий, соединённых каналами: каждая стадия — горутина, которая читает из входного канала, обрабатывает и пишет в выходной, а закончив — закрывает его. `gen(1..n)` → `square` → `print`. Данные текут по одному, и в памяти не нужно держать всё сразу.
Чтобы конвейер можно было остановить досрочно, каждая стадия отправляет через `select` с `ctx.Done()` — иначе стадии, которым некуда писать, зависнут навсегда.

**Термины**
- **конвейер** *(новое)* — цепочка горутин-стадий, связанных каналами
- **стадия** — горутина конвейера: читает вход, пишет выход

#### GO-20.1.3 Fan-out и fan-in
**Вопросы**
- [ ] Что такое fan-out и fan-in? · `fan out fan in go`
- [ ] Слей N каналов в один. · `merge n channels golang`
- [ ] Когда закрывать общий выходной канал при слиянии? · `close merged channel waitgroup`
- [ ] Как распараллелить медленную стадию конвейера через fan-out? · `parallelize pipeline stage`

**Гуглить:** `go fan-in fan-out` · `go merge channels`

**Должен знать**
Fan-out — несколько горутин читают из одного канала и делят работу (так устроен пул воркеров). Fan-in — значения из нескольких каналов сливаются в один: на каждый входной канал своя горутина пересылает значения в общий выход, а `WaitGroup` и ещё одна горутина закрывают выход, когда все входы исчерпаны.
Вместе они распараллеливают медленную стадию конвейера: раздать её работу нескольким горутинам и собрать результаты обратно.

**Термины**
- **fan-out** *(новое)* — раздача работы из одного канала нескольким горутинам
- **fan-in** *(новое)* — слияние нескольких каналов в один

#### GO-20.1.4 Семафор на буферизованном канале
**Вопросы**
- [ ] Как ограничить число одновременно работающих горутин? · `limit concurrent goroutines semaphore channel`
- [ ] Как работает `sem := make(chan struct{}, 10)`: взять — отправить, освободить — получить? · `buffered channel semaphore`
- [ ] Чем семафор отличается от пула воркеров? · `semaphore vs worker pool`
- [ ] Что есть готового (`golang.org/x/sync/semaphore`)? · `x/sync semaphore weighted`
- [ ] Сделай свою `WaitGroup` на семафоре. · `implement waitgroup with channels`

**Гуглить:** `go semaphore pattern` · `x/sync/semaphore`

**Должен знать**
Семафор — счётчик разрешений: работать одновременно могут не больше N горутин. На буферизованном канале: перед работой `sem <- struct{}{}` (если занято N мест — ждём), после — `<-sem`. Горутин можно запустить сколько угодно, но параллельно работает не больше N.
В отличие от пула, горутины создаются под каждую задачу; это проще, когда задач немного. Есть готовый `x/sync/semaphore` с весами.

**Термины**
- **семафор** *(новое)* — ограничитель числа одновременных участников

#### GO-20.1.5 errgroup
**Вопросы**
- [ ] Что даёт `errgroup` по сравнению с `WaitGroup`? · `errgroup vs waitgroup`
- [ ] Отмени группу задач при первой ошибке через `errgroup.WithContext`. · `errgroup withcontext cancel on error`
- [ ] Что вернёт `g.Wait()`, если ошибок было несколько? · `errgroup first error`
- [ ] Как ограничить число одновременных задач (`g.SetLimit`)? · `errgroup SetLimit`

**Гуглить:** `golang errgroup` · `x/sync/errgroup example`

**Должен знать**
`errgroup.Group` из `golang.org/x/sync` — `WaitGroup` с ошибками: `g.Go(func() error { … })` запускает задачу, `g.Wait()` ждёт все и возвращает первую ошибку. С `errgroup.WithContext(ctx)` получаешь контекст, который отменится при первой ошибке, — остальные задачи увидят это и остановятся.
`g.SetLimit(n)` ограничивает число одновременно работающих задач — пул воркеров в одну строку.

**Термины**
- **errgroup** *(новое)* — группа горутин с ожиданием, первой ошибкой и общей отменой

#### GO-20.1.6 Сигнал всем горутинам через закрытие канала
**Вопросы**
- [ ] Как разом дать сигнал остановки всем горутинам? · `broadcast close channel signal`
- [ ] Почему закрытие работает для любого числа получателей, а отправка — только для одного? · `close vs send broadcast`
- [ ] Почему для этого берут `chan struct{}`? · `done channel struct{}`
- [ ] Как это связано с `ctx.Done()`? · `ctx.Done is closed channel`

**Гуглить:** `go done channel close broadcast`

**Должен знать**
Отправка в канал будит одного получателя, а закрытие — всех сразу: чтение из закрытого канала мгновенно возвращается у каждого. Поэтому сигнал «все стоп» — это `close(done)`, где `done` — `chan struct{}` (значения не нужны, только факт). Каждая горутина слушает `<-done` в своём `select`.
`ctx.Done()` устроен ровно так же — это и есть закрываемый канал.

**Термины**
- **сигнальный канал** — `chan struct{}`, который закрывают, чтобы оповестить всех

#### GO-20.1.7 Плавная остановка воркеров
**Вопросы**
- [ ] Как плавно остановить воркеры, не потеряв задачи? · `graceful shutdown workers go`
- [ ] Чем «перестать брать новые задачи и доделать начатые» отличается от «бросить всё»? · `drain vs abort`
- [ ] В каком порядке: закрыть приём задач → дождаться воркеров → закрыть результаты? · `shutdown order channels waitgroup`
- [ ] Как ограничить время плавной остановки, чтобы она не длилась вечно? · `graceful shutdown timeout`

**Гуглить:** `golang graceful shutdown worker pool` · `drain channel shutdown`

**Должен знать**
Плавная остановка — перестать принимать новые задачи, доделать начатые и только потом выйти. Порядок: закрыть канал задач (воркеры доберут оставшееся и выйдут из `range`) → `wg.Wait()` → закрыть канал результатов. Задачи не теряются, результаты не обрываются.
На случай, если что-то зависло, ожидание ограничивают таймаутом: по истечении отменяют контекст и выходят принудительно.

**Термины**
- **плавная остановка** *(новое)* — завершение с доделкой начатой работы

**Позже:** плавная остановка сервера по сигналу — GO-22.3.2.

#### GO-20.1.8 Сбор результатов с сохранением порядка
**Вопросы**
- [ ] Запусти N задач параллельно и верни результаты в исходном порядке. · `parallel map preserve order go`
- [ ] Почему можно писать в разные элементы одного слайса из разных горутин без мьютекса? · `write different slice indices goroutines safe`
- [ ] Как передать номер задачи вместе с результатом через канал? · `result with index channel`
- [ ] Как вернуть ошибку отдельной задачи, не теряя остальные результаты? · `collect results and errors`

**Гуглить:** `go parallel processing ordered results`

**Должен знать**
Самый простой способ — заранее создать слайс результатов длиной N и дать каждой горутине записать в свой элемент `res[i]`: разные элементы — разная память, гонки нет, а после `wg.Wait()` всё видно. Порядок сохраняется сам.
Если результаты идут через канал, вместе с ними передают номер задачи и раскладывают по месту. Ошибки хранят рядом — в таком же слайсе или в поле результата.

**Термины**
- **сбор по номеру** — каждая горутина пишет результат в свой элемент слайса

### GO-20.2 Время

#### GO-20.2.1 time.Timer
**Вопросы**
- [ ] Чем `time.Timer` отличается от `time.Ticker`? · `timer vs ticker go`
- [ ] Как создать таймер, остановить его (`Stop`) и перезапустить (`Reset`)? · `time.NewTimer Stop Reset`
- [ ] Что изменилось в Go 1.23 с `Stop` и `Reset` (больше не нужно вычитывать канал)? · `go 1.23 timer reset changes`
- [ ] Что делает `time.AfterFunc`? · `time.AfterFunc`

**Гуглить:** `golang time.Timer` · `go 1.23 timers`

**Должен знать**
`time.NewTimer(d)` — одноразовый таймер: через `d` в его канал `C` придёт значение. `Stop()` отменяет, `Reset(d)` перезапускает. С Go 1.23 канал таймера стал небуферизованным, и после `Stop`/`Reset` старое значение гарантированно не придёт — раньше его приходилось вычитывать вручную.
`time.AfterFunc(d, f)` вызывает `f` в отдельной горутине по истечении времени.

**Термины**
- **`time.Timer`** — одноразовое срабатывание через заданное время

#### GO-20.2.2 time.Ticker и ограничение частоты
**Вопросы**
- [ ] Как сделать «не чаще N раз в секунду»? · `rate limit go ticker`
- [ ] Что будет со значениями тикера, если получатель не успевает их читать? · `ticker drops ticks slow receiver`
- [ ] Почему тикер нужно останавливать (`defer t.Stop()`)? · `stop ticker`
- [ ] Что даёт `golang.org/x/time/rate` (ведро с жетонами) по сравнению с тикером? · `x/time/rate limiter`

**Гуглить:** `golang ticker` · `golang rate limiting` · `token bucket`

**Должен знать**
`time.NewTicker(d)` присылает значение в канал каждые `d`. Если получатель не успевает, лишние тики пропускаются, а не копятся. Ограничение частоты на стандартной библиотеке: перед каждой операцией ждать `<-ticker.C` — не чаще одного раза в `d`. Тикер останавливают через `Stop`, когда он больше не нужен.
Для всплесков и гибких лимитов есть `x/time/rate` — ограничитель по принципу «ведра с жетонами», которое пополняется с постоянной скоростью.

**Термины**
- **тикер** *(новое)* — периодическое срабатывание через равные промежутки
- **ограничение частоты** — не больше N операций за промежуток времени

**Позже:** ограничение частоты в сервисе — ИНФРА-2.3.5.

#### GO-20.2.3 time.After в цикле
**Вопросы**
- [ ] Чем был опасен `time.After` в цикле и что поменялось в Go 1.23? · `time.After in loop memory leak`
- [ ] Почему `select` с `time.After` в цикле создаёт новый таймер на каждой итерации? · `time.After creates new timer each call`
- [ ] Чем таймаут «на всю операцию» отличается от таймаута «с последнего события»? · `overall timeout vs idle timeout`
- [ ] Как переписать цикл на один таймер с `Reset` или на context? · `reuse timer reset loop`

**Гуглить:** `time.After leak` · `go 1.23 timer garbage collection`

**Должен знать**
Каждый вызов `time.After` создаёт новый таймер. До Go 1.23 таймер жил до срабатывания, даже если его канал уже никто не ждал, — в частом цикле с долгим таймаутом они копились тысячами. С Go 1.23 неиспользуемые таймеры собирает сборщик мусора.
Логическая ловушка осталась: `time.After` внутри `for`-`select` даёт таймаут «с последнего события», а не на всю операцию. Для общего срока создают один таймер или контекст до цикла.

**Термины**
- **таймаут простоя** — срабатывает, если давно не было событий

### GO-20.3 Найди баг

#### GO-20.3.1 Гонка на общем счётчике
**Вопросы**
- [ ] Найди баг: несколько горутин делают `counter++`. · `go race counter goroutines`
- [ ] Что выведет такая программа и почему ответ разный от запуска к запуску? · `nondeterministic counter result`
- [ ] Исправь тремя способами: мьютекс, атомик, подсчёт в каждой горутине отдельно. · `fix counter race mutex atomic`
- [ ] Что выведет код с горутинами и `Printf` без ожидания? · `goroutines printf no wait`

**Гуглить:** `go data race counter example` · `go race detector example`

**Должен знать**
`counter++` из нескольких горутин — гонка данных: итог меньше ожидаемого и разный от запуска к запуску, детектор гонок ловит её сразу. Исправления: `sync.Mutex` вокруг прибавления; `atomic.Int64`; или каждая горутина считает в свою переменную, а результаты складываются после `Wait`.
Тот же код без ожидания вообще ничего не обещает: `main` может выйти раньше, чем горутины что-то напечатают.

**Термины**
- **гонка на счётчике** — классический баг собеса: `counter++` без синхронизации

#### GO-20.3.2 wg.Add внутри горутины
**Вопросы**
- [ ] Найди баг: `wg.Add` вызывается внутри запущенной горутины. · `wg.Add inside goroutine bug`
- [ ] Почему `Wait` может вернуться до того, как горутины начали работу? · `wait returns early waitgroup`
- [ ] Исправь двумя способами: `Add` до `go` или `wg.Go`. · `fix waitgroup add placement`

**Гуглить:** `waitgroup add race` · `go vet waitgroup`

**Должен знать**
Если `wg.Add(1)` стоит внутри горутины, `main` может дойти до `wg.Wait()`, пока счётчик ещё 0, — и выйти, не дождавшись. Баг проявляется не всегда, что делает его коварным. Исправление: `wg.Add` перед `go` (или один `wg.Add(n)` до цикла), а с Go 1.25 — `wg.Go`.

**Термины**
- **ранний выход из `Wait`** — счётчик увеличили слишком поздно

#### GO-20.3.4 Чтение из канала, в который никто не пишет
**Вопросы**
- [ ] Найди баг: горутина читает канал, в который при ошибке никто не отправляет. · `goroutine blocked forever on receive`
- [ ] Почему на ранней ветке выхода (ошибка, `return`) часто забывают отправить или закрыть? · `forgot to send on error path`
- [ ] Как исправить: закрывать канал через `defer` у отправителя или слушать `ctx.Done()`? · `defer close channel sender`

**Гуглить:** `goroutine leak receive never sent`

**Должен знать**
Получатель ждёт значение, а отправитель на какой-то ветке (обычно при ошибке) ушёл, ничего не отправив и не закрыв канал. Если ждёт `main` — программа упадёт с «deadlock», если другая горутина — она утечёт молча.
Исправление: отправитель закрывает канал через `defer` на любом пути, а получатель ждёт в `select` вместе с `ctx.Done()`.

**Термины**
- **вечное ожидание получателя** — канал, в который никто не напишет

#### GO-20.3.5 Отправка без получателя и утёкшая горутина
**Вопросы**
- [ ] Найди баг: горутина отправляет результат в небуферизованный канал, а `main` уже ушёл по таймауту. · `goroutine leak send after timeout`
- [ ] Почему горутина застрянет на отправке навсегда? · `send blocks forever no receiver`
- [ ] Исправь двумя способами: буфер на одно значение или `select` с `ctx.Done()`. · `buffered channel size 1 fix leak`

**Гуглить:** `goroutine leak timeout send` · `go leak buffered channel 1`

**Должен знать**
`main` ждёт результат с таймаутом и уходит по `time.After`. Горутина позже пытается отправить в небуферизованный канал — получателя больше нет, и она ждёт вечно. Это утечка, которая растёт с каждым таймаутом.
Исправления: канал с буфером на одно значение — отправка не ждёт; или отправка через `select` с `case <-ctx.Done(): return`.

**Термины**
- **утёкшая горутина** — горутина, навсегда застрявшая на отправке или получении

#### GO-20.3.6 Повторный Lock в той же горутине
**Вопросы**
- [ ] Найди баг: метод под `Lock` вызывает другой метод, который тоже берёт `Lock`. · `go mutex lock reentrant deadlock method`
- [ ] Почему в Go это гарантированная взаимная блокировка? · `go mutex not recursive`
- [ ] Как исправить: внутренний метод без блокировки (`fooLocked`), который вызывают уже под мьютексом? · `locked suffix method convention`

**Гуглить:** `go recursive mutex deadlock` · `go mutex reentrant`

**Должен знать**
Мьютекс в Go не повторный: если метод `A` взял `mu.Lock()` и вызвал метод `B`, который тоже делает `mu.Lock()`, горутина ждёт сама себя вечно. Исправление — разделить: публичные методы берут мьютекс, а внутренняя логика вынесена в неблокирующие функции (часто с суффиксом `Locked`), которые вызывают уже под мьютексом.

**Термины**
- **повторный захват** — `Lock` того же мьютекса той же горутиной; в Go — взаимная блокировка

#### GO-20.3.7 Конкурентная запись в map
**Вопросы**
- [ ] Найди баг: несколько горутин пишут в одну map. · `concurrent map writes bug`
- [ ] Чем это закончится: паникой, фатальной ошибкой или тихой порчей? · `concurrent map writes fatal`
- [ ] Исправь тремя способами: мьютекс, `sync.Map`, отдельные map и слияние после. · `fix concurrent map writes`

**Гуглить:** `fatal error concurrent map writes fix`

**Должен знать**
Одновременная запись в map — фатальная ошибка `concurrent map writes`, которую не перехватить. Исправления: защитить map мьютексом; для особых случаев — `sync.Map`; или дать каждой горутине свою map и слить их после `Wait`.

**Термины**
- **запись в общую map** — классический баг: map без защиты из нескольких горутин

#### GO-20.3.8 Забытый cancel и утечка таймера
**Вопросы**
- [ ] Найди баг: `context.WithTimeout` в цикле без вызова `cancel`. · `context withtimeout loop without cancel leak`
- [ ] Почему `defer cancel()` внутри цикла — тоже плохо? · `defer cancel in loop`
- [ ] Как правильно: вынести тело цикла в функцию с `defer cancel()` или вызывать `cancel()` в конце итерации? · `cancel per iteration`

**Гуглить:** `go vet lostcancel loop` · `context leak loop`

**Должен знать**
Каждый `WithTimeout` создаёт таймер и запись у родителя. Без `cancel()` они живут до истечения срока, и цикл накапливает их тысячами. `defer cancel()` прямо в цикле не помогает — отложенные вызовы выполнятся только при выходе из функции.
Правильно: тело цикла — отдельная функция с `defer cancel()`, или явный `cancel()` в конце каждой итерации.

**Термины**
- **утечка контекста** — незакрытые контексты держат таймеры и связи с родителем

#### GO-20.3.9 Поиск утечек горутин инструментами
**Вопросы**
- [ ] Как найти утёкшие горутины в работающей программе? · `find goroutine leaks production`
- [ ] Что покажет растущий `runtime.NumGoroutine()`? · `numgoroutine growing leak`
- [ ] Как снять дамп всех горутин и найти, где они стоят? · `goroutine dump stack traces`
- [ ] Как проверить отсутствие утечек в тестах (`goleak`)? · `uber goleak tests`
- [ ] Что за профиль утечек горутин появился в Go 1.26–1.27? · `go goroutineleak profile`

**Гуглить:** `detect goroutine leaks go` · `uber-go/goleak` · `goroutineleak profile go 1.26`

**Должен знать**
Первый признак утечки — число горутин растёт и не падает. Дальше снимают дамп всех горутин с их стеками и смотрят, где их много стоит в одном месте (обычно на отправке или получении из канала). В тестах `goleak` проверяет, что после теста не осталось лишних горутин.
С Go 1.26 экспериментом, а с Go 1.27 штатно есть профиль `goroutineleak`: рантайм сам находит горутины, которые ждут то, что уже никогда не случится.

**Термины**
- **дамп горутин** — стеки всех горутин в момент снимка
