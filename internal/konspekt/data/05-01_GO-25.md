### GO-25.1 Запросы из Go

#### GO-25.1.1 Пакет database/sql
**Вопросы**
- [ ] Что такое `*sql.DB`: одно соединение или что-то другое? · `go sql.DB is a pool`
- [ ] Почему `sql.Open` не подключается к базе и как проверить соединение (`PingContext`)? · `sql.Open does not connect ping`
- [ ] Почему `*sql.DB` создают один раз на всю программу и не закрывают после каждого запроса? · `sql.DB long lived reuse`
- [ ] Почему `database/sql` одинаков для любой базы, а различается только драйвер? · `database/sql driver interface`

**Гуглить:** `go database/sql tutorial` · `go-database-sql.org`

**Должен знать**
`database/sql` — общий интерфейс стандартной библиотеки к SQL-базам; конкретную базу подключает драйвер. `*sql.DB` — не одно соединение, а набор соединений, которыми он управляет сам; им можно пользоваться из всех горутин. `sql.Open` лишь создаёт его, не подключаясь; проверить доступность базы — `db.PingContext(ctx)` при запуске.
`*sql.DB` создают один раз в `main` и передают тем, кому он нужен; закрывают при остановке программы.

**Термины**
- **database/sql** *(новое)* — стандартный пакет доступа к SQL-базам
- **`*sql.DB`** — управляемый набор соединений к базе, общий для всей программы

#### GO-25.1.3 Пул соединений
**Вопросы**
- [ ] Как работает пул соединений и что будет, когда все соединения заняты? · `go sql connection pool how it works`
- [ ] Почему открывать соединение с Postgres на каждый запрос дорого? · `postgres connection cost process per connection`
- [ ] Когда соединение возвращается в пул (после `Close` строк, после `Commit`)? · `when connection returned to pool`
- [ ] Почему незакрытые строки и висящие транзакции «съедают» пул? · `connection pool exhaustion`

**Гуглить:** `go sql connection pool` · `postgresql process per connection`

**Должен знать**
Пул держит набор открытых соединений и выдаёт их запросам: свободное — сразу, нет свободного — открывает новое, если не превышен предел, иначе запрос ждёт освобождения (пока не отменится контекст). Новое соединение с Postgres дорогое: на каждое база запускает отдельный процесс.
Соединение возвращается в пул, когда запрос полностью завершён: строки прочитаны и закрыты, транзакция зафиксирована или откачена. Незакрытые строки и забытые транзакции держат соединения, и скоро все запросы встают в очередь.

**Термины**
- **пул соединений** *(новое)* — набор открытых соединений, переиспользуемых запросами

#### GO-25.1.5 Query, QueryRow и Exec
**Вопросы**
- [ ] Чем `Query` отличается от `QueryRow` и `Exec`? · `go sql Query QueryRow Exec`
- [ ] Как прочитать строки в цикле `for rows.Next() { rows.Scan(&…) }`? · `go rows.Next Scan`
- [ ] Почему нужно проверить `rows.Err()` после цикла? · `rows.Err after loop`
- [ ] Как узнать число изменённых строк после `Exec` (`RowsAffected`)? · `go Exec RowsAffected`
- [ ] Как получить `id` вставленной строки в Postgres (`QueryRow` с `RETURNING`)? · `go postgres insert returning id`

**Гуглить:** `go database/sql query examples` · `postgres returning id go`

**Должен знать**
`Query` — для запросов, возвращающих много строк: читаешь в цикле `for rows.Next()` с `rows.Scan(&a, &b)` и после цикла проверяешь `rows.Err()`. `QueryRow` — для одной строки: `db.QueryRowContext(ctx, q, id).Scan(&u.Name)`. `Exec` — для запросов без результата (`UPDATE`, `DELETE`): возвращает `Result` с `RowsAffected()`.
В Postgres `id` новой строки получают `QueryRow` с `INSERT … RETURNING id`, а не `LastInsertId`.

**Термины**
- **`Query` / `QueryRow` / `Exec`** — много строк / одна строка / без результата

#### GO-25.1.6 Закрыть rows
**Вопросы**
- [ ] Что будет, если не закрыть `rows`? · `go forgot rows.Close`
- [ ] Где ставить `defer rows.Close()`? · `defer rows.Close placement`
- [ ] Почему ранний `return` из цикла чтения без `Close` держит соединение? · `return inside rows loop leak`
- [ ] Чем это похоже на незакрытое тело HTTP-ответа? · `rows close vs resp body close`

**Гуглить:** `go rows.Close importance` · `database/sql connection leak`

**Должен знать**
Пока `rows` не закрыты, соединение занято и не возвращается в пул. Если выйти из цикла раньше (ошибка `Scan`, нашли что нужно) без закрытия, соединение утекает; несколько таких утечек — и пул исчерпан, сервис встал. Правило: сразу после проверки ошибки `Query` — `defer rows.Close()`.
Это та же история, что с телом HTTP-ответа: открытый поток держит ресурс.

**Термины**
- **`rows.Close`** — освобождение соединения после чтения результата

#### GO-25.1.7 sql.ErrNoRows
**Вопросы**
- [ ] Как отличить «строка не найдена» от настоящей ошибки? · `go sql.ErrNoRows`
- [ ] Кто возвращает `sql.ErrNoRows` (`QueryRow…Scan`) и кто нет (`Query` просто без строк)? · `ErrNoRows QueryRow only`
- [ ] Как перевести её в ошибку своего слоя (`ErrNotFound`) и потом в `404`? · `map sql.ErrNoRows to not found`
- [ ] Как проверять: `errors.Is(err, sql.ErrNoRows)` (или `pgx.ErrNoRows`)? · `errors.Is sql.ErrNoRows`

**Гуглить:** `go sql.ErrNoRows handling`

**Должен знать**
`QueryRow(…).Scan` возвращает sentinel-ошибку `sql.ErrNoRows`, если строки нет (в `pgx` — `pgx.ErrNoRows`). Это не сбой, а ответ «не найдено»: проверяют `errors.Is(err, sql.ErrNoRows)` и превращают в ошибку своего слоя `ErrNotFound`, которую обработчик переведёт в `404`. `Query` без строк ошибки не даёт — цикл просто не выполнится.

**Термины**
- **`sql.ErrNoRows`** — sentinel-ошибка «строка не найдена»

#### GO-25.1.8 NULL в Go: sql.Null-типы и указатели
**Вопросы**
- [ ] Как прочитать NULL из базы в Go? · `go scan null value`
- [ ] Что будет, если сканировать NULL в обычный `string`? · `converting NULL to string is unsupported`
- [ ] Чем `sql.NullString` отличается от `*string`? · `sql.NullString vs pointer`
- [ ] Как `sql.Null[T]` (Go 1.22) обобщает эти типы? · `go 1.22 sql.Null generic`
- [ ] Почему проще избегать NULL в схеме, где это возможно? · `avoid nullable columns`

**Гуглить:** `go sql null types` · `sql.Null generic`

**Должен знать**
NULL нельзя положить в обычный `string` или `int` — `Scan` вернёт ошибку. Варианты: `sql.NullString` (поля `String` и `Valid`), с Go 1.22 — общий `sql.Null[T]`, или указатель `*string` (nil — NULL). Указатели удобнее в JSON, Null-типы — без лишних выделений памяти.
Лучший вариант — не допускать NULL там, где он не нужен по смыслу: `NOT NULL` в схеме избавляет от этих проверок.

**Термины**
- **`sql.Null…`** — типы для значений, которые могут быть NULL

#### GO-25.1.9 SQL-инъекция и плейсхолдеры
**Вопросы**
- [ ] Что такое SQL-инъекция и почему плейсхолдеры от неё защищают? · `sql injection explained`
- [ ] Почему `fmt.Sprintf("… WHERE name = '%s'", name)` — дыра? · `sprintf sql injection go`
- [ ] Как пишутся плейсхолдеры в Postgres (`$1`, `$2`)? · `postgres placeholders $1`
- [ ] Почему плейсхолдер нельзя использовать для имени таблицы или столбца и как тогда быть (белый список)? · `placeholder for column name whitelist`
- [ ] Как безопасно сделать `IN` по списку значений (`= ANY($1)`)? · `postgres any array placeholder go`

**Гуглить:** `owasp sql injection` · `go prevent sql injection`

**Должен знать**
SQL-инъекция — данные пользователя вклеены в текст запроса и становятся его частью: имя `' OR 1=1 --` превращает запрос «найти пользователя» в «выдать всех». Плейсхолдеры (`$1`, `$2` в Postgres) передают значения отдельно от текста запроса — база никогда не исполняет их как SQL.
Поэтому значения — только через плейсхолдеры, никакого `Sprintf`. Имена таблиц и столбцов плейсхолдерами не передаются — их выбирают из белого списка в коде. Список значений — `WHERE id = ANY($1)` со слайсом.

**Термины**
- **SQL-инъекция** *(новое)* — внедрение SQL через данные, вклеенные в текст запроса
- **плейсхолдер** — место для значения в запросе: `$1`, `$2`

### GO-25.2 Транзакции в коде

#### GO-25.2.1 BeginTx, Commit и Rollback через defer
**Вопросы**
- [ ] Покажи правильный каркас транзакции в Go: где `Begin`, где `Commit` и где `Rollback`. · `go sql transaction pattern defer rollback`
- [ ] Почему `defer tx.Rollback()` безопасен после успешного `Commit`? · `rollback after commit no-op`
- [ ] Почему все запросы внутри транзакции должны идти через `tx`, а не через `db`? · `use tx not db inside transaction`
- [ ] Как вынести каркас в помощник `withTx(ctx, func(tx) error)`? · `go transaction helper function`
- [ ] Что будет с соединением, если забыть и `Commit`, и `Rollback`? · `forgotten transaction connection leak`

**Гуглить:** `go database transactions` · `go withTx helper pattern`

**Должен знать**
Каркас: `tx, err := db.BeginTx(ctx, nil); if err != nil { return err }; defer tx.Rollback()`; дальше все запросы через `tx.ExecContext` и `tx.QueryRowContext`; в конце `return tx.Commit()`. Отложенный `Rollback` после успешного `Commit` ничего не делает, а на любой ошибке или панике откатит транзакцию.
Запрос через `db` внутри транзакции пойдёт по другому соединению и в транзакцию не попадёт. Забытая транзакция держит соединение и блокировки до таймаута. Каркас обычно выносят в `withTx`.

**Термины**
- **`BeginTx` / `Commit` / `Rollback`** — начать, зафиксировать, откатить транзакцию из Go
- **`*sql.Tx`** — объект транзакции, через который идут её запросы

**Вопросы**
- [ ] Как задать уровень изоляции из кода (`&sql.TxOptions{Isolation: sql.LevelRepeatableRead}`)? · `go sql TxOptions isolation`
- [ ] Как сделать транзакцию только для чтения? · `go read only transaction`
- [ ] Как то же сделать в `pgx` (`pgx.TxOptions`)? · `pgx begin tx options isolation`

#### GO-25.2.3 Повтор транзакции при ошибке сериализации
**Вопросы**
- [ ] Что делать в коде, если транзакция упала с ошибкой сериализации? · `go retry serialization failure postgres`
- [ ] Как распознать её (`*pgconn.PgError` с кодом `40001`, взаимная блокировка — `40P01`) через `errors.As`? · `pgconn.PgError code 40001`
- [ ] Напиши цикл повтора всей функции транзакции с ограничением попыток. · `go transaction retry loop`
- [ ] Почему внутри повторяемой функции не должно быть внешних действий? · `side effects retried transaction`

**Гуглить:** `pgx serialization failure retry` · `pgerrcode`

**Должен знать**
Ошибку сериализации достают через `errors.As(err, &pgErr)` и проверяют `pgErr.Code == "40001"` (взаимная блокировка — `"40P01"`). Повторяют всю транзакцию целиком: функцию, которая начинает транзакцию, читает данные заново и фиксирует. Попыток немного (3–5), с небольшой случайной паузой, затем ошибка наверх.
Функция внутри повтора должна быть «чистой» по отношению к внешнему миру: никаких писем и вызовов других сервисов.

**Термины**
- **повторяемая транзакция** — функция транзакции, которую безопасно выполнить заново

#### GO-25.2.4 Сетевой вызов внутри транзакции
**Вопросы**
- [ ] Почему внутри транзакции нельзя ходить в другой сервис по сети? · `http call inside database transaction`
- [ ] Что держит открытая транзакция, пока идёт медленный вызов (соединение, блокировки строк)? · `long transaction holds locks connection`
- [ ] Что делать, если после фиксации нужно отправить событие или письмо? · `send event after commit`
- [ ] Почему «сначала вызвать сервис, потом записать в базу» тоже неидеально? · `dual write problem`

**Гуглить:** `database transaction external call anti pattern` · `dual write problem`

**Должен знать**
Пока транзакция открыта, она держит соединение из пула и блокировки изменённых строк. Сетевой вызов внутри неё может длиться секунды — всё это время другие запросы ждут, а при сбое вызова неясно, что делать с транзакцией. Да и откатить уже сделанный вызов транзакция не может.
Внешние вызовы выносят за пределы транзакции. Задача «записать в базу и отправить событие надёжно» — классическая проблема, её решение будет в следующем этапе.

**Термины**
- **внешний вызов в транзакции** — антипаттерн: транзакция держит соединение и блокировки во время сетевого ожидания

**Позже:** двойная запись — БРОК-2.6.1; transactional outbox — БРОК-2.6.2.

#### GO-25.2.5 SELECT FOR UPDATE из Go
**Вопросы**
- [ ] Как из Go взять строку под блокировку до конца транзакции? · `go select for update transaction`
- [ ] Почему `SELECT … FOR UPDATE` должен идти через `tx`, а не через `db`? · `for update outside transaction`
- [ ] Напиши списание с баланса: прочитать с блокировкой, проверить, обновить, зафиксировать. · `go balance withdraw for update`
- [ ] Чем эта схема хуже условного `UPDATE` и когда она всё же нужна? · `for update vs conditional update`

**Гуглить:** `go postgres select for update example`

**Должен знать**
`tx.QueryRowContext(ctx, "SELECT balance FROM accounts WHERE id = $1 FOR UPDATE", id).Scan(&b)` блокирует строку до `Commit`; дальше проверка в коде, `tx.ExecContext(… UPDATE …)` и `tx.Commit()`. Через `db` блокировка снялась бы сразу после запроса.
Если проверка простая, условный `UPDATE … WHERE balance >= $2` проще и быстрее; `FOR UPDATE` нужен, когда решение требует логики в коде или нескольких строк.

**Термины**
- **блокировка из кода** — `SELECT … FOR UPDATE` внутри `*sql.Tx`

### GO-25.3 Схема базы во времени

#### GO-25.3.1 Миграция схемы
**Вопросы**
- [ ] Что такое миграция и почему схему нельзя менять руками на проде? · `database migrations explained`
- [ ] Из чего состоит миграция (номер, «вверх», «вниз»)? · `migration up down files`
- [ ] Где база запоминает, какие миграции уже применены? · `schema_migrations table`
- [ ] Когда применять миграции: при запуске сервиса или отдельным шагом выкладки? · `run migrations on startup vs separate step`
- [ ] Почему уже применённую миграцию нельзя редактировать? · `never edit applied migration`

**Гуглить:** `database schema migrations` · `migrations best practices`

**Должен знать**
Миграция — файл с изменением схемы и номером по порядку (`0003_add_orders_status.up.sql`), часто с обратным шагом (`.down.sql`). Миграции лежат в git вместе с кодом, а в базе ведётся таблица уже применённых. Так схема на всех окружениях одинакова и меняется воспроизводимо, а не руками.
Применённую миграцию не редактируют — новое изменение оформляют новой миграцией. Применяют обычно отдельным шагом выкладки.

#### GO-25.3.3 Миграции без остановки сервиса
**Вопросы**
- [ ] Как переименовать столбец так, чтобы работающий сервис не упал? · `rename column zero downtime`
- [ ] Почему старая и новая версии сервиса какое-то время работают с одной базой одновременно? · `rolling deploy schema compatibility`
- [ ] Что такое схема «расширить → перенести → сузить»? · `expand and contract migration`
- [ ] Почему `CREATE INDEX` на большой таблице блокирует запись, а `CREATE INDEX CONCURRENTLY` — нет? · `create index concurrently postgres`
- [ ] Какие изменения схемы безопасны сразу (добавить столбец, допускающий NULL), а какие нет? · `safe postgres schema changes`

**Гуглить:** `zero downtime migrations postgres` · `expand contract pattern`

**Должен знать**
При выкладке старая и новая версии сервиса работают с базой одновременно, поэтому каждая миграция должна быть совместима с обеими. Переименование — в несколько выкладок: добавить новый столбец → писать в оба и перенести старые данные → перевести чтение на новый → удалить старый. Это схема «расширить, затем сузить».
Опасные операции — блокирующие таблицу надолго: обычный `CREATE INDEX` (нужен `CONCURRENTLY`), смена типа с переписыванием таблицы. Добавить новый столбец без обязательности — безопасно.

**Термины**
- **«расширить — сузить»** — смена схемы в несколько шагов, совместимых со старым и новым кодом

#### GO-25.3.4 ORM против чистого SQL
**Вопросы**
- [ ] ORM или чистый SQL: что выберешь в Go и почему? · `go orm vs raw sql`
- [ ] Что такое ORM и что она делает за тебя? · `what is orm`
- [ ] Почему в Go-сообществе ORM недолюбливают (скрытые запросы, N+1, магия)? · `why go developers avoid orm`
- [ ] Что делает sqlc (генерирует типизированный код из SQL-запросов)? · `sqlc go`
- [ ] Есть ли для Go хорошая ORM? Обоснуй ответ. · `gorm review`

**Гуглить:** `sqlc tutorial` · `gorm vs sqlc vs pgx`

**Должен знать**
ORM сопоставляет таблицы и структуры и строит запросы сама: удобно для простых операций, но SQL скрыт, легко получить N+1 и неожиданные запросы, а сложные запросы с ней труднее. В Go чаще пишут SQL явно — с `pgx`, а скучный код сканирования генерируют: sqlc по SQL-запросам создаёт типизированные функции.
Самая известная ORM — GORM; честный ответ на собесе — «есть, но для сервиса я предпочту SQL + sqlc/pgx, потому что видно, что уходит в базу».

**Термины**
- **ORM** *(новое)* — библиотека, сопоставляющая таблицы объектам и строящая запросы
- **sqlc** — генератор типизированного Go-кода по SQL-запросам

**Граница:** GORM и sqlc — названиями и одной фразой.
