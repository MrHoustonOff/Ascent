## ТЕСТ-1. Тестирование

### ТЕСТ-1.1 Пакет testing

#### ТЕСТ-1.1.1 Зачем тесты и пирамида тестов
**Вопросы**
- [ ] Что такое пирамида тестов? · `test pyramid`
- [ ] Чем модульный тест отличается от теста с настоящей базой и от сквозного (end-to-end)? · `unit vs integration vs e2e tests`
- [ ] Почему модульных тестов много, а сквозных — мало? · `why fewer e2e tests`
- [ ] Что тесты дают, кроме поиска багов (смелость менять код, документация поведения)? · `benefits of tests refactoring`
- [ ] Что тестировать в первую очередь (бизнес-логику, граничные случаи, ошибки)? · `what to test first`

**Гуглить:** `test pyramid martin fowler` · `unit vs integration tests`

**Должен знать**
Пирамида тестов: в основании — много быстрых модульных тестов (одна функция или тип без внешних систем), выше — меньше тестов с настоящими внешними системами (база, другой сервис), на вершине — немного сквозных (вся система как у пользователя). Чем выше, тем дольше, дороже и хрупче тест.
Тесты позволяют менять код без страха и показывают, как он должен себя вести. Начинают с бизнес-логики: правила, граничные значения, ошибки.

**Термины**
- **пирамида тестов** *(новое)* — много модульных, меньше тестов с внешними системами, немного сквозных
- **модульный тест** — тест одной части кода без внешних систем

**Позже:** тесты с настоящими внешними системами — ТЕСТ-1.3.1.

#### ТЕСТ-1.1.2 Пакет testing и go test
**Вопросы**
- [ ] Как устроен тест в Go и как его запустить? · `go testing package basics`
- [ ] Почему файл называется `…_test.go`, а функция — `TestXxx(t *testing.T)`? · `go test file naming`
- [ ] Как запустить тесты всего модуля, одного пакета и одного теста (`go test ./...`, `-run`)? · `go test run flag`
- [ ] Чем тест в том же пакете отличается от теста в пакете `xxx_test` (снаружи, через экспорт)? · `go test package vs package_test`
- [ ] Почему `go test` кэширует результаты и как заставить перезапустить (`-count=1`)? · `go test cache count=1`

**Гуглить:** `go testing tutorial` · `go test flags`

**Должен знать**
Тест — функция `func TestCalc(t *testing.T)` в файле `calc_test.go` рядом с кодом; никакого фреймворка не нужно. `go test ./...` запускает все тесты модуля, `-run Calc` — подходящие по имени, `-v` — с подробным выводом, `-count=1` — без кэша результатов.
Тест в пакете `calc` видит всё, тест в пакете `calc_test` — только экспортированное, как настоящий пользователь пакета.

**Термины**
- **`testing.T`** — объект теста: сообщать об ошибках, запускать подтесты
- **`go test`** — команда запуска тестов

#### ТЕСТ-1.1.3 Табличные тесты
**Вопросы**
- [ ] Что такое табличный тест и почему так пишут почти все тесты в Go? · `go table driven tests`
- [ ] Как выглядит слайс анонимных структур с полями `name`, `in`, `want`? · `table driven test example`
- [ ] Как одним тестом проверить и обычные случаи, и граничные, и ошибки? · `table test edge cases errors`
- [ ] Почему добавить новый случай — одна строка? · `table tests maintainability`

**Гуглить:** `go wiki table driven tests` · `dave cheney prefer table driven tests`

**Должен знать**
Табличный тест — слайс случаев (обычно анонимные структуры с полями `name`, входные данные, ожидаемый результат) и один цикл, который прогоняет каждый: `for _, tc := range tests { got := Calc(tc.in); if got != tc.want { t.Errorf(…) } }`. Новый случай — одна строка в таблице.
Так в одном месте видны все проверяемые ситуации: обычные, граничные (ноль, пусто, максимум) и ошибочные.

**Термины**
- **табличный тест** *(новое)* — тест, прогоняющий таблицу случаев одним циклом

#### ТЕСТ-1.1.4 t.Run и подтесты
**Вопросы**
- [ ] Что даёт `t.Run(tc.name, func(t *testing.T) { … })` в табличном тесте? · `go t.Run subtests`
- [ ] Как запустить один подтест (`-run 'TestCalc/zero'`)? · `run single subtest`
- [ ] Как запустить подтесты параллельно (`t.Parallel()`) и что важно помнить про переменную цикла? · `t.Parallel table test loop variable`

**Гуглить:** `go subtests` · `t.Parallel`

**Должен знать**
`t.Run(name, f)` делает из каждого случая отдельный подтест: в выводе видно, какой именно упал, его можно запустить отдельно (`-run 'TestCalc/zero'`), а `t.Fatal` в нём остановит только этот случай. `t.Parallel()` внутри подтеста запускает подтесты одновременно; с Go 1.22 переменная цикла своя на каждой итерации, раньше её нужно было копировать.

**Термины**
- **подтест** — именованный тест внутри теста, `t.Run`

#### ТЕСТ-1.1.5 t.Error против t.Fatal
**Вопросы**
- [ ] Чем `t.Error` отличается от `t.Fatal`? · `t.Error vs t.Fatal`
- [ ] Когда нужен `t.Fatal` (дальнейшие проверки бессмысленны, например не удалось подготовить данные)? · `when to use t.Fatal`
- [ ] Почему `t.Fatal` нельзя вызывать из другой горутины? · `t.Fatal from goroutine`
- [ ] Как писать понятные сообщения (`got %v, want %v`)? · `go test error message got want`

**Гуглить:** `go testing Error vs Fatal`

**Должен знать**
`t.Error` отмечает тест упавшим и продолжает его — можно увидеть все несовпадения сразу. `t.Fatal` отмечает и сразу останавливает тест — когда дальше проверять бессмысленно (не создалась база, вернулась ошибка там, где нужен результат). `t.Fatal` работает только из горутины теста.
Сообщение пишут в формате «что вызвали, что получили, что ждали»: `Calc(3) = 5, want 6`.

**Термины**
- **`t.Error` / `t.Fatal`** — отметить ошибку и продолжить / отметить и остановить тест

#### ТЕСТ-1.1.6 Покрытие кода
**Вопросы**
- [ ] Как посмотреть покрытие кода тестами (`go test -cover`)? · `go test cover`
- [ ] Как увидеть непокрытые строки (`-coverprofile` и `go tool cover -html`)? · `go tool cover html`
- [ ] Почему 100% покрытия не значит, что тесты хорошие? · `code coverage misleading`
- [ ] Какое покрытие разумно требовать? · `reasonable code coverage target`

**Гуглить:** `go cover story` · `go test coverprofile`

**Должен знать**
`go test -cover` показывает процент выполненных тестами строк, `-coverprofile=c.out` с `go tool cover -html=c.out` — какие строки не выполнялись. Это способ найти непроверенные ветки, а не оценка качества: можно выполнить все строки и ничего не проверить.
Разумная цель — высокое покрытие бизнес-логики, а не одна цифра на весь проект.

**Термины**
- **покрытие кода** — доля кода, выполненного тестами

#### ТЕСТ-1.1.8 TDD
**Вопросы**
- [ ] Что такое TDD и в каком порядке пишут тест и код (красный → зелёный → улучшить)? · `tdd red green refactor`
- [ ] Почему TDD не обязателен, но полезен для логики с чёткими правилами? · `tdd pros cons`

**Гуглить:** `test driven development explained`

**Должен знать**
TDD — разработка через тесты: сначала пишут падающий тест на новое поведение, потом минимальный код, чтобы он прошёл, потом улучшают код, сохраняя тесты зелёными. Подход не обязателен, но хорошо работает для логики с чёткими правилами (расчёты, разбор форматов).

**Термины**
- **TDD** — разработка, в которой тест пишется раньше кода

**Граница:** одной фразой, что это и почему не обязательно.

### ТЕСТ-1.2 Подмена зависимостей

#### ТЕСТ-1.2.1 Тестовые двойники: заглушка и мок
**Вопросы**
- [ ] Чем заглушка отличается от мока? · `stub vs mock`
- [ ] Что такое фейк (рабочая упрощённая реализация, например хранилище в map)? · `fake vs stub vs mock`
- [ ] Почему тест, проверяющий только «какие методы вызвали», хрупкий? · `over mocking brittle tests`
- [ ] Когда фейк лучше мока? · `prefer fakes over mocks`

**Гуглить:** `test doubles mocks stubs fakes` · `mocks arent stubs fowler`

**Должен знать**
Тестовый двойник — подмена настоящей зависимости. Заглушка возвращает заранее заданные ответы («`ByID` всегда вернёт этот заказ»). Мок ещё и проверяет, как его вызвали («`Save` вызвали ровно один раз с такими данными»). Фейк — рабочая упрощённая реализация, например репозиторий на map.
Тесты на моках, проверяющие каждый вызов, ломаются от любой перестройки кода; там, где можно, лучше фейк и проверка результата.

**Термины**
- **заглушка** *(новое)* — двойник с заранее заданными ответами
- **мок** *(новое)* — двойник, проверяющий, как его вызвали
- **фейк** — упрощённая рабочая реализация зависимости

#### ТЕСТ-1.2.2 Мок через интерфейс
**Вопросы**
- [ ] Как подменить базу в тесте сервиса и что для этого должно быть в архитектуре? · `go mock repository interface`
- [ ] Как написать фейк-репозиторий на map, подходящий под интерфейс сервиса? · `go fake repository map`
- [ ] Как в двойнике задать ошибку, чтобы проверить ветку обработки ошибок? · `test error path with stub`

**Должен знать**
Если сервис получает репозиторий через конструктор и знает его только как маленький интерфейс, в тесте передают свою реализацию: `type fakeRepo struct{ orders map[int64]Order; err error }` с нужными методами. Через поле `err` удобно проверить ветку «база вернула ошибку».

### ТЕСТ-1.3 Тесты ближе к реальности

#### ТЕСТ-1.3.1 Интеграционный тест
**Вопросы**
- [ ] Что такое интеграционный тест и зачем он, если есть моки? · `integration test explained`
- [ ] Какие ошибки ловит только тест с настоящей базой (опечатка в SQL, ограничения, транзакции)? · `bugs mocks cannot catch`
- [ ] Как отделить медленные интеграционные тесты от быстрых (метки сборки, `-short`, переменная окружения)? · `go separate integration tests build tags short`
- [ ] Как готовить и чистить данные между тестами? · `test database cleanup between tests`

**Гуглить:** `go integration tests` · `testing.Short`

**Должен знать**
Интеграционный тест проверяет код вместе с настоящей внешней системой — обычно репозиторий с настоящим Postgres. Мок не заметит опечатку в SQL, нарушение ограничения, неверную работу транзакции — интеграционный заметит.
Они медленнее, поэтому их отделяют: `if testing.Short() { t.Skip() }` или отдельная метка сборки. Данные готовят в каждом тесте и чистят после — транзакцией с откатом или очисткой таблиц.

**Термины**
- **интеграционный тест** *(новое)* — тест кода вместе с настоящей внешней системой

**Вопросы**
- [ ] Как в тесте поднять настоящую базу? · `testcontainers go postgres`

#### ТЕСТ-1.3.4 Тест конкурентного кода и флаг -race
**Вопросы**
- [ ] Как тестировать конкурентный код? · `testing concurrent code go`
- [ ] Почему тесты нужно гонять с `-race` и что он найдёт? · `go test -race`
- [ ] Как спровоцировать гонку в тесте (много горутин, много повторов, `-count`)? · `stress test race detector`
- [ ] Почему `time.Sleep` в тестах — плохая синхронизация? · `avoid sleep in tests`

**Гуглить:** `go test race` · `flaky tests sleep`

**Должен знать**
Конкурентный код проверяют с `go test -race`: запускают много горутин, работающих с общими данными, и повторяют (`-count=100`), чтобы гонка проявилась. Детектор найдёт гонку, если она случилась при запуске.
`time.Sleep` для «подождать, пока горутина успеет» делает тесты медленными и нестабильными; ждут явно — каналом, `WaitGroup` или средствами следующего урока.

**Термины**
- **тест с `-race`** — запуск тестов с детектором гонок

#### ТЕСТ-1.3.5 testing/synctest
**Вопросы**
- [ ] Как тестировать код, который зависит от текущего времени? · `go testing time dependent code`
- [ ] Что делает `testing/synctest` (Go 1.25): изолированная «пузырь»-среда с поддельным временем? · `go 1.25 testing/synctest`
- [ ] Как в нём время «перематывается», когда все горутины ждут? · `synctest fake clock advances blocked`
- [ ] Чем это лучше, чем передавать в код свой интерфейс часов? · `synctest vs clock interface`

**Гуглить:** `go blog testing/synctest` · `go 1.25 synctest`

**Должен знать**
`synctest.Test(t, func(t *testing.T) { … })` (общедоступен с Go 1.25) запускает код в изолированной среде с поддельными часами: время стоит, пока горутины работают, и мгновенно перематывается вперёд, когда все они ждут таймеров. Тест с таймаутом в минуту выполняется за миллисекунды и без нестабильности. `synctest.Wait()` ждёт, пока все горутины среды заблокируются.
Раньше для этого в код передавали свой интерфейс часов; теперь можно тестировать код с настоящими `time.Sleep` и таймерами.

**Термины**
- **`testing/synctest`** — тестирование конкурентного кода с поддельным временем

### ТЕСТ-1.4 Скорость

#### ТЕСТ-1.4.1 Бенчмарки
**Вопросы**
- [ ] Как написать бенчмарк и что он показывает? · `go benchmark tutorial`
- [ ] Как выглядит `func BenchmarkX(b *testing.B) { for b.Loop() { … } }` (Go 1.24) и старая форма с `b.N`? · `go 1.24 b.Loop`
- [ ] Как запустить (`go test -bench=. -run=^$`)? · `go test bench flag`
- [ ] Как доказать, что одна реализация быстрее другой (несколько прогонов и `benchstat`)? · `benchstat compare benchmarks`
- [ ] Почему компилятор может «выкинуть» вычисление в бенчмарке и как `b.Loop` от этого защищает? · `benchmark dead code elimination`

**Должен знать**
Бенчмарк — функция `BenchmarkX(b *testing.B)`, которая много раз выполняет код: с Go 1.24 — `for b.Loop() { … }`, раньше — `for i := 0; i < b.N; i++`. `go test -bench=. -run=^$` показывает время на операцию. `b.Loop` ещё и не даёт компилятору выбросить результат как ненужный.
Один прогон ничего не доказывает: запускают несколько раз (`-count=10`) и сравнивают версии `benchstat` — он покажет разницу и её достоверность.

**Термины**
- **бенчмарк** *(новое)* — тест, измеряющий скорость кода
- **`benchstat`** — сравнение результатов бенчмарков со статистикой

#### ТЕСТ-1.4.2 Выделения памяти в бенчмарке
**Вопросы**
- [ ] Как в бенчмарке увидеть выделения памяти (`-benchmem`, `b.ReportAllocs`)? · `go benchmark allocations benchmem`
- [ ] Что значат колонки `B/op` и `allocs/op`? · `B/op allocs/op meaning`
- [ ] Как проверить, что предвыделение ёмкости убрало выделения? · `benchmark preallocation allocs`

**Гуглить:** `go benchmem` · `reduce allocations benchmark`

**Должен знать**
`-benchmem` (или `b.ReportAllocs()` в коде) добавляет колонки `B/op` — байтов выделено на операцию — и `allocs/op` — число выделений. По ним видно, помогла ли оптимизация: предвыделение ёмкости слайса или переиспользование буфера должны уменьшить `allocs/op`.

**Термины**
- **`allocs/op`** — число выделений памяти на операцию в бенчмарке

#### ТЕСТ-1.4.3 Fuzzing
**Вопросы**
- [ ] Что такое fuzzing и как запустить его в Go (`go test -fuzz`)? · `go fuzzing tutorial`
- [ ] Для какого кода он полезен (разбор входных данных)? · `fuzzing use cases parsers`

**Гуглить:** `go fuzzing`

**Должен знать**
Fuzzing — тест, которому Go сам подбирает случайные и «хитрые» входные данные, пытаясь вызвать панику или нарушить проверку; найденный случай сохраняется как новый тест. Полезен для кода, который разбирает внешний ввод.

**Термины**
- **fuzzing** — автоматический поиск входных данных, ломающих код

**Граница:** одной фразой, что это.
