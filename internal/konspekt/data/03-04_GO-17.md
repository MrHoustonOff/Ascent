## GO-17. Каналы и select

### GO-17.1 Канал

#### GO-17.1.1 Канал
**Вопросы**
- [ ] Что такое канал и зачем он нужен? · `go channels explained`
- [ ] Как создать канал: `make(chan int)`? Какой у него тип? · `golang make chan`
- [ ] Что значит девиз «не общайтесь через общую память, делитесь памятью через общение»? · `share memory by communicating`
- [ ] Чем канал похож на `queue.Queue` в Python и чем отличается? · `python queue vs go channel`
- [ ] Какое нулевое значение у канала? · `go nil channel zero value`

**Гуглить:** `go tour channels` · `go by example channels` · `effective go share by communicating`

**Должен знать**
Канал — «труба» между горутинами: одна кладёт значение, другая забирает, и при этом они синхронизируются — получатель гарантированно видит всё, что отправитель сделал до отправки. Создаётся через `make(chan T)`, тип — `chan T`; переменная канала, как и map, указывает на общую внутреннюю структуру.
Вместо того чтобы несколько горутин трогали одну переменную под мьютексом, данные передают по каналу — владеет ими в каждый момент одна горутина. Мост из Python: похоже на потокобезопасную `queue.Queue`, но встроено в язык и работает с `select`. Нулевое значение канала — nil.

**Термины**
- **канал** *(новое)* — средство передачи значений между горутинами с синхронизацией

#### GO-17.1.2 Отправка и получение
**Вопросы**
- [ ] Как отправить значение в канал и получить из него (`ch <- v`, `v := <-ch`)? · `go channel send receive syntax`
- [ ] Можно ли получить значение и выбросить его (`<-ch` отдельной строкой)? · `go receive discard value`
- [ ] Как получить результат из горутины через канал? · `get result from goroutine channel`
- [ ] Что гарантирует канал о порядке значений от одного отправителя? · `channel fifo order`

**Гуглить:** `golang channel send receive` · `return value from goroutine channel`

**Должен знать**
`ch <- v` — отправить, `v := <-ch` — получить; `<-ch` без присваивания просто ждёт и выбрасывает значение. Так получают результат горутины: `go func() { ch <- compute() }(); res := <-ch`.
Значения от одного отправителя приходят в том порядке, в котором отправлены.

**Термины**
- **отправка** — `ch <- v`
- **получение** — `<-ch`

#### GO-17.1.3 Небуферизованный канал
**Вопросы**
- [ ] Что будет при отправке в небуферизованный канал, если никто не читает? · `unbuffered channel send blocks`
- [ ] Почему отправка и получение в таком канале «встречаются» в одной точке? · `unbuffered channel rendezvous`
- [ ] Как небуферизованный канал работает как сигнал «я закончил»? · `channel done signal`
- [ ] Что выведет `ch := make(chan int); ch <- 1; fmt.Println(<-ch)` в `main`? · `send on unbuffered channel in main deadlock`

**Гуглить:** `unbuffered channel blocking` · `go channel synchronization`

**Должен знать**
У небуферизованного канала нет места для значения: отправитель ждёт, пока кто-то примет значение, получатель — пока кто-то отправит. Передача — это встреча двух горутин; после неё обе знают, что вторая дошла до этого места.
Поэтому `ch <- 1` в `main` без другой горутины, которая читает, зависнет навсегда — Go заметит это и упадёт с ошибкой взаимной блокировки.

**Термины**
- **небуферизованный канал** — канал без места: отправитель ждёт получателя

#### GO-17.1.4 Буферизованный канал
**Вопросы**
- [ ] Чем небуферизованный канал отличается от буферизованного (`make(chan int, 3)`)? · `buffered vs unbuffered channel`
- [ ] Когда отправка в буферизованный канал ждёт, а когда нет? · `buffered channel full blocks`
- [ ] Когда получение из буферизованного канала ждёт? · `buffered channel empty blocks`
- [ ] Почему буфер — не способ «починить» взаимную блокировку? · `buffered channel hides deadlock`
- [ ] Как выбрать размер буфера? · `how to choose channel buffer size`

**Гуглить:** `go buffered channels` · `channel buffer size choice`

**Должен знать**
`make(chan int, 3)` — канал с буфером на 3 значения. Отправка ждёт, только когда буфер полон, получение — только когда пуст. Это развязывает отправителя и получателя: короткие всплески не тормозят того, кто быстрее.
Буфер не меняет логику: если получатель не придёт никогда, отправитель всё равно рано или поздно застрянет. Размер обычно выбирают по смыслу (число задач, число работников), а не «побольше на всякий случай».

**Термины**
- **буферизованный канал** *(новое)* — канал с местом под несколько значений

#### GO-17.1.5 len и cap канала
**Вопросы**
- [ ] Что возвращают `len(ch)` и `cap(ch)`? · `go channel len cap`
- [ ] Почему по `len(ch)` нельзя надёжно решить, отправлять ли значение? · `len channel race condition`
- [ ] Чему равны `len` и `cap` у небуферизованного канала? · `unbuffered channel cap 0`

**Гуглить:** `golang len of channel`

**Должен знать**
`cap(ch)` — размер буфера (0 у небуферизованного), `len(ch)` — сколько значений лежит в нём сейчас. Но пока ты смотришь на `len`, другие горутины уже могли что-то положить или забрать, поэтому решения по `len` — гонка. Годится только для отладки и наблюдения за заполненностью.

**Термины**
- **`len`/`cap` канала** — заполненность и размер буфера

#### GO-17.1.6 Направленные каналы
**Вопросы**
- [ ] Зачем нужны направленные каналы `chan<-` и `<-chan`? · `go directional channels`
- [ ] Как обычный канал превращается в направленный при передаче в функцию? · `convert bidirectional to directional channel`
- [ ] Что будет, если попытаться читать из `chan<- int`? · `receive from send-only channel error`
- [ ] Как функция-производитель возвращает `<-chan T`? · `generator function returns receive only channel`

**Гуглить:** `golang channel direction` · `send only receive only channel`

**Должен знать**
`chan<- T` — канал только для отправки, `<-chan T` — только для получения. Обычный `chan T` автоматически превращается в любой из них при передаче в функцию. Так в сигнатуре видно, кто что делает с каналом, а ошибка «читает из канала, куда должен только писать» ловится при компиляции.
Типичный приём: функция запускает горутину-производителя и возвращает `<-chan T` — вызывающий может только читать.

**Термины**
- **направленный канал** — канал только для отправки или только для получения

### GO-17.2 Закрытие канала

#### GO-17.2.1 close
**Вопросы**
- [ ] Что значит закрыть канал (`close(ch)`)? · `go close channel`
- [ ] Что происходит со значениями, которые уже лежат в буфере при закрытии? · `close buffered channel remaining values`
- [ ] Что происходит с горутинами, которые ждали получения? · `close wakes receivers`
- [ ] Нужно ли закрывать каждый канал, как файл? · `do you need to close channels`

**Гуглить:** `golang close channel` · `when to close a channel`

**Должен знать**
`close(ch)` — сигнал «значений больше не будет». Значения, уже лежащие в буфере, получатели ещё заберут; после них получение сразу возвращает нулевое значение, а все ждущие получатели просыпаются.
Закрывать каждый канал не обязательно — неиспользуемый канал соберёт сборщик мусора. Закрывают, когда получателям нужно знать о конце данных.

**Термины**
- **закрытие канала** — сигнал получателям, что значений больше не будет

#### GO-17.2.2 Чтение из закрытого канала и проверка «comma ok»
**Вопросы**
- [ ] Что вернёт чтение из закрытого канала и как понять, что канал закрыт? · `receive from closed channel zero value`
- [ ] Чем `v, ok := <-ch` отличается от `v := <-ch`? · `channel comma ok`
- [ ] Почему без `ok` нельзя отличить «закрыт» от «пришёл ноль»? · `zero value vs closed channel`
- [ ] Ждёт ли чтение из закрытого канала? · `closed channel never blocks`

**Гуглить:** `golang check if channel closed` · `channel comma ok idiom`

**Должен знать**
Получение из закрытого и опустевшего канала никогда не ждёт и сразу возвращает нулевое значение. Чтобы отличить это от настоящего нуля, используют `v, ok := <-ch`: `ok` равно `false`, если канал закрыт и пуст.
Отдельной функции «закрыт ли канал» нет — это и есть способ узнать.

**Термины**
- **comma ok у канала** — `v, ok := <-ch`, `ok == false` значит «закрыт и пуст»

#### GO-17.2.3 Запись в закрытый канал
**Вопросы**
- [ ] Что будет при записи в закрытый канал? · `send on closed channel panic`
- [ ] Почему Go паникует, а не молча выбрасывает значение? · `why send on closed channel panics`
- [ ] Как устроить код, чтобы отправитель никогда не писал в закрытый канал? · `avoid send on closed channel`

**Гуглить:** `golang panic send on closed channel`

**Должен знать**
Отправка в закрытый канал — паника `send on closed channel`. Это ошибка логики: кто-то закрыл канал, пока другой ещё считал его открытым. Молча выбросить значение было бы хуже — данные пропадали бы незаметно.
Защита — правило владения: закрывает тот, кто отправляет, и только когда точно больше не будет отправлять.

**Термины**
- **паника при отправке** — отправка в закрытый канал

#### GO-17.2.4 Повторное закрытие
**Вопросы**
- [ ] Что будет при повторном закрытии канала? · `close of closed channel panic`
- [ ] Что будет при закрытии nil-канала? · `close of nil channel panic`
- [ ] Как безопасно закрыть канал, если закрыть могут несколько мест (`sync.Once`)? · `close channel once sync.Once`

**Гуглить:** `close of closed channel` · `sync.Once close channel`

**Должен знать**
Повторное закрытие — паника `close of closed channel`; закрытие nil-канала — тоже паника. Если закрыть канал могут из нескольких мест (например, при отмене), закрытие оборачивают в `sync.Once` — тогда оно выполнится ровно один раз.

**Термины**
- **повторное закрытие** — второй `close` того же канала, паника

**Позже:** `sync.Once` — GO-18.2.1.

#### GO-17.2.5 Кто закрывает канал
**Вопросы**
- [ ] Кто должен закрывать канал и почему не получатель? · `who should close channel sender`
- [ ] Что делать, если отправителей несколько? · `multiple senders close channel waitgroup`
- [ ] Как сообщить отправителям «хватит», если остановиться хочет получатель? · `receiver signal sender to stop done channel`

**Гуглить:** `go channel closing principle` · `how to gracefully close channels`

**Должен знать**
Закрывает отправитель: он знает, когда значений больше не будет, а получатель — нет. Если получатель закроет канал, отправитель запаникует на следующей отправке.
Если отправителей несколько, закрывает кто-то один после того, как все закончили: например, отдельная горутина ждёт их через `WaitGroup` и потом вызывает `close`. Если остановиться хочет получатель, он сигналит отправителям отдельным каналом «стоп», а не закрывает канал данных.

**Термины**
- **правило закрытия** — канал закрывает единственный отправитель или тот, кто дождался всех отправителей

**Позже:** сигнал «стоп» всем горутинам — GO-20.1.6.

#### GO-17.2.6 for range по каналу
**Вопросы**
- [ ] Как работает `for v := range ch` и когда он заканчивается? · `range over channel`
- [ ] Что будет, если канал никто не закроет? · `range channel never closed hangs`
- [ ] Как связать производителя и потребителя через `range` и `close`? · `producer consumer range close`

**Гуглить:** `golang range channel` · `producer consumer go`

**Должен знать**
`for v := range ch` получает значения, пока канал не закрыт и не опустел, — и тогда цикл заканчивается сам. Если канал не закроют, цикл будет ждать вечно.
Классическая пара: производитель отправляет значения и в конце делает `close(ch)`, потребитель читает через `range`.

**Термины**
- **`range` по каналу** — получать значения до закрытия канала

#### GO-17.2.7 nil-канал
**Вопросы**
- [ ] Что происходит при чтении, записи и закрытии nil-канала? · `nil channel operations block forever`

#### GO-17.3.2 Отправка в полный канал
**Вопросы**
- [ ] Что происходит с горутиной, которая отправляет в полный канал? · `send to full channel goroutine parked`

**Должен знать**

Когда получатель забирает значение из буфера, он берёт первого ждущего отправителя, кладёт его значение в освободившееся место и делает эту горутину снова готовой к выполнению.

**Термины**
- **парковка на канале** — горутина ждёт в очереди канала, пока её не разбудят

#### GO-17.3.3 Прямая передача ждущему получателю
**Вопросы**
- [ ] Что происходит, если в момент отправки уже есть ждущий получатель? · `channel direct send to waiting receiver`
- [ ] Почему значение копируется прямо получателю, минуя буфер? · `channel copy to receiver stack`
- [ ] Почему это быстрее, чем через буфер? · `direct handoff optimization`

**Гуглить:** `go channel direct send` · `channel send waiting receiver`

**Должен знать**
Если получатель уже ждёт, отправитель не трогает буфер: он копирует значение прямо в место, куда получатель его ждёт, и будит его. Это экономит копирование и работу с буфером. Так же получатель берёт значение прямо у ждущего отправителя небуферизованного канала.

**Термины**
- **прямая передача** — значение копируется от отправителя к ждущему получателю минуя буфер

### GO-17.4 select

#### GO-17.4.1 Оператор select
**Вопросы**
- [ ] Что делает `select`? · `go select statement`
- [ ] Как ждать сразу два канала? · `select two channels`
- [ ] Что будет, если ни одна ветка не готова и нет `default`? · `select blocks until ready`
- [ ] Можно ли в `select` смешивать отправку и получение? · `select send and receive cases`

**Гуглить:** `go tour select` · `go by example select`

**Должен знать**
`select { case v := <-a: …; case b <- x: … }` ждёт сразу несколько операций с каналами и выполняет ту, которая готова. Если не готова ни одна, `select` ждёт. В ветках можно и получать, и отправлять.
Это главный инструмент для таймаутов, отмены и обработки нескольких источников событий.

**Термины**
- **`select`** — ожидание сразу нескольких операций с каналами

#### GO-17.4.2 Несколько готовых веток select
**Вопросы**
- [ ] Что будет, если готовы сразу несколько веток? · `select multiple ready cases random`
- [ ] Почему Go выбирает случайно, а не первую по порядку? · `why select random choice`
- [ ] Как сделать приоритет одной ветки, если очень нужно? · `select priority pattern`

**Гуглить:** `golang select random` · `select prioritize channel`

**Должен знать**
Если готово несколько веток, `select` выбирает одну случайно — чтобы ни один канал не «голодал». Порядок записи веток ничего не значит.
Нужен приоритет — делают два `select` подряд: сначала неблокирующая проверка важного канала, затем общий.

**Термины**
- **случайный выбор** — из нескольких готовых веток `select` берёт любую

- [ ] Когда выполняется ветка `default`? · `select default when`
- [ ] Почему `for { select { … default: } }` без паузы съест процессор? · `busy loop select default`
- [ ] Как «выбросить» значение, если канал полон (не ждать медленного читателя)? · `drop message if channel full`

**Гуглить:** `go select default non blocking` · `busy wait select default`

**Должен знать**
Ветка `default` выполняется, если ни одна другая не готова прямо сейчас, — так операции с каналом становятся неблокирующими: «отправь, если есть место, иначе пропусти». Удобно, например, чтобы не ждать медленного получателя логов.
Ловушка: `default` в бесконечном цикле превращает ожидание в пустую прокрутку, которая занимает целое ядро.

**Термины**
- **`default` в `select`** — ветка «если ничего не готово»

#### GO-17.4.4 Таймаут через time.After
**Вопросы**
- [ ] Как сделать таймаут на ожидание из канала? · `go select timeout time.After`
- [ ] Что возвращает `time.After` и когда в канал придёт значение? · `time.After returns channel`
- [ ] Почему `time.After` в долгом цикле раньше вызывал утечку памяти и что изменилось в Go 1.23? · `time.After leak loop go 1.23 timers`
- [ ] Когда лучше `time.NewTimer` с `Stop` или `Reset`? · `time.NewTimer vs time.After`

**Гуглить:** `go select timeout` · `go 1.23 timer changes`

**Должен знать**
`time.After(d)` возвращает канал, в который через `d` придёт текущее время. В `select` это ветка-таймаут: `case <-time.After(time.Second): return errTimeout`.
До Go 1.23 каждый `time.After` держал свой таймер в памяти до срабатывания, и в частом цикле они копились. С Go 1.23 неиспользуемые таймеры сразу собираются сборщиком мусора. Для повторяющихся ожиданий всё равно аккуратнее один `time.NewTimer` с `Reset`.

**Термины**
- **`time.After`** — канал, в который значение придёт через заданное время

#### GO-17.4.5 nil-канал в select
**Вопросы**
- [ ] Зачем в `select` каналу присваивают nil? · `nil channel select disable case`
- [ ] Как слить два канала в один и правильно закончить, когда оба закрыты? · `merge two channels nil out closed`
- [ ] Что будет, если все каналы в `select` стали nil? · `select all nil channels block`

**Гуглить:** `nil channel in select` · `merge channels go`

**Должен знать**
Операция с nil-каналом никогда не готова, поэтому ветка с ним в `select` просто не срабатывает. Так «выключают» ветку: когда канал `a` закрылся (`ok == false`), пишут `a = nil`, и `select` дальше ждёт только оставшиеся. Когда оба стали nil — работа закончена.

**Термины**
- **выключение ветки** — присвоить каналу nil, чтобы `select` его не ждал

#### GO-17.4.7 Цикл for с select внутри
**Вопросы**
- [ ] Как выйти из цикла `for`, внутри которого `select`? · `break out of for select loop`
- [ ] Почему `break` внутри `select` не выходит из цикла? · `break in select only exits select`
- [ ] Как выглядит типичная горутина-работник: `for { select { case job := <-jobs: …; case <-stop: return } }`? · `worker loop for select stop channel`

**Должен знать**

**Термины**
- **`for`-`select`** — бесконечный цикл ожидания событий из нескольких каналов

### GO-17.5 Взаимные блокировки на каналах

#### GO-17.5.1 «all goroutines are asleep — deadlock!»
**Вопросы**
- [ ] Когда Go сам пишет «all goroutines are asleep — deadlock!», а когда программа просто зависает? · `all goroutines are asleep deadlock`
- [ ] Почему достаточно одной живой горутины (например, таймера или сетевого ожидания), чтобы Go этого не заметил? · `deadlock not detected partial`
- [ ] Что будет, если отправить в канал, у которого нет читателей? · `send to channel no receiver`
- [ ] Можно ли перехватить эту ошибку через `recover`? · `fatal error deadlock cannot recover`

**Гуглить:** `fatal error all goroutines are asleep` · `go deadlock detection`

**Должен знать**
Рантайм проверяет только один случай: все горутины программы ждут, и разбудить их некому. Тогда он падает с фатальной ошибкой «all goroutines are asleep — deadlock!» — перехватить её нельзя.
Если хоть одна горутина работает или ждёт сеть или таймер, рантайм считает, что надежда есть, и молчит. Поэтому в настоящем сервисе зависшие горутины чаще всего не падают, а тихо копятся.

**Термины**
- **обнаружение взаимной блокировки** — рантайм падает, только если ждут все горутины

#### GO-17.5.2 Типичные взаимные блокировки на каналах
**Вопросы**
- [ ] Приведи два примера взаимной блокировки на каналах. · `go channel deadlock examples`
- [ ] Почему отправка и получение в одной горутине на небуферизованном канале — блокировка? · `send receive same goroutine deadlock`
- [ ] Почему `range` по каналу, который никто не закроет, — блокировка? · `range channel not closed deadlock`
- [ ] Как `WaitGroup.Wait` до чтения результатов может заблокировать отправителей? · `wg.Wait before reading results deadlock`

**Гуглить:** `common go deadlocks channels` · `deadlock waitgroup channel`

**Должен знать**
Частые случаи: горутина отправляет в небуферизованный канал, который сама же должна читать; `range` по каналу, который никто не закрывает; `wg.Wait()` перед чтением результатов — работники ждут, пока кто-то прочитает, а читатель ждёт, пока работники закончат.
Лечение — продумать, кто отправляет, кто читает и кто закрывает, и чтобы ожидание никогда не шло по кругу.

**Термины**
- **блокировка по кругу на каналах** — горутины ждут друг друга через каналы

#### GO-17.5.3 Утечка горутин
**Вопросы**
- [ ] Что такое утечка горутин и откуда она берётся? · `goroutine leak`
- [ ] Почему горутина, ждущая канал, в который никто не напишет, живёт вечно? · `blocked goroutine never collected`
- [ ] Чем утечка горутин опасна для сервиса? · `goroutine leak memory growth`
- [ ] Как не допустить утечку: у каждой горутины должен быть способ закончиться? · `prevent goroutine leaks`
- [ ] Как найти утечку (`runtime.NumGoroutine`, профиль горутин, `goleak` в тестах)? · `detect goroutine leak goleak`

**Гуглить:** `goroutine leak` · `uber goleak` · `how to find goroutine leaks`

**Должен знать**
Утечка горутин — горутина ждёт то, что никогда не случится (канал, в который никто не пишет, получатель, который ушёл), и висит вечно вместе со своим стеком и всем, на что ссылается. Сборщик мусора такие горутины не собирает. В сервисе их число растёт с каждым запросом, пока не кончится память.
Правило: запуская горутину, знай, как она закончится. Найти утечку помогают счётчик горутин, профиль горутин и проверки в тестах.

**Термины**
- **утечка горутин** *(новое)* — горутины, которые никогда не завершатся
