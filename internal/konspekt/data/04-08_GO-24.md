## GO-24. gRPC и protobuf

### GO-24.1 protobuf

#### GO-24.1.1 protobuf
**Вопросы**
- [ ] Что такое protobuf и чем он отличается от JSON? · `protobuf vs json`
- [ ] Почему protobuf компактнее и быстрее разбирается (двоичный формат, номера полей вместо имён)? · `protobuf binary encoding`
- [ ] Почему схема описывается заранее в отдельном файле? · `protobuf schema first`
- [ ] Что неудобно в protobuf по сравнению с JSON (не прочитать глазами, нужна схема)? · `protobuf drawbacks`

**Гуглить:** `protocol buffers overview` · `protobuf encoding`

**Должен знать**
protobuf — формат данных со схемой: структура сообщений описывается в `.proto`-файле, а данные передаются двоичными байтами, где вместо имён полей — их номера. Получается в разы компактнее JSON и быстрее разбирается, а по схеме генерируется типизированный код.
Плата — данные не прочитать глазами, и без схемы их не понять. JSON удобнее для публичных API и отладки, protobuf — для общения сервисов между собой.

**Термины**
- **protobuf** *(новое)* — двоичный формат данных со схемой в `.proto`-файле

#### GO-24.1.2 Файл .proto: сообщения и поля
**Вопросы**
- [ ] Как описать сообщение в `.proto`? · `proto3 message syntax`
- [ ] Что значит `string name = 1;` — тип, имя и номер поля? · `protobuf field number`
- [ ] Как описать список (`repeated`) и вложенное сообщение? · `protobuf repeated nested message`
- [ ] Что такое `optional` в proto3 и зачем он (отличить «не задано» от нуля)? · `proto3 optional presence`
- [ ] Как описать перечисление и почему первое значение — `…_UNSPECIFIED = 0`? · `protobuf enum unspecified zero`

**Гуглить:** `proto3 language guide` · `protobuf best practices`

**Должен знать**
`message User { int64 id = 1; string name = 2; repeated string tags = 3; Address address = 4; }` — сообщение с полями: тип, имя и номер. Номер, а не имя, попадает в байты. `repeated` — список, поле с типом-сообщением — вложенная структура.
В proto3 непереданное поле равно нулевому значению — как в Go; чтобы отличать «не задано» от нуля, есть `optional`. Нулевое значение перечисления делают «не указано».

**Термины**
- **сообщение** — описание структуры данных в `.proto`
- **номер поля** — число, которым поле обозначается в байтах

#### GO-24.1.3 Генерация кода
**Вопросы**
- [ ] Как из `.proto` получить код на Go (`protoc` с плагином `protoc-gen-go`)? · `protoc go plugin`
- [ ] Что такое `buf` и чем он удобнее? · `buf build protobuf`
- [ ] Нужно ли хранить сгенерированный код в git рядом с исходным? · `commit generated protobuf code`
- [ ] Как выглядит сгенерированная структура и методы `Get…`? · `protobuf go generated getters`

**Гуглить:** `protobuf go tutorial` · `buf.build quickstart`

**Должен знать**
Компилятор `protoc` с плагином `protoc-gen-go` генерирует Go-код (для сервисов есть второй плагин — тема GO-24.2): структуры с полями и методами `GetName()` (они безопасны и на nil). Инструмент `buf` упрощает генерацию и проверяет схемы на ломающие изменения. Генерацию запускают командой в проекте, а сгенерированный код обычно хранят рядом с исходным.

**Термины**
- **генерация кода** — получение Go-типов из `.proto`

#### GO-24.1.4 Номера полей и совместимость схем
**Вопросы**
- [ ] Почему нельзя менять номер поля? · `protobuf never change field number`
- [ ] Как менять схему, не ломая старых клиентов (добавлять поля с новыми номерами)? · `protobuf backward compatibility`
- [ ] Что делает старый клиент с незнакомым полем? · `protobuf unknown fields`
- [ ] Как правильно удалить поле (`reserved`)? · `protobuf reserved fields`
- [ ] Почему переименовать поле безопасно, а сменить тип — нет? · `protobuf rename field vs change type`

**Гуглить:** `protobuf updating message type` · `buf breaking`

**Должен знать**
В байтах лежат номера, поэтому номер поля — его вечное имя. Сменить номер или тип — значит, старые клиенты прочитают мусор. Безопасно: добавлять новые поля с новыми номерами (старые клиенты незнакомое пропустят), переименовывать поля (имя в байты не попадает).
Удалённое поле объявляют `reserved` с его номером и именем, чтобы номер никто не занял снова.

**Термины**
- **совместимость схем** — новые и старые версии `.proto` понимают друг друга
- **`reserved`** — запрет повторно использовать номер удалённого поля

### GO-24.2 gRPC

#### GO-24.2.1 gRPC
**Вопросы**
- [ ] Что такое gRPC и на чём он работает (HTTP/2 + protobuf)? · `what is grpc`
- [ ] Почему gRPC называют «вызовом удалённой функции»? · `grpc remote procedure call`
- [ ] Что даёт HTTP/2 для gRPC (одно соединение, много вызовов, стримы)? · `grpc http2 multiplexing`
- [ ] Почему из браузера gRPC напрямую не вызвать? · `grpc browser grpc-web`

**Гуглить:** `grpc introduction` · `grpc go quickstart`

**Должен знать**
gRPC — фреймворк удалённого вызова: на клиенте вызываешь метод, как обычную функцию, — `client.GetUser(ctx, req)`, — а он выполняется на другом сервере. Под капотом HTTP/2 (много вызовов по одному соединению, потоки данных в обе стороны) и protobuf для сообщений.
Браузеры не дают нужного доступа к HTTP/2, поэтому для фронтенда нужен посредник (gRPC-Web); внутри компании между сервисами gRPC — обычный выбор.

**Термины**
- **gRPC** *(новое)* — фреймворк удалённого вызова процедур поверх HTTP/2 и protobuf
- **RPC** — вызов функции на другом компьютере как локальной

#### GO-24.2.2 Сервис в .proto
**Вопросы**
- [ ] Как описать сервис в `.proto`: `service Users { rpc GetUser(GetUserRequest) returns (User); }`? · `grpc service definition proto`
- [ ] Что генерируется для сервера (интерфейс для реализации) и для клиента (готовая структура)? · `grpc go generated server client`
- [ ] Как написать gRPC-сервер на Go: реализовать интерфейс и зарегистрировать на `grpc.NewServer()`? · `grpc go server example`
- [ ] Зачем встраивать `Unimplemented…Server` в свою реализацию? · `grpc UnimplementedServer embed why`

**Гуглить:** `grpc go basics tutorial` · `UnimplementedServer forward compatibility`

**Должен знать**
`service` в `.proto` перечисляет методы с типами запроса и ответа. Генератор даёт серверу интерфейс, который нужно реализовать, а клиенту — готовую структуру с методами. Сервер: структура, встраивающая `Unimplemented…Server`, методы `func (s *srv) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.User, error)`, затем `grpc.NewServer()`, регистрация и `Serve(listener)`.
Встраивание `Unimplemented…Server` делает реализацию совместимой с будущими методами: новые методы ответят «не реализовано», а не сломают сборку.

**Термины**
- **сервис gRPC** — набор удалённых методов, описанный в `.proto`

#### GO-24.2.3 Четыре вида вызовов: унарный и три вида стримов
**Вопросы**
- [ ] Какие четыре вида вызовов есть в gRPC? · `grpc unary server streaming client streaming bidirectional`
- [ ] Когда нужен серверный стрим (подписка на обновления), клиентский (загрузка частями), двусторонний (чат)? · `grpc streaming use cases`
- [ ] Как записывается стрим в `.proto` (`stream` перед типом)? · `grpc stream syntax proto`
- [ ] Как читать стрим в Go до `io.EOF`? · `grpc stream recv io.EOF`

**Гуглить:** `grpc streaming go example` · `grpc core concepts`

**Должен знать**
Унарный — один запрос, один ответ (как обычная функция). Серверный стрим — один запрос, поток ответов (подписка, большая выдача частями). Клиентский стрим — поток запросов, один ответ (загрузка файла частями). Двусторонний — потоки в обе стороны независимо (чат, телеметрия).
В `.proto` это `stream` перед типом; в Go стрим читают в цикле `Recv()` до `io.EOF`.

**Термины**
- **унарный вызов** — один запрос и один ответ
- **стрим** — поток сообщений в рамках одного вызова

#### GO-24.2.4 Коды статусов и дедлайны
**Вопросы**
- [ ] Как передать дедлайн и вернуть ошибку в gRPC? · `grpc deadline error codes`
- [ ] Какие коды статусов ты знаешь (`NotFound`, `InvalidArgument`, `DeadlineExceeded`, `Unavailable`, `Internal`)? · `grpc status codes list`
- [ ] Как вернуть ошибку с кодом (`status.Error(codes.NotFound, "…")`) и как прочитать код на клиенте (`status.Code(err)`)? · `grpc status.Error status.Code`
- [ ] Как дедлайн из `ctx` клиента доходит до сервера и дальше по цепочке? · `grpc deadline propagation`
- [ ] Какие коды можно повторять? · `grpc retryable status codes`

**Гуглить:** `grpc status codes` · `grpc deadlines`

**Должен знать**
Вместо кодов HTTP у gRPC свои коды статусов: `NotFound`, `InvalidArgument`, `AlreadyExists`, `PermissionDenied`, `Unauthenticated`, `DeadlineExceeded`, `Unavailable`, `Internal`. Сервер возвращает `status.Error(codes.NotFound, "user not found")`, клиент читает `status.Code(err)`.
Дедлайн задают контекстом клиента; gRPC передаёт его серверу, и `ctx` сервера отменится в тот же момент — а дальше передаётся во все вложенные вызовы. Повторять имеет смысл в основном `Unavailable`.

**Термины**
- **код статуса gRPC** — стандартный код результата вызова
- **дедлайн** — момент, после которого вызов отменяется на всех участниках

#### GO-24.2.5 Интерсепторы
**Вопросы**
- [ ] Что такое интерсептор и на что он похож в `net/http`? · `grpc interceptor middleware`
- [ ] Чем унарный интерсептор отличается от потокового? · `unary vs stream interceptor`
- [ ] Что обычно делают интерсепторами (логи, метаданные, восстановление после паники, проверка доступа)? · `grpc interceptor use cases`
- [ ] Как передать служебные данные запроса в gRPC (метаданные вместо заголовков)? · `grpc metadata`

**Гуглить:** `grpc go interceptors` · `go-grpc-middleware`

**Должен знать**
Интерсептор — middleware для gRPC: функция, которая получает вызов, делает что-то до и после и передаёт его дальше. Бывают для унарных вызовов и для стримов, клиентские и серверные. Им делают логирование, проверку доступа, восстановление после паники, передачу номера запроса.
Служебные данные вызова (аналог заголовков HTTP) называются метаданными.

**Термины**
- **интерсептор** *(новое)* — обёртка над вызовом gRPC, аналог middleware
- **метаданные** — служебные пары ключ-значение вызова gRPC

#### GO-24.2.6 gRPC против REST
**Вопросы**
- [ ] Когда выбрать gRPC, а когда REST? · `grpc vs rest when to use`
- [ ] Сравни по пунктам: формат, контракт, скорость, стримы, поддержка браузеров, удобство отладки. · `grpc rest comparison table`
- [ ] Почему внутри компании часто gRPC, а наружу — REST? · `grpc internal rest external`
- [ ] Чем контракт в `.proto` удобнее описания REST API для командной работы? · `grpc strong contract codegen`

**Гуглить:** `grpc vs rest` · `when to use grpc`

**Должен знать**
gRPC: двоичный protobuf, строгий контракт со сгенерированным кодом, быстрее, стримы из коробки, но нужен посредник для браузера и труднее отлаживать глазами. REST: текстовый JSON, понятен всем и работает в браузере и `curl`, кэшируется средствами HTTP, но контракт мягче и медленнее.
Типичный выбор: между своими сервисами — gRPC, для браузеров, мобильных приложений и внешних партнёров — REST.

**Термины**
- **gRPC против REST** — строгий быстрый RPC против простого универсального HTTP API
