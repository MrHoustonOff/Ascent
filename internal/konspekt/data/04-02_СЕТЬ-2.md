## СЕТЬ-2. HTTP и TLS

### СЕТЬ-2.1 HTTP

#### СЕТЬ-2.1.1 HTTP
**Вопросы**
- [ ] Что такое HTTP и поверх чего он работает? · `what is http`
- [ ] Почему HTTP называют протоколом «запрос — ответ»? · `http request response model`
- [ ] Что значит, что HTTP не хранит состояние между запросами? · `http stateless`
- [ ] Как посмотреть запрос и ответ во вкладке «Сеть» (Network) инструментов разработчика браузера? · `chrome devtools network tab`
- [ ] Почему HTTP/1.1 можно прочитать глазами — это текст? · `http 1.1 text protocol`

**Гуглить:** `http overview mdn` · `devtools network tab` · `http stateless meaning`

**Должен знать**
HTTP — прикладной протокол поверх TCP: клиент присылает запрос, сервер отвечает, и на этом обмен закончен. Каждый запрос самодостаточен — сервер по самому HTTP ничего не помнит о предыдущих; «память» добавляют отдельно, через заголовки. HTTP/1.1 — текст, его видно во вкладке «Сеть» инструментов разработчика в браузере.
Почти весь бэкенд разговаривает по HTTP: браузеры, мобильные приложения и сервисы между собой.

**Термины**
- **HTTP** *(новое)* — протокол «запрос — ответ» поверх TCP
- **отсутствие состояния** — каждый запрос обрабатывается независимо от прошлых

#### СЕТЬ-2.1.2 Запрос: метод, путь, заголовки, тело
**Вопросы**
- [ ] Из чего состоит HTTP-запрос? · `http request structure`
- [ ] Что такое строка запроса `GET /users/42?sort=name HTTP/1.1` по частям? · `http request line method path query`
- [ ] Что такое заголовки и какой заголовок обязателен в HTTP/1.1 (`Host`)? · `http host header required`
- [ ] Где передают параметры: в пути, в строке параметров после `?`, в теле? · `path vs query params vs body`
- [ ] Как отделяются заголовки от тела? · `http headers body blank line`

**Гуглить:** `http request anatomy` · `mdn http messages`

**Должен знать**
Запрос: строка запроса (метод, путь с параметрами после `?`, версия), затем заголовки `Имя: значение` по одному в строке, пустая строка и необязательное тело. `Host` указывает, к какому сайту запрос, — на одном адресе их может быть много.
Путь называет ресурс (`/users/42`), параметры после `?` уточняют (сортировка, фильтры), тело несёт данные (например, JSON с новым пользователем).

**Термины**
- **метод** — что сделать с ресурсом: `GET`, `POST` и другие
- **путь** — какой ресурс: `/users/42`
- **заголовок HTTP** *(новое)* — служебная пара `Имя: значение` в запросе или ответе
- **тело** — данные запроса или ответа

#### СЕТЬ-2.1.3 Ответ: код, заголовки, тело
**Вопросы**
- [ ] Из чего состоит HTTP-ответ? · `http response structure`
- [ ] Что значит строка `HTTP/1.1 404 Not Found`? · `http status line`
- [ ] Какие заголовки ответа встретятся чаще всего (`Content-Type`, `Content-Length`, `Location`)? · `common response headers`
- [ ] Как клиент понимает, где кончается тело (`Content-Length` или передача частями)? · `content-length chunked transfer encoding`

**Должен знать**
Ответ: строка состояния (версия, трёхзначный код, короткое описание), заголовки, пустая строка, тело. По коду клиент понимает исход, по заголовкам — что лежит в теле и сколько его. Длину тела задаёт `Content-Length` или передача частями, когда длина заранее неизвестна.

**Термины**

#### СЕТЬ-2.1.4 Методы GET, POST, PUT, PATCH, DELETE
**Вопросы**
- [ ] Чем `GET` отличается от `POST`? · `get vs post`
- [ ] Чем `PUT` отличается от `PATCH`? · `put vs patch`
- [ ] Почему у `GET` не принято передавать тело? · `get request with body`
- [ ] Какой метод выбрать для создания заказа, получения списка, замены профиля, изменения одного поля, удаления? · `http methods crud mapping`
- [ ] Что делают `HEAD` и `OPTIONS` — одной фразой? · `http head options methods`

**Гуглить:** `http methods mdn` · `put vs patch difference`

**Должен знать**
`GET` — получить ресурс, ничего не меняя. `POST` — создать или выполнить действие. `PUT` — заменить ресурс целиком тем, что прислали. `PATCH` — изменить часть полей. `DELETE` — удалить. Параметры `GET` передают в пути и после `?`, а не в теле.
Разница `PUT` и `PATCH`: `PUT` с неполными данными «стирает» непереданные поля, `PATCH` трогает только присланные.

**Термины**
- **`GET` / `POST` / `PUT` / `PATCH` / `DELETE`** — получить, создать, заменить, изменить часть, удалить

#### СЕТЬ-2.1.5 Безопасные и идемпотентные методы
**Вопросы**
- [ ] Какие методы безопасные, а какие идемпотентные? Зачем это знать? · `safe vs idempotent methods`
- [ ] Что такое идемпотентность простыми словами? · `idempotency explained`
- [ ] Почему `PUT` и `DELETE` идемпотентны, а `POST` — нет? · `why post not idempotent`
- [ ] Почему идемпотентный запрос можно безопасно повторить при сетевой ошибке? · `retry idempotent requests`
- [ ] Как сделать `POST` создания заказа безопасным для повтора (ключ идемпотентности)? · `idempotency key post`

**Гуглить:** `idempotent http methods` · `idempotency key stripe`

**Должен знать**
Безопасный метод ничего не меняет на сервере: `GET`, `HEAD`. Идемпотентный — повтор даёт тот же итог, что и один вызов: `GET`, `PUT`, `DELETE` (удалить дважды — всё равно удалено). `POST` не идемпотентен: два одинаковых запроса создадут два заказа.
Это важно при сбоях: ответ мог потеряться, и клиент не знает, выполнился ли запрос. Идемпотентный можно просто повторить; для `POST` клиент передаёт уникальный ключ, и сервер не выполняет повтор с тем же ключом.

**Термины**
- **безопасный метод** — метод, не меняющий данных
- **идемпотентность** *(новое)* — повтор операции даёт тот же результат, что и один раз

**Позже:** повтор `POST` и ключ идемпотентности — СЕТЬ-3.1.7; идемпотентность во всей системе — СИСД-3.1.5.

#### СЕТЬ-2.1.6 Группы кодов ответа
**Вопросы**
- [ ] Что значат группы кодов ответа 1xx, 2xx, 3xx, 4xx, 5xx? · `http status code classes`
- [ ] Почему 4xx — «виноват клиент», а 5xx — «виноват сервер»? · `4xx vs 5xx`
- [ ] Почему при 4xx повторять тот же запрос бессмысленно, а при некоторых 5xx — можно? · `retry on 5xx not 4xx`
- [ ] Почему вернуть `200` с текстом «ошибка» в теле — плохо? · `200 with error body antipattern`

**Гуглить:** `http status codes mdn` · `http cats`

**Должен знать**
Первая цифра кода — его смысл: 1xx — промежуточный ответ, 2xx — успех, 3xx — перенаправление, 4xx — ошибка запроса (клиент прислал не то), 5xx — ошибка сервера. Клиенты, библиотеки и мониторинг смотрят на код, поэтому ошибку возвращают правильным кодом, а не `200` с «ошибкой» в теле.
Тот же запрос при 4xx снова получит 4xx; при 5xx (особенно 502, 503, 504) повтор может помочь.

**Термины**
- **код ответа** *(новое)* — трёхзначный код исхода запроса

#### СЕТЬ-2.1.7 Частые коды ответа
**Вопросы**
- [ ] Чем `401` отличается от `403`? · `401 vs 403`
- [ ] Чем `502` отличается от `504`? · `502 vs 504`
- [ ] Когда `201`, а когда `204`? · `201 created 204 no content`
- [ ] Чем `400` отличается от `422`, а `409` — от них обоих? · `400 vs 422 vs 409`
- [ ] Что значат `301`, `304`, `429`, `503`? · `301 304 429 503 meaning`

**Гуглить:** `http status codes list` · `401 vs 403 explained`

**Должен знать**
`200` — успех, `201` — создано, `204` — успех без тела. `301` — ресурс переехал навсегда, `304` — не изменилось, бери из кэша. `400` — запрос не разобрать, `422` — разобрали, но данные не проходят проверку, `409` — конфликт с текущим состоянием (уже есть такой email). `401` — «не знаю, кто ты» (нет или неверны учётные данные), `403` — «знаю, но нельзя». `404` — нет ресурса, `429` — слишком часто.
`500` — ошибка в самом сервере. `502` — промежуточный сервер получил от следующего некорректный ответ, `504` — не дождался ответа. `503` — сервис временно недоступен.

**Термины**
- **`401` / `403`** — «не знаю, кто ты» / «знаю, но нельзя»
- **`502` / `504`** — плохой ответ / нет ответа от следующего сервера

**Граница:** 200, 201, 204, 301, 304, 400, 401, 403, 404, 409, 422, 429, 500, 502, 503, 504 — остальные не учим.

#### СЕТЬ-2.1.8 Заголовки Content-Type, Accept, Authorization
**Вопросы**
- [ ] Что говорит `Content-Type: application/json`? · `content-type header`
- [ ] Чем `Accept` отличается от `Content-Type`? · `accept vs content-type`
- [ ] Что передают в `Authorization` и почему не в пути? · `authorization header why not url`
- [ ] Почему без правильного `Content-Type` сервер может не разобрать тело? · `missing content-type json`

**Гуглить:** `content-type mdn` · `http accept header`

**Должен знать**
`Content-Type` — что лежит в теле этого сообщения: `application/json`, `text/html`, `multipart/form-data`. `Accept` — какой формат клиент хочет получить в ответ. `Authorization` — учётные данные клиента; их передают в заголовке, а не в пути, потому что пути попадают в журналы, историю и закладки.

**Термины**
- **`Content-Type`** — формат тела сообщения
- **`Accept`** — желаемый формат ответа
- **`Authorization`** — заголовок с учётными данными

#### СЕТЬ-2.1.9 Cookie
**Вопросы**
- [ ] Что такое cookie и как сервер его ставит (`Set-Cookie`)? · `http cookies explained`
- [ ] Как браузер сам отправляет cookie в следующих запросах? · `browser sends cookies automatically`
- [ ] Что значат атрибуты `HttpOnly`, `Secure`, `SameSite`, `Max-Age`? · `cookie attributes httponly secure samesite`
- [ ] Почему cookie — способ дать HTTP «память» между запросами? · `cookies session state`

**Гуглить:** `mdn http cookies` · `cookie samesite explained`

**Должен знать**
Cookie — небольшая строка, которую сервер просит браузер сохранить (`Set-Cookie: sid=abc; HttpOnly; Secure`), а браузер сам отправляет её обратно в каждом запросе к этому сайту (`Cookie: sid=abc`). Так HTTP получает «память» между запросами: по cookie сервер узнаёт клиента.
`HttpOnly` — cookie недоступна скриптам на странице, `Secure` — только по защищённому соединению, `SameSite` — ограничивает отправку с чужих сайтов, `Max-Age` — срок жизни.

**Термины**
- **cookie** *(новое)* — строка, которую браузер хранит и отправляет сайту в каждом запросе

#### СЕТЬ-2.1.10 Keep-alive
**Вопросы**
- [ ] Что такое keep-alive? · `http keep-alive`
- [ ] Почему открывать новое TCP-соединение на каждый запрос дорого? · `tcp connection per request cost`
- [ ] Включён ли keep-alive по умолчанию в HTTP/1.1? · `http 1.1 persistent connections default`
- [ ] Почему на одном соединении HTTP/1.1 запросы идут строго по очереди? · `http 1.1 one request at a time`

**Гуглить:** `http persistent connection` · `keep-alive explained`

**Должен знать**
Keep-alive — одно TCP-соединение используют для многих запросов подряд, а не открывают заново на каждый. Так экономится рукопожатие (а с защищённым соединением — ещё больше). В HTTP/1.1 это поведение по умолчанию.
Но на одном соединении HTTP/1.1 следующий запрос ждёт ответа на предыдущий, поэтому браузеры открывают к сайту несколько соединений параллельно.

**Термины**
- **keep-alive** *(новое)* — повторное использование соединения для многих запросов

**Позже:** переиспользование соединений в Go-клиенте — GO-23.1.4.

#### СЕТЬ-2.1.11 HTTP/1.1, HTTP/2 и HTTP/3
**Вопросы**
- [ ] Чем HTTP/2 отличается от HTTP/1.1? · `http/2 vs http/1.1`
- [ ] Что такое мультиплексирование: много запросов одновременно по одному соединению? · `http2 multiplexing`
- [ ] Почему HTTP/2 двоичный и что дало сжатие заголовков? · `http2 binary framing hpack`
- [ ] Что нового в HTTP/3 и почему он поверх UDP (QUIC)? · `http/3 quic`
- [ ] Какую проблему TCP решает HTTP/3 (блокировка в голове очереди)? · `http3 head of line blocking`

**Гуглить:** `http/1.1 vs http/2 vs http/3` · `quic explained`

**Должен знать**
HTTP/2 сохранил смысл запросов, но поменял передачу: двоичные кадры, много запросов одновременно по одному соединению (мультиплексирование), сжатие заголовков. Очередь запросов на соединении исчезла — но потеря одного TCP-пакета всё равно тормозит все потоки.
HTTP/3 работает поверх QUIC — протокола на UDP со своей надёжностью для каждого потока отдельно и с быстрым установлением соединения; потеря пакета задерживает только свой поток.

**Термины**
- **мультиплексирование** — несколько запросов одновременно по одному соединению
- **QUIC** — транспортный протокол поверх UDP, основа HTTP/3

**Граница:** QUIC — одной фразой.

#### СЕТЬ-2.1.12 Кэширование в HTTP: Cache-Control и ETag
**Вопросы**
- [ ] Зачем нужны `ETag` и `Cache-Control`? · `etag cache-control explained`
- [ ] Что значат `Cache-Control: max-age=3600`, `no-cache`, `no-store`? · `cache-control directives`
- [ ] Как работает проверка через `ETag` и `If-None-Match` с ответом `304`? · `etag if-none-match 304`
- [ ] Почему `no-cache` не значит «не кэшировать»? · `no-cache vs no-store`
- [ ] Почему ответы с данными пользователя нельзя кэшировать общим кэшем (`private`)? · `cache-control private public`

**Гуглить:** `mdn http caching` · `etag explained`

**Должен знать**
`Cache-Control: max-age=3600` — ответ можно брать из кэша час без обращения к серверу. `no-store` — не хранить вообще; `no-cache` — хранить можно, но каждый раз проверять у сервера. `private` — только кэш браузера, не общий.
`ETag` — «версия» ответа. Клиент присылает её в `If-None-Match`, и если ничего не изменилось, сервер отвечает `304` без тела — экономится передача данных.

**Термины**
- **`Cache-Control`** — правила кэширования ответа
- **`ETag`** — метка версии ответа для проверки свежести

#### СЕТЬ-2.1.13 CORS
**Вопросы**
- [ ] Зачем нужен CORS и кто его проверяет: сервер или браузер? · `cors explained`
- [ ] Что такое политика одного источника (same-origin) и что такое источник (схема, хост, порт)? · `same origin policy`
- [ ] Что такое предварительный запрос `OPTIONS` и когда браузер его делает? · `cors preflight request`
- [ ] Какими заголовками сервер разрешает чужой источник (`Access-Control-Allow-Origin`)? · `access-control-allow-origin`
- [ ] Почему запросы из программ и между серверами CORS не касается? · `cors only browsers`

**Гуглить:** `mdn cors` · `cors preflight explained`

**Должен знать**
Браузер по умолчанию не даёт скрипту со страницы одного источника (схема + хост + порт) читать ответы другого — это политика одного источника. CORS — способ для сервера сказать браузеру «этому источнику можно»: заголовком `Access-Control-Allow-Origin`. Для «непростых» запросов браузер сначала спрашивает разрешения запросом `OPTIONS`.
Проверяет браузер, а не сервер: программы и другие сервисы CORS не касается. Это защита пользователя браузера, а не сервера.

**Термины**
- **CORS** *(новое)* — правила, по которым браузер разрешает запросы к чужому источнику
- **источник** — схема, хост и порт страницы

#### СЕТЬ-2.1.14 WebSocket
**Вопросы**
- [ ] Что такое WebSocket и когда он нужен? · `websocket explained`
- [ ] Как обычный запрос «превращается» в WebSocket (заголовок `Upgrade`, ответ `101`)? · `websocket upgrade 101`
- [ ] PhoneGyro: почему телефон передаёт данные гироскопа по WebSocket, а не отдельными запросами? · `websocket realtime vs http polling`

**Должен знать**
WebSocket — постоянное двустороннее соединение поверх TCP: после обычного запроса с `Upgrade: websocket` сервер отвечает `101`, и дальше обе стороны шлют сообщения когда угодно. **Термины**
- **WebSocket** — постоянный двусторонний канал поверх соединения HTTP

**Граница:** одной фразой, когда нужен.

### СЕТЬ-2.2 TLS и HTTPS

#### СЕТЬ-2.2.1 Симметричное и асимметричное шифрование
**Вопросы**
- [ ] Чем симметричное шифрование отличается от асимметричного? · `symmetric vs asymmetric encryption`
- [ ] Почему асимметричное шифрование решает проблему «как передать ключ по открытой сети»? · `key exchange problem`
- [ ] Почему для самих данных всё же используют симметричное (оно быстрее)? · `why tls uses symmetric for data`
- [ ] Что такое цифровая подпись и как она связана с парой ключей? · `digital signature explained`

**Гуглить:** `symmetric vs asymmetric encryption` · `public key cryptography simple`

**Должен знать**
Симметричное шифрование — один общий ключ шифрует и расшифровывает; быстро, но ключ надо как-то передать. Асимметричное — пара ключей: открытый можно раздавать всем, а расшифровать или подписать может только владелец закрытого. Медленнее, но решает передачу ключа.
Поэтому защищённые соединения используют оба: асимметричное — чтобы безопасно договориться об общем ключе и доказать, кто ты; симметричное — чтобы шифровать сами данные. Подпись — закрытым ключом, проверка — открытым.

**Термины**
- **шифрование** *(новое)* — превращение данных в вид, понятный только владельцу ключа
- **открытый / закрытый ключ** — пара ключей асимметричного шифрования
- **цифровая подпись** — доказательство, что данные подписал владелец закрытого ключа

**Граница:** математика алгоритмов — не нужна.

#### СЕТЬ-2.2.2 Сертификат и центр сертификации
**Вопросы**
- [ ] Что такое сертификат и кто подтверждает, что ему можно верить? · `tls certificate explained`

**Должен знать**
Сертификат — открытый ключ сайта вместе с его именем и сроком, подписанные центром сертификации (ЦС). Браузер доверяет сертификату, если цепочка подписей ведёт к корневому ЦС из встроенного списка ОС или браузера.
PhoneGyro: для адреса `192.168.x.x` в домашней сети публичный ЦС сертификат не выдаст. Корневой ограничен локальными сетями, чтобы его нельзя было использовать для чужих сайтов.

**Термины**

- **цепочка доверия** — подписи от сертификата сайта до корневого ЦС

#### СЕТЬ-2.2.3 Рукопожатие TLS
**Вопросы**
- [ ] Как проходит рукопожатие TLS в общих чертах? · `tls handshake explained`
- [ ] Что клиент проверяет в сертификате (подпись, срок, имя)? · `certificate validation client`
- [ ] Как стороны получают общий ключ, не передавая его по сети? · `tls key exchange diffie hellman simple`
- [ ] Чем TLS 1.3 быстрее TLS 1.2 (один круг вместо двух)? · `tls 1.3 vs 1.2 handshake`
- [ ] Чем SSL отличается от TLS? · `ssl vs tls`

**Гуглить:** `tls 1.3 handshake` · `illustrated tls connection`

**Должен знать**
После TCP-рукопожатия клиент и сервер проходят рукопожатие TLS: клиент предлагает параметры, сервер присылает сертификат, клиент проверяет подпись, срок и имя, затем стороны договариваются об общем симметричном ключе так, что подслушивающий его не узнает. Дальше все данные шифруются этим ключом. TLS 1.3 укладывает это в один круг до сервера.
SSL — старое название и старые небезопасные версии; сейчас используется только TLS 1.2 и 1.3.

**Термины**
- **TLS** *(новое)* — протокол защищённого соединения поверх TCP
- **рукопожатие TLS** — проверка сертификата и выработка общего ключа

**Граница:** алгоритмы шифрования — названиями.

### СЕТЬ-2.3 Путь запроса целиком

#### СЕТЬ-2.3.1 Что происходит, когда вводишь адрес в браузере
**Вопросы**
- [ ] Расскажи по шагам, что происходит, когда вводишь адрес сайта в браузере. · `what happens when you type a url`
- [ ] Где в этом пути DNS, TCP-рукопожатие, рукопожатие TLS, запрос и ответ? · `url to page steps dns tcp tls http`
- [ ] Что происходит после ответа: разбор страницы, загрузка картинок и скриптов отдельными запросами? · `browser rendering subresources`
- [ ] На каком шаге запрос может застрять и как это понять (`nslookup`, вкладка «Сеть» в браузере)? · `debug slow website steps`
- [ ] Где в этом пути кэши, которые могут ускорить шаги? · `caches along request path`

**Гуглить:** `what happens when you type google.com` · `alex what-happens-when github`

**Должен знать**
Браузер разбирает адрес → находит адрес сервера через DNS (кэши браузера и ОС, затем резолвер) → открывает TCP-соединение (рукопожатие) → проходит рукопожатие TLS и проверяет сертификат → отправляет HTTP-запрос → сервер обрабатывает и отвечает → браузер разбирает страницу и отдельными запросами (по тому же соединению) догружает картинки, стили и скрипты.
Застрять можно на каждом шаге: имя не находится — DNS; долго нет соединения — сеть или брандмауэр; ошибка сертификата — TLS; код 5xx — сервер. Вкладка «Сеть» в браузере показывает время каждого шага.

**Термины**
- **путь запроса** — DNS → TCP → TLS → HTTP → ответ → догрузка ресурсов
