## СЕТЬ-3. REST и аутентификация

### СЕТЬ-3.1 REST

#### СЕТЬ-3.1.1 REST
**Вопросы**
- [ ] Что такое REST и что такое ресурс? · `what is rest api`
- [ ] Почему REST — стиль, а не стандарт? · `rest is architectural style not standard`
- [ ] Какие главные идеи REST: ресурсы с адресами, методы HTTP как действия, отсутствие состояния на сервере между запросами? · `rest principles`
- [ ] Чем REST отличается от «просто HTTP-ручек» вида `/doSomething`? · `rest vs rpc over http`
- [ ] Какие есть альтернативы (RPC-стиль, GraphQL) — названиями? · `rest vs grpc vs graphql`

**Гуглить:** `rest api explained` · `rest vs rpc` · `restful api design`

**Должен знать**
REST — стиль проектирования API поверх HTTP. Данные описываются как ресурсы с адресами (`/orders/42`), действия над ними — методами HTTP (`GET` прочитать, `POST` создать…), а результат — кодами ответа. Каждый запрос несёт всё нужное, сервер не помнит клиента между запросами.
Это не стандарт, а набор договорённостей, поэтому вокруг него много споров. Альтернативы — RPC-стиль (вызвать «функцию» сервера) и GraphQL.

**Термины**
- **REST** *(новое)* — стиль API: ресурсы, методы HTTP, коды ответа
- **ресурс** — сущность API с собственным адресом

**Позже:** gRPC — GO-24.2.1; gRPC против REST — GO-24.2.6.

#### СЕТЬ-3.1.2 Ресурсы и пути
**Вопросы**
- [ ] Как будут выглядеть пути и методы для списка заказов, одного заказа и его отмены? · `rest api path naming`
- [ ] Почему в путях существительные во множественном числе, а не глаголы (`/orders`, а не `/getOrders`)? · `rest nouns not verbs`
- [ ] Как выразить вложенность (`/users/42/orders`) и когда она лишняя? · `nested resources rest`
- [ ] Как оформить действие, которое не ложится на CRUD (отмена заказа)? · `rest action endpoint cancel`
- [ ] Где передавать фильтры и сортировку? · `rest filtering sorting query params`

**Гуглить:** `rest resource naming` · `rest api design best practices`

**Должен знать**
Путь называет ресурс существительным во множественном числе: `GET /orders` — список, `POST /orders` — создать, `GET /orders/42` — один заказ, `PATCH /orders/42` — изменить, `DELETE /orders/42` — удалить. Вложенность показывает принадлежность (`/users/42/orders`), но больше одного уровня обычно не нужно.
Действия вне CRUD оформляют как подресурс или отдельное действие: `POST /orders/42/cancel`. Фильтры и сортировка — в параметрах после `?`: `GET /orders?status=paid&sort=-created_at`.

**Термины**
- **CRUD** — создать, прочитать, изменить, удалить
- **подресурс** — ресурс внутри другого: `/orders/42/items`

#### СЕТЬ-3.1.3 Какой код ответа вернуть
**Вопросы**
- [ ] Какие коды вернуть при создании, при конфликте и при ошибке в теле запроса? · `rest status codes create conflict validation`
- [ ] Что вернуть, если заказа нет: `404` или `200` с пустым телом? · `rest 404 vs empty`
- [ ] Что вернуть при успешном удалении? · `rest delete 204`
- [ ] Как оформить тело ошибки, чтобы клиенту было понятно (код, сообщение, поля)? · `rest error response format problem details`

**Гуглить:** `rest status codes cheat sheet` · `rfc 9457 problem details`

**Должен знать**
Создали — `201` (и `Location` с адресом нового ресурса). Удалили или изменили без тела ответа — `204`. Нет ресурса — `404`. Запрос не разобрать — `400`, данные не проходят проверку — `422` (часто тоже `400`), конфликт с состоянием (email занят, заказ уже оплачен) — `409`. Ошибка сервера — `500`.
Тело ошибки — в одном формате на весь API: машинный код, сообщение для человека и при необходимости список полей с ошибками.

**Термины**
- **формат ошибки** — единая структура тела ответа при ошибке

#### СЕТЬ-3.1.4 Пагинация: смещение и курсор
**Вопросы**
- [ ] Чем пагинация через смещение хуже пагинации через курсор? · `offset vs cursor pagination`
- [ ] Почему при смещении строки «съезжают», если между страницами добавили запись? · `offset pagination duplicates skipped`
- [ ] Как устроен курсор: «дай 20 после `id = 1234`»? · `keyset pagination`
- [ ] Почему курсор работает быстро даже на миллионной странице? · `cursor pagination performance`
- [ ] Чего курсор не умеет (перейти сразу на страницу 57)? · `cursor pagination drawbacks`

**Гуглить:** `cursor vs offset pagination` · `keyset pagination`

**Должен знать**
Смещение — `?page=3&per_page=20` → `LIMIT 20 OFFSET 40`. Просто, но медленно на дальних страницах (базе нужно пройти все пропущенные строки), и при вставке новых записей строки сдвигаются: что-то повторится, что-то пропадёт.
Курсор — клиент получает «где остановились» (например, последний `id`) и просит следующие: `WHERE id > 1234 ORDER BY id LIMIT 20`. Быстро на любой глубине и устойчиво к вставкам, но нельзя прыгнуть на произвольную страницу.

**Термины**
- **пагинация** *(новое)* — выдача списка частями
- **курсор** — метка «где остановились» для запроса следующей части

**Позже:** почему курсор быстр в базе — PG-2.3.1.

#### СЕТЬ-3.1.5 Версионирование API
**Вопросы**
- [ ] Как версионировать API: в пути (`/v1/`), в заголовке, в параметре? · `api versioning strategies`
- [ ] Какие изменения ломают клиентов, а какие нет (добавить поле — можно, переименовать — нельзя)? · `breaking vs non breaking api changes`
- [ ] Почему старую версию нельзя просто выключить в день выхода новой? · `api deprecation period`
- [ ] Как жить без новой версии, добавляя только необязательные поля? · `backward compatible api evolution`

**Гуглить:** `rest api versioning` · `breaking changes api`

**Должен знать**
Версию чаще всего пишут в пути: `/v1/orders`. Новая версия нужна только при ломающих изменениях: удалить или переименовать поле, поменять тип, сделать поле обязательным. Добавить новое необязательное поле или новый путь — не ломает, если клиенты игнорируют незнакомые поля.
Старую версию поддерживают, пока клиенты не перейдут: мобильные приложения обновляются месяцами.

**Термины**
- **ломающее изменение** — изменение API, после которого старые клиенты перестают работать
- **обратная совместимость** — новая версия понимает старых клиентов

#### СЕТЬ-3.1.7 Повтор POST и ключ идемпотентности
**Вопросы**
- [ ] Клиент повторил `POST` создания платежа из-за таймаута. Как не создать два платежа? · `idempotency key payment`
- [ ] Как устроен ключ идемпотентности: клиент генерирует, сервер запоминает результат? · `idempotency-key header`
- [ ] Что должен сделать сервер, если пришёл тот же ключ, а первый запрос ещё выполняется? · `idempotency key concurrent request`
- [ ] Где хранить ключи и сколько (таблица с ограничением уникальности, срок жизни)? · `store idempotency keys database unique`
- [ ] Что делать, если с тем же ключом пришло другое тело? · `idempotency key different payload`

**Гуглить:** `idempotency keys stripe` · `designing robust apis idempotency`

**Должен знать**
Клиент генерирует уникальный ключ (UUID) для каждой операции и шлёт его в заголовке `Idempotency-Key`; при повторе — тот же ключ. Сервер сохраняет ключ вместе с результатом в таблицу с ограничением уникальности: первый запрос выполняется, повтор с тем же ключом получает сохранённый ответ, а не второй платёж.
Если первый ещё выполняется — повтор получает `409` или ждёт. Ключ с другим телом — ошибка. Ключи хранят ограниченное время (например, сутки).

**Термины**
- **ключ идемпотентности** — уникальный ключ операции, по которому сервер узнаёт повтор

### СЕТЬ-3.2 Кто ты и что тебе можно

#### СЕТЬ-3.2.1 Аутентификация против авторизации
**Вопросы**
- [ ] Чем аутентификация отличается от авторизации? · `authentication vs authorization`
- [ ] Какой код ответа при проблеме с каждой (`401` и `403`)? · `401 authentication 403 authorization`
- [ ] Приведи пример из жизни (пропуск на входе и доступ в кабинет). · `authn authz analogy`
- [ ] Что такое роли и права — в общих словах? · `rbac simple`

**Гуглить:** `authentication vs authorization` · `аутентификация и авторизация разница`

**Должен знать**
Аутентификация — «кто ты?»: проверка, что пользователь тот, за кого себя выдаёт (пароль, код, сертификат). Авторизация — «что тебе можно?»: проверка прав уже известного пользователя. Пропуск на входе в здание — аутентификация, доступ в конкретный кабинет — авторизация.
Ошибка аутентификации — `401`, авторизации — `403`. Права часто задают через роли: «администратор», «покупатель».

**Термины**
- **аутентификация** *(новое)* — установление, кто пользователь
- **авторизация** *(новое)* — проверка, что пользователю разрешено

#### СЕТЬ-3.2.2 Хранение паролей
**Вопросы**
- [ ] Как правильно хранить пароли и зачем соль? · `how to store passwords securely`
- [ ] Почему пароли нельзя хранить как есть и нельзя «просто зашифровать»? · `never store plaintext passwords`
- [ ] Почему обычный быстрый хеш (SHA-256) — плохой выбор для паролей? · `why not sha256 for passwords`
- [ ] Чем хороши `bcrypt` и `argon2id` (специально медленные)? · `bcrypt vs argon2`
- [ ] Как проверить пароль при входе, если исходный не хранится? · `verify password hash`

**Гуглить:** `password hashing best practices` · `owasp password storage cheat sheet` · `go bcrypt`

**Должен знать**
Пароли не хранят — хранят результат специальной хеш-функции. При входе от введённого пароля снова считают хеш и сравнивают. Соль — случайная строка, уникальная для каждого пользователя и смешиваемая с паролем: одинаковые пароли дают разные хеши, и заранее посчитанные таблицы не помогают.
Для паролей нужны намеренно медленные функции — `bcrypt`, `argon2id`, `scrypt`: перебор миллиардов вариантов становится непосильным. Быстрые хеши вроде SHA-256 для этого не годятся. В Go — `golang.org/x/crypto/bcrypt`.

**Термины**
- **соль** *(новое)* — случайная добавка к паролю перед хешированием
- **хеш пароля** — результат медленной хеш-функции от пароля и соли

#### СЕТЬ-3.2.3 Сессия на сервере и cookie
**Вопросы**
- [ ] Как работает сессия с cookie? · `session based authentication`
- [ ] Где хранятся данные сессии и что лежит в cookie (только случайный идентификатор)? · `session id cookie server store`
- [ ] Как выйти из системы и как «выкинуть» пользователя со всех устройств? · `logout invalidate session`
- [ ] Почему cookie сессии ставят с `HttpOnly`, `Secure`, `SameSite`? · `session cookie security flags`
- [ ] Где хранить сессии, если серверов несколько? · `shared session store multiple servers`

**Гуглить:** `session authentication explained` · `owasp session management`

**Должен знать**
После входа сервер создаёт сессию — запись в своём хранилище (база или быстрое хранилище в памяти) со сведениями о пользователе — и отдаёт браузеру cookie со случайным идентификатором сессии. Каждый следующий запрос несёт cookie, сервер находит сессию и узнаёт пользователя.
Выход — удалить запись, и cookie становится бесполезной; так же легко выкинуть со всех устройств. Cookie сессии ставят с `HttpOnly`, `Secure` и `SameSite`. Если серверов несколько, хранилище сессий должно быть общим.

**Термины**
- **сессия** — запись на сервере о вошедшем пользователе
- **идентификатор сессии** — случайная строка в cookie, по которой находят сессию

#### СЕТЬ-3.2.4 JWT
**Вопросы**
- [ ] Что такое JWT и из чего он состоит (заголовок, полезная нагрузка, подпись)? · `jwt structure explained`
- [ ] Почему содержимое JWT видно любому, но подделать его нельзя? · `jwt signed not encrypted`
- [ ] Как сервер проверяет JWT без обращения к базе? · `jwt stateless verification`
- [ ] Почему JWT нельзя просто отозвать до истечения срока? · `jwt revocation problem`
- [ ] Где передавать токен (`Authorization: Bearer …`) и что нельзя класть внутрь? · `bearer token header jwt sensitive data`

**Гуглить:** `jwt introduction jwt.io` · `jwt revocation` · `jwt pitfalls`

**Должен знать**
Токен — строка, которую клиент предъявляет вместо пароля. JWT — токен из трёх частей через точку: заголовок, полезная нагрузка (кто пользователь, до какого времени токен действует) и подпись сервера. Части не зашифрованы, а только закодированы — прочитать может любой, поэтому секретов внутри не держат. Но изменить нельзя: подпись не сойдётся.
Сервер проверяет подпись и срок сам, без базы — это удобно. Обратная сторона: выданный JWT действует до конца срока, и «отозвать» его можно только списком запрещённых токенов. Передают в `Authorization: Bearer <токен>`.

**Термины**
- **токен** *(новое)* — строка-доказательство, которую клиент предъявляет серверу
- **JWT** *(новое)* — подписанный токен с данными о пользователе и сроком

#### СЕТЬ-3.2.5 Access- и refresh-токены
**Вопросы**
- [ ] Зачем нужны два токена: access и refresh? · `access token vs refresh token`
- [ ] Почему access-токен живёт минуты, а refresh — дни? · `short lived access token`
- [ ] Как клиент получает новый access-токен по refresh-токену? · `token refresh flow`
- [ ] Почему refresh-токен хранят на сервере и меняют при каждом использовании? · `refresh token rotation`
- [ ] Как это решает проблему отзыва JWT? · `refresh token revocation`

**Гуглить:** `refresh token explained` · `refresh token rotation`

**Должен знать**
Access-токен (обычно JWT) живёт коротко — минуты — и проверяется без базы на каждом запросе. Refresh-токен живёт долго, хранится на сервере и используется только для получения нового access-токена. Так отзыв становится возможным: удалили refresh-токен — через несколько минут пользователь потеряет доступ.
Хорошая практика — выдавать новый refresh-токен при каждом обновлении, а старый сразу аннулировать: украденный токен выдаст себя при повторном использовании.

**Термины**
- **access-токен** — короткоживущий токен для запросов
- **refresh-токен** — долгоживущий токен для получения нового access-токена

#### СЕТЬ-3.2.6 Сессия против JWT
**Вопросы**
- [ ] Что такое JWT и чем он отличается от сессии? · `session vs jwt`
- [ ] Сравни: где хранится состояние, как отозвать, нужна ли база на каждом запросе. · `session vs token comparison`
- [ ] Почему для обычного веб-сайта сессии часто проще и безопаснее? · `sessions better than jwt for web apps`
- [ ] Когда JWT уместнее (между сервисами, мобильные клиенты)? · `jwt use cases microservices`

**Гуглить:** `jwt vs session cookies` · `stop using jwt for sessions`

**Должен знать**
Сессия: состояние на сервере, в cookie только идентификатор; каждый запрос — обращение к хранилищу, зато отзыв мгновенный. JWT: состояние в самом токене, проверка без хранилища, но отзыв сложен, и токен больше.
Для обычного сайта сессии с cookie проще и безопаснее. JWT удобен, когда проверять должны многие сервисы без общего хранилища, и для мобильных и внешних клиентов — обычно вместе с refresh-токенами.

**Термины**
- **сессия против JWT** — состояние на сервере против состояния в токене

#### СЕТЬ-3.2.7 OAuth 2.0
**Вопросы**
- [ ] Что такое OAuth в одной фразе? · `oauth 2.0 simple explanation`
- [ ] Как работает «Войти через Яндекс/Google» в общих чертах? · `login with google oauth flow simple`

**Гуглить:** `oauth 2.0 simplified`

**Должен знать**
OAuth 2.0 — протокол, по которому пользователь разрешает приложению действовать от его имени в другом сервисе, не отдавая пароль: «Войти через Яндекс» — приложение получает от Яндекса токен с ограниченными правами.

**Термины**
- **OAuth** *(новое)* — протокол выдачи приложению прав доступа через чужой сервис

**Граница:** одной фразой, что это вход через чужой сервис.
