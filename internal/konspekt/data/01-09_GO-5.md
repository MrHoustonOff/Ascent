## GO-5. Пакеты и модули

### GO-5.1 Свой пакет

#### GO-5.1.1 Несколько файлов в одном пакете
**Вопросы**
- [ ] Как разложить код одного пакета по нескольким файлам? · `go package multiple files`
- [ ] Почему функция из `a.go` видна в `b.go` без импорта? · `go same package different files visibility`
- [ ] Почему все файлы в одной папке должны иметь одинаковую строку `package`? · `go found packages main and x in directory`
- [ ] Как запустить программу из нескольких файлов (`go run .` вместо `go run main.go`)? · `go run . vs go run main.go`
- [ ] Как решать, что положить в отдельный файл? · `go organize code into files`

**Гуглить:** `golang package multiple files` · `go run multiple files`

**Должен знать**
Пакет в Go — это папка: все `.go`-файлы в ней с одинаковой строкой `package` составляют один пакет, и имена из одного файла видны во всех остальных без импорта. Разные имена пакетов в одной папке — ошибка компиляции.
Поэтому запускают и собирают папку целиком: `go run .`. Если запустить `go run main.go`, компилятор увидит только один файл и не найдёт функции из соседних.

**Термины**
- **файл пакета** — `.go`-файл, входящий в пакет своей папки

**Граница:** файлы, которые собираются только под определённую ОС, — знать, что так бывает.

#### GO-5.1.2 Свой пакет в подпапке
**Вопросы**
- [ ] Как создать свой пакет в подпапке и импортировать его? · `go create package subdirectory import`
- [ ] Из чего складывается путь импорта: путь модуля + путь папки? · `go import path module path folder`
- [ ] Должно ли имя пакета совпадать с именем папки? · `go package name vs directory name`
- [ ] Почему пакеты не могут импортировать друг друга по кругу? · `go import cycle not allowed`
- [ ] Как называть пакеты (коротко, строчными, без `util` и `common`)? · `go package naming conventions`

**Гуглить:** `golang create your own package` · `go import cycle` · `go blog package names`

**Должен знать**
Подпапка — новый пакет. Его путь импорта — путь модуля из `go.mod` плюс путь папки: модуль `example.com/app`, папка `store` → `import "example.com/app/store"`, вызов `store.Save()`. Имя пакета принято делать таким же, как имя папки: короткое, строчное, без подчёркиваний.
Импорт по кругу (A импортирует B, B — A) запрещён — компилятор откажет. Это заставляет продумывать, кто от кого зависит.

**Термины**
- **путь импорта** — путь модуля плюс путь папки пакета
- **циклический импорт** — пакеты импортируют друг друга по кругу; запрещено

#### GO-5.1.3 Экспорт имён и инкапсуляция
**Вопросы**
- [ ] Как в Go сделать имя видимым из другого пакета? · `go exported names capital letter`
- [ ] Что будет при обращении к `store.save()` из другого пакета? · `go cannot refer to unexported name`
- [ ] Что такое инкапсуляция и как она связана с экспортом? · `encapsulation go packages`
- [ ] Почему в Go видимость задаётся на уровне пакета, а не файла? · `go visibility package level`
- [ ] Чем это отличается от соглашения `_name` в Python? · `python underscore private convention vs go`
- [ ] Зачем папка `internal` и что она запрещает? · `go internal packages`

**Гуглить:** `golang exported unexported` · `go encapsulation` · `go internal directory`

**Должен знать**
Имя, которое начинается с заглавной буквы (`Save`, `MaxSize`), экспортируется — видно из других пакетов. Со строчной (`save`) — видно только внутри своего пакета. Это правило одно для функций, переменных, констант и типов.
Инкапсуляция — прятать детали реализации и показывать наружу только то, на что можно опираться. В Go она устроена на уровне пакета, и компилятор её соблюдает — в отличие от `_name` в Python, которое лишь соглашение. Пакет в папке `internal` можно импортировать только из кода рядом с ней.

**Термины**
- **экспорт** *(новое)* — имя с заглавной буквы видно из других пакетов
- **инкапсуляция** *(новое)* — сокрытие деталей реализации за ограниченным набором доступных имён
- **`internal`** — папка, пакеты которой доступны только «своему» коду

#### GO-5.1.4 Псевдонимы импорта и пустой импорт
**Вопросы**
- [ ] Как импортировать пакет под другим именем и когда это нужно? · `go import alias`
- [ ] Что делает `import _ "pkg"` и зачем нужен такой импорт? · `go blank import`
- [ ] Почему драйвер базы данных подключают через пустой импорт? · `go blank import database driver`
- [ ] Что такое импорт через точку (`import . "pkg"`) и почему его не любят? · `go dot import discouraged`

**Гуглить:** `golang import alias` · `go blank import side effects`

**Должен знать**
`import str "strings"` — свой локальный псевдоним для пакета; нужен при совпадении имён двух пакетов. `import _ "pkg"` — пустой импорт: имена пакета не используются, но он загружается и выполняет свою подготовку при запуске. Так подключают, например, драйверы баз данных, которые сами регистрируются в общем списке.
`import . "pkg"` вываливает имена пакета в текущий файл без префикса — читать такой код трудно, поэтому так почти не делают.

**Термины**
- **псевдоним импорта** — локальное имя для импортированного пакета
- **пустой импорт** — импорт ради подготовки пакета при запуске, без использования его имён

### GO-5.2 Инициализация пакета

#### GO-5.2.1 Инициализация переменных пакета
**Вопросы**
- [ ] В каком порядке получают значения переменные пакета? · `go package variable initialization order`
- [ ] Почему `var a = b + 1; var b = 2` работает, хотя `b` объявлена ниже? · `go initialization dependency order`
- [ ] В каком порядке инициализируются пакеты: сначала импортированные, потом свой? · `go package initialization order imports`
- [ ] Сколько раз инициализируется пакет, который импортируют несколько других пакетов? · `go package initialized once`

**Гуглить:** `golang package initialization` · `go spec package initialization`

**Должен знать**
До запуска `main` Go подготавливает пакеты: сначала все импортированные (по цепочке зависимостей), затем текущий. Каждый пакет подготавливается ровно один раз, даже если его импортируют многие.
Внутри пакета переменные получают значения в порядке зависимостей: если `a` зависит от `b`, сначала посчитают `b`, независимо от порядка строк в файле.

**Термины**
- **инициализация пакета** — подготовка пакета до запуска `main`

**Граница:** точные правила порядка между файлами — не нужны; не пиши код, который от них зависит.

#### GO-5.2.2 Функция init
**Вопросы**
- [ ] Что такое `init` и когда она вызывается? · `golang init function`
- [ ] Сколько функций `init` может быть в одном пакете и в одном файле? · `multiple init functions go`
- [ ] Можно ли вызвать `init` вручную? · `go cannot call init`
- [ ] В каком порядке: переменные пакета, `init`, `main`? · `go init order variables main`
- [ ] Для чего `init` используют в стандартной библиотеке и драйверах? · `go init registration pattern`

**Гуглить:** `golang init function` · `go init order`

**Должен знать**
`func init()` — функция без параметров и результатов, которую Go вызывает сам после инициализации переменных пакета и до `main`. Их может быть несколько — даже в одном файле, — и вызвать их вручную нельзя.
Порядок запуска программы: пакеты-зависимости (переменные, затем `init`) → переменные своего пакета → его `init` → `main`. Типичное применение — регистрация драйвера или формата в общем списке.

**Термины**
- **init** *(новое)* — функция, которую Go вызывает при подготовке пакета до `main`

#### GO-5.2.3 Минусы init
**Вопросы**
- [ ] Чем плох `init` и почему его стараются избегать? · `go init considered harmful`
- [ ] Почему `init` неудобен для тестов? · `go init testing problems`
- [ ] Почему в `init` нельзя нормально вернуть ошибку? · `go init cannot return error`
- [ ] Чем явная функция подготовки, вызванная из `main`, лучше? · `explicit initialization vs init go`

**Гуглить:** `go avoid init functions` · `uber go style guide init`

**Должен знать**
`init` срабатывает скрыто, просто от того, что пакет импортировали: читатель `main` не видит, что произошло. Вернуть ошибку из него нельзя — остаётся только паника. В тестах он выполняется всегда, даже когда мешает.
Поэтому подготовку (чтение настроек, подключение к базе) делают явной функцией и вызывают из `main`. `init` оставляют для простых вещей без побочных эффектов.

**Термины**
- **скрытое поведение** — то, что происходит без видимого вызова в коде

### GO-5.3 Чужие модули

#### GO-5.3.1 go get и внешние модули
**Вопросы**
- [ ] Как подключить внешний модуль? · `go get module`
- [ ] Что меняется в `go.mod` после `go get`: строка `require` и версия? · `go.mod require directive`
- [ ] Как выбрать конкретную версию (`@v1.2.3`, `@latest`)? · `go get specific version`
- [ ] Что значат части версии `v1.2.3` (семантическое версионирование)? · `semantic versioning explained`
- [ ] Где Go хранит скачанные модули на компьютере? · `go module cache location`
- [ ] Почему у модуля версии v2 и выше другой путь импорта (`/v2`)? · `go module major version suffix v2`

**Гуглить:** `go get tutorial` · `semver explained` · `go modules reference`

**Должен знать**
`go get example.com/lib@v1.4.0` скачивает модуль и записывает зависимость в `go.mod` строкой `require`. После этого пакеты модуля можно импортировать. Скачанное кладётся в общий кэш на компьютере, а не в проект.
Версии следуют семантическому версионированию: `vMAJOR.MINOR.PATCH`; изменение MAJOR означает, что старый код может сломаться, поэтому у v2+ меняется и путь импорта.

**Термины**
- **зависимость** — чужой модуль, которым пользуется твой проект
- **`require`** — строка в `go.mod`, задающая зависимость и её версию
- **семантическое версионирование** — правило `MAJOR.MINOR.PATCH` для номеров версий

**Граница:** как Go выбирает версию, когда несколько зависимостей требуют разные, — одной фразой: берёт наименьшую подходящую всем.

#### GO-5.3.2 go.sum
**Вопросы**
- [ ] Что лежит в `go.sum` и зачем он нужен? · `go.sum file explained`
- [ ] Что такое контрольная сумма и как она защищает от подмены кода? · `checksum verify download`
- [ ] Почему `go.sum` нужно класть в систему контроля версий вместе с `go.mod`? · `should go.sum be committed`
- [ ] Что значит ошибка `checksum mismatch`? · `go checksum mismatch`
- [ ] Что такое общая база контрольных сумм `sum.golang.org`? · `go checksum database sum.golang.org`

**Гуглить:** `go.sum explained` · `go module checksum database` · `go.mod vs go.sum`

**Должен знать**
`go.mod` говорит, *какие* версии зависимостей нужны, а `go.sum` — *какими они должны быть побайтово*: в нём контрольные суммы каждой скачанной версии. При каждой загрузке Go сверяет сумму; не совпала — сборка останавливается, потому что код мог быть подменён.
Оба файла хранят в проекте вместе: так у всех разработчиков и на сервере собирается в точности один и тот же код.

**Термины**
- **go.sum** *(новое)* — файл контрольных сумм зависимостей
- **контрольная сумма** — короткое число, вычисленное по содержимому; меняется при любом изменении

**Граница:** как вычисляется контрольная сумма — не нужно.

#### GO-5.3.3 go mod tidy
**Вопросы**
- [ ] Что делает `go mod tidy`? · `go mod tidy what does it do`
- [ ] Когда его нужно запускать (после добавления или удаления импорта)? · `when to run go mod tidy`
- [ ] Что значат строки с `// indirect` в `go.mod`? · `go.mod indirect dependencies`
- [ ] Чем `go mod tidy` отличается от `go get`? · `go get vs go mod tidy`

**Гуглить:** `go mod tidy` · `go.mod indirect`

**Должен знать**
`go mod tidy` приводит `go.mod` и `go.sum` в соответствие с кодом: добавляет зависимости, которые импортируются, но не записаны, и удаляет те, что больше не используются. Его запускают после изменения импортов и перед сохранением изменений.
`// indirect` помечает зависимость, которую твой код напрямую не импортирует, — она нужна какой-то из твоих зависимостей.

**Термины**
- **`go mod tidy`** — команда, приводящая `go.mod` и `go.sum` в порядок
- **косвенная зависимость** — зависимость твоей зависимости

#### GO-5.3.4 Документация пакетов: go doc и pkg.go.dev
**Вопросы**
- [ ] Как посмотреть описание функции из терминала (`go doc strings.Split`)? · `go doc command`
- [ ] Что можно найти на pkg.go.dev и как оценить, живой ли модуль? · `pkg.go.dev`
- [ ] Как писать комментарий к функции, чтобы он стал документацией? · `go doc comments`
- [ ] Где смотреть примеры использования в документации стандартной библиотеки? · `go documentation examples`

**Гуглить:** `go doc command` · `pkg.go.dev` · `go doc comments guide`

**Должен знать**
`go doc strings.Split` показывает описание прямо в терминале; pkg.go.dev — сайт с документацией всех публичных модулей, примерами, списком версий и тем, кто от модуля зависит. По дате последней версии и числу пользователей видно, живой ли модуль.
Документацией становится обычный комментарий прямо над экспортируемым именем, начинающийся с этого имени: `// Split делит строку…`.

**Термины**
- **doc-комментарий** — комментарий над именем, который становится его документацией

**Граница:** оформление документации пакета целиком — не нужно.
