## ФУНД-1. От исходника к процессу

### ФУНД-1.1 Что понимает процессор

#### ФУНД-1.1.1 Машинные инструкции: что на самом деле выполняет процессор
**Вопросы**
- [ ] Что такое машинная инструкция? Назови 3–4 действия, которые может сделать одна инструкция. · `что такое машинная инструкция простыми словами`
- [ ] Почему процессор не может выполнить текст программы напрямую? · `почему процессор понимает только машинный код`
- [ ] В каком порядке процессор выполняет инструкции и что значит «перейти» к другой инструкции? · `fetch decode execute cycle`
- [ ] Почему инструкции для процессоров Intel и AMD в ноутбуке не подходят процессору ARM в телефоне? · `набор инструкций x86 и ARM разница`

**Гуглить:** `machine code explained` · `как процессор выполняет программу` · `instruction set architecture simple`

**Должен знать**
Процессор умеет выполнять только машинные инструкции — очень простые команды: взять число, сложить, записать результат, перейти к другой инструкции. Он выполняет их одну за другой и очень быстро. Любая программа, на каком бы языке она ни была написана, перед выполнением должна стать длинной последовательностью таких инструкций.
У каждого семейства процессоров свой набор инструкций, поэтому готовая программа для одного семейства не подходит другому.

**Термины**
- **машинная инструкция** *(новое)* — одна простая команда, которую процессор выполняет сам
- **машинный код** — программа, записанная машинными инструкциями
- **набор инструкций** — все инструкции, которые понимает конкретное семейство процессоров (x86, ARM)

**Граница:** как устроен процессор внутри (регистры, кэши процессора) — не нужно.

#### ФУНД-1.1.2 Исходный код и зачем его переводить
**Вопросы**
- [ ] Что такое исходный код и чем он отличается от машинных инструкций? · `исходный код что это`
- [ ] Почему программы пишут на Go или Python, а не сразу машинными инструкциями? · `язык высокого уровня и машинный код`
- [ ] Что значит «перевести» программу: что подаётся на вход и что получается на выходе? · `source code vs machine code`
- [ ] Почему один и тот же исходный код можно запустить на компьютерах с разными процессорами? · `portable source code why`

**Гуглить:** `high-level vs low-level programming language` · `зачем нужны языки программирования`

**Должен знать**
Исходный код — текст программы на языке, удобном человеку: Go, Python и другие. Процессор этот текст не понимает, поэтому перед выполнением исходный код переводят в машинные инструкции. Переводит специальная программа; способов перевода два, их разбирает следующая тема.
Исходник не привязан к конкретному процессору: один и тот же текст можно перевести под разные наборы инструкций.

**Термины**
- **исходный код** *(новое)* — текст программы на языке программирования
- **язык высокого уровня** — язык, на котором удобно писать человеку, а не процессору

### ФУНД-1.2 Два способа перевести

#### ФУНД-1.2.1 Компилятор
**Вопросы**
- [ ] Что делает компилятор: что подаётся ему на вход и что получается на выходе? · `что делает компилятор простыми словами`
- [ ] Что такое исполняемый файл? Почему для его запуска не нужны ни исходный код, ни компилятор? · `исполняемый файл что это exe`
- [ ] Когда компилятор сообщает об ошибке в тексте программы — до запуска или во время работы? Что это даёт? · `ошибка компиляции что это`
- [ ] Почему исполняемый файл, собранный для Windows, не запустится на Linux или на процессоре другого семейства? · `why executable does not run on another os`
- [ ] Сколько раз нужно компилировать программу, чтобы потом запускать её много раз? · `compile once run many times`

**Гуглить:** `what does a compiler do` · `compiler explained for beginners` · `компиляция программы что происходит`

**Должен знать**
Компилятор — программа, которая заранее и целиком переводит исходный код в машинные инструкции. По пути он проверяет текст и сообщает об ошибках ещё до запуска.
Результат — исполняемый файл: готовая программа, которой для работы больше не нужны ни исходник, ни компилятор. Компилируют один раз, запускают сколько угодно. Исполняемый файл привязан к операционной системе и семейству процессора, под которые его собрали. Go — компилируемый язык.

**Термины**
- **компилятор, компиляция** *(новое)* — перевод всего исходного кода в машинные инструкции заранее
- **исполняемый файл** *(новое)* — результат компиляции, который можно запустить (`.exe` в Windows)
- **ошибка компиляции** — ошибка в тексте программы, найденная до запуска

**Граница:** внутренние этапы компилятора (разбор текста, оптимизации) — не нужно.
**Позже:** интерпретатор — ФУНД-1.2.2; команда `go build` — GO-1.3.2; сборка под другую ОС и процессор — GO-1.3.4.

#### ФУНД-1.2.2 Интерпретатор
**Вопросы**
- [ ] Что делает интерпретатор и чем его работа отличается от работы компилятора? · `интерпретатор что это простыми словами`
- [ ] Почему для запуска программы на Python на компьютере должен быть установлен Python? · `why python needs interpreter installed`
- [ ] Что такое байткод и почему это не машинные инструкции? · `что такое байткод`
- [ ] По каким шагам CPython выполняет файл `.py`: исходный код → байткод → выполнение по одной команде? · `how cpython executes python code`
- [ ] Что лежит в папке `__pycache__` и в файлах `.pyc`? Зачем CPython их сохраняет? · `pycache pyc files explained`
- [ ] Как посмотреть байткод своей функции в Python? · `python dis bytecode example`

**Гуглить:** `interpreter vs compiler` · `CPython bytecode virtual machine` · `байткод python dis`

**Должен знать**
Интерпретатор — программа, которая выполняет чужую программу сама, по ходу, а не готовит заранее исполняемый файл. Поэтому для запуска кода на Python нужен установленный Python.
CPython работает в два шага: сначала переводит исходный код в байткод — упрощённые команды для самого CPython (не для процессора), затем выполняет байткод по одной команде в своём цикле. Байткод кэшируется в `.pyc`, чтобы не переводить файл заново при каждом запуске. Каждая команда байткода выполняется через лишнюю прослойку, отсюда и разница в скорости с машинными инструкциями.

**Термины**
- **интерпретатор** *(новое)* — программа, которая выполняет исходный код по ходу
- **байткод** *(новое)* — промежуточные команды, которые выполняет интерпретатор, а не процессор
- **CPython** — основная реализация Python, написанная на C
- **`.pyc`, `__pycache__`** — сохранённый на диск байткод файлов Python

**Граница:** внутреннее устройство CPython глубже «байткод → выполнение по одной команде» — не нужно.
**Позже:** что из этого следует для скорости и ошибок — ФУНД-1.2.3; GIL в CPython — ФУНД-4.2.3.

#### ФУНД-1.2.3 Компиляция против интерпретации: что из этого следует
**Вопросы**
- [ ] Когда в Go ты узнаёшь об ошибке в тексте программы, а когда в Python? Почему так? · `compile time vs runtime error`
- [ ] Опечатка в имени переменной в ветке `if`, которая редко выполняется: что будет в Go и что в Python? · `python NameError only at runtime`
- [ ] Почему программа на Go обычно работает быстрее такой же на Python? · `why compiled languages are faster`
- [ ] Что нужно на компьютере, чтобы запустить готовую программу на Go и на Python? Как это влияет на установку программы у пользователя? · `go single binary deployment`
- [ ] Почему программе на Go не нужна отдельная программа-исполнитель, как CPython для Python? · `why go has no virtual machine`
- [ ] Чем платит каждый подход: что удобнее при разработке, что — при запуске? · `compiled vs interpreted pros and cons`

**Гуглить:** `compiled vs interpreted language` · `компилируемые и интерпретируемые языки разница`

**Должен знать**
Компиляция переносит работу на этап до запуска: ошибки в тексте находятся сразу, программа работает быстро, получается один исполняемый файл без зависимостей. Цена — сборку нужно повторять после каждого изменения и отдельно для каждой ОС и процессора.
Интерпретация позволяет запустить код сразу, но ошибка в редко выполняемой ветке «спит» до момента, когда эта ветка выполнится, а скорость ниже из-за прослойки. Для запуска нужен установленный интерпретатор.
Go — компилируемый язык без отдельного исполнителя, Python в CPython — интерпретируемый через байткод. Это один из первых вопросов на собесе.

**Термины**
- **компилируемый язык** — язык, программы на котором переводятся компилятором заранее (Go, C)
- **интерпретируемый язык** — язык, программы на котором выполняет интерпретатор (Python в CPython)

**Граница:** смешанные подходы (JIT-компиляция в Java и PyPy) — одной фразой, не глубже.

### ФУНД-1.3 Процесс

#### ФУНД-1.3.1 Процесс: как исполняемый файл становится работающей программой
**Вопросы**
- [ ] Что такое процесс и чем он отличается от исполняемого файла на диске? · `процесс и программа разница`
- [ ] Что делает операционная система, когда ты запускаешь исполняемый файл двойным щелчком или из терминала? · `what happens when you run a program os`
- [ ] Можно ли запустить один исполняемый файл несколько раз одновременно? Сколько получится процессов? · `one program multiple processes`
- [ ] Что такое PID и как посмотреть список процессов в Windows и в Linux? · `диспетчер задач процессы pid`
- [ ] Что происходит с процессом и его памятью, когда программа завершается? · `process termination memory freed`
- [ ] Когда ты запускаешь `python script.py`, какой процесс на самом деле работает — скрипта или интерпретатора? · `python script process interpreter`

**Гуглить:** `what is a process operating system` · `процесс в операционной системе простыми словами`

**Должен знать**
Исполняемый файл — просто файл на диске. Когда его запускают, операционная система создаёт процесс: загружает инструкции программы в оперативную память, выделяет ей память и ресурсы и начинает выполнение. Процесс — это запущенная программа вместе с её памятью и состоянием.
Из одного файла можно запустить много процессов, у каждого будет свой номер — PID. Когда программа завершается, ОС забирает всю память процесса. Программа на Python работает внутри процесса интерпретатора.

**Термины**
- **процесс** *(новое)* — запущенная программа с собственной памятью и состоянием
- **операционная система (ОС)** — программа, которая запускает процессы и распределяет между ними ресурсы
- **PID** — номер процесса, который выдаёт ОС

**Граница:** как ОС переключает процессор между процессами — не нужно.

#### ФУНД-1.3.2 Изоляция памяти процессов
**Вопросы**
- [ ] Может ли один процесс прочитать или изменить память другого? Почему нет? · `process memory isolation`
- [ ] Кто обеспечивает изоляцию: сама программа или операционная система вместе с процессором? · `os memory protection`
- [ ] Что происходит, если программа обращается к памяти, которая ей не принадлежит? · `segmentation fault access violation`
- [ ] Зачем изоляция нужна: что было бы, если бы сломанная программа могла испортить память браузера или самой ОС? · `зачем изоляция памяти процессов`
- [ ] Если чужую память читать нельзя, как процессы обмениваются данными? · `inter process communication examples`

**Гуглить:** `memory isolation between processes` · `изоляция процессов операционная система`

**Должен знать**
Каждый процесс видит только свою память. Чужую память он не может ни прочитать, ни изменить: за этим следят ОС и процессор. Попытка обратиться к чужой или недоступной памяти заканчивается тем, что ОС аварийно завершает процесс (segmentation fault в Linux, access violation в Windows).
Изоляция защищает систему: упавшая программа не ломает другие, а вредная — не крадёт пароли из браузера. Обмениваться данными процессы могут только через посредника — ОС: файлы, сеть и другие способы, которые даёт ОС.

**Термины**
- **изоляция памяти** — у каждого процесса своя память, недоступная другим
- **segmentation fault / access violation** — аварийное завершение процесса при обращении к чужой памяти

**Граница:** как именно устроена изоляция внутри ОС — не нужно.
